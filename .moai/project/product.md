# minidiscord — 제품 개요

> 설계 원문: `.moai/plan/2026-08-26-minidiscord/spec-v2.md`, `plan-v2.md` (v1 문서는 대조용으로 보존). 이 문서의 「현재 상태」 절은 **2026-09-08 기준**(v2 리팩토링 병합 뒤, main `18b866f`)이다. v2 에서 무엇을 왜 바꿨는지는 `.moai/reports/v2-review.md`. 구현 구조는 `.moai/project/structure.md`, 기술 스택은 `tech.md`, 파일 단위 지도는 `codemaps/`.

## 무엇을 만드는가

minidiscord는 회사 네트워크 등 디스코드를 쓸 수 없는 환경에서, 클로드코드 세션을 봇으로 참여시켜 대화할 수 있는 **자체 호스팅 채팅 서버**다. 디스코드의 역할을 대신한다고 보면 된다.

Claude Code는 공식 Channels 기능으로 세션을 디스코드·텔레그램 같은 메신저에 봇으로 접속시킬 수 있다. 하지만 이 프로젝트의 사용자는 회사에서 디스코드를 쓸 수 없어 이 기능을 그대로 활용하지 못한다. minidiscord는 「사내망·과제원에서 쓸 나만의 디스코드」를 만들어 이 문제를 해결한다 — 배치 목표는 사내망·과제원이고, 서버의 기본 바인드는 지금도 `127.0.0.1`이라 지금은 이 PC에서만 접속된다.

## 왜 필요한가 (배경)

- 사용자는 항상 켜져 있어 서버를 띄워 둘 수 있는 PC를 가지고 있다.
- 그 PC에서 minidiscord 서버를 띄워두면, 사용자는 회사 PC를 포함해 어디서든 브라우저로 `http://<내PC주소>:3000`에 접속해 자신의 클로드코드 세션들과 대화할 수 있다.
- 클로드코드 세션은 공식 Channels 계약을 구현한 **커스텀 채널 플러그인**을 통해 이 서버에 봇으로 참여한다.

```
브라우저(회사 PC 등) ──HTTP/SSE──▶ minidiscord 서버(사내망·과제원) ◀──WebSocket── 채널 플러그인 ◀──stdio(MCP)── Claude Code 세션들
```

## 성공 기준

1. 방을 만들고 봇을 등록해 방에 참여시키면(세션 접속) 대화가 오간다.
2. 긴 대화가 서버 재시작·브라우저 재접속 후에도 그대로 남아 있다.
3. 파일을 올리고 받을 수 있다(사람↔봇 양방향).
4. 한 방에 여러 봇이 동시에 접속해 각자 독립적으로 답변한다.
5. `@TO`/`@CC` 멘션으로 누가 답할지 제어한다.
6. 봇이 세션을 초기화(`clear`)했어도 스스로 대화 기록을 다시 가져올 수 있고, 멘션 없이 오간 대화도 커서로 따라잡을 수 있다.

## 현재 상태 (2026-09-07)

로드맵 M1~M6 과 그 뒤 카드 t9~t43, v2 리팩토링(C1·A·B·C2)이 전부 `main` 에 있다. 실 세션 검증은 카드 `t32` 에서 실제 Claude Code 세션 하나로 열두 항을 사람이 손으로 관측해 통과했고, v2 에서는 A-0 관측으로 다시 쟀다. 살아 있는 SPEC 은 19개(`SPEC-BOTMODEL-001` 포함)이고, v2 에서 대체되거나 사라진 11개는 `.moai/specs/_archive/` 에 있다.

| 성공 기준 | 상태 | 근거 |
|---|---|---|
| 1. 방·봇 등록·참여·대화 | 됨 | t32 실 세션 관측 · v2 A-0 관측, E2E 1~7단계 |
| 2. 재시작 영속성 | 됨 | `server/test/restart-persistence.test.ts`, E2E 14단계 |
| 3. 파일 양방향 | 됨 | 사람 업로드/다운로드는 항상; 봇 첨부는 `MINIDISCORD_BOT_FILES_DIR` 를 지정해야 켜진다 |
| 4. 여러 봇 동시 접속 | 됨 | 봇마다 토큰 하나(`bots.token`), 방 참여는 `room_bots` 행 — 한 봇이 여러 방에, 한 방에 여러 봇이. 게이트웨이 시험·E2E «봇 하나·방 둘». 실 Claude 세션 동시 다중 접속은 t32 범위(세션 1개) 밖 |
| 5. `@TO`/`@CC` 라우팅 | 됨 | `mention.ts` + 팬아웃, 웹 `@` 자동완성 |
| 6. `fetch_history` 따라잡기 | 됨 | 결과 JSON 의 `cursor` 필드를 `since_id` 로 되넘기는 방식 (줄머리 `#번호` 방식은 커서 오염 원인으로 폐기) |

**배치 전제는 «아는 사람 몇 명, 같은 PC 나 서로 믿는 사내망» 이다.** v2 리팩토링이 그 전제에 맞지 않는 장치(비밀번호·가입·방 구성원 인가·게이트웨이 핸드셰이크·전선 봉투·전송 스킴 검사)를 걷어냈다. 봇 토큰은 전선과 표에서 평문이고 방 사이에 경계가 없다. 사내망 밖으로 여는 «서비스화» 는 README 「보안에 대해 알아둘 점」의 «없는 것» 목록을 채운 뒤의 일이고, 서버 TLS 종단(보류 카드 t23)이 그 첫 조건이다 — `README.md` 「채널 플러그인을 붙이기 전에」, `ROADMAP.md` 「보류 카드」.

## 기능 요구사항

| 영역 | 내용 |
|---|---|
| **계정** | 소수 그룹이 각자 이름 하나로 로그인한다 (32자 이하, 비밀번호 없음). 처음 보는 이름은 로그인 순간 계정이 된다. |
| **방 접근** | 방 사이에 경계가 없다 — 로그인한 사람은 모든 방을 읽고 쓰고 보관하고, 어느 방의 봇 승인 요청에도 답한다. *(카드 t11 의 방 구성원 명단·인가(SPEC-ROOMAUTHZ-001)는 v2 C1 에서 결정 ④ 로 지웠다. 비공개 방을 되살리는 자리는 `.moai/reports/v2-refactoring-guide.md` §0 ④.)* |
| **방** | 대화방을 만들고 이름을 붙인다. 프로젝트(과제)마다 방을 새로 만드는 것을 기본 사용 패턴으로 삼는다. |
| **방 보관** | 방을 닫으면(archive) 대화·파일은 읽기 전용으로 보존된다. 사람의 새 메시지·참여 추가는 409, 봇의 글·상태는 조용히 버려지고(t43), 봇의 이력 조회는 계속 된다. 봇 접속은 봇 단위라 끊기지 않고, 다음 `welcome` 의 방 목록에서 그 방이 빠진다. 사이드바에서 보관된 방은 접어서 보여준다. |
| **봇 등록/참여** | 봇(이름, 설명, 역할 `orchestrator`/`worker`)을 전역으로 등록하면 그 봇의 접속 토큰 하나가 발급되고(평문은 이 응답 한 번만), 세션 실행 명령 안내가 화면에 뜬다. 방에는 등록된 봇을 참여시킨다(멱등). 한 봇이 여러 방에 참여해도 접속은 하나다. 참여를 빼면 그 방의 커서도 사라져 다시 참여시키면 그 방의 타깃 메시지가 전부 재전송된다. |
| **메시지** | 방에서 긴 대화를 나눈다. 접속 전에 오간 메시지를 포함해 전부 서버 DB 에 저장되고, 이후 접속한 봇도 이를 불러올 수 있다. |
| **@TO/@CC 라우팅** | `@TO(봇)` 은 지정 봇에게 전달하고 응답을 의무로 한다. `@CC(봇)` 은 전달만 하고 응답을 금지한다. 멘션이 없는 메시지는 어느 봇에게도 전달되지 않는다. 한 메시지에 여러 멘션을 섞어 쓸 수 있고, 모르는 이름이 하나라도 있으면 메시지 전체가 거부된다(400). 입력창에는 봇 이름 자동완성이 붙는다. |
| **파일** | 사람은 파일을 업로드/다운로드할 수 있다. 봇은 `MINIDISCORD_BOT_FILES_DIR` 아래 파일만 첨부로 보낼 수 있고, 업로드된 파일은 로컬 절대 경로로 받아 읽는다. |
| **권한 릴레이** | 봇이 도구 사용 승인이 필요하면 방에 승인 요청 메시지가 뜨고, 사람이 버튼 또는 `yes <id>`/`no <id>` 로 판정한다. 판정은 요청한 세션 접속 하나에만 되돌아간다. |
| **기록 조회** | 봇은 `fetch_history` 도구로 방의 대화 기록을(전체/부분/발화자별) 가져온다. 결과는 `{cursor, messages}` JSON 이고, `cursor` 를 다음 호출의 `since_id` 로 넘기면 그 다음부터만 받는다. 세션 초기화 뒤 맥락 복구와 멘션 없는 대화 따라잡기의 유일한 경로다. |
| **봇 상태** | 각 봇의 온라인/오프라인, 「입력 중」 상태가 방 화면에 표시된다. |

## 비기능 요구사항

- **구현 언어/런타임**: Node.js 24 + TypeScript strict.
- **프로세스 구조**: 단일 서버 프로세스. 채널 플러그인은 세션마다 하나씩 뜨는 별도 프로세스다.
- **저장소**: SQLite 하나(WAL)로 모든 영속 데이터를 관리한다. 업로드 파일은 같은 데이터 폴더의 `uploads/`.
- **응답 방식**: 봇 응답은 완성된 답변을 한 번에 보낸다. 스트리밍은 없다.
- **통신/인증**: HTTP + 이름 로그인 세션 쿠키. 봇은 등록 때 받은 평문 토큰을 `hello` 에 실어 접속한다(핸드셰이크·봉투 없음). HTTPS 는 서비스화 전 조건(t23)으로 남아 있다.
- **모델 컨텍스트 보호**: 세션으로 나가는 본문·이름·경로·이력 문서에 바이트 상한을 둔다.
