# minidiscord — 구조 개요

> 설계 원문: `.moai/plan/2026-08-26-minidiscord/spec.md` §3~6, `plan.md` 파일 구조 섹션
> 이 프로젝트는 아직 구현 코드가 없는 그린필드 상태다. 아래 구조는 설계 문서에 정의된
> "만들 구조"이며, `.moai/project/codemaps/`는 스캔할 코드가 없어 생성하지 않는다.

## 세 컴포넌트

minidiscord는 세 개의 독립 컴포넌트로 구성된다.

| 컴포넌트 | 위치 | 역할 |
|---|---|---|
| **minidiscord 서버** | 내 PC, 단일 Node 프로세스 | 웹 UI 서빙, REST API, SSE 실시간 push, 봇 게이트웨이(WebSocket), SQLite/파일 저장 |
| **채널 플러그인** (`minidiscord-channel`) | 각 Claude Code 세션마다 spawn | 공식 Channels 계약을 구현한 MCP 서버(stdio). 위로는 세션에 이벤트를 push하고, 아래로는 게이트웨이에 WebSocket으로 접속한다 |
| **웹 UI** | 브라우저 | 디스코드형 2단 레이아웃(방 목록 + 채팅). 로그인, 메시지, 파일, 봇 초대/상태 표시 |

### 연결 흐름

```
브라우저 ──HTTP/SSE──▶ minidiscord 서버 ◀──WebSocket── 채널 플러그인 ◀──stdio(MCP)── Claude Code 세션
```

서버와 채널 플러그인은 같은 머신(내 PC)에서 돌기 때문에, 채널의 게이트웨이 접속 주소는 항상
로컬(`ws://127.0.0.1:3000/bot`)이다. 이 전제 덕분에 파일 전달도 로컬 경로 직접 전달 방식으로
단순화된다(자세한 내용은 아래 "주요 흐름" 참고).

## 핵심 원칙 (세 가지)

이 세 원칙은 아키텍처 전반의 설계 결정을 관통하므로, 코드를 건드리기 전에 먼저 이해해야 한다.

1. **세션은 정확히 한 방에만 접속한다 (세션→방 N:1). 방에는 여러 세션이 접속한다 (방→세션 1:N).**
   세션이 여러 방의 메시지를 동시에 받으면 대화 맥락이 섞이므로 이를 금지한다. 공식 Channels가
   "한 세션에 이벤트가 순차로 줄 선다"는 특성을 가지고 있는데, 이 원칙 아래에서는 줄 서는 이벤트가
   전부 같은 방의 것이므로 무해하다.

2. **서버는 세션을 직접 조종하지 않는다.** 채널 플러그인이 토큰을 들고 게이트웨이에 접속해 오면
   그 방에 봇이 있는 것으로 취급한다. 세션 프로세스가 죽으면 서버는 봇을 오프라인으로 표시할 뿐,
   메시지는 계속 DB에 쌓아둔다. 즉 서버가 세션의 생사를 관리하지 않고, 세션이 능동적으로 접속·이탈한다.

3. **서버는 페르소나를 모른다.** 봇의 성격·지식·전문 분야는 각 봇의 작업 디렉터리(`CLAUDE.md`,
   `.claude/`)가 책임진다. 서버가 갖는 봇 정보는 표시용 이름·설명뿐이다. 과제가 바뀌면 방을 새로
   만들고 봇을 다시 초대하며, 세션 기억은 방마다 리셋되는 것이 기본이다. 산출물·자료의 연속성은
   봇들이 공유하는 레포가 담당하며, 이는 이 설계의 범위 밖이다.

### 다중 봇 접속이 어떻게 가능한가

"한 방에 여러 클로드코드 봇이 접속할 수 없다"는 통념은 사실 세 가지 서로 다른 제약이 섞인 것이며,
minidiscord는 이를 각각 다르게 해결한다.

| 실제 제약 | 출처 | 이 시스템의 대책 |
|---|---|---|
| 봇 자격증명(토큰) 하나는 프로세스 하나만 쓸 수 있다 | 디스코드 게이트웨이 규칙 | 해당 없음 — minidiscord가 플랫폼이므로 규칙을 직접 정한다. (방, 봇) 조합마다 별도 토큰을 발급한다 |
| 공식 채널 플러그인이 고정 상태 파일을 쓴다 | 공식 디스코드/텔레그램 플러그인이 `~/.claude/channels/<이름>/.env`에 상태 저장 | 채널 플러그인을 **무상태·인자 기반**으로 만든다. 방 ID·토큰·서버 주소는 전부 실행 인자/환경변수로 받고 디스크에 아무것도 쓰지 않는다 |
| 한 세션이 여러 방을 받으면 기록이 섞인다 | 채널 이벤트는 세션 안에서 순차 처리된다 | 위 핵심 원칙 1(세션→방 N:1)로 원천 해결 |

## 계획된 디렉터리 구조

구현 레포(`minidiscord`, 이 설계 레포와는 별도 신규 레포)에 만들 npm workspaces 구조다.

```
minidiscord/
├── package.json                    # npm workspaces root
├── server/
│   ├── package.json
│   ├── tsconfig.json
│   ├── src/
│   │   ├── index.ts                # 조립+시작 (모든 라우트/게이트웨이 연결)
│   │   ├── config.ts               # 포트·데이터 경로
│   │   ├── db.ts                   # SQLite 연결+스키마
│   │   ├── auth.ts                 # 가입/로그인/세션 쿠키/requireAuth
│   │   ├── routes-rooms.ts         # 방 생성/목록/보관
│   │   ├── routes-bots.ts          # 봇 등록/목록 + 방 초대(토큰 발급)
│   │   ├── routes-messages.ts      # 메시지 전송(multipart)/목록/다운로드
│   │   ├── mention.ts              # @TO/@CC 파서 (순수 함수)
│   │   ├── sse.ts                  # SSE 허브 (방별 구독/발행)
│   │   ├── gateway.ts              # 봇 게이트웨이 (WebSocket 서버)
│   │   └── permissions.ts          # 권한 릴레이 브로커
│   └── test/                       # 각 src 모듈에 대응하는 vitest 스펙
├── channel/
│   ├── package.json                # bin: minidiscord-channel
│   ├── tsconfig.json
│   ├── src/
│   │   ├── index.ts                # 진입점: MCP 서버 + 게이트웨이 클라이언트 연결
│   │   ├── channel-server.ts       # MCP 채널 계약 구현 (capabilities/reply/fetch_history)
│   │   └── gateway-client.ts       # WebSocket 클라이언트 (재접속 백오프)
│   └── test/
├── web/
│   ├── index.html
│   ├── app.js
│   └── style.css
├── scripts/
│   └── e2e.mjs                     # 전체 시나리오 자동 검증
└── README.md
```

**책임 경계**: `gateway.ts`는 WebSocket 연결과 봇 토큰 인증만 담당하고, `routes-messages.ts`는
HTTP 요청 처리와 멘션 라우팅만, `permissions.ts`는 승인 요청 상태만 알도록 분리한다. `mention.ts`는
순수 함수로 분리해 파서 로직만 단독으로 테스트할 수 있게 한다.

전체 19개 구현 태스크(스캐폴드 → DB 스키마 → 인증 → 방/봇 API → 멘션 파서 → SSE → 게이트웨이 →
메시지 API → 권한 릴레이 → 채널 패키지 → 웹 UI → E2E)의 상세 순서는 `plan.md`를 참고한다.

## 데이터 모델 (SQLite)

서버는 SQLite 한 파일로 모든 영속 데이터를 관리한다. 테이블 목록과 용도는 다음과 같다
(전체 DDL은 `spec.md` §5 참고).

| 테이블 | 용도 |
|---|---|
| `users` | 로그인 계정 (아이디, 비밀번호 해시) |
| `rooms` | 대화방. `status`가 `active`/`archived`로 방 보관 상태를 나타낸다 |
| `bots` | 봇 정의(표시용 이름·설명만). 페르소나 내용은 포함하지 않는다 |
| `bot_tokens` | "봇 초대" 1건 = 1행. (방, 봇) 조합의 접속 자격증명(토큰) 및 재접속 시 이어받을 메시지 커서(`last_delivered_id`) |
| `messages` | 방의 모든 메시지. `author_type`으로 사람/봇/시스템(입장·승인요청 등) 메시지를 구분 |
| `message_targets` | 사용자 메시지가 어느 봇에게 to/cc로 전달됐는지 기록 |
| `attachments` | 메시지에 첨부된 파일의 메타데이터(실제 파일은 디스크 별도 저장) |

봇의 온라인/오프라인 상태는 DB가 아니라 게이트웨이의 WebSocket 접속 여부(메모리)로 판단하며,
`last_seen_at`은 "마지막 접속" 표시용으로만 쓰인다. 토큰은 해시로만 저장하고 언제든 철회(revoke)할
수 있다.

## 봇 게이트웨이 프로토콜 (WebSocket, JSON)

채널 플러그인과 서버 사이의 실시간 통신 프로토콜이다. 모든 메시지는 `type` 필드를 가진 JSON이며,
경로는 `/bot`이다.

| 방향 | 메시지 타입 | 용도 |
|---|---|---|
| 채널 → 서버 | `hello` | 토큰으로 인증 요청 |
| 서버 → 채널 | `welcome` | 인증 성공, 방 정보와 놓친 메시지 커서(`missed_after_id`) 전달 |
| 서버 → 채널 | `message` | 사람이 보낸 메시지를 봇에게 전달(`delivery: "to"` 또는 `"cc"`) |
| 채널 → 서버 | `bot_message` | 봇의 응답을 서버로 전송 |
| 채널 → 서버 | `status` | 봇의 작업 상태(`working`/`idle`) 보고 — "입력 중" 표시에 쓰임 |
| 채널 → 서버 | `permission_request` | 도구 사용 승인이 필요할 때 요청 |
| 서버 → 채널 | `permission_verdict` | 사람의 승인/거절 결과 전달 |
| 채널 → 서버 | `history_request` | 방 대화 기록 조회 요청 |
| 서버 → 채널 | `history_response` | 조회된 기록 응답 |

서버는 `room_id`별 접속 목록을 관리하며, 사용자 메시지는 멘션 파싱 결과에 따라 **지정된 봇의
채널에만** 전달한다. 각 메시지 `id`는 방마다 단조 증가하는 커서로, 재접속 시 `missed_after_id`
이후 메시지만 재전송해 중복 수신을 막는다.
