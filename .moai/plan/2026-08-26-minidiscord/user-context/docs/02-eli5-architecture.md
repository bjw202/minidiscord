# 이 프로그램이 왜 이렇게 생겼는지 — 처음부터 차근차근

> 대상: 코딩을 거의 안 해본 사람.
> 낯선 단어는 **처음 나올 때 바로 옆에 뜻을 붙였습니다.** 외울 필요 없습니다.

---

## 0. 한 문장으로

**카톡방 하나에 AI 조수 한 명을 붙여놓고, 그 조수의 기억이 가득 차면 몰래 새 조수로 바꿔치기하면서 인수인계서를 손에 쥐여 주는 프로그램입니다.**

사용자는 조수가 바뀐 걸 모릅니다. 그게 핵심입니다.

---

## 1. 먼저 알아야 할 단어 6개

이 문서에서 계속 나옵니다. 지금 한 번만 읽고 넘어가세요.

| 단어 | 뜻 | 일상 비유 |
|---|---|---|
| **Claude Code** | 터미널에서 돌아가는 AI 코딩 조수 프로그램 | 내 컴퓨터에 앉아 일하는 인턴 |
| **세션(session)** | 그 인턴과의 **대화 한 판**. 시작부터 끝까지의 기록 전체 | 인턴 한 명의 근무 기간 |
| **토큰(token)** | AI가 글을 세는 단위. 한글은 대략 글자 1개 = 1~1.5토큰 | 종이 몇 장 |
| **컨텍스트 창(context window)** | 한 세션이 담을 수 있는 **최대 분량** | 책상 위에 올릴 수 있는 종이 한도 |
| **컴팩션(compaction)** | 대화가 길어지면 AI가 스스로 요약해서 자리를 비우는 기능 | 종이를 요약본으로 바꿔치기 |
| **핸드오프(handoff)** | 이 프로젝트가 하는 것. 인수인계서를 쓰고 새 세션으로 넘기기 | 알바 교대 + 인수인계 노트 |

---

## 2. 문제의 출발점: AI는 사실 기억력이 없습니다

이게 제일 오해하기 쉬운 부분입니다.

우리는 "AI가 대화를 기억한다"고 느끼지만, 실제로는 **매번 대화 전체를 처음부터 다시 읽습니다.**

```
1번째 질문:  [질문1]                        → 답변
2번째 질문:  [질문1][답변1][질문2]           → 답변
3번째 질문:  [질문1][답변1][질문2][답변2][질문3] → 답변
                                              ↑ 갈수록 길어진다
```

기억하는 게 아니라, **지금까지의 기록을 통째로 다시 갖다 붙이는 것**입니다.

### 그래서 한도가 있습니다

Claude Code의 기본 한도는 **20만 토큰**입니다.

### 비유: 오픈북 시험

교수님이 오픈북 시험을 허락했는데, 조건이 있습니다. **책상 위에 종이를 200장까지만** 올릴 수 있어요.

- 문제를 풀 때마다 책상 위 종이를 **전부** 다시 훑습니다.
- 풀이를 쓸수록 종이가 한 장씩 쌓입니다.
- 200장이 꽉 차면? **더 못 올립니다. 시험이 거기서 끝납니다.**

긴 대화가 결국 죽는 이유가 이겁니다.

> 📌 비유의 한계
> 실제로는 "매번 전부 다시 읽는" 비용이 **캐싱**(caching, 앞부분을 다시 계산하지 않고 저장해둔 걸 재사용하는 최적화)으로 많이 줄어듭니다. 하지만 **자리를 차지하는 건 똑같습니다.** 종이는 그대로 쌓여요.

---

## 3. Claude Code의 기본 해법과, 우리가 그걸 안 쓰는 이유

### 기본 해법: 오토컴팩트

종이가 차오르면 Claude Code가 알아서 **200장을 요약해 20장으로 줄이고 나머지를 버립니다.** 이게 오토컴팩트(auto-compact)입니다.

편한데, 문제가 셋입니다.

| 문제 | 실제로 무슨 일이 벌어지나 |
|---|---|
| **언제 터질지 모른다** | 한창 질문 중인데 갑자기 몇 초에서 수십 초 멈춥니다 |
| **뭘 버릴지 AI가 정한다** | "아까 그 결정, 왜 그렇게 했더라?"가 요약에서 빠질 수 있습니다 |
| **요약 위에 또 요약이 쌓인다** | 복사본을 또 복사하는 것과 같습니다. 반복할수록 원본에서 멀어집니다 |

세 번째가 특히 고약합니다. 대화가 길어질수록 AI가 **자기가 뭘 하고 있었는지 점점 흐릿해집니다.**

### 그래서 껐습니다

```bash
DISABLE_AUTO_COMPACT=1
```

`.claude/settings.json`에 넣어둔 이 한 줄이 오토컴팩트를 끕니다.

### ⚠️ 그런데 끄면 이렇게 됩니다 (반드시 알아야 함)

Claude Code 공식 문서 원문입니다.

> "With auto-compaction off, sessions stop at the 200K boundary with the context-limit error instead of compacting."
>
> (오토컴팩트를 끄면, 세션은 20만 토큰 경계에서 요약하는 대신 컨텍스트 한도 에러를 내고 멈춥니다.)

**우아하게 안 끝납니다. `Prompt is too long`(프롬프트가 너무 깁니다)이라는 에러를 내고 그냥 죽습니다.**

봇으로 쓰고 있다면? 사용자 눈에는 이렇게 보입니다.

```
🧑 이거 좀 봐줘
   ...
   ...   (아무 반응 없음)
```

그래서 **오토컴팩트를 끄는 순간, 한도에 닿기 전에 우리가 먼저 손을 쓰는 게 의무**가 됩니다. 선택이 아닙니다.

그 "먼저 손 쓰는 것"이 바로 핸드오프입니다.

## 4. 핸드오프가 뭔가

### 비유: 편의점 알바 교대

오후 알바가 퇴근할 시간입니다. **일 잘하는 알바는 그냥 나가지 않습니다.**

1. **인수인계 노트를 씁니다** — "3번 냉장고 온도 이상함, 점장님께 말해뒀음. 택배 2건 카운터 밑에 있음. 단골 아저씨 담배 예약해두심."
2. 야간 알바가 와서 **그 노트를 읽습니다.**
3. **손님 입장에서는?** 아무것도 안 바뀝니다. 계산대에 사람이 서 있고, 계산이 되고, 담배도 나옵니다.

우리 프로그램이 하는 게 정확히 이겁니다.

```
   옛 세션                                     새 세션
 (종이 150/200장)                            (종이 4/200장)
       │                                          ▲
       │ ① "인수인계서 써라"                       │ ③ 인계서를 읽혀서 시작
       ▼                                          │
   .claude/HANDOFF.md ─────── ② 사본 보관 ─────────┘
                          .claude/session-history/

   사용자가 보는 카톡방: 처음부터 끝까지 그대로 하나
```

### 인계서에 뭘 적어야 하나

여기서 대부분이 실수합니다.

**"무슨 일을 하고 있었는지"만 적고, "어떻게 대화하고 있었는지"를 안 적습니다.**

| 적어야 할 것 | 안 적으면 생기는 일 |
|---|---|
| 지금 목표 | 새 조수가 엉뚱한 걸 합니다 |
| **말투·호칭·언어** | 봇이 갑자기 말투가 바뀝니다 → **사용자가 즉시 눈치챕니다** |
| **직전 3~5번의 사용자 말 원문** | "아까 그거"를 못 알아듣습니다 |
| 확정된 결정 + **왜 그렇게 정했는지** | 이미 퇴짜 놓은 방법을 다시 제안합니다 |
| 건드린 파일 **경로만** | (내용을 다시 적으면 인계서가 또 종이를 잡아먹습니다) |
| 물어봐 놓고 답 못 받은 질문 | 사용자가 답을 줬는데 뭘 물어봤는지 모릅니다 |

두 번째 항목이 제일 중요합니다. 사람은 **내용이 아니라 말투로** 상대가 바뀐 걸 알아챕니다.

실제 지시문은 [`prompts/handoff_write.md`](../prompts/handoff_write.md)에 있습니다. 나중에 손볼 일이 있으면 대부분 이 파일입니다.

## 5. 프로그램 전체 그림

먼저 큰 그림부터 보고, 아래에서 하나씩 뜯어봅니다.

```
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │  Telegram    │   │   Discord    │   │  로컬 터미널  │   ← ①어댑터
 │  #프로젝트A   │   │  #실험실      │   │  (연습용)     │
 └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
        │       "이 방에서, 이 말이 왔다"        │
        └──────────────┬────────────────────┬─┘
                       ▼
             ┌───────────────────────┐
             │   ②본체 (core.py)      │  ← 텔레그램이 뭔지 모름
             │  1. 이 방 담당 조수 찾기 │
             │  2. 조수에게 전달       │
             │  3. 답장 먼저 보내기    │
             │  4. 종이 몇 장 찼나 계산 │
             │  5. 넘칠 것 같으면 교대  │
             └───┬───────────┬───────┘
                 │           │
    ┌────────────▼──┐   ┌───▼──────────────┐
    │ ③좌석 배정표   │   │ ④교대 담당관       │
    │ 방 → 조수      │   │ 인계서 쓰기        │
    │ (작은 DB 파일) │   │  → 보관 → 새 조수  │
    └───────────────┘   └───┬──────────────┘
                            │
                 ┌──────────▼──────────┐
                 │ ⑤조수 호출 담당      │
                 │ claude 프로그램 실행 │
                 └─────────────────────┘
```

### 여기서 배울 설계 원칙 하나

**②본체는 "텔레그램"이라는 단어를 한 번도 안 씁니다.**

①어댑터가 플랫폼마다 다른 형식을 `(어느 방인지, 뭐라고 했는지, 답장은 이렇게 보내면 됨)` 딱 세 가지로 번역해서 넘겨줄 뿐입니다.

덕분에 나중에 슬랙을 붙이고 싶으면 **어댑터 파일 하나만 추가하면 끝**입니다. 본체는 안 건드려도 돼요.

이걸 **관심사의 분리**(separation of concerns, 각 부품이 자기 일만 알게 만드는 설계 원칙)라고 부릅니다.

## 6. ③좌석 배정표 — 이 프로젝트의 심장

### 왜 필요한가

Claude Code 공식 문서에 이런 문장이 있습니다.

> "Claude Code leaves sessions created with `claude -p` or the Agent SDK out of the session picker and out of `claude --continue`. You can still resume one by passing its session ID."
>
> (`claude -p`로 만든 세션은 세션 목록에도, `--continue` 대상에도 안 들어갑니다. 세션 ID를 직접 넘기면 이어갈 수 있습니다.)

쉽게 풀면 이렇습니다.

> `claude -p`(터미널에서 한 번 실행하고 끝나는 방식)로 만든 대화는 **Claude Code가 목록에 안 보여줍니다.**
> 그 대화의 **ID 번호를 우리가 안 적어두면, 그 대화는 영영 못 찾습니다.**

그래서 우리가 직접 명단을 관리합니다. 그게 [`session_store.py`](../bridge/session_store.py)입니다.

### 비유: 강의실 좌석 배정표

- **`chat_key`(방 번호)** = 좌석 번호. `telegram:12345` 같은 것
- **`session_id`(조수 번호)** = 그 자리에 앉은 사람의 학번

핸드오프는 **좌석은 그대로 두고 앉은 사람만 바꾸는 것**입니다.

```
교대 전:  telegram:12345  →  3aa7da9a   (1대째)
교대 후:  telegram:12345  →  6547c8ed   (2대째)
          ^^^^^^^^^^^^^^      ^^^^^^^^
          안 바뀜             바뀜
```

사용자의 카톡방 번호는 안 바뀌니까, 사용자 화면은 그대로입니다. **이게 "자연스럽게 이어지는" 것의 정체입니다.**

### 방 번호를 어떻게 짓느냐 — 여기서 "봇 하나에 대화창 하나" 문제가 풀립니다

| 어디서 온 메시지냐 | 방 번호를 이렇게 만든다 | 결과 |
|---|---|---|
| 텔레그램 1:1 대화 | `telegram:<채팅ID>` | 사람마다 따로 |
| 텔레그램 포럼 토픽 | `telegram:<채팅ID>:<토픽ID>` | **토픽마다 따로** |
| 디스코드 채널/스레드 | `discord:<채널ID>` | **채널마다 따로** |

디스코드 서버에 `#프로젝트A` `#프로젝트B` `#실험실` 세 채널을 만들면, **봇은 하나인데 조수는 셋**이 됩니다. 서로 대화가 안 섞입니다.

### 공식 기능으로는 왜 이게 안 되나

Claude Code에도 Channels라는 공식 기능이 있습니다. 문서 원문입니다.

> "Events queue into the session and are processed in order... To process independent event streams concurrently, run separate sessions."
>
> (이벤트는 세션에 줄을 서서 순서대로 처리됩니다... 독립적인 흐름을 동시에 처리하려면 세션을 따로 띄우세요.)

쉽게 풀면:

> 공식 기능은 **모든 방의 메시지를 조수 한 명 앞에 줄 세웁니다.**
> A방 대화와 B방 대화가 **같은 종이 위에 섞입니다.**

그래서 "봇 1개 = 대화창 1개"처럼 느껴졌던 겁니다. 정확히는 **"봇 1개 = 조수 1명"**이었어요.

우리처럼 좌석 배정표를 직접 들고 있으면 이 제약이 사라집니다. **브리지를 직접 만드는 가장 큰 이유가 이겁니다.**

## 7. ⑤조수 호출 담당 — 종이가 몇 장 찼는지 어떻게 아나

여기가 **제일 틀리기 쉬운 부분**입니다. 잘못하면 프로그램이 조용히 망가집니다.

조수를 부를 때 이렇게 부릅니다.

```bash
claude -p "사용자가 한 말" --output-format json --resume <조수번호>
```

`--output-format json`은 "답을 사람 읽는 글이 아니라 **프로그램이 읽기 좋은 형식**으로 달라"는 뜻입니다. 그러면 이런 게 돌아옵니다.

```json
{
  "result": "답변 텍스트",
  "session_id": "3aa7da9a-...",
  "total_cost_usd": 0.0123,
  "usage": {
    "input_tokens": 3000,
    "cache_read_input_tokens": 51000,
    "cache_creation_input_tokens": 4800,
    "output_tokens": 1200
  }
}
```

`usage`가 "이번에 종이 몇 장 썼는지"입니다.

### 함정: `input_tokens`만 보면 안 됩니다

왜냐면 아까 말한 **캐싱** 때문입니다.

대화가 길어지면 앞부분은 매번 새로 계산하지 않고 저장해둔 걸 씁니다. 그런데 그 부분이 **`cache_read_input_tokens`라는 다른 칸으로 빠집니다.** `input_tokens`에는 **이번에 새로 들어간 것만** 남아요.

```
실제로 책상에 쌓인 종이: 60,000장

  input_tokens                 3,000장  ← 이것만 보면 "아 3%밖에 안 찼네"
  cache_read_input_tokens     51,000장  ← 실제로는 여기가 대부분!
  cache_creation_input_tokens  4,800장
  output_tokens                1,200장
                              ---------
                              60,000장  ← 4개를 다 더해야 진짜
```

`input_tokens`만 보면 **실제의 5% 수준으로 과소평가**합니다. 그러면 어떻게 될까요?

- "아직 3%밖에 안 찼네" → 교대 안 함
- "아직 4%네" → 교대 안 함
- ...
- **어느 날 갑자기 `Prompt is too long`으로 봇이 죽음**

Anthropic 공식 문서도 이 값을 "Input **includes cache reads and writes**"(입력에는 캐시 읽기와 쓰기가 포함됨)라고 정의합니다.

그래서 우리는 **4개를 다 더합니다.** → [`claude_runner.py`](../bridge/claude_runner.py)의 `context_tokens_from_usage()` 함수가 그 일만 합니다.

## 8. 메시지 하나가 처리되는 순서 (순서가 중요합니다)

[`core.py`](../bridge/core.py)의 `handle()` 함수를 말로 푼 것입니다.

```
1. 이 방에 자물쇠를 건다
   └ 같은 방에서 메시지 두 개가 동시에 오면 기록이 뒤엉킨다.
     한 번에 하나씩만 처리한다.
     (다른 방끼리는 상관없이 동시에 돈다)

2. 좌석 배정표를 본다 (없으면 새 조수 배정)

3. 조수에게 전달하고 답을 받는다

4. 👉 사용자에게 답장부터 보낸다 👈
   └ ★여기가 핵심★
     교대를 먼저 하면 사용자는 답을 받으려고 30초를 더 기다려야 한다.
     답장부터 하고, 교대는 뒤에서 조용히.

5. 종이가 몇 % 찼는지 계산한다

6. 75%를 넘었으면 → 교대 절차 시작
```

### 왜 하필 75%인가

인계서를 쓰는 것도 **조수를 한 번 더 부르는 일**이고, 그것도 종이를 씁니다.

| 임계값 | 결과 |
|---|---|
| 90% | 인계서 쓰다가 한도를 넘겨서 **교대 자체가 실패** |
| 50% | 너무 자주 교대해서 매번 맥락이 얇아짐 |
| **75%** | **인계서 쓸 여유 25%를 남겨둠** ✅ |

코드에는 92%를 "여기까지 오면 위험" 선으로 따로 두고, 넘으면 기록에 경고를 남깁니다.

## 9. 교대 절차 3단계, 실제 코드

[`handoff.py`](../bridge/handoff.py)의 `perform()` 함수입니다.

### ① 인계서 쓰게 하기

```python
write_result = self.runner.run(
    HANDOFF_WRITE_PROMPT,           # "인수인계서 써라" 지시문
    cwd=workspace,
    resume_session_id=binding.session_id,   # ← 옛 조수를 이어서 부름
)
```

옛 조수가 `.claude/HANDOFF.md`라는 파일을 씁니다.

> 💡 **왜 옛 조수가 직접 쓰나?**
> 제3자가 대화 기록을 읽고 요약하는 것보다, **본인이 자기 일을 정리하는 게** 훨씬 정확합니다. 퇴근하는 알바가 인수인계 노트를 쓰는 것과 같아요. 점장이 CCTV 돌려보고 쓰는 것보다 낫죠.

혹시 파일 쓰기가 막혀서 조수가 파일 대신 그냥 글로 뱉으면? 그 글을 **우리가 대신 파일로 저장합니다.** (안전장치)

### ② 사본 보관

```
.claude/session-history/gen001-20260826-143022.md
```

나중에 "3대 전 조수가 무슨 결정을 했더라?"를 추적할 수 있습니다.

### ③ 새 조수에게 인계서 먹이기

```python
new_session_id = str(uuid.uuid4())      # 새 조수 번호 발급
seed_result = self.runner.run(
    HANDOFF_RESUME_PROMPT,              # 지시문은 여기로
    cwd=workspace,
    new_session_id=new_session_id,
    stdin_text=handoff_text,            # 인계서 본문은 여기로
)
```

> 💡 **왜 인계서를 따로 넣나?**
> 명령어 뒤에 붙일 수 있는 글자 수에 한도가 있습니다(맥에서 약 26만 자). 인계서가 길면 넘칠 수 있어요.
> 그래서 **지시문은 명령어에, 긴 데이터는 stdin**(파이프로 밀어 넣는 통로)으로 나눕니다.
> 공식 문서도 `cat 파일.txt | claude -p "설명해줘"`를 표준 방법으로 안내합니다.

그리고 새 조수에게 이렇게 지시합니다 ([`prompts/handoff_resume.md`](../prompts/handoff_resume.md)).

> "세션이 바뀌었다는 사실을 길게 설명하지 마라. 사과하지 마라. 요약 보고하지 마라.
> **사용자는 대화가 끊긴 줄 모른다. 끊기지 않은 것처럼 행동해라.**"

**이 한 문단이 "자연스러움"의 90%를 만듭니다.** 이게 없으면 새 조수가 "안녕하세요! 이전 대화를 인계받았습니다. 지금까지의 내용을 요약해드리면..." 하고 시작해버립니다.

마지막으로 좌석 배정표를 갈아끼웁니다.

```python
self.store.bind(binding.chat_key, resolved_id, workspace)
#              (같은 방 번호)     (새 조수 번호)
```

## 10. 파일별 역할

| 파일 | 하는 일 | 읽는 순서 |
|---|---|---|
| `bridge/config.py` | 설정값 읽어오기 | 값만 바꿀 거면 `.env`만 보면 됨 |
| `bridge/session_store.py` | **좌석 배정표** (작은 DB 파일에 저장) | ★ 1번 |
| `bridge/claude_runner.py` | 조수 부르기 + 종이 세기 | ★ 2번 |
| `bridge/handoff.py` | 교대 3단계 | ★ 3번 |
| `bridge/core.py` | 전체 진행 순서 | ★ 4번 |
| `bridge/adapters/telegram.py` | 텔레그램 연결 (설치할 것 없음) | 봇 붙일 때 |
| `bridge/adapters/discord_bot.py` | 디스코드 연결 | 봇 붙일 때 |
| `bridge/adapters/local_repl.py` | 봇 없이 터미널에서 테스트 | **맨 처음 여기** |
| `prompts/*.md` | 인계서 지시문 | 품질 손볼 때 |
| `tests/fake_claude.py` | **가짜 조수.** 돈 안 쓰고 전 과정 테스트 | 개발할 때 |

> 💡 `session_store.py`가 쓰는 건 **SQLite**입니다. 서버를 따로 안 띄워도 되는, 파일 하나로 끝나는 아주 작은 데이터베이스예요. 엑셀 파일 하나에 표를 저장한다고 생각하면 됩니다.

## 11. 실제로 터지는 고장들

| 증상 | 진짜 원인 | 고치는 법 |
|---|---|---|
| 교대가 영원히 안 일어남 | `input_tokens`만 세고 캐시를 안 더함 | `context_tokens_from_usage()` 확인 (7장 참고) |
| 교대는 되는데 대화가 뚝 끊긴 느낌 | 인계서에 **말투·호칭·직전 발화**가 없음 | `prompts/handoff_write.md`의 2번 항목 보강 |
| 새 조수가 시작하자마자 종이 40% 참 | 인계서에 파일 내용을 복붙함 | "경로만 적어라" 규칙 강조. 300줄 상한 |
| 봇이 아무 말 없이 죽음 | `Prompt is too long` | 임계값을 0.75 → 0.65로 |
| 여러 방 대화가 섞임 | 방마다 작업 폴더를 안 나눔 | `workspace_for()`가 방마다 폴더를 나누는지 확인 |
| 아무나 봇에 명령함 | **방 번호로** 접근 제한을 걸었음 | **사람 번호로** 걸어야 함 (아래 참고) |
| 텔레그램 그룹에서 무반응 | 프라이버시 모드 | BotFather → `/setprivacy` → Disable |
| 디스코드에서 멘션만 들어옴 | Message Content Intent 꺼짐 | 개발자 포털에서 켜기 |

### 접근 제한은 "방"이 아니라 "사람"으로

이게 왜 중요하냐면:

```
❌ "이 그룹방은 허용" 으로 걸면
   → 그 그룹에 있는 사람 아무나 봇에게 명령할 수 있다
   → 그 봇은 당신 컴퓨터에서 실제로 파일을 고치고 명령을 실행한다

✅ "이 사람 ID만 허용" 으로 걸어야 한다
```

Claude Code 공식 문서도 똑같이 경고합니다. "Gate on the sender's identity, not the chat or room identity."

## 12. 그래서 뭘 하면 되나

순서대로 하세요.

**1단계 — 돈 안 쓰고 확인**
```bash
python3 tests/test_handoff_flow.py
```
가짜 조수로 3턴을 돌려서 교대가 제대로 되는지 봅니다. API 비용 0원.

**2단계 — 진짜 조수로 터미널에서**
```bash
python3 -m bridge local
```
`/status`를 쳐보면서 종이가 차오르는 걸 눈으로 봅니다.

**3단계 — 봇 붙이기**

`.env`에 토큰과 **허용 사람 목록**을 채우고 `python3 -m bridge telegram`.

**4단계 — ★진짜 작업★**

며칠 돌려본 뒤 `.claude/session-history/`에 쌓인 인계서들을 읽어보세요.
**교대 직후에 대화가 어색했던 지점**을 찾아서, 그 원인이 된 항목을 `prompts/handoff_write.md`에 추가하세요.

코드는 한 번 짜면 끝이지만, **인계서 항목은 계속 자랍니다.** 4단계가 이 프로젝트의 본체입니다.
