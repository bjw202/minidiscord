## 4. 미검증 (Gaps) — 통과로 읽어서는 안 된다

1. **테스트 실행 결과 전부.** `node_modules` 가 없어 `npm test -w channel` 을 **한 번도 실행하지 않았다.** §2.1(변이 D·E 집합)·§2.2(AC-007 이 RED 에서 통과)·§2.4③(변이 A 가 005 를 무너뜨린다)는 **전부 소스 대조 판정**이다. 근거가 되는 사실(단언 원문, `it` 구조, `tick` 값, 하네스 반환값)은 파일에서 직접 읽었다.
2. **N-7 교정 후 실소요.** 129회 루프에서 6,450ms 를 걷어냈다는 것은 산술이다. `client.notification` 129회 자체의 비용과 `tick()` 4회(200ms)는 재지 못했다. 여유는 크지만 관측이 아니다.
3. **변이 C 의 실제 실패 집합.** 작성자와 마찬가지로 확정하지 못했다(§6 참조).
4. **`helloAgain()` 의 실제 동작.** 같은 소켓 위 `welcome` 재전송이 클라이언트 상태를 뒤집는지는 구현이 없어 확인 불가. `AC-CHANAUTH-003` (나) 전체가 이 전제 위에 있다 — **2차 Gap 3 과 동일하며 해소되지 않았다.**
5. **`AC-CHANAUTH-011` (d)의 stdio `initialize` 왕복.** 자식이 `"result"` 를 돌려주는지 실행 미확인.
6. **커버리지·타입 검사·lint.** 실행 불가.
7. **변이 F·G·H 의 사이드이펙트.** 세 변이가 형제 기준을 건드리지 않는다는 것은 대상 함수의 호출 범위로 추론했고, 각 형제 기준 본문을 전건 대조하지는 않았다 — **가설이다.**
8. **`AC-CHANNEL-004 (a)`·`005 (a)` 셸 프로브의 실행 단계.** `acceptance.md:682` 은 "M2 단계 3 의 빌드 뒤", `plan.md:126` 은 M2 **단계 4** 에서 실행하라고 적는다. 모순은 아니지만("단계 3 의 빌드 뒤" ⊃ 단계 4) 한 문장으로 못 박히지 않았다 — 결함으로 올리지 않고 여기 남긴다.

## 5. 잔여 위험 (Residual-risk)

- **F-01 이 되돌림 사고로 이어지는 경로가 실재한다.** 표 아래 보호 문구는 A·B 행만 지킨다. D·E 에서 집합이 어긋나면 run 이 "기준이 틀렸다"로 판정할 여지가 그대로 열려 있고, 그 판정의 대상은 재생 차단 단언 — 이 카드가 존재하는 이유다. 편집 한 줄로 닫히므로 이 위험을 남길 이유가 없다.
- **F-03 은 지금 고치지 않으면 영영 고쳐지지 않는다.** `it` 이름은 커밋되면 이후 어떤 라운드도 되묻지 않는다. 이 프로젝트가 이미 기록한 "회귀 스위트 밖의 기준" 부류와 같은 형태다.
- **변이 C 는 계획이 유일하게 열어 둔 판단 자리다.** 처리는 정직하고 절차도 적혀 있으나(§6), DoD 의 이분법 게이트가 그 열림을 흡수하지 못한다.
- **`helloAgain()` 전제(Gap 4)는 세 라운드 내내 열려 있다.** 구현이 없어 계획 단계에서 닫을 수 없는 종류이며, run 단계 M1 단계 1 이 이 전제를 처음 실측하는 자리가 된다. 어긋나면 `AC-CHANAUTH-003` (나)의 하네스 설계를 다시 정해야 한다.
- **테스트를 한 번도 못 돌린 채 세 라운드가 끝났다.** 이 감사가 내린 모든 "실패한다/통과한다"는 소스 대조다. run 단계의 첫 실행이 계획 전체의 첫 실측이 된다.

## 6. 변이 C 이연 판정 — 정직한가, 충분히 경계 지어졌는가

**정직하다.** 세 자리에 같은 사실이 적혀 있다 — 표 C 행(`:699`, "실행으로 확정하지 못했으므로"), 표 아래 주(`:706`, "계획 단계에서는 변이를 한 번도 실행하지 못했다"), 처리 대장 §3.3("확정하지 못한 유일한 변이 행이다"). 숨기거나 확정으로 위장한 자리는 없다.

**경계도 대체로 지어졌다.** 절차("실측한 집합을 원문으로 §E.2 에 남기고 판정한 뒤 진행")와 되돌림 금지(A·B 행)가 함께 적혔고, 어긋남의 방향("003 (나)가 함께 실패할 수 있다")까지 예측해 뒀다. 근거도 타당하다 — `throw` 로 소켓이 끊기면 `helloAgain()` 이 죽은 소켓으로 나가므로 (나)가 해소되지 않는다.

**다만 게이트가 그 열림을 흡수하지 못한다.** DoD(`:712`)와 §G(`plan.md:168`)는 "여덟 행 **전건** 집합 일치"를 이분법으로 요구하는데, C 행의 칸은 집합이 아니라 "둘 중 하나"다. run 은 그 DoD 항목을 참으로도 거짓으로도 표시할 수 없다. **한 줄 카브아웃이면 닫힌다** — 아래 F-08.

숨긴 모순은 아니다. 미완성 게이트다.

## 11. run 단계가 물려받는 것

이 절은 **판정이 FAIL 이든 운영자가 debt 수용을 고르든 동일하게 유효하다.**

1. **`node_modules` 가 전제다.** 세 라운드 어느 감사도 테스트를 실행하지 못했다. `npm ci` 가 M1 단계 0 보다 먼저다. 이 계획의 모든 "실패한다/통과한다"는 **소스 대조 예측**이며, run 의 첫 실행이 그 전체의 첫 실측이다.
2. **변이 C 는 열린 채로 넘어간다.** 실측 집합을 §E.2 에 원문으로 남기고, `{005}` 든 `{005, 003(나)}` 든 **문서를 고치지 말고 보고한다.** A·B 행의 003(가)·004·005·`notes` 단언은 어떤 경우에도 "기준이 틀렸다"로 되돌리지 않는다.
3. **`t15` 경계는 축소 불가다.** 사칭 채팅 주입과 이력 오염은 13개 요구사항을 전부 구현해도 열린 채 남는다. run·sync 어느 보고도 이 카드를 「F-01 을 닫았다」로 적어서는 안 된다. §E.2 에 그 사실이 없으면 완료가 아니다.
4. **`helloAgain()` 전제는 미검증이다.** `AC-CHANAUTH-003` (나) 전체가 "같은 소켓 위 `welcome` 재전송이 클라이언트 상태를 세운다"에 얹혀 있고, 구현이 없어 세 라운드 내내 확인하지 못했다. M1 단계 1 이 이것을 처음 실측하는 자리다 — 어긋나면 하네스 설계를 다시 정해야 하므로 멈추고 보고한다.
5. **순서 규율 둘은 절대 앞당기지 않는다.** M1 단계 1b(형제 일곱 건 실패 원문)와 M3 단계 1.3(개정 전 CHANPERM 다섯 건 실패 원문)은 개정본 투입 **전에** 관측한다. 개정본을 먼저 넣으면 계약 충돌이 실재했다는 증거가 영구히 사라진다.
