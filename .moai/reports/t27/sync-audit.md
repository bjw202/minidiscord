# SPEC-CI-001 sync 단계 감사 (카드 `t27`) — 렌즈 `--security`

> 감사 주체: `sync-auditor` (독립 판정). 대상 head **`a111aeb`** (sync 커밋). 나무 `.claude/worktrees/t27` · 브랜치 `WT-ci-test-wiring`.

## 0. 쉬운 말 요약

이 카드는 GitHub Actions에 테스트 워크플로 하나를 세웠습니다. **판정은 통과(PASS)입니다** — 점수 **0.866**, 통과선 0.80.

무엇이 잘 됐는가: 워크플로가 **실제로 붉어질 수 있다**는 것을 제가 직접 확인했습니다. 일부러 테스트를 깨뜨린 커밋과 `pretest`를 지운 커밋 두 건이 원격에서 진짜로 `failure`가 됐고, 되돌린 뒤 다시 초록이 됐습니다. 「초록이니까 통과」가 아니라 「붉어질 줄 아는 초록」이라는 뜻입니다. 수용 기준 열두 건 중 일곱 건은 제가 명령을 다시 돌려 기록과 글자 그대로 같은 출력을 얻었고, 나머지는 GitHub에 직접 물어 확인했습니다.

보안 면은 **실제로 작습니다** — 억지로 결함을 만들어 붙이지 않겠습니다. 권한이 `contents: read` 하나뿐이고 비밀값을 쓰는 단계가 없어서, 포크에서 온 PR이 권한을 얻거나 비밀을 읽을 경로가 없습니다. 낮은 등급 두 건만 적었습니다.

무엇이 막혔는가: **차단 사유는 없습니다.** 다만 이 프로젝트가 이름 붙인 반복 결함 「정정이 스스로 낡은 기록을 남긴다」가 `spec.md`에 **두 자리** 살아 있는데, sync 레인은 그중 **한 자리만** 찾아 공시했습니다. 나머지 한 자리(`spec.md:97`의 「`.nvmrc` 없음」)는 아무도 언급하지 않았습니다. 이것이 이번 감사가 새로 찾은 가장 실질적인 지적이며, 판정을 뒤집을 정도는 아닙니다.

## 4. `--security` 렌즈

**결론부터: 이 카드의 보안 표면은 실제로 작다.** 두께를 꾸미려고 findings를 만들어 붙이지 않겠다. Critical/High **0건**, Low 2건, 정보성 3건이다.

### 4.1 트리거 표면 — 포크 PR 상승 경로 없음 (확인함)

`ci.yml` 29행 전문을 통독했다. 관측:

- 트리거는 **`push`와 `pull_request` 둘뿐**이다. **`pull_request_target` 없음 · `workflow_run` 없음** — 이 둘이 포크 PR에 쓰기 권한과 비밀값을 넘기는 두 대표 경로인데, 어느 쪽도 없다.
- 순수 `pull_request`는 포크에서 올 때 **GITHUB_TOKEN이 강제로 읽기 전용이 되고 저장소 비밀값이 주입되지 않는다.** 워크플로가 이 기본값을 완화하는 장치를 하나도 두지 않았다.
- 작업 안에 `secrets.*` 참조가 **0건**이다(파일 통독). 비밀값을 쓰는 단계가 없으므로 유출할 비밀 자체가 없다.
- 저장소는 **비공개 단일 소유자**(`bjw202/minidiscord`)라 포크 PR이 현실적으로 발생하지 않는다.

**`permissions: contents: read`는 진짜 최소권한인가 — 예.** 이 작업이 하는 일은 체크아웃 + `npm ci` + typecheck + test다. 이슈·PR·패키지·배포 어디에도 쓰지 않으므로 `contents: read`가 필요 최소이고, 더 줄이면(`{}`) 체크아웃이 실패한다. 과잉 부여가 한 항목도 없다.

### 4.2 액션 SHA 고정 — **과잉 지적으로 판단한다** (근거를 붙여 적는다)

`actions/checkout@v4` · `actions/setup-node@v4`는 태그 고정이며 태그는 가변이다. 교과서적으로는 SHA 고정을 권한다. 그러나 **이 저장소의 위협 모형에서 실질 위험은 낮다**고 판단하며, 반사적으로 목록에 올리는 대신 근거를 적는다.

- 둘 다 **GitHub 자사 1차 액션**이다. 태그 탈취가 일어나면 전 세계 수백만 워크플로가 동시에 영향받는 사건이며, 이 저장소 고유의 위험이 아니다.
- 액션이 탈취돼도 **탈취할 비밀이 없다**(§4.1) — 토큰은 `contents: read` 하나다.
- 배포·퍼블리시·아티팩트 업로드 경로가 **없다** — 오염된 산출물이 밖으로 나갈 통로가 없다.
- 남는 실제 피해는 **비공개 저장소 소스의 유출**과 읽기 전용 토큰 노출이다. 0은 아니지만, 취미 규모 비공개 저장소에서 SHA 고정과 그 유지 비용(Dependabot 배선 없이는 갱신이 수동)을 정당화할 만큼은 아니다.

→ **Low · 비차단 · 조치 권고 아님**(F-04). 저장소가 공개로 전환되거나 비밀값을 쓰는 단계가 생기면 이 판단은 재검토해야 한다.

### 4.3 `npm ci` 라이프사이클 스크립트 — 이 워크플로가 악화시키지도, 완화하지도 않는다

`npm ci`는 러너에서 모든 의존성의 설치 스크립트를 실행한다. 이 카드가 만든 변화를 정직하게 가른다.

- **악화 요인 없음**: 이 워크플로가 `--ignore-scripts`를 제거한 것이 아니라 애초에 없었다. 캐시(`cache: npm`)는 `package-lock.json` 해시 키이고 npm이 tarball 무결성 해시를 검증하므로 캐시 오염만으로 임의 코드가 들어가지 않는다.
- **완화 요인 있음**: `contents: read` + 비밀값 부재 + 배포 경로 부재가 폭발 반경을 러너 수명 안으로 가둔다.
- **`--ignore-scripts`는 이 저장소에서 쓸 수 없다** — `better-sqlite3`가 prebuild를 설치 스크립트로 받는다(`spec.md` §2.4). 권고할 수 없는 조치를 권고하지 않는다.

### 4.4 `checkout` 자격증명 잔류 — **유일하게 실행 가능한 보안 지적**

`actions/checkout`은 기본값 `persist-credentials: true`로 GITHUB_TOKEN을 `.git/config`에 남긴다. 이 작업에서는 그 뒤에 `npm ci`가 서므로, **악성 의존성의 설치 스크립트가 `.git/config`를 읽어 읽기 전용 토큰을 얻을 수 있다.**

- 실패 시나리오: 의존성 하나가 탈취돼 설치 스크립트가 `cat .git/config`로 토큰을 얻고, 그 토큰으로 이 **비공개** 저장소를 읽어 외부로 보낸다.
- 영향: 읽기 전용·작업 수명 한정. 쓰기·배포 불가.
- 닫는 법 (한 줄):
  ```yaml
  - uses: actions/checkout@v4
    with:
      persist-credentials: false
  ```
  이 워크플로는 체크아웃 이후 git 인증을 쓰지 않으므로 부작용이 없다.

→ **Low · 비차단**(F-03).

### 4.5 `pretest` 훅이 실행 통로가 되는가 — **아니다** (검토했고 부정한다)

`"pretest": "tsc"`가 모든 `npm test`에 붙었고, 개발자 로컬에서도 돈다. 실행 통로가 되는지 따졌다.

- **`tsc`는 컴파일 대상 소스를 실행하지 않는다.** 악의적 PR이 `channel/src/*.ts`를 바꿔도 `tsc`가 그 코드를 돌리지 않는다.
- `tsconfig.json`의 `plugins`는 **language service** 플러그인이며 `tsc` 본체가 로드하지 않는다. tsconfig를 통한 코드 실행 경로가 없다.
- 실제 실행 통로는 `pretest`가 아니라 **`npm ci`의 설치 스크립트**이며, 그것은 이 카드 이전부터 있던 표면이다(§4.3).
- 부작용은 하나 있다 — `npm test`가 이제 `channel/dist`에 **쓴다**. 작업 트리 오염이 되는지 확인했다: `.gitignore:3`의 `dist/`가 `channel/dist`를 덮는다(`git check-ignore -v channel/dist` → `.gitignore:3:dist/`, 이 세션 실행). 추적 대상이 되지 않는다.

→ **정보성. finding 아님.**

### 4.6 워크플로가 거짓말할 수 있는가 — 파일을 읽고, 그리고 실측으로 부정했다

주장을 받지 않고 `ci.yml` 29행을 직접 통독했다. 억제 장치를 **하나도 찾지 못했다**:

| 찾은 것 | 결과 |
|---|---|
| `continue-on-error` | 없음 |
| `if:` 조건부 단계 | 없음 (4개 `run` 단계 전부 무조건) |
| `\|\| true` · `set +e` | 없음 |
| 재시도 액션 (`nick-fields/retry` 등) | 없음 |
| `exit 0` 강제 | 없음 |

그리고 **정적 판독보다 강한 증거가 있다** — §3.2에서 두 변이 커밋이 원격에서 실제로 `failure`를 냈다. 「아무것도 실행하지 않는 워크플로가 초록으로 통과한다」는 이 SPEC이 스스로 경계한 형태는 **관측으로 부정됐다.**

정보성 두 가지를 함께 적는다:
- **`cancel-in-progress: true`는 거짓 초록을 만들지 못한다** — 취소된 실행의 결론은 `cancelled`이지 `success`가 아니다. 다만 빠르게 두 번 밀면 앞 실행이 붉어졌을지 확인할 기회가 사라진다. 최신 head는 여전히 통과해야 하므로 게이트가 뚫리지는 않는다.(F-09)
- **브랜치 보호가 없으므로 붉은 CI가 병합을 기계적으로 막지 않는다.** 「CI가 있다」와 「CI가 병합을 잠근다」는 다른 말이다. 이 카드는 `spec.md` §5에서 명시적으로 배제했고 **CHANGELOG가 그 경계를 정확히 공시했다**(「브랜치 보호 규칙(required status checks)도 설정하지 않았습니다」). 과장도 축소도 아니다.(F-07)

### 7.1 열린 관측 (통과도 실패도 아님)
