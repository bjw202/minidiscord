### 0.2 Tier 판정 — 1회차 O1 을 철회한다

1회차에서 나는 `:140` 범위 축만으로 **Tier S** 를 판정했다. 리드가 예산 표(`:146-152`, S = 8/8)의 실재를 확인해 주었고 — 나 자신도 1회차 보고서 §0 에서 그 표를 「M = 16/16」으로 인용했으므로 표의 실재는 내 쪽에서도 이미 읽은 것이었다 — 레인의 도출을 텍스트로 다시 검토했다.

레인의 논증: 범위 축은 S, 예산 축은 M(REQ 12·AC 10 은 8/8 을 양쪽 다 초과), 그리고 `:154` 가 범위 축을 **스스로 「지침」이라 낮추는** 반면 `:152` 는 예산 축에 **처방**을 붙인다 — 그러므로 지침 축이 처방 축에 진다.

**이 논증을 나는 깨뜨리지 못했다.** 내가 시도한 반론 둘과 그 결말을 적는다.

1. **「예산 표는 Tier 의 *결과*이지 *입력*이 아니다」** — 표 머리가 「the tier **also caps** how many requirements…」라고 적으므로 방향은 Tier → 예산이다. 그러나 `:152` 가 「Exceeding either ceiling is **a signal to tier up**」이라고 명시해 **예산 → Tier 의 되먹임을 규칙 자신이 승인**한다. 반론 실패.
2. **「`:152` 는 세 번째 길 — 예산에 맞게 줄이기 — 도 허용한다」** — 이것은 참이다. `:152` 는 「tier up 또는 split」만 명시하지만, 「줄여서 맞추기」는 예산을 *완화*하는 것이 아니라 *준수*하는 것이므로 금지되지 않는다. 그리고 같은 문장이 「an over-budget SPEC is the same **over-formalization failure** the tier taxonomy exists to prevent」라고 적는다 — 40~60행 YAML 하나를 만드는 카드가 요구 12건·기준 10건을 지는 것은 문면 그대로 그 실패의 모양이다. **그러나 이것은 「M 이 틀렸다」가 아니라 「M 도 S 도 아닌 셋째 선택지가 있었다」이며, `:152` 가 명시적으로 제시하는 두 길 중 하나를 고른 것을 규칙 위반이라 할 근거가 되지 못한다.** 반론이 판정을 뒤집지 못한다.

**판정: Tier M 을 수용한다. 통과선 0.80 을 적용한다. 1회차 O1 은 철회한다.**

부기(비차단, R2-10): 그럼에도 `:152` 의 「over-formalization」 문장은 이 SPEC 에 그대로 들어맞는다. 셋째 길 — 요구·기준을 8/8 로 줄이고 Tier S 로 남기 — 을 **검토했다는 기록이 어디에도 없다.** `plan.md` §0.2 는 「쪼갤 이유는 없다」만 적고 「줄일 이유는 없다」는 적지 않는다. 라벨을 올리는 것과 형식을 줄이는 것 중 왜 전자인지는 아직 논증되지 않았다.

## 3. 차단 발견 (blocking) — 4건

### R2-1 — AC-CI-006 의 파괴 커밋은 이 저장소의 pre-commit 게이트가 거부한다

`acceptance.md:236-237` — Severity: critical — Class: blocking

AC-CI-006 의 절차는 **의도적으로 실패하는 테스트 파일**을 더한 뒤 커밋한다:

```bash
git add server/test/zz-scratch-fail.test.ts          # 경로 명시. -a 금지
git commit -m "scratch: CI 변별 — 의도적 실패 (병합 금지)"
```

이 저장소에는 pre-commit 훅이 살아 있고, 그 훅의 마지막 단계가 테스트를 돌린다:

```
$ ls /Users/…/minidiscord/.git/hooks/ | grep -v '\.sample$'
pre-commit
pre-push

$ cat …/.git/hooks/pre-commit          # 발췌
# MoAI-ADK pre-commit hook — fast subset (gofmt + go vet) + heavy gate (moai gate)
# Bypass via: SKIP_MOAI_PRECOMMIT=1 git commit
if command -v moai >/dev/null 2>&1; then
    if ! moai gate; then
        printf '\n[pre-commit] FAILED: moai gate reported errors above.\n' >&2
        exit 1
    fi
fi

$ command -v moai
/Users/byunjungwon/.local/bin/moai            ← 훅의 조건이 성립한다
```

훅 자신의 머리말이 `moai gate` 를 「vet + lint + **test**, 16-language detection」이라 적는다. 즉 **일부러 실패시킨 테스트가 게이트를 붉게 만들고, 그 커밋은 거부된다.** AC-CI-006 의 명령열에는 `SKIP_MOAI_PRECOMMIT=1` 도, 이 훅에 대한 한 줄의 언급도 없다.

이것은 1회차 D2 와 **같은 부류가 한 겹 아래에서 재현된 것**이다 — 「적힌 대로 실행하면 돌아가지 않는다」. 다른 점은 원인이 문서가 아니라 저장소 환경이라는 것뿐이고, 이 프로젝트는 그 환경을 이미 두 번 겪었다(카드 `t22` 가 `SKIP_MOAI_PRECOMMIT=1` 을 공식 우회로 쓰고 커밋에 공시했고, 프로젝트 기억 `fresh-worktree-needs-channel-build` 가 「문서만 담은 커밋도 pre-commit 게이트에 막힘」을 기록한다).

**미검증 표시**: `moai gate` 가 이 저장소의 JS 스위트를 실제로 돌린다는 것은 **훅의 머리말 + 위 두 프로젝트 기록**에 근거한 것이며, 나는 `moai gate` 를 실행하지 않았다(감사 도중 스위트가 `server/data` 를 다시 만들고 수십 초를 쓴다). 이 한 고리는 **가설**로 표시한다. 다만 훅이 존재하고 `moai` 가 PATH 에 있다는 것 — 즉 게이트가 **발동한다**는 것 — 은 위 두 명령으로 실측했다.

**대칭 확인**: AC-CI-007 의 파괴 커밋은 `ci.yml` 만 담으므로 스위트가 초록이고 게이트를 통과한다. **막히는 것은 006 하나뿐**이다.

**필요한 수정**: AC-CI-006 의 커밋 줄을 `SKIP_MOAI_PRECOMMIT=1 git commit -m "…"` 로 바꾸고, **왜 이 자리에서만 우회가 정당한지**(이 커밋의 붉음이 측정 대상 자체이며 병합되지 않는다) 를 기준 본문에 한 줄로 공시한다. 우회를 조용히 넣으면 그것이 다음 회차의 결함이 된다.

### R2-2 — AC-CI-007 의 제거 스크립트는 인접 단계까지 지울 수 있고, 그 유일한 검사가 그것을 못 잡는다

`acceptance.md:278-292` — Severity: major — Class: blocking

빌드 단계 블록의 끝을 찾는 줄:

```python
start = max(i for i in range(hit + 1) if re.match(r'\s*- (name|run):', lines[i]))
indent = len(lines[start]) - len(lines[start].lstrip())
end = next((i for i in range(start + 1, len(lines))
            if re.match(r'\s*- (name|run):', lines[i])
            and len(lines[i]) - len(lines[i].lstrip()) == indent), len(lines))
```

경계 정규식이 `- name:` 과 `- run:` **둘만** 인식한다. GitHub Actions 의 단계는 `- uses:` 로도 시작하며, `plan.md` §E 가 제안하는 워크플로에는 `actions/setup-node` 단계가 반드시 들어간다. 빌드 단계 **바로 다음**이 이름 없는 `- uses:` 단계라면 `end` 탐색이 그것을 건너뛰고 **그 다음 `- name:`/`- run:` 까지 지운다** — 빌드 단계 하나가 아니라 둘이 사라진다.

그리고 이 절차의 유일한 확인은:

```bash
grep -c 'npm run build -w channel' .github/workflows/ci.yml   # → 0 (제거 확인)
```

이것은 「빌드 단계가 사라졌다」만 재고 **「그것만 사라졌다」는 재지 못한다.** 과삭제가 일어나면 관측된 `failure` 의 원인이 빌드 순서인지 함께 지워진 단계인지 갈리지 않는다 — 이 SPEC 이 `plan.md` §G 마지막 행에서 스스로 이름 붙인 **「굵은 변이는 절반을 가린다」** 부류이며, 같은 행이 「AC-CI-007 은 빌드 단계 **하나만** 변이」라고 방어를 주장한다. 주장이 스크립트보다 넓다.

**미검증 표시**: `.github/workflows/ci.yml` 은 아직 존재하지 않으므로(run 단계 산출물) 나는 이 스크립트를 **실제 대상에 돌리지 못했다.** 위 판단은 스크립트 본문의 정규식 독해에 근거한 **가설**이다. 다만 정규식이 `uses` 를 담지 않는다는 것은 인용한 두 줄에서 문면으로 확인된다.

**필요한 수정**: 경계 정규식에 `uses` 를 더하고(`- (name|run|uses):`), 확인 명령을 **삭제 폭의 단언**으로 바꾼다 — 스크립트가 이미 `print('removed lines', start, '..', end)` 를 내므로 그 폭이 예상 범위인지 단언하거나, 제거 전후의 `len(job['steps'])` 차이가 정확히 1 임을 단언한다.

## 8. 권고 — 3회차를 향한 수정 지시

**이번 개정은 잘 됐다.** 1회차 차단 7건이 전건 닫혔고, 내가 가장 강하게 때린 자리(AC-CI-009)는 내 공격 열 가지 중 여덟을 막아냈다. 남은 것은 성격이 다르다 — 둘은 **한 겹 아래에서 같은 부류가 재현된 것**이고 둘은 **개정 자신이 남긴 낡음과 그것을 잡았어야 할 표의 불완전함**이다.

1. **[차단] AC-CI-006 의 커밋에 `SKIP_MOAI_PRECOMMIT=1` 을 넣고 그 정당성을 공시한다** (R2-1). 이 자리에서만 우회가 옳은 이유 — 커밋의 붉음이 측정 대상이고 병합되지 않는다 — 를 기준 본문에 한 줄로 적는다. AC-CI-007 은 손대지 않는다(게이트를 통과한다).
2. **[차단] AC-CI-007 의 경계 정규식에 `uses` 를 더하고, 확인을 「하나만 지워졌다」의 단언으로 바꾼다** (R2-2). 지금의 `grep -c … → 0` 은 과삭제를 보지 못한다.
3. **[차단] R2-3 의 아홉 자리를 한 커밋에서 고치고, 세 벌의 재훑기 출력을 원문으로 남긴다.** `DoD [0-9]` · 개수 인용 · `AC-CI-004` 오지목. **`spec.md:213` 을 먼저 본다** — D4 를 닫으려고 새로 쓴 문장이 틀린 DoD 번호를 가리킨다.
4. **[차단] §D-2 파급표에 「그 밖의 자리」 열을 더한다** (R2-4) — §E 형태 표 · §C 사전 점검 · §F M5. 그리고 M1 의 [HARD] 를 「모든 열」에서 「모든 자리」로 넓힌다.

### 3회차 범위

이 보고서의 **R2-1 ~ R2-11 + §0.2 Tier 판정**이 3회차 재감사의 범위다. 3회차는 백지 전면 재감사가 아니라 이 델타 + 회귀 점검으로 수행한다. R2-1~R2-4 가 미해결로 남으면 다른 점수와 무관하게 자동 FAIL 이다.

**[HARD] 3회차가 한계다** (`plan-auditor` Retry Loop Contract, `harness.yaml` `max_iterations: 3`). 3회차에서도 통과선에 닿지 못하면 리드가 운영자에게 세 선택지 — 부채 인수 통과(PASS-with-debt) / 범위 축소 / 명시적 연장 — 를 제시해야 한다. 현재 미달 폭이 0.012 이고 남은 차단이 넷이므로 **3회차 통과는 충분히 도달 가능한 거리**다.
