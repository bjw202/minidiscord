## 쉬운 말 요약

교정은 성공했다. 두 라운드 동안 계속 어긋났던 이음매 — 장식 기능을 만드는 쪽과 쓰는 쪽을 실제로 이어 붙이는 한 줄 — 이 이번에 닫혔다. 두 SPEC 이 그 한 줄에 대한 설명 문단을 **글자 하나까지 똑같이** 싣고 있는 것을 md5 로 직접 대조해 확인했고, 넘기는 값도 양쪽이 같은 것(팩토리 그 자체)을 가리킨다. 그리고 그 배선이 실제로 동작하는지를 보는 관측이 처음으로 생겼다 — 잘못 배선한 구현은 그 관측에서 반드시 실패한다는 것도 경로를 따라가 확인했다.

기준 SHA 가 없으면 조용히 통과하던 문제도 닫혔고, 빠져 있던 허용 파일도 들어갔다. 세 라운드에 걸친 MUST-FIX 열한 건이 **전부 종결**됐다.

남은 것은 일곱 건인데 전부 가볍다. 그중 하나만 실제로 손해가 있다 — 새로 쓴 줄 세기 명령이 경계에서 한 칸 어긋나서, **옳게 구현했는데도 붉어질 수 있는 자리가 딱 한 군데** 있다. 직접 실행해서 확인했다. 다만 그 자리는 실패하면 원인이 바로 화면에 보이므로 run 단계에서 몇 분이면 진단된다.

판정은 세 SPEC 전부 **통과**, 그리고 두 번 연속 불합격이던 **교차 SPEC 통합 표면도 이번에 통과**다. 카드는 run 단계에 들어갈 준비가 됐다.

### 관측 5 가 `.decorate` 배선을 실제로 실패시키는가 — **실패시킨다** (경로 추적)

잘못 배선한 구현 `registerMessageDecorator(createRichContext({ api, doc }).decorate)` 을 놓고 `openRoom` 경로를 따라갔다.

1. 모듈 적재 시점에 컨텍스트가 하나 만들어지고 `ctx.decorate` 가 등록된다.
2. `openRoom` 3-1 단계가 `factory({ api, doc: document })` 를 부른다 → 실제로는 `decorate({ api, doc }, undefined)` 가 불린다.
3. `decorate` 안에서 `m.attachments` 접근이 `TypeError` 로 죽거나(→ 테스트가 예외로 실패), 널 가드가 있으면 `undefined` 를 반환한다.
4. 3-1 단계가 그 `undefined` 를 방의 컨텍스트로 보관한다 → falsy → `renderMessage` 는 "등록 없음"으로 판단해 훅을 부르지 않는다 (`WEBCHAT/spec.md` L270).
5. `document.querySelectorAll('#messages .message a.attachment')` 가 **0개** → `expect(nodes).toHaveLength(1)` 실패.

두 갈래(예외 사망 / 노드 0개) 모두 실패로 끝난다. **관측 5 는 그럴듯해 보이는 것이 아니라 실제로 판별한다.**

관측 4 도 함께 운다: 잘못된 형태는 문자열이 `registerMessageDecorator(createRichContext(` 이므로 첫 명령(`…(createRichContext)` 개수)이 `1` 이 아닌 `0` 이 되고, 둘째 명령이 `0` 이 아닌 `1` 이 된다. `plan.md` L410 의 변이 검증 주장과 일치한다.

관측 5 의 스텁이 형제 계약과 맞는지도 대조했다 — `GET /api/rooms/:id/messages` → `{ messages: [...] }` (`WEBCHAT/spec.md` L88·L132), `startsWith` 매칭이므로 쿼리 파라미터에 안전하다.

### 잔여 `.decorate` 텍스트 — **한 곳 남았다** (경미)

전수 대조 결과, `.decorate` 를 넘긴다는 표현이 남은 자리는 **하나**다.

> `SPEC-WEBRICH-001/plan.md` L32 — "…이 SPEC 은 그 훅에 끼울 함수(`createRichContext(...).decorate`)**만** 공급한다."

두 가지가 낡았다: 넘기는 값의 형태(현행 계약은 팩토리)와 "**만**"(현행 소유표는 배선 한 줄도 이 SPEC 의 것으로 준다). 0.2.0 의 소유 반전을 설명하는 서술 문단 안이라 역사적 기술로 읽히기는 하나, 0.3.0 교정 표시가 없다.

나머지 `.decorate` 등장은 전부 **부정형**(하지 말라는 지시), **변이 검증 대상**, 또는 **HISTORY 기록**이며, `plan.md` L368 의 `createRichContext().decorate` 는 M2 산출물 이름 표기이지 배선 지시가 아니다. 비차단 — §5 R3-3 참조.

## §2 — MF-10 (공허 가드) 검증

가드별로 "정말 그 길을 막는가"를 따로 판정했다.

| 가드 | 막는 길 | 판정 |

### 넓힌 awk 패턴 — 실행 확인 (새 실패 모드 없음)

세 선언 형태를 실제로 넣어 돌렸다. 전부 범위를 잡는다.

```
export function renderMessage(m) {   → 1,3
const renderMessage = (m) => {       → 1,3
export function renderMessage (m) {  → 1,3
```

오탐 검사도 했다 — `export function renderMessageList(a)` 가 앞에 있는 파일에서 범위가 `4,6`(진짜 `renderMessage`)으로 잡힌다. **패턴을 넓힌 것이 새 실패 모드를 만들지 않았다.**

### 3-c 계수 명령 — 실행 확인 (경계 결함 1건)

한 번도 실행된 적 없는 명령이므로 합성 diff 로 직접 돌렸다. 범위는 `120,148` 로 고정.

| 입력 | 출력 | 판정 |
|------|------|------|
| 범위 안 수정 `@@ -130,1 +130,1 @@` | `add=1 del=1` | **옳다** — 진짜 위반을 잡는다 |
| 범위 **앞** 삽입 `@@ -119,0 +119,1 @@` | `add=0 del=0` | **옳다** — 함수 밖 삽입을 세지 않는다 |
| 범위 **직후**(닫는 중괄호 다음) 삽입 `@@ -148,0 +149,1 @@` | `add=1 del=0` | **틀렸다** — 함수 밖 삽입인데 위반으로 센다 |

원인은 길이 0 헝크의 경계 처리다. `-a,0` 형태에서 `en = st + 0 - 1 = st - 1` 이므로 범위가 뒤집히고, 겹침 판정 `!(en < lo || st > hi)` 가 `st == hi` 를 "안"으로 읽는다. 삽입 지점은 `st` 와 `st+1` **사이**이므로 `st >= lo && st < hi` 여야 한다.

**결과**: 배선 한 줄을 `renderMessage` 의 닫는 중괄호 **바로 다음**에 두는 옳은 구현이 AC-016 에서 붉어진다. 앞쪽 경계는 안전하고 뒤쪽 경계만 한 칸 어긋난다. 비차단 — §5 R3-1.

**질문**: 넷째 절이 사람에게 "초과분이 주석이었는지 확인하라"고 요구하는 기준은, 라운드 1부터 계속 거절해 온 "위장된 MANUAL" 인가?

**판정: 위장된 MANUAL 이 아니다. 다만 근거는 작성자가 든 것과 다르고, 조항을 붙인 자리가 틀렸다.**

받아들이는 이유 두 가지.

1. **판정의 무게가 이진 명령에 남아 있다.** 첫째(`==1`)와 둘째(`==0`)는 사람 판단이 개입하지 않는 이진값이고, 이 둘만으로 MF-9 의 두 얼굴(배선 부재 / 호출 결과 전달)이 완전히 갈린다. 사람 확인 조항은 **보조 계수 두 개에만** 붙는다.
2. **하나 남은 구멍을 같은 기준의 다른 관측이 막는다.** 셋째 명령만이 유일하게 잡는 오구현은 "옳은 배선 + 다른 값으로 하는 두 번째 등록"이다(첫째 `1`·둘째 `0` 이면서 셋째만 `3`). 사람이 그것을 "주석이겠거니" 하고 넘길 수 있다. 그러나 두 번째 등록은 팩토리를 덮어쓰므로 **관측 5(실제 `openRoom` 경로)가 노드 0개로 운다.** 사람 조항이 통과시킬 수 있는 유일한 경우를 같은 기준의 행위 관측이 독립적으로 잡는다 — 이것이 이 조항을 살려 두는 실질 근거다.

**그런데 조항을 잘못된 명령에 붙였다.** 주석 민감성은 셋째·넷째만의 성질이 아니다. 첫째 명령 `grep -c "registerMessageDecorator(createRichContext)" web/app.js` 도 앵커가 없어 주석 안의 인용을 센다 — 구현자가 `// registerMessageDecorator(createRichContext) 는 팩토리를 넘긴다` 같은 한국어 주석을 달면 `2` 가 나와 **판정의 무게를 지는 명령이 옳은 구현에서 붉어진다.** 이쪽에는 완화 조항이 없다.

**더 나은 해법이 있고 조항 자체가 필요 없어진다**: 네 명령을 `^` 로 앵커하면(`grep -c "^registerMessageDecorator(createRichContext)"`) 주석은 전부 빠지고 — 동시에 **모듈 최상위(들여쓰기 없음)라는 계약이 같은 명령으로 강제된다.** 사람 조항을 지우고 네 명령을 다시 이진으로 되돌릴 수 있다. 권고이지 차단 사유는 아니다 — §5 R3-2.

같은 부류가 `WEBCHAT/acceptance.md` L877 DoD 에도 있다(`grep -c "registerMessageDecorator(" == 1`). 사람이 읽는 체크박스라 손해는 더 작다.

## §8 — 권고

1. **카드는 run 단계에 들어갈 준비가 됐다.** 세 라운드 MUST-FIX 열한 건이 전부 닫혔고, 두 번 불합격이던 통합 표면이 통과했다. 이음매 아홉 항목이 아홉 전부 일치하며 마지막 항목은 두 SPEC 에 바이트 동일 문단으로 실려 있다.
2. **run 단계 킥오프에서 네 줄만 먼저 고치면 좋다** (선택, 각각 한 줄): R3-1 의 경계 조건(`len==0` 일 때 `st>=lo && st<hi`), R3-2 의 `^` 앵커 넷, R3-4 의 WEBSHELL DoD 한 줄, R3-6 의 `vi.waitFor`. 넷 다 SPEC 재감사를 요구하지 않는 기준 문면 수정이다.
3. **고치지 않고 진입해도 살아남는다.** 최악의 경우는 옳은 구현이 AC-016 에서 한 번 거짓으로 붉어지는 것이고, 그 자리는 범위와 diff 가 함께 출력돼 자가 진단된다. 배선이 실제로 틀린 경우와는 신호가 다르다(관측 4의 첫째·둘째 명령이 함께 운다).
4. **run 단계에서 지켜볼 한 가지**: 배선 한 줄을 `renderMessage` 닫는 중괄호 바로 다음이 아니라 **파일 상단 import 근처**에 두면 R3-1 과 R3-5 를 동시에 피한다. 계약이 "모듈 최상위"라고만 하고 위치를 좁히지 않으므로 구현자의 자유이며, 상단 배치가 안전하다.
5. **3회 상한 소진.** 이 라운드가 3회차다. 추가 교정 라운드는 필요 없다 — 남은 일곱 건은 run 단계 실행자가 기준 문면을 손대며 처리할 수 있는 부류이고, 어느 것도 SPEC 의 요구사항·소유·경계를 바꾸지 않는다.

- **쓰기 없음**: SPEC 산출물은 한 글자도 고치지 않았다. 이 보고서만 새로 썼다.
