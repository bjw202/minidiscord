**D1. 2차 판별자가 H-1·H-2·H-3 을 가르지 못한다 — 셋이 같은 관측 한 쌍을 낸다**
`spec.md:211-217` (§5.4 2차 판정표) · `spec.md:167-171` (§4 갈래표) · `acceptance.md:123-135` (AC-WSUPGRADE-004)
Severity: **critical** · Class: **blocking**

이 SPEC 은 §4 에서 세 갈래를 열어 두고, 그 셋을 「자기 포트 대조」와 「주소 계열 대조」로 가른다고 적는다(`spec.md:171` — 「자기 포트를 함께 기록하지 않으면 세 갈래가 같은 바이트로 보인다」). **그 두 관측은 셋을 가르지 못한다.** 주 체크아웃(`node_modules` 보유)에서 세 번 실행해 확인했다.

*관측 1 — 「원격 포트 ≠ 자기 포트」(H-1 의 판별 관측, `spec.md:216`)는 원리적으로 발생하지 않는다.*
시험은 `server/test/gateway.test.ts:88` 에서 `new WebSocket(\`ws://127.0.0.1:${port}/bot\`)` 로 붙고, 그 `port` 는 `:55` 의 `app.server.address().port` 다. 클라이언트 소켓의 `remotePort` 는 TCP 정의상 **자기가 건 포트**이므로 자기 포트와 항상 같다.

```
$ node --input-type=module -e "…http 404 서버 + ws 클라이언트 + unexpected-response…"
own port 60316 address() {"address":"::","family":"IPv6","port":60316}
status 404
remote 127.0.0.1 60316 IPv4
remotePort===ownPort ? true
socket family IPv4 vs address().family IPv6
```

*관측 2 — 「주소 계열 불일치」(H-2 의 판별 관측, `spec.md:217`)는 아무 경합이 없는 정상 상태에서도 참이다.*
위 출력의 마지막 줄이 그것이다. 서버가 하나뿐이고 경합이 전혀 없는데도 소켓 계열(IPv4)과 `address().family`(IPv6)가 어긋난다. 그리고 이 저장소의 실제 앱은 더 심하다 —

```
$ node --input-type=module -e "…fastify listen({port:0}) vs listen({port:0,host:'127.0.0.1'})…"
fastify 5.12.1 {port:0}                  -> {"address":"::1","family":"IPv6","port":60321}
fastify 5.12.1 {port:0,host:127.0.0.1}   -> {"address":"127.0.0.1","family":"IPv4","port":60322}
```

`gateway.test.ts:54` 는 `{port: 0}` 이므로 자기 앱의 `address().family` 는 **언제나 IPv6**, 클라이언트 소켓은 리터럴 `127.0.0.1` 을 걸므로 **언제나 IPv4** 다. 계열 대조는 상수 「불일치」다.

*관측 3 — 진짜 오배선(H-1)을 만들어도 표는 H-2 라고 답한다.*
게이트웨이 없는 앱을 `127.0.0.1:P` 에 먼저 붙이고, 게이트웨이를 단 Fastify 앱을 같은 P 에 붙인 뒤(이 방향은 EADDRINUSE 가 아니라 **성공**한다), `ws://127.0.0.1:P/bot` 을 건다:

```
OTHER app (no gateway, IPv4) bound {"address":"127.0.0.1","family":"IPv4","port":60451}
MY app (gateway attached) bound     {"address":"::1","family":"IPv6","port":60451}
*** GOT status 404 body {"message":"Route GET:/bot not found","error":"Not Found","statusCode":404}
remotePort 60451 ownPort 60451 equal? true
sockFamily IPv4 ownAddress().family IPv6
```

**관측된 실패 서명이 그대로 재현됐고**(Fastify 모양 404), 표의 두 입력은 `포트 같음 + 계열 불일치` → 표는 **H-2** 를 낸다. 진실은 H-1(다른 앱이 답했다)이다. 그리고 관측 1 의 정상 케이스(자기 앱, H-3)도 **같은 두 입력**을 낸다. 즉 셋이 구별되지 않는다.

역방향은 막힌다는 것도 함께 쟀다 — `{port:0}` 이 먼저면 `127.0.0.1:P` 는 `EADDRINUSE`. 공존은 「IPv4 먼저 → 기본 호스트 나중」 한 방향에서만 성립한다. 이 사실은 `spec.md:275` (§7 미검증 3)이 「재지 않았다」고 적은 바로 그것이며, **명령 한 줄로 측정된다.**

AC-004 는 이 붕괴를 잡지 못한다. `acceptance.md:129` 의 이분 판정이 「**세 가지 합성 입력**이 각각 다른 갈래 이름을 내면 통과」이고 `plan.md:98` 이 「**합성 입력만 쓴다**」고 못 박기 때문이다. 순수 함수가 세 입력을 세 이름으로 가르는 것은 참이지만, **그 세 입력 중 둘은 실제 관측에서 결코 발생하지 않는다.** 이 저장소가 여러 번 겪은 부류다 — 기준이 함수는 재고 그 함수의 정의역이 도달 가능한지는 재지 않는다.

*최소 수정.* 판별을 소켓 튜플에서 **응답자 신원**으로 옮긴다. 새 파일도 새 설정도 필요 없다:
1. `spec.md:215-217` 의 두 행(포트 대조·계열 대조)을 **자기 앱이 그 요청을 실제로 받았는가**로 바꾼다 — 자기 앱에 인프로세스 요청 카운터(또는 `onRequest` 훅 한 줄)를 두고, 포획 시점에 그 값이 증가했는지 기록한다. 증가 안 함 → H-1/H-2(다른 앱), 증가 → H-3(자기 앱).
2. 계열은 **소켓 계열 대 `app.server.address().family`** 로 피연산자를 명시하되, 갈래 판정이 아니라 **기록 항목**으로 내린다(상수이므로 판별력이 없다).
3. `spec.md:275` (§7-3)을 위 실측으로 갱신하고, `spec.md:167`·`:169` 의 판별 관측 칸도 함께 고친다 — 한 자리만 고치면 형제 세 자리가 조용히 거짓이 된다.
4. `acceptance.md:129` 의 이분 판정에 **정의역 도달성 조항**을 더한다: 「세 갈래 각각에 대해, 그 갈래를 내는 입력이 실제 포획에서 발생 가능함을 보이는 관측 또는 실행 근거가 함께 기록된다.」

4. **P1 을 실행으로 시험하지 않았다** — WSS 가 붙은 Fastify 서버가 `/bot` 업그레이드에 404 를 낼 수 있는 경로가 있는지 재지 않았다. 따라서 H-3 을 「반증됐다」고 적지 않고 PLAUSIBLE 로 두었다.
5. **`moai gate` 의 워크스페이스 동시성을 확인하지 않았다.** `spec.md:130` 이 이것을 추론으로 표시한 것은 옳고, 이 감사도 재지 못했다.
6. **7ms 라는 시각이 무엇을 재는지 확인하지 않았다.** SPEC 의 §7-5 와 같은 상태다.
7. **플랫폼 일반화를 확인하지 않았다.** 모든 측정은 Darwin 25.5.0 · Node v24.12.0 · fastify 5.12.1 · ws 8.21.3 한 기계에서 나왔다. Linux 나 CI 에서 `{port:0}` 의 바인드 계열과 공존 규칙이 같은지는 **재지 않았다** — CI 에서 404 가 재현된 적이 없다는 관측(`spec.md:31`)과 함께 읽으면, 이 차이 자체가 다음 회차의 관측 항목일 수 있다.
8. **교차 모델 2차 의견을 받지 않았다.** `audit_model` 설정을 읽지 않았고 `mcp__moai__audit_multi`·`codex_audit`·`glm_audit` 중 어느 것도 호출하지 않았다. 이 판정은 단일(Claude) 감사다.
