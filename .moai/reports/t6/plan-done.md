## 3. 리드 검토가 필요한 결정 (D1~D4)

### D1 — 악수 하네스 재사용 vs 셋째 사본  **[잠정: 재사용]**

`scripts/e2e.mts` 로 쓰고 `npx tsx` 로 돌리며 `server/test/gateway-v2.ts` 의 `connectV2`/`innerOf` 를 import 합니다.

- **근거**: ① 이미 있는 헬퍼가 정확히 이 일을 합니다. ② **독립성 축이 무너지지 않습니다** — 그 하네스의 독립성은 「사본이 여럿」 이 아니라 「구현 함수를 부르지 않고 스스로 유도한다」 에 있고(`gateway-v2.ts:1-5` 주석), 재사용해도 그 성질은 그대로입니다. ③ 구현↔하네스 어긋남은 이미 왕복 기준 `AC-GWAUTH2-020` 이 감시합니다 — 사본을 늘리면 **감시자 없는 사본**만 늘어납니다.
- **비용(정직하게)**: E2E 가 `server/test/` 를 가로질러 import 합니다. 워크스페이스 경계를 넘는 참조라 낯설고, `server/test` 를 시험 전용으로 보는 독자에게 설명이 필요합니다. 스크립트 머리 주석으로 공시하도록 계획에 넣었습니다.
- 뒤집히면: 파일이 `.mjs` 가 되고 암호 코드 약 60줄이 늘며, 그 사본을 감시할 기준이 하나 더 필요합니다.

### D2 — `npm test` 편입 vs 별도 `npm run e2e`  **[잠정: 별도]**

- 이유 ① E2E 는 프로세스와 포트를 잡아 실패 양상이 단위 스위트와 다릅니다 — 섞이면 이 프로젝트의 기준선(「서버 N + 채널 M 통과」)이 흐려집니다. ② `npm test` 는 워크스페이스 위임인데 E2E 는 루트에서 둘을 함께 구동합니다. ③ **CI 배선은 카드 `t27`(N4) 소유**라 여기서 `npm test` 를 바꾸면 t27 의 자리를 미리 흔듭니다.
- AC-E2E-011 이 「`scripts.test` 값이 글자 그대로 불변」 을 `git diff` 로 잽니다.

### D3 — 실 Claude 세션 수동 체크리스트  **[잠정: 문서로만, 실행 안 함]**

- `plan-v2.md` Task 19 Step 2 의 12항목은 실 세션을 요구하고, 운영자 축소 결정이 그 실행을 뺐습니다.
- **어떤 수용 기준도 「수동 검증을 수행했다」 를 주장하지 않습니다.** AC-E2E-016 이 그 주장의 부재를 기준으로 세웠습니다 — 주장하면 그것이 관측하지 않은 완료 주장이기 때문입니다.
- 뒤집히면: 이 카드가 API 비용을 지는 카드가 되고 Tier 재산정이 필요합니다.

### D4 — `ws` 루트 의존성 선언  **[잠정: 선언 안 함]**

- `plan-v2.md` 는 `npm install ws` 를 지시하지만, 실측 결과 `ws@8.21.3` 이 `server` 의 의존성으로 루트에 호이스팅돼 **루트 선언 없이 해소**됩니다 (`node -e "console.log(require.resolve('ws/package.json'))"` → 루트 `node_modules/ws`).
- **다만 함정이 있습니다** — 이 워크트리에는 `node_modules` 자체가 없어서 위 해소가 **부모 디렉터리(기본 체크아웃)로 올라간 결과**입니다. CI 나 새 클론에는 그 부모가 없습니다. 그래서 스크립트가 의존성 부재를 「`npm install` 을 먼저 돌리세요」 한 줄로 끝내도록 요구사항에 넣었습니다.

## 6. 기준 품질에 대해 (이 프로젝트가 반복해 실패한 자리)

- **셸 전용 기준의 공허함을 짝으로 막았습니다.** AC-E2E-008(실프로세스 재시작)만 두면 E2E 스크립트를 지우는 순간 영속성을 재는 자리가 하나도 남지 않습니다. 그래서 **AC-E2E-009 가 `server/test/` 의 인프로세스 vitest 회귀 짝을 요구**하고, 그 짝의 변이(`openDb(config.dbPath)` → `openDb(':memory:')`)를 명시했습니다.
- **자기 자신을 검증하는 기준을 넣었습니다.** AC-E2E-004 는 「단언을 거짓으로 바꾸면 exit≠0 이고 프로세스가 안 남는다」 를 잽니다. 이것이 없으면 AC-E2E-001 은 「무엇이든 exit 0」 인 스크립트에도 초록을 줍니다.
- **개수가 아니라 순서 문자열을 대조합니다.** AC-E2E-007 은 `[1/13]…[13/13]` 전체를 대조해 단계 바꿔치기도 잡습니다.
- **어간으로 훑습니다.** AC-E2E-012 는 「생산 배치」 어간 적중 0 + 「배포 경계」 잔존 ≥1 을 **각각** 재서, 「한 자리만 고침」 과 「통째로 지움」 을 서로 다른 측정이 잡게 했습니다. 실측으로 그 문구가 **세 자리(5·225·236행)** 임을 확인했습니다 — 디스패치에는 5행 하나로 전달됐습니다.
- **문자열 부재 grep 을 기준으로 쓰지 않았습니다.** AC-E2E-010 은 「개수 비교가 없다」 를 grep 으로 재는 대신, 재시작 뒤 메시지를 하나 더 넣고 같은 단언이 여전히 통과하는지를 **실행**으로 잽니다.

## 8. 미검증 (Gaps)

- **E2E 시나리오를 한 번도 돌려보지 않았습니다.** 이 SPEC 은 스크립트가 무엇을 해야 하는지를 정의할 뿐, 통과한다는 증거가 없습니다. 통과 여부는 run 단계의 관측입니다.
- **이 나무에서 서버를 띄워 보지 않았습니다.** `node_modules` 가 없어 기동이 부모 디렉터리 해소에 기대야 하고, 그 상태에서 잰 결과는 CI 를 대표하지 않습니다. run 첫 일이 `npm install` 후 기동 확인입니다.

- **`npm run build -w channel` 이 커밋 시 필요한지 확인하지 않았습니다.** 과거 기록상 `channel/dist` 부재가 pre-commit 게이트에서 거짓 실패를 냈습니다. plan §B-3 에 M1 확인 항목으로 남겼습니다.
- **`connectV2` 가 실제로 이 나무의 서버와 붙는지 실행으로 확인하지 않았습니다.** `server/test/gateway.test.ts` 가 그것을 쓴다는 사실을 코드로 읽었을 뿐, 시험을 돌려보지 않았습니다.
- **README 갱신 문안 초안을 쓰지 않았습니다.** 무엇을 어디서 고칠지(행 번호·측정)까지만 정했고, 실제 문장은 M5 에서 씁니다.

**1회차 판정 요약**: must-pass 실패는 **0** 이었다. 감점은 전부 Testability(0.50)에서 왔고 — 요구사항 층·범위 경계·§4 발견·「재지 않은 수」 규율은 감사가 모두 좋다고 평가했다 — 검증 층 열 자리가 「지워도 초록」이거나 측정 불가였다. 감사는 §0 에서 이 SPEC 의 중심 발견(`plan-v2.md` Task 18 초안이 낡았다는 네 항목)을 **전건 독립 실행으로 재확인**했다.

**개정 1차 처리**: 감사 §8 우선순위 1~8 순서를 그대로 따라 D-01~D-10 을 닫고 권고 D-11~D-16 도 전건 수용했다. **REQ 16 · AC 16 은 변동 없다** — 리드 [HARD] 제약대로 새로 만들지 않고 기존 것의 절을 넓히거나 뒤집었으므로 Tier M(통과선 0.80)이 유지된다.

**부분 반박 1건**: D-01 의 **발견**(기준이 측정 불가)은 전건 수용하되 **처방된 기제**(`recordSocket`)는 채택하지 않았다 — 그 도구는 서버 쪽 소켓을 감싸는 인프로세스 전용이고 E2E 는 서버를 별도 프로세스로 띄운다(`grep -n "onConnection" server/src/gateway.ts` → `85`·`87`·`103`; `sed -n '47p' server/src/index.ts` → `buildServer` 는 `onConnection` 을 넘기지 않음). 같은 방향(전선을 잰다)을 다른 기제(v2 성립 양성 + v1 음성 대조군)로 구현했다.

**2회차 판정 요약**: 1회차 16건이 **전건 CLOSED** 로 확인됐고 must-pass 실패는 0 이었다. **D-01 기제 반박은 감사관이 자기 1회차 처방을 철회하고 개정자가 옳다고 인정했다** — `server/src/index.ts:47` 이 `onConnection` 을 넘기지 않음을 축자 확인했고, 「내 처방은 구조적으로 실행 불가능한 것이었다」고 적었다. 그러나 개정 1차가 **새 결함 넷**을 만들어 Testability 를 0.70 으로 눌렀고, 통과폭이 0.03 에 그쳤다. **감사관이 자기 판정의 취약점을 공시했다**: N-01 을 Medium 이 아니라 High 로 보면 Testability 0.50 → 총점 **0.755 = FAIL** 로 뒤집힌다.

**개정 2차 처리**: 그 취약점의 원인인 넷을 전부 닫아 **취약점 자체를 없앴다**. 넷 중 셋(N-01·N-02 와, 정리 중 스스로 재현한 훑기 표의 자기 계수)이 **「검사가 자기를 검사 대상으로 삼는다」는 한 뿌리**였으므로, 값을 고치는 대신 **세는 대상을 바꿔** 부류로 닫았고 편집 불변성을 실행으로 확인했다. N-04 는 리드가 지정한 문언(«트리거는 t6, 「내 PC」 문구는 t26 이월 · 과도기 공시»)으로 고쳤다. **REQ 16 · AC 16 변동 없음** — Tier M 유지.

**3회차 판정 요약**: 1·2회차 지적이 전건 CLOSED 로 확인됐고 **차단 발견은 0건**이었다. 새 발견 여섯은 전부 **§7.3 훑기 표의 증거 기재 방식**에 몰려 있었다 — 표가 자기를 세고(P-01·P-03), 적은 명령이 적은 값을 내지 않는(P-02·P-05) 형태다. 감도 분석상 한 등급으로도 두 차원 동시로도 판정이 뒤집히지 않아, 2회차의 「0.03 차」 취약 구조가 해소됐다.

**개정 3차 처리**: 리드 지시 ①~⑤ 를 그대로 이행했다. **값을 고치는 대신 처방을 적용**했다 — 값 축이 이미 쓰던 방식(제외를 명령 안에)을 명제 축에 맞게 구현해 `[SWEEP-ROW]` 표지 + `grep -v` 로 닫았다. 작업 중 **줄 번호 열거가 이 라운드의 HISTORY 추가로 +1 밀려 즉시 거짓이 되는 것을 재현**했고(P-01 과 다른 뿌리 — 「고정 좌표가 편집으로 이동한다」), 판정 열을 앵커 문구로 바꿨다. **P-06 은 실행해 봐야 형태가 정해지므로 고치지 않고 run 으로 이월**했다.

### 9.1 이 보고서 본문의 정정 (본문은 고치지 않고 여기에 적는다)

이 보고서는 **작성 시점의 기록**이므로 본문을 소급 수정하지 않는다. 다만 뒤에 틀린 것으로 밝혀진 두 가지를 여기에 적어, 이 문서를 나중에 읽는 사람이 본문만 믿지 않게 한다.

1. **§5 표의 `server/src/routes-messages.ts:173` 은 틀렸다 — 실제는 `:163` 이다** (감사 D-07). 실행 확인:
   `sed -n '163p;173p' server/src/routes-messages.ts` → `163` = `return reply.send(createReadStream(att.stored_path))`, `173` = `if (m.author_type === 'user') {`(`displayName()` 안, 첨부와 무관). **결함 자체는 참이고 앵커만 틀렸다** — `grep -c existsSync server/src/routes-messages.ts` → `0`. 정정본은 `spec.md` §5 t8 절에 있다. **카드 `t8` 은 `:163` 을 볼 것.**

2. **§5 의 「README «내 PC» 문구의 소유는 t6 으로 확정했습니다」는 개정 1차에서 뒤집혔다 — 이제 `t26` 이다.** 근거는 정본 직독이다: `.moai/plan/2026-08-31-queue-redesign/proposal.md` §5 마지막 문장이 「README·`config.ts:5` 주석의 «내 PC 에서만 도는 서버» 도 «사내망 전용» 으로 같이 고친다(**N3 에 포함**)」라고 적어, README 와 `config.ts` 를 **한 묶음으로 N3(=t26)** 에 넣는다. v0.1.0 작성 시점에는 이 파일을 열지 못했다(원본 체크아웃에만 있는 미추적 산출물). 상세와 과도기 비용은 `plan-revision-1.md` §3 · `spec.md` §3 D5. **리드 결정이 필요한 항목이다.**
