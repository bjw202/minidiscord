## 0. 쉬운 말 요약

3차 개정은 2차 감사가 잡은 일곱 건(N-01~N-07)을 **전부 닫았다.** 일곱 건 모두 내가 대상 파일을 직접 열어 확인했고, 리드 레인이 `plan-done-3.md` §2 에 적은 일곱 개의 「닫힘」 판정은 **전건 사실과 일치한다.** 리드 레인의 검증이 이번 라운드의 신뢰 축이었는데, 그 축은 무너지지 않았다.

가장 컸던 N-01 — 「고쳤다고 적어 놓고 실제로는 안 고친 자리」 — 은 두 자리 모두에 2차 개정 주석이 붙었고, 1차 주석도 지워지지 않았다. 그 주석이 새로 주장하는 「§7·§9 의 잔여 위험에서 초대 라우트는 빠졌고 남은 방 범위 라우트는 보관 하나」도 실제 §7·§9 와 대조해 참임을 확인했다. 같은 부류를 다시 훑는 작업도 실제로 이뤄져 `SPEC-PERM-001` 한 자리가 더 고쳐졌고, 나는 반대 방향(형제 파일 → 표)으로 이 SPEC 이 형제에 남긴 주석 **35개 자리를 전건 열거해** 아직 거짓인 것이 더 없는지 직접 확인했다 — 없다.

개정 에이전트가 도중에 죽은 것 때문에 **반쪽 편집이 남았는지**도 따로 봤다. 코드 블록 짝, 표 행, 번호 목록, 파일 끝, 상호 참조를 훑었고 깨진 자리는 없었다. 마지막으로 쓰였다는 `progress.md` 도 문장 중간에서 끊기지 않았다.

리드 레인이 「추론이지 측정이 아니다」로 정직하게 남긴 두 항목 중 하나(테스트 재실행)는 **내가 직접 돌려 사실로 확정했다** — 서버 104 + 채널 70 = 174 전건 통과. 다른 하나(폭발 반경 34 미재계수)는 근거를 따져 보니 타당하다.

남은 것은 두 건인데 **둘 다 차단 등급이 아니다.** 하나는 재발 방지책(양방향 대조)이 완료 정의에는 들어갔는데 계획서의 M4 작업 목록에는 안 들어간 것이고, 다른 하나는 REQ-005 표의 선언을 강화하면서 일곱 행 중 한 행을 다시 도출하지 않은 것이다. 둘 다 한 줄짜리 수정이고, 어느 것도 문서를 거짓으로 만들지 않는다.

**통과시킨다. 마지막 라운드라서가 아니라, 일곱 건이 실제로 닫혔고 새로 열린 차단 등급이 없기 때문이다.**

### 1.1 N-01 — 닫힘, 그리고 **가리키는 곳까지 참이다**

**두 자리 모두에 2차 주석이 실재한다** (`sed -n '40,60p;165,190p' .moai/specs/SPEC-BOT-001/spec.md` 로 판독).

- `:47` 1차 주석 — **원문 그대로 보존**. 「이 SPEC 의 봇 초대 라우트에는 멤버십 게이트가 걸리지 않았다」가 지워지지 않았다.
- `:49` 2차 주석 — 「위 1차 주석의 뒷부분 세 문장이 뒤집혔다 … 봇 초대 라우트 셋에는 멤버십 게이트가 **걸린다** … «로그인한 사람은 여전히 모든 활성 방에 봇을 초대할 수 있다»도 «후속 카드가 필요하다»도 더 이상 참이 아니다」.
- `:176` 1차 보존 / `:178` 2차 주석 — 「위 1차 주석의 «이 SPEC 의 라우트에는 게이트가 걸리지 않았다»가 뒤집혔다」.

**좁아진 §7·§9 포인터를 대상 문서와 대조했다** — 2차 감사가 요구한 두 번째 절반이며, 이번 라운드에서 가장 틀리기 쉬운 자리였다.

주석의 주장: 「§7·§9 의 잔여 위험 항목에서 초대 라우트 셋은 빠졌고, 그 자리에 남은 방 범위 라우트는 `POST /api/rooms/:id/archive` **하나**다(그리고 방 밖 경로인 `GET /api/attachments/:id`)」.

실제 `spec.md` §7 「Out of Scope — 이 SPEC 이 닫지 않는 방 범위 경로」(`:439-448`)의 항목은 정확히 셋이다 — `GET /api/attachments/:id`(`:441`), 취소선 처리된 초판 항목(`:443`)과 그 개정 주석(`:445`), 그리고 `POST /api/rooms/:id/archive`(`:447`). 방 범위 라우트로 남은 것은 보관 하나이고, 첨부는 「방 밖 경로」로 주석이 스스로 구별해 적었다. §9(`:471-476`)도 같다 — 초대 행은 취소선 + 「부분 해소」, 남는 행은 보관 둘(파괴적 쓰기 / 실재 오라클)과 첨부 하나.

**포인터가 가리키는 곳이 실제로 그 모양이다.** 2차 감사가 「따라가면 없는 기록을 찾게 된다」고 지적한 상태는 해소됐다.

**§6 표의 처리 칸도 갱신됐다** (`spec.md:387`): 「1차 개정 주석이 D2 v1 기준이어서 D2 v2 이후 정반대의 거짓이 됐고(2차 감사 N-01), 3차에 두 자리 모두에 2차 개정 주석을 덧붙였다 — 1차 주석은 지우지 않았다」. 표가 이제 **실제로 일어난 일**을 적는다.

### 1.4 N-04 — 닫힘. 열거 자체도 맞다

`SPEC-PERM-001/spec.md:186` (`git diff` 로 이번 라운드 신규 추가임을 확인):

> 게이트는 **여덟 곳**이다 — 메시지 `POST`·`GET /api/rooms/:id/messages`, SSE 구독(`GET /api/rooms/:id/events`), 방 목록(`GET /api/rooms`), 판정 수용, 그리고 `POST`·`GET /api/rooms/:id/invites` 와 `DELETE /api/rooms/:id/invites/:botId`(REQ-ROOMAUTHZ-017).

**여덟이 맞는가 — SPEC 의 자기 정의와 대조했다.** `spec.md:141` D2 v2 는 「D2 v1 의 **다섯 곳**에 더해 봇 초대 라우트 셋」이라 적고, D2 v1(`:132`)의 다섯은 메시지 POST·GET·SSE·판정 수용 + `GET /api/rooms` 좁히기다. 5 + 3 = 8. 열거된 여덟 개와 정확히 일치한다.

**`POST /api/rooms/:id/members` 가 빠진 것은 결함이 아니다.** 그 라우트의 검사는 D1(멤버십 획득) 소관이지 D2(게이트 범위) 소관이 아니며, 문서가 그 구별을 일관되게 쓴다 — `plan.md:379` 가 「술어를 부르는 자리 아홉 = M3 의 게이트 여덟 + M2 의 members」로 명시한다. 「게이트 여덟」과 「술어 호출 자리 아홉」은 서로 다른 셈이고 문서가 둘을 섞지 않는다.

**세 자리가 서로 같은 말을 하는가 — 그렇다.**

| 자리 | 문면 |

| `spec.md:346` (REQ-013 본문) | 보관 라우트는 이 금지를 만족하지 못한다. 게이트를 걸지 않으며, 그것은 **위반이 아니라 인수한 미준수**다 |

### N-08 (Medium, 선택) — 재발 방지책은 검사 가능하지만, 실행 주체가 지정되지 않았다

**먼저 잘된 것부터 적는다.** 완료 조건의 변경은 **서술이 아니라 검사 가능한 조건**이다. 이것이 3차의 핵심 산출물이며, 「검사할 수 없는 대책은 같은 결함의 한 단계 위」라는 물음에 대한 답은 **검사할 수 있다** 이다. `acceptance.md:974-978`:

- **판정 대상이 갈라져 있다** — 「표 → 파일」과 「파일 → 표」 두 방향.
- **실패 술어가 명시돼 있다** — 「반대 문장(«게이트가 걸리지 않았다»·«후속 카드가 필요하다»)이 정정되지 않은 채 남아 있으면 **실패**」. 판정이 참/거짓으로 갈린다.
- **명령이 적혀 있다** — `grep -rn "SPEC-ROOMAUTHZ-001" .moai/specs/` 로 전건 열거한 뒤 「현재의 D2 v2 범위(게이트 여덟 곳)」 기준으로 하나씩 판정.
- **증거 경로가 지정돼 있다** — 「두 방향의 실행 결과(명령과 판정)를 `progress.md` §E.2 에 남긴다. **주석이 존재한다는 사실은 증거가 아니다 — 참이라는 판정이 증거다.**」
- HISTORY `0.3.0` 행(`spec.md:24`)이 이 변경을 기록한다.

**그런데 그 조건을 실행할 자리가 비어 있다.** `plan.md:350` 의 M4 4번은 3차 개정을 거치고도 초판 문면 그대로다.

> 4. `spec.md` §6 표의 문서 전부에 개정 주석을 단다. 원문은 지우지 않는다. **`progress.md` 두 건은 말미 추가 방식**이다(§E 4번).

이것은 정확히 **「주석이 달렸다」** 를 지시하는 문장이며, 2차 N-01 이 통과한 바로 그 경로다. 새 완료 조건이 요구하는 **양방향 대조와 §E.2 기록**은 이 목록에 없다. 더해서 `plan.md:361` §G 는 「구현 완료 판정은 `acceptance.md` 의 AC-ROOMAUTHZ-001..018 전부다. **별도 기준을 만들지 않는다**」로 적어, 완료 판정을 18개 AC 로 좁힌다 — 양방향 대조는 AC 가 아니라 완료 정의 항목이므로 이 문면 아래서 위치가 모호해진다.

**왜 차단이 아닌가.** 완료 정의는 `acceptance.md` 안에 있고, §G 도 그 파일을 판정 근거로 지목하므로 「완전히 사라졌다」고 말할 수는 없다. 어떤 문장도 거짓이 아니다. 그러나 **run 담당자가 작업 목록으로 읽는 자리에는 없고**, 이 SPEC 이 3차에서 얻은 가장 값진 교훈이 그 자리에서만 빠져 있다.

**요구되는 수정 (한 줄).** `plan.md:350` M4 4번에 문장 하나를 더한다 — 「그리고 `acceptance.md` 완료 정의의 **§6 표 ↔ 대상 파일 양방향 대조**를 실행해 두 방향의 명령과 판정을 `progress.md` §E.2 에 남긴다. 주석의 존재가 아니라 **참임**을 적는다.」 §G 의 「별도 기준을 만들지 않는다」를 「완료 정의 항목을 포함한 `acceptance.md` 전부다」로 넓히면 모호성도 함께 사라진다.

### N-09 (Low, 선택) — 선언을 강화했는데 한 행을 다시 도출하지 않았다

2차 N-05 는 「이 표의 모든 행에 대응 기준이 있다」가 본문 칸에서 거짓이라고 지적했다. 3차는 **선언을 좁히지 않고 재는 쪽**을 골랐고, 그 과정에서 선언을 오히려 **강화했다** (`spec.md:250`):

> **이 표의 모든 행이 — 상태 코드와 본문 둘 다 — 대응 기준을 갖는다.**

일곱 행을 새 선언 기준으로 다시 도출했다.

| REQ-005 표 행 | 상태 코드 | 본문 | 재는 자리 |
|---|---|---|---|
| 성공 `201` `{ok:true}` | ✅ | ✅ | `acceptance.md:418`·`:419` |
| 이미 멤버 `200` `{ok:true,already:true}` | ✅ | ✅ | `:423`·`:424` |
| 호출자 비멤버 `404` | ✅ | ✅ | `:454`·`:455` (`toEqual({ error: '방을 찾을 수 없습니다' })`) |
| 없는 방 `404` | ✅ | ✅ | `:433`-`:434` |

**실행한 확인.** `grep -n "사용자를 찾을 수 없습니다" acceptance.md` → **종료 코드 1, 결과 0줄.** 그 문자열은 수용 기준 어디에도 없다.

**통과하는 틀린 구현.** 없는 사용자에게 `400 { error: '방을 찾을 수 없습니다' }` 를 돌려주는 구현이 통과한다 — 상태 코드는 맞고 본문만 다른 오류를 말한다. 실질 손해는 작지만(진단 문구 하나), **「모든 행이 — 상태 코드와 본문 둘 다」는 참이 아니다.**

이것은 이 저장소가 반복해 데는 형태다 — **표 머리의 규칙을 강하게 바꾸면 모든 행을 새 규칙 아래 다시 도출해야 하는데, 감사가 이름 부른 행만 고쳤다.**

## 5. 리드 레인의 두 추론 — 하나는 실행으로 확정, 하나는 타당

`plan-done-3.md` §8 이 「추론이지 측정이 아니다」로 정직하게 갈라 적은 둘을 각각 판정했다.

### 5.1 「테스트를 재실행하지 않았다」 — **내가 돌렸다. 추론이 맞았다 (실행)**

```
$ npm test
 RUN v4.1.11 …/t11/server      Test Files 10 passed (10)   Tests 104 passed (104)   Duration 7.16s
 RUN v4.1.11 …/t11/channel     Test Files  5 passed  (5)   Tests  70 passed  (70)   Duration 5.70s
```

**서버 104 + 채널 70 = 174 전건 통과.** 이 항목은 이제 추론이 아니라 관측이다.

추론의 전제(「코드 변경 0건」)도 실행으로 확인했다 — `git status --short -- server web channel` 이 **빈 출력**이고 `git diff --stat HEAD -- server` 도 빈 출력이다. 3차 개정은 `.moai/` 아래 문서만 건드렸다.

### 5.2 「34건 폭발 반경을 재도출하지 않았다」 — **추론이 타당하다 (판독)**

전제는 「3차는 문언만 건드렸고 게이트 범위(D2 v2)를 바꾸지 않았다」이며, 이것이 성립하는지 따로 따졌다.

- **게이트 범위 무변경** — D2 v2(`spec.md:139-145`)는 이번 라운드에 손대지 않았고 여전히 여덟이다. `plan.md:324` M3 도 「게이트 여덟 곳」 그대로다.
- **§D 의 분모 무변경** — `server/test/` 아래 파일이 하나도 바뀌지 않았다(§5.1 의 빈 `git status`). 34건의 분모인 기존 테스트 집합이 그대로다.

## 6. 이번 라운드에 더해진 것의 변이 저항 — 틀린 구현을 이름으로 댄다

새로 붙은 기준은 두 자리다. 각각 「통과하는 틀린 구현」을 실제로 하나씩 구성했다.

### 6.1 N-05 의 본문 단언 (`acceptance.md:419`·`:424`)

- **잡는다**: `{ ok: false, already: true }`, `{ ok: true }` 에 여분 키를 붙인 응답(`toEqual` 은 여분 키를 거부한다), 재초대를 `409` 로 만든 구현.

### 6.2 N-02 의 sweep 추가 (`acceptance.md:856`)

- **잡는다**: `POST /members` 의 술어를 `created_by` 로 복사한 구현 — `before` 는 `404`(mallory 는 생성자가 아니다)로 통과하지만 `after` 에서 mallory 가 멤버가 된 뒤에도 `404` 로 남아 `not.toBe(404)` 단언에 걸린다. 이것이 이 추가가 실제로 사는 자리다.
- **통과하는 틀린 구현 ①**: `POST /members` 가 멤버십을 **방 상태 조회 뒤에** 두는 구현. AC-017 의 sweep 은 **활성 방** 하나만 쓰므로 순서가 뒤집혀도 비멤버는 `404`, 멤버는 `201` 로 방향이 같다. AC-017 은 이 결함을 못 잡는다 — 잡는 것은 AC-006 두 번째 시나리오(`:470-484`)다. 문서가 그 분담을 적고 있으므로 결함은 아니나, AC-017 이 「분기 탐지」로 잡는 범위의 경계다.

**두 추가 모두 「지금 이 순간 복사한 구현은 통과한다」는 한계를 문서가 스스로 적는다**(`spec.md:277`, `acceptance.md:878`). 과장은 없다.

- **형제 문서의 렌더링을 눈으로 확인하지 않았다.** 코드 블록 짝·들여쓰기·번호 목록을 텍스트로 검사했을 뿐, 실제 마크다운 렌더 결과를 본 것은 아니다(§3.5).
- **개정 에이전트가 `10:05:08` 이후 무엇을 하려 했는지 여전히 알 수 없다.** 2차 감사의 일곱 건 대비 이행 여부는 전건 판정했으나(§1), 그 밖에 에이전트가 계획했으나 남기지 않은 작업이 있었는지는 관측할 수 없다. N-08 이 그 공백의 흔적일 가능성을 §3.5 에 적었다.
- **`web/` 과 `channel/` 의 소스를 읽지 않았다.** REQ-016 이 범위 밖으로 두었고, `git status` 로 무변경만 확인했다.
- **`moai spec lint` 를 이번 라운드에 다시 돌리지 않았다.** 2차가 낸 네 경고는 전부 `SpecsDirForeignEntry` 도구 오탐이었고 문서 구조가 그 부류에 대해 바뀌지 않았으나, **이것은 무변경에 근거한 추론이지 재실행이 아니다.**
