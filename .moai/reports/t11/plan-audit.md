## 0. 쉬운 말 요약

이 계획서는 이 저장소에서 본 것 중 가장 잘 쓰인 축에 든다. 수용 기준 16개 중 13개가 「비멤버는 막히고 멤버는 통과한다」를 한 시나리오 안에 짝으로 넣어, 「전부 거부하는 구현」과 「게이트가 없는 구현」을 동시에 걸러 낸다. 깨질 테스트 34개도 내가 직접 다시 세어 **정확히 34개로 일치**했다.

그런데 구멍이 있다. 가장 큰 것은 **봇 초대 라우트가 열려 있다는 사실이 「봇을 넣을 수 있다」로만 적혀 있다는 점**이다. 실제로는 그 통로로 계정 하나가 남의 방 대화 전체를 읽을 수 있다 — 봇 토큰을 발급받아 게이트웨이에 붙으면 그 방의 메시지 이력이 통째로 넘어온다. 이 SPEC 이 REQ-009 로 닫으려 한 바로 그 읽기가 다른 문으로 열린 채 남는데, 잔여 위험 표는 그것을 적지 않았다.

그 밖에 (1) 방 범위 라우트 두 개(`GET`·`DELETE /api/rooms/:id/invites`)가 게이트에도 잔여 위험에도 **어디에도 없고**, (2) 「멤버십을 방 상태보다 먼저 본다」는 계약이 POST 메시지에서 **한 기준도 재지 않으며**, (3) SSE 라우트를 추출해도 `index.ts` 가 그 함수를 쓰는지 **아무 기준도 확인하지 않아** 프로덕션 게이트가 통째로 빠져도 전건 초록이 된다. 여기에 형제 문서 개정 sweep 이 두 자리를 놓쳤다.

전부 문서 수정으로 닫히는 것들이고 설계 자체는 흔들리지 않는다. 그러나 「하나의 기준도 재지 않는 요구사항」이 셋 남은 문서는 통과시킬 수 없다.

## 2. 발견별 증거

### F-01 (High, 차단) — 봇 초대 라우트는 "봇 하나 추가"가 아니라 방 전체 읽기 통로다

**SPEC 이 뭐라고 적었나.** `spec.md:299`:

> `SPEC-BOT-001` 의 봇 초대 라우트(`POST /api/rooms/:id/invites`)도 이 SPEC 이 게이트를 걸지 않는다 — D2 가 확정한 범위 다섯 곳에 들어 있지 않다.

`spec.md:391` 잔여 위험:

> | 봇 초대·방 보관 라우트가 열려 있다 | 비멤버가 남의 방에 봇을 넣거나 남의 방을 보관한다 |

**실제로 무엇이 열리는가.** 내가 읽은 코드:

```
$ grep -rn "app\.\(get\|post\|delete\)(" server/src/routes-bots.ts
server/src/routes-bots.ts:34:  app.post('/api/bots', { preHandler: [requireAuth] }, …)      ← 봇 생성, 게이트 없음
server/src/routes-bots.ts:47:  app.post('/api/rooms/:id/invites', { preHandler: [requireAuth] }, …)
```

`routes-bots.ts:47-61` 은 `requireAuth` 만 통과하면 임의 방 번호에 대해 **평문 봇 토큰을 응답에 실어 돌려준다**(`:59-61`). 그 토큰으로 게이트웨이에 붙으면:

```
server/src/gateway.ts:98    conns.set(ws, { roomId: row.room_id, … })
server/src/gateway.ts:179   let rows = db.prepare('SELECT * FROM messages WHERE room_id = ? ORDER BY id DESC LIMIT ?').all(info.roomId, limit)
server/src/gateway.ts:186   send(..., { type: 'history_response', … })
```

즉 `history_request` 한 번에 **그 방 메시지 전체**가 넘어온다. 여기에는 권한 릴레이가 방에 띄운 system 메시지(`permissions.ts:34-40`, `request_id` 포함)도 들어 있다.

정리하면, 이 SPEC 이 착지한 뒤에도 계정 하나로 다음이 성립한다.

```
1. POST /api/auth/register
2. POST /api/bots                          (게이트 없음)
3. POST /api/rooms/<victim>/invites        (게이트 없음 — 평문 토큰 수령)
4. ws /bot  →  hello  →  history_request   (봇 인가는 토큰이 정한다, REQ-015)
   → 남의 방 대화 전체 + 대기 중 request_id 를 읽는다
```

**왜 결함인가.** 세 겹이다.

1. **잔여 위험 서술이 실제 노출을 축소한다.** "봇을 넣는다"와 "그 방 대화를 전부 읽는다"는 다른 크기의 사실이다. `spec.md` §1.2 는 이 SPEC 이 사슬을 "첫 걸음에서 끊는다"고 적었는데(`:77`), 위 경로는 §1.2 의 2-3단계(열거·`request_id` 읽기)를 다시 성립시킨다. 승인 누르기(4단계)는 REQ-008 게이트가 막으므로 **F-14 자체는 닫힌다** — 그 점은 확인했다. 그러나 REQ-009 가 닫으려는 읽기는 닫히지 않는다.
2. **REQ-015 의 문장이 이 통로를 정당화하는 모양이 된다.** `spec.md:297` 은 "봇의 방 접근 자격은 지금처럼 토큰이 정한다"고 적는다. 토큰을 **누구나 발급받을 수 있는 동안** 이 문장은 "사람 멤버십 경계는 봇을 하나 만들면 우회된다"와 같은 말이다.
3. 이 SPEC 의 `plan-done.md:269` Gaps 4번도 같은 축소를 반복한다.

**요구되는 수정.** 다음 중 하나. (a) `POST /api/rooms/:id/invites` 를 게이트 다섯 곳에 넣는다(D2 확장이므로 운영자 확인 필요), 또는 (b) §7·§9 의 잔여 위험 문장을 **관측한 사실로** 다시 쓴다 — "비멤버가 봇 토큰을 발급받아 게이트웨이 `history_request` 로 그 방 메시지 전체를 읽을 수 있으며, 이는 REQ-009 가 닫으려는 읽기와 같은 것이다. 후속 카드 필요." 어느 쪽이든 `spec.md:77` 의 "첫 걸음에서 끊는다"에는 "승인 경로에 한해"라는 한정이 붙어야 한다.

### F-02 (High, 차단) — 방 범위 라우트 둘이 어디에도 없다

**내가 실행한 명령과 출력**(전체 라우트 열거):

```
$ grep -rn "app\.\(get\|post\|put\|delete\|patch\|all\)(" server/src/
server/src/routes-rooms.ts:11    GET    /api/rooms                       → REQ-011 (좁힘)
server/src/routes-rooms.ts:19    POST   /api/rooms                       → REQ-004
server/src/routes-rooms.ts:28    POST   /api/rooms/:id/archive           → §7 잔여로 기록됨
server/src/routes-messages.ts:29 POST   /api/rooms/:id/messages          → REQ-008
server/src/routes-messages.ts:123 GET   /api/rooms/:id/messages          → REQ-009
server/src/routes-messages.ts:142 GET   /api/attachments/:id             → §7 잔여로 기록됨
server/src/index.ts:57           GET    /api/rooms/:id/events            → REQ-010
server/src/routes-bots.ts:47     POST   /api/rooms/:id/invites           → §7 잔여로 기록됨
server/src/routes-bots.ts:65     GET    /api/rooms/:id/invites           → ❌ 어디에도 없음
server/src/routes-bots.ts:76     DELETE /api/rooms/:id/invites/:botId    → ❌ 어디에도 없음
```

`spec.md:364-365` 의 "이 SPEC 이 닫지 않는 읽기 경로" 절은 첨부·봇 초대(POST)·보관 셋만 적는다. `spec.md:390-391` 의 §9 표도 같다.

**왜 결함인가.**

- `GET /api/rooms/:id/invites`(`:65-73`)는 **읽기 경로**다. 로그인한 누구나 남의 방에 붙은 봇 이름과 접속 여부를 본다. "이 SPEC 이 닫지 않는 읽기 경로"라는 제목을 단 절이 읽기 경로 하나를 빠뜨렸다.
- `DELETE /api/rooms/:id/invites/:botId`(`:76-81`)는 **쓰기 경로**이자 파괴적이다. 방 번호와 봇 번호만 알면 남의 방 봇 토큰을 철회해 그 봇의 세션 접속을 끊을 수 있다. 잔여 위험 표의 "비멤버가 남의 방에 봇을 넣거나 남의 방을 보관한다"에 "남의 방 봇을 끊는다"가 없다.

`plan.md:305` 의 안티패턴 "첨부 라우트를 겸사겸사 함께 막기 — 열려 있음을 §7·§9 에 적었다"는 **적었다는 사실**을 전제로 범위 밖 수정을 금지한다. 적히지 않은 두 라우트에는 그 전제가 성립하지 않는다.

**요구되는 수정.** §7 "이 SPEC 이 닫지 않는 읽기 경로"와 §9 표에 두 라우트를 각각 한 줄로 추가하고, 노출 내용(봇 명단·접속 상태 열람 / 타 방 봇 강제 단절)을 적는다.

### F-03 (High, 차단) — REQ-013 은 서버 전체를 구속하는데 서버 전체가 그것을 만족하지 못한다

`spec.md:285`:

> 서버는 **비멤버에게 방의 존재 여부를 드러내서는 안 된다.** 비멤버의 방 범위 요청에 대한 응답은 없는 방에 대한 응답과 **구별 불가능**해야 한다

주어가 "서버"이고 대상이 "비멤버의 방 범위 요청" 전체다. 그런데 같은 문서 `spec.md:365` 가 세 라우트를 게이트 밖에 둔다. 그 셋은 실재 오라클이다 — 내가 코드에서 읽은 분기:

| 라우트 | 없는 방 | 있는 방 | 근거 |
|---|---|---|---|
| `POST /api/rooms/:id/archive` | `404` | `200` 또는 `409` | `routes-rooms.ts:46-50` |
| `POST /api/rooms/:id/invites` | `404 방을 찾을 수 없습니다` | `409` 또는 `404 봇을 찾을 수 없습니다` | `routes-bots.ts:53-56` |
| `GET /api/rooms/:id/invites` | `[]` | 봇이 붙어 있으면 비어 있지 않은 배열 | `routes-bots.ts:67-72` |

**왜 결함인가.** 요구사항 하나와 범위 결정 하나가 같은 문서 안에서 서로를 반증한다. 그리고 이 모순은 **어떤 기준으로도 검출되지 않는다** — AC-ROOMAUTHZ-013(`acceptance.md:570-588`)은 `listMsg` 셋만 비교하므로 위 셋을 건드리지 않는다. `spec.md:289` 가 "인가 결함을 닫으러 온 SPEC 이 열거 통로를 열어 둘 수는 없다"고 적어 놓고, 실제로는 열거 통로 셋을 열어 둔 채 남긴다.

**요구되는 수정.** REQ-013 의 적용 범위를 D2 가 확정한 다섯 곳(+ 초대 라우트)으로 **문면에 한정**하고, 한정 밖 라우트가 실재 오라클로 남는다는 사실을 §9 잔여 위험에 별도 행으로 적는다. 요구사항을 무조건 금지로 유지하려면 세 라우트에 게이트를 걸어야 하며 그것은 D2 확장이다.

### F-04 (High, 차단) — 순서 계약을 재는 기준이 없다

`spec.md:240`(REQ-008)은 순서를 요구사항으로 못 박는다.

> `requireAuth` 통과 직후 그리고 **방 상태(보관 여부)를 확인하기 전에** 멤버십을 확인해야 한다.

> **대조군**(인증된 요청은 성공한다)이 깨진다 = AC-MSG-012

그 테스트의 대조군은 실제로 이렇다(`messages.test.ts:343-348`):

const attId = (db.prepare('SELECT id FROM attachments').get() as { id: number }).id   // undefined.id → TypeError

**요구되는 수정.** `plan.md:130` 이유 칸을 실제 실패 지점(`:329` 설정 코드)으로 정정하고, `spec.md:336` 의 대조군 서술도 함께 고친다. M4 하네스 교정 시 `!== 401` 을 실제 성공 코드 단언으로 좁힐 것을 §D 에 덧붙이면 더 좋다(선택).
