## 1. 쉬운 말 요약

이 서버에는 "누가 어느 방에 속하는가"라는 개념이 아예 없다. 그래서 계정을 하나 만들면 남의 방을 목록에서 찾아 열고, 그 안의 대화를 읽고, 봇이 요청한 도구 실행 승인을 **대신 눌러 줄 수 있다.** 승인 코드를 서버가 스스로 방에 띄우기 때문에 코드를 알아내는 것도 어렵지 않다. 네 번의 평범한 요청이면 아무도 허가하지 않은 명령 실행이 승인된다.

이번 plan 은 그 구멍을 닫는 설계를 문서로 확정했다. 방에 `room_members` 라는 구성원 표를 만들고, 방을 만든 사람이 그 자리에서 구성원이 되며, 그 뒤로는 **기존 구성원만** 다른 사람을 초대할 수 있다. 스스로 들어오는 문은 만들지 않는다. 그리고 글쓰기·읽기·실시간 구독·승인 네 곳에 구성원 검사를 걸고, 방 목록도 자기가 속한 방만 보이게 좁힌다.

작업하면서 두 가지를 함께 처리했다. 하나는 **과거 결정의 정정**이다. 원래 기획서에 "방별 접근 권한은 필요 없다(YAGNI)"라고 적혀 있었는데, 그 판단은 승인 릴레이 기능이 들어오기 전 이야기라 지금은 맞지 않는다. 그 문장과 그것을 근거로 삼은 형제 문서 22곳에 개정 주석을 달았고, 원문은 지우지 않았다. 다른 하나는 **깨질 테스트를 미리 세어 둔 것**이다. 기존 테스트 중 34개가 이 변경으로 실패할 것으로 grep 으로 열거했고, 파일과 테스트 이름까지 계획서에 적었다.

정직하게 말할 것이 셋 있다. (1) 34개는 소스를 읽어 판정한 것이지 **실제로 테스트를 돌려 확인한 숫자가 아니다.** (2) 기존 방에 대한 백필은 보안 이득이 없다 — 조이는 효과는 앞으로 만들어질 방에만 생긴다. (3) 첨부파일 다운로드 경로는 이번 범위 밖이라 **여전히 열려 있다.**

## 2. SPEC 이 확정한 것

산출물: `.moai/specs/SPEC-ROOMAUTHZ-001/` (`spec.md` · `plan.md` · `acceptance.md` · `progress.md`)

### 2.1 닫는 결함 — F-14 의 공격 사슬

각 걸음에 필요한 것은 `requireAuth` 통과, 즉 계정 하나뿐이다.

```
1. POST /api/auth/register        계정 생성
2. GET  /api/rooms                모든 방 열거 (routes-rooms.ts:12)
3. GET  /api/rooms/<id>/messages  대기 중 request_id 읽기 (routes-messages.ts:123)
4. POST /api/rooms/<id>/messages  "yes <id>" 전송 (routes-messages.ts:29)
   → permissions.ts:43-58 이 누가 눌렀는지 보지 않고 판정을 봇에 전달
```

이 SPEC 은 **1단계에서** 사슬을 끊는다. 4단계만 막으면 `request_id` 는 여전히 읽히고 사슬이 한 요청 길어질 뿐이다.

### 2.2 요구사항 16개 (요약)

| 묶음 | 내용 |
|------|------|
| 데이터 모델 (001-003) | `room_members` 복합 PK 표, `rooms.created_by`(NULL 허용, **권한이 아니라 기록**), `PRAGMA table_info` 기반 컬럼 추가 + 표식 기반 1회성 백필 |
| 획득 (004-006) | 생성자 자동 참가(단일 트랜잭션), `POST /api/rooms/:id/members`(멤버만·멱등), 자율 참가 경로 금지 |
| 술어와 게이트 (007-012) | `isRoomMember`/`requireRoomMember` 단일 술어, POST 메시지 · GET 메시지 · SSE · `GET /api/rooms` 좁히기 · 판정 수용 |
| 금지 조항 (013-016) | 방 실재 은닉(`404`), 비멤버 판정 무효화, 봇 경로 불변, `server/` 밖 수정 금지 |

### 2.3 시그니처 개정 — 문자 그대로

```ts
// 지금 (SPEC-PERM-001 REQ-PERM-004 가 글자 그대로 고정)
tryHandleUserReply(roomId: number, text: string): boolean

// 개정 후 (REQ-ROOMAUTHZ-012)
tryHandleUserReply(roomId: number, userId: number, text: string): boolean
```

`userId` 를 두 번째에 둔 이유는 `(roomId, userId)` 가 멤버십 술어의 인자 순서와 같아서다. **REQ-PERM-004 는 이 인터페이스를 코드 블록으로 못 박고 있으므로**, 코드만 고치고 문서를 두면 다음 감사자가 문서를 근거로 구현을 결함이라 판정한다. 그래서 그 SPEC 문서 개정을 이 카드의 산출물에 포함했다.

라우트 게이트가 이미 막는데 브로커도 스스로 확인하는 이유는 백스톱이다 — 두 번째 호출부가 생기는 날 라우트 게이트는 그 경로를 보호하지 않고, 게이트가 실수로 제거돼도 가장 비싼 동작(판정)만은 막힌다.

### 2.4 `403` 이 아니라 `404` — 무엇을 포기했는가

비멤버에게는 **없는 방·활성 방·보관된 방 세 응답이 글자 그대로 같다** (`404` + `{ error: '방을 찾을 수 없습니다' }`).

| | `403` | `404` (채택) |
|---|---|---|
| 방의 실재 | 확인해 준다 | 숨긴다 |
| 열거 공격 | 계정 하나로 방 번호 스캔 가능 | 불가 |
| 진단 | "초대받지 못했다"를 알 수 있다 | "없다"와 구별 못 함 |

**받아들인 정보 누출: 진단 가능성.** 방 번호를 잘못 받은 사람은 원인을 스스로 알 수 없고 초대한 사람에게 물어야 한다. 그 대가로 §2.1 사슬의 2-3단계를 차단했다. `403` 은 계정만 있으면 누구에게나 "이 번호에 방이 있다"를 확인해 주고, 그것이 열거의 출발점이다.

부수 계약: **멤버십 검사가 방 상태(보관 여부) 검사보다 앞에 온다.** 뒤에 두면 비멤버가 `409`(보관됨)와 `404`(없음)를 구별할 수 있어 실재가 샌다.

## 3. 운영자 결정 3건과 기각안

`spec.md` §3 에 기각 사유와 함께 부호화했다. 재검토 대상이 아니다.

### D1 — 획득 방식: 생성자 + 초대뿐

- **채택**: `created_by` 기록 + 생성자 자동 참가, 그 뒤로는 기존 멤버만 `POST /api/rooms/:id/members` 호출 가능. 자율 참가 라우트 없음.
- **기각 — 자율 참가(join) 라우트**: 감사 기록(누가 언제 들어왔는가)은 남지만 §2.1 사슬이 그대로 성립한다. 공격자의 요청이 하나 늘어날 뿐 막히지 않는다. 인가처럼 보이면서 인가가 아니다.
- **기각 — 생성자 전용(초대 없음)**: 검사는 가장 단순하나 여러 사람이 한 방을 쓰는 것이 원천 금지된다. `spec-v2.md` 2장의 "소수 그룹" 전제 자체를 부순다.

### D2 — 게이트 범위: 읽기·쓰기·구독 전부

- **채택**: POST 메시지 · GET 메시지 · GET 이벤트(SSE) · 판정 수용 넷 + `GET /api/rooms` 좁히기.
- **근거**: 승인 누르는 자리 하나만 막으면 `request_id` 는 여전히 읽힌다. 사슬은 1단계에서 끊어야 하고, 그러려면 열거와 읽기가 함께 닫혀야 한다.

### D3 — 기존 데이터: 전원 백필

- **채택**: 상향 시점의 모든 방 × 모든 사용자를 멤버로 넣는다.
- **왜**: 넣지 않으면 상향 직후 어느 방에도 멤버가 없어 전원이 자기 방에서 잠긴다. 초대는 기존 멤버만 할 수 있으므로 **복구 경로가 없다.**
- **정직한 한계**: 기존 방에 대해서는 **보안 이득이 전혀 없다.** 상향 전과 똑같이 모두가 모든 옛 방을 읽는다. 조이는 효과는 상향 이후에 생기는 방에만 적용된다. 이것이 잠금 방지와 맞바꾼 값이며, 문서는 그것을 이득인 척하지 않는다.
- **1회성 보장 방식**: `schema_migrations(name PK)` 표에 `roomauthz-001-backfill` 을 기록하고, 이름이 이미 있으면 백필을 건너뛴다. 백필 SQL 은 `INSERT OR IGNORE`, 백필과 표식 기록은 **하나의 트랜잭션**이다.
  - `OR IGNORE` 만으로는 부족하다 — 같은 실행 안의 충돌은 삼키지만 **재실행 자체를 막지 못한다.** `db.ts` 는 기동마다 `SCHEMA` 를 무조건 실행하므로, 표식이 없으면 탈퇴 기능이 생기는 날 나간 사람이 재기동마다 되돌아온다.
  - 표식만으로도 부족하다 — 부분 실패 시 중복 삽입으로 터진다. 둘은 서로 다른 실패를 막는다.
  - 이 성질은 AC-ROOMAUTHZ-003 이 직접 잰다(1차 개방 후 행 하나를 지우고 2차 개방 → 되살아나지 않아야 통과).

### 6.2 판정 규칙

깨지는 조건은 둘 중 하나 — (a) 방을 직접 INSERT 해 놓고 로그인 사용자로 게이트 걸린 라우트를 부른다(그 사용자는 비멤버), (b) `GET /api/rooms` 가 모든 방을 돌려준다고 단언한다.

**깨지지 않는 조건도 밝혀 뒀다**: 하네스가 이벤트 라우트를 자기 파일 안에 사본으로 등록하면(`sse.test.ts:30`, `permissions.test.ts:51`) `index.ts` 에 붙는 SSE 게이트가 사본에는 닿지 않는다.

살아남는 것: `messages.test.ts:354`, `permissions.test.ts:124`·`:133`, `sse.test.ts:176`, 그리고 다른 여섯 파일 전부.

### 6.4 2차 효과를 별도로 센 이유

REQ-ROOMAUTHZ-010 이 이벤트 라우트 등록을 `registerEventRoute(app)` 로 내보내고 하네스도 **같은 함수**를 쓰도록 요구한다. 그러지 않으면 게이트가 통째로 빠져도 `sse.test.ts` 는 초록이다 — 즉 **게이트를 측정하는 테스트가 존재하지 않는 상태**가 된다. 그 요구를 이행하면 `sse.test.ts` 의 사본이 사라지고, 존재하지 않는 방 `1` 로 스트림을 여는 나머지 7개가 게이트에 걸린다. 여기에 `permissions.test.ts:147` 이 같은 이유로 합류해 8개다.

**"추출을 미루면 피할 수 있다"고 읽으면 안 된다** — 미루면 게이트가 테스트로 측정되지 않는 상태가 남고, 그것이 그 요구사항이 존재하는 이유다.

### 6.5 이 목록의 쓰임

run 단계는 **이 34개 밖의 실패만 결함으로 본다.** 그리고 M4 단계 1이 실제 실패 목록을 받아 이 표와 대조하며, 어긋난 항목은 문서가 놓친 결합이므로 고치기 전에 원인을 `progress.md` §E.2 에 적는다. AC-ROOMAUTHZ-016 이 그 대조 기록의 존재를 통과 조건으로 건다.

## 7. 수용 기준의 변이 저항 — 어떻게 설계했나

이 프로젝트는 기준 품질을 변이로 측정한다. 인가 기준은 한 방향만 재면 반드시 뚫리므로, **모든 게이트 기준에 부정 사례와 대조군을 짝으로 넣었다.**

| 순진한 기준 | 무엇을 통과시키나 | 대신 관측하는 것 |
|---|---|---|
| "비멤버가 `404` 를 받는다" | 모든 요청을 `404` 로 막는 구현 | 같은 시나리오에서 **멤버는 성공한다** |
| "멤버가 성공한다" | 게이트가 아예 없는 구현 | 같은 시나리오에서 **비멤버는 거부된다** |
| "비멤버가 남의 메시지를 못 본다" | 빈 배열을 돌려주는 구현 — 방의 실재는 그대로 노출 | 상태 코드 `404` + 본문이 **없는 방과 글자 그대로 같은가** |
| "비멤버가 `404` 를 받는다" | 보관 방을 `409` 로 알려 주는 구현 | 세 응답(없는 방·활성·보관)의 `Set` 크기가 `1` 인가 |
| "비멤버의 판정이 전달되지 않았다" | 모든 판정을 죽인 구현 | 시도 뒤에도 **멤버의 진짜 판정이 성립하는가** |
| "두 번 열어도 오류가 안 난다" | 매번 다시 채워 넣는 백필 | 사이에 지운 행이 **되살아나지 않는가** |
| "방을 만들면 목록에 보인다" | 목록을 좁히지 않은 구현 | `room_members` 행을 직접 세고, 남의 방이 내 목록에 **없는가** |

AC-ROOMAUTHZ-012(F-14 를 직접 재는 기준)는 라우트 경유 시나리오 **하나**와 브로커를 직접 부르는 시나리오 **하나**를 둘 다 둔다 — 라우트 게이트만 있으면 브로커의 검사 유무가 구별되지 않기 때문이다.

## 9. Gaps — 확인하지 못한 것

**이 절의 항목은 전부 "관측하지 않았다"는 뜻이다. 추정을 사실로 적지 않았다.**

1. **테스트 34개 목록은 실행으로 확인하지 않았다.** 소스 읽기와 grep 으로 판정한 것이다. 실제 실패 목록은 M4 단계 1이 받아 대조하며, AC-ROOMAUTHZ-016 이 그 대조 기록을 통과 조건으로 건다. 어긋나면 그것이 놓친 결합이다.
2. **`ALTER TABLE` · 백필 · `PRAGMA table_info` 동작을 실행해 보지 않았다.** SQLite 문서와 현재 `db.ts` 구조를 근거로 설계했다. `better-sqlite3` 의 `ALTER TABLE ... ADD COLUMN ... REFERENCES` 지원 여부는 M1 이 RED 로 먼저 확인해야 한다.
3. **`GET /api/attachments/:id` 는 닫히지 않았다.** 첨부는 방이 아니라 첨부 번호로 조회되고 번호는 1부터 증가하는 정수라 추측 가능하다. D2 확정 범위 다섯 곳에 없어 게이트를 걸지 않았고, **이것이 이 SPEC 이 남기는 가장 큰 구멍이다.** `spec.md` §7·§9 에 잔여 위험으로 올렸다 — 후속 카드 필요.
4. **`POST /api/rooms/:id/invites`(봇 초대)와 `POST /api/rooms/:id/archive` 도 열려 있다.** 같은 이유로 비멤버가 남의 방에 봇을 넣거나 남의 방을 보관할 수 있는 상태가 남는다.
5. **백필은 기존 방에 보안 이득이 없다** (§3 D3). 잠금 방지와 맞바꾼 값이며 이득인 척하지 않았다.
6. **웹 UI(`web/`)가 좁아진 방 목록·`404` 응답을 어떻게 렌더링하는지 확인하지 않았다.** 범위 밖이라 읽지 않았고, 화면이 깨질 가능성을 배제하지 못한다.
7. **형제 문서 개정 22곳은 렌더링을 눈으로 확인하지 않았다.** 표 안에 삽입돼 표를 깨뜨린 한 건(`SPEC-PERM-001/plan.md`)은 자동 점검으로 찾아 표 뒤로 옮겼고, 나머지 21곳은 같은 점검에서 표 인접이 아님을 확인했다. 그러나 실제 렌더링 결과는 보지 않았다.
8. **`moai spec lint` 는 통과했으나**(`✓ No findings`), 그것은 구조 검사지 내용 검증이 아니다.
