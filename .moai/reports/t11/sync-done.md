## 1. 쉬운 말 요약

이 카드가 닫겠다고 한 것은 닫혔습니다. 방에 초대받지 않은 계정은 그 방의 메시지를 쓰지도 읽지도 못하고, 실시간 스트림도 못 열고, 남의 방 도구 승인을 대신 눌러 줄 수도 없습니다. 방 목록에도 남의 방은 안 뜹니다.

저는 run 레인이 넘긴 «125개 전부 통과»를 믿지 않고 처음부터 다시 돌렸고 같은 값을 봤습니다. 그리고 방어가 정말 작동하는지 보려고 **막는 자리를 하나씩 일부러 망가뜨려** 봤습니다. 아홉 자리 전부, 망가뜨리는 즉시 테스트가 잡아냈습니다 — 아무도 지켜보지 않는 방어는 하나도 없었습니다.

감사자는 여기에 더해 **조립된 서버에서 라우트를 기계로 전수 열거해** 방 관련 문 열한 개를 확정하고, 문마다 「방에 없는 사람」과 「없는 방 번호」의 응답을 상태 코드·본문·헤더까지 맞대어 봤습니다. 한 글자도 다르지 않았습니다 — 방이 실재하는지 새어 나가지 않는다는 뜻입니다.

막히지 않은 것은 처음부터 «이 카드에서 안 막는다»고 적어 둔 둘입니다 — 첨부 파일 내려받기와 방 보관. 감사자가 실제로 남의 방 첨부를 내려받아 보였습니다. 문서가 그것을 미리 적어 두었으므로 숨겨진 구멍은 아니지만, 다음 카드가 반드시 가져가야 합니다.

### F-01 — sync 레인이 직접 재검증한 일곱 자리

sync 레인은 처음에 두 자리만 찾았고, 감사자가 여섯이라 했으며, 재확인 결과 **일곱**이다.

```
server/src/room-members.ts:2      "술어를 부르는 자리는 아홉이다"
server/src/room-members.ts:7      @MX:ANCHOR — "게이트 여덟 곳(…목록…)이 호출한다"
server/src/routes-rooms.ts:13     "술어의 아홉 호출부 중 목록은"
server/src/routes-rooms.ts:46     "이 라우트는 술어의 아홉 호출부 중 하나다"
server/src/routes-messages.ts:31  "이 라우트는 술어의 아홉 호출부 중 하나다"
.moai/specs/SPEC-ROOMAUTHZ-001/plan.md:379      "술어를 부르는 자리는 아홉이다"
.moai/specs/SPEC-ROOMAUTHZ-001/spec.md:277      "술어를 부르는 자리 아홉 중 일곱"
(+ progress.md:153 — §E.2 의 역사적 관측 기록. 고치지 않는다)
```

**참인 값:** 술어(`isRoomMember`/`requireRoomMember`) 호출부는 **여덟**이다 — preHandler 일곱(`routes-messages.ts:32·:128`, `routes-events.ts:13`, `routes-rooms.ts:47`, `routes-bots.ts:50·:70·:82`) + 브로커 백스톱(`permissions.ts:53`). 아홉 번째로 세어 온 방 목록(`routes-rooms.ts:18`)은 술어를 부르지 않고 **인라인 SQL 하위 질의로 같은 조건을 따로 적는다.**

**동작은 옳다.** REQ-ROOMAUTHZ-011 이 그 SQL 을 문면으로 지정했고, AC-ROOMAUTHZ-011 이 실제로 잰다 — sync 레인이 그 SQL 을 `WHERE ? IS NOT NULL` 로 변이시키자 테스트 1건이 실패했다(M9).

**REQ-007 이 반증됐는가 — 감사 판정은 «아니다».** SPEC §2 가 게이트를 «비멤버를 거르는 지점»으로 정의하는데 목록은 거르지 않고 좁히며, spec.md §5.3 이 목록을 AC-017 sweep 밖으로 이미 이름 붙여 뒀다. 다만 §5.3 이 적은 **예외 사유가 틀렸다** — 「상태 코드로 방향이 안 드러나서」라 적혀 있으나 실제 사유는 「두 번째 SQL 판정이 따로 존재해서」다.

**왜 그냥 두면 안 되는가.** 저 문장들이 앉아 있는 함수의 존재 이유 자체가 «판정을 복사하지 말라»이다. 다음 사람이 «이 함수 하나만 고치면 전부 고쳐진다»고 믿고 목록을 놓치는 것이 정확히 이 SPEC 이 막으려던 결함 부류다. 사용자 도달 문서(`CHANGELOG.md:41`·`README.md`)는 처음부터 사실대로 적었으므로 사용자에게 거짓은 없다 — 그래서 비차단이다.

### F-02 — sync 레인이 재확인

공시는 결과를 둘(파괴적 쓰기 · 실재 오라클)로 적으나 감사 실측은 넷이다. 비멤버가 남의 방을 보관하면 **그 방 멤버의 메시지 전송이 `409`, 봇 초대가 `409`** 로 막히고, sync 레인이 `routes-rooms.ts` 를 훑어 확인한 바 **보관을 되돌리는 라우트가 API 에 없다**(`unarchive` 히트 0). 즉 비멤버 한 명이 남의 방을 **API 로는 복구 불가능하게** 정지시킬 수 있다. 게이트를 추가하지 말라는 지시는 유효하므로 이 카드에서 닫지 않되, **후속 카드의 우선순위 근거로 이 크기를 정확히 적어야 한다.**
