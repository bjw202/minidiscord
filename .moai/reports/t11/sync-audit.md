## 0. 먼저 — 쉬운 말 요약

이 카드는 **닫겠다고 한 것을 실제로 닫았다.** 나는 sync 레인이 넘긴 증거를 믿지 않고 처음부터 다시 쟀다. 서버 테스트 125개가 내 손에서 전부 통과했고(종료 코드 0), 타입 검사도 0이다. 그리고 조립된 서버에서 **라우트를 기계적으로 전수 열거해** 방과 관련된 문 열 개를 하나도 빠뜨리지 않고 확인한 뒤, 문마다 「방에 없는 사람」과 「없는 방 번호」의 응답을 **상태 코드·본문·헤더까지 바이트로 맞대어** 봤다. 활성 방에서도, 보관된 방에서도, `HEAD` 요청에서도 두 응답은 글자 하나 다르지 않았다. 방이 있다는 사실 자체가 새지 않는다는 이 카드의 핵심 약속은 참이다.

**열려 있다고 적힌 두 경로도 실제로 열려 있는지 직접 확인했다.** 방에 속하지 않은 계정으로 남의 방 첨부 파일을 내려받아 「TOP SECRET」이라는 내용을 실제로 손에 넣었고, 남의 방을 보관해 그 방을 얼려 버렸다. 둘 다 문서가 **미리, 정확하게** 적어 둔 것이다 — 숨기지 않았다. 다만 보관 쪽 설명이 한 걸음 모자란다: 문서는 「파괴적 쓰기이고 봇 접속이 끊긴다」까지만 적는데, 실제로는 그 뒤로 **그 방 구성원이 메시지도 못 보내고 봇 초대도 못 한다**(둘 다 `409`). 계정 하나로 남의 방을 통째로 정지시킬 수 있다는 뜻이라 그 문장이 있어야 한다.

**판정을 FAIL로 내리지 않은 이유를 분명히 적는다.** sync 레인이 스스로 신고한 G-T11-01 — 「목록은 술어를 부른다」는 주석이 거짓이다 — 은 사실이고, 내가 세어 보니 그 거짓 문장은 신고된 두 자리가 아니라 **여섯 자리**에 있다. 그런데 이것은 요구사항 위반이 아니다. SPEC §2 가 「게이트」를 «비멤버를 거르는 지점»으로 정의하는데 목록은 거르지 않고 좁히며, REQ-ROOMAUTHZ-011 이 그 SQL 을 문면 그대로 지정했으므로 구현은 요구사항을 정확히 따랐다. 게다가 **사용자가 읽는 문서(CHANGELOG:41)는 이 예외를 정직하게 적어 두었다.** 거짓인 것은 코드 주석과 SPEC 본문의 «개수 세기» 문장뿐이고, 동작은 옳고 측정도 된다. 그래서 Medium·비차단이다.

## 2. 통로 열거 — 넘겨받은 목록을 믿지 않고 다시 셌다

### 2.1 조립된 서버의 라우트 전수 (기계 열거)

sync 레인의 행렬은 `grep isRoomMember` 가 여덟을 찾고 아홉째(`GET /api/rooms`)는 SQL 인라인이라 놓쳤다고 적는다. **그 열거가 완전한지를 grep 이 아니라 런타임에 물었다** — 실제 조립된 서버가 등록한 라우트 전부를 뽑았다.

```
├── /api/health (GET, HEAD)
├── /api/auth/register (POST) · /api/auth/login (POST) · /api/auth/logout (POST)
├── /api/attachments/:id (GET, HEAD)
├── /api/rooms (GET, HEAD, POST)
│   ├── /:id/members (POST)
│   ├── /:id/messages (POST, GET, HEAD)
│   ├── /:id/archive (POST)
│   ├── /:id/invites (POST, GET, HEAD)
│   │   └── /:botId (DELETE)
│   └── /:id/events (GET, HEAD)
└── /api/bots (GET, HEAD, POST)
```

**방의 내용·실재·부작용에 닿는 경로는 정확히 열 개이고, 그 밖은 없다.**

| # | 경로 | 강제 방식 | 상태 |
|---|------|-----------|------|
| 1 | `POST /api/rooms/:id/messages` | `requireRoomMember` preHandler | 닫힘 |
| 2 | `GET /api/rooms/:id/messages` | 동상 | 닫힘 |
| 3 | `GET /api/rooms/:id/events` | 동상 | 닫힘 |
| 4 | `POST /api/rooms/:id/members` | 동상 | 닫힘 |
| 5 | `POST /api/rooms/:id/invites` | 동상 | 닫힘 |
| 6 | `GET /api/rooms/:id/invites` | 동상 | 닫힘 |
| 7 | `DELETE /api/rooms/:id/invites/:botId` | 동상 | 닫힘 |
| 8 | `GET /api/rooms` (목록) | **인라인 SQL** 하위 질의 | 닫힘 (축소) |
| 9 | `PermissionBroker.tryHandleUserReply` | `isRoomMember` 직접 호출 | 닫힘 (백스톱) |
| 10 | `POST /api/rooms/:id/archive` | **`requireAuth` 만** | **열림 — 공시됨** |

`GET /api/attachments/:id` 는 방 범위 라우트가 아니지만 방 내용에 닿으므로 열한 번째로 센다 — **열림, 공시됨**.

**열째가 있는가?** 있다 — `POST /api/rooms/:id/archive` 다. 그리고 그것은 sync 레인의 행렬이 「놓친」 것이 아니라 **범위 밖으로 정확히 공시된** 것이다(§7·§9·CHANGELOG·README 네 곳). 그 밖의 열한째는 찾지 못했다. Fastify 가 자동 등록한 `HEAD` 짝들도 같은 preHandler 를 물려받는 것을 프로브 B 로 실측했다(§3.1) — 「GET 만 막고 HEAD 는 뚫린」 형태는 없다.

### 2.2 봇 게이트웨이 쪽 우회로도 함께 봤다

`gateway.ts:176-190` 의 `history_request` 는 토큰 하나로 그 방 메시지 전체를 넘긴다 — 이 카드가 초대 라우트 셋을 범위에 넣은 이유다(D2 v2). 토큰 발급 경로 셋이 전부 게이트 뒤로 들어간 것을 프로브 B 로 확인했으므로, **계정 하나로 토큰을 받아 그 문으로 읽는 경로는 닫혔다.** 이미 토큰을 쥔 봇의 자격이 토큰에 남는 것은 REQ-ROOMAUTHZ-015 가 명시한 설계다.

## 3. 보안 렌즈 — 적대적으로 밀어 본 것

### 3.1 방 실재 누출 — 바이트 대조 (프로브 B·E)

비멤버 `mallory` 의 응답과 존재하지 않는 방 번호(`999999`)의 응답을 **상태 코드 + 본문 + 헤더(`date`·`content-length` 제외)** 로 직렬화해 문자열 비교했다.

```
SAME   GET    /api/rooms/{}/messages          404 {"error":"방을 찾을 수 없습니다"}
SAME   POST   /api/rooms/{}/messages          404 {"error":"방을 찾을 수 없습니다"}
SAME   GET    /api/rooms/{}/events            404 {"error":"방을 찾을 수 없습니다"}
SAME   POST   /api/rooms/{}/members           404 {"error":"방을 찾을 수 없습니다"}
SAME   POST   /api/rooms/{}/invites           404 {"error":"방을 찾을 수 없습니다"}
SAME   GET    /api/rooms/{}/invites           404 {"error":"방을 찾을 수 없습니다"}
SAME   DELETE /api/rooms/{}/invites/1         404 {"error":"방을 찾을 수 없습니다"}
SAME   HEAD   /api/rooms/{}/messages          404 (빈 본문)
SAME   HEAD   /api/rooms/{}/invites           404 (빈 본문)
DIFF!! POST   /api/rooms/{}/archive           비멤버 200 {"ok":true} / 없는 방 404
```

**보관된 방에서 다시 잰 결과도 같다** (프로브 E — REQ-013 의 순서 계약이 실제로 무는 자리다):

```
방 1 보관 완료: archived
SAME   POST   /api/rooms/{}/messages   비멤버=404 없는방=404 | 멤버(보관방)=409 "보관된 방에는 메시지를 보낼 수 없습니다"
SAME   GET    /api/rooms/{}/messages   비멤버=404 없는방=404 | 멤버(보관방)=200 {"messages":[]}
SAME   POST   /api/rooms/{}/members    비멤버=404 없는방=404 | 멤버(보관방)=409 "보관된 방에는 초대할 수 없습니다"
SAME   POST   /api/rooms/{}/invites    비멤버=404 없는방=404 | 멤버(보관방)=409 "보관된 방에는 초대할 수 없습니다"
SAME   GET    /api/rooms/{}/invites    비멤버=404 없는방=404 | 멤버(보관방)=200 []
SAME   DELETE /api/rooms/{}/invites/1  비멤버=404 없는방=404 | 멤버(보관방)=200 {"ok":true}
```

**멤버에게는 `409` 가 보이고 비멤버에게는 `404` 가 보인다** — 게이트가 방 상태 검사보다 앞선다는 계약이 실행으로 성립한다. 「보관됐다」는 사실이 비멤버에게 새는 자리는 게이트 일곱 곳 어디에도 없다. **빈 배열로 답하는 자리도 없다** — `GET /invites` 도 `GET /messages` 도 비멤버에게 `404` 다.

### 3.2 권한 릴레이 — 소모도 교란도 되지 않는다 (프로브 C·D)

```
비멤버 carol 판정 반환 : false
비멤버 carol 재시도    : false
멤버 alice 판정 반환   : true    ← 대기 항목이 살아남았다는 증거
멤버 alice 재소비      : false   ← 그때 비로소 소모됐다
```

HTTP 경로(정식 multipart)에서도 같다:

```
비멤버 carol : 404 {"error":"방을 찾을 수 없습니다"}
멤버 alice   : 200 {"ok":true,"consumed_by":"permission"}
방 메시지    : [system "🔒 봇이 도구 사용 승인을…", system "⚠️ 봇이 접속해 있지 않아 판정을 전달하지 못했습니다 (fghij)"]
```

`permissions.ts:53` 의 멤버십 검사가 `open.get(requestId)` 와 `open.delete(requestId)` **앞**에 있어, 거부된 답은 레지스트리를 읽지도 지우지도 않는다. REQ-ROOMAUTHZ-014 의 본체 —「비멤버가 답해도 멤버가 여전히 판정할 수 있다」— 가 실행으로 성립한다. **교란(소모 없이 상태를 흔드는 것)도 성립하지 않는다.**

### 3.3 SSE — 비멤버 요청이 구독을 남기지 않는다

```
구독 전 subscriberCount=0
비멤버 SSE: 404 {"error":"방을 찾을 수 없습니다"}
요청 후 subscriberCount=0
```

`hijack()` 앞에서 끝나므로 응답 없는 열린 스트림도, 허브에 남는 유령 구독도 없다.

### 3.4 권한 상승 — 스스로 멤버가 되는 길이 없다

```
비멤버 자가초대: 404 {"error":"방을 찾을 수 없습니다"}
POST .../join : 404 Route POST:/api/rooms/1/join not found   ← 라우트 자체가 없다
판정 후 멤버?  : false
```

`POST /api/rooms/:id/members` 는 게이트 뒤이므로 남의 방에 자신을 넣을 수 없고, 자율 참가 라우트는 존재하지 않는다(§2.1 의 전수 열거가 그것을 뒷받침한다 — 추측이 아니다). REQ-ROOMAUTHZ-006 준수.

### 3.5 백필 재실행 — 지운 멤버십은 되살아나지 않는다

```
재개방 전 행수=3 → 삭제 후=2 → 재개방 후=2
표식: [{"name":"roomauthz-001-backfill"}]
삭제한 멤버십 부활? false
표식 삭제 후 재개방: 부활? true, 총 행수=6
```

이행 표식이 실제로 재실행을 막는다 — REQ-ROOMAUTHZ-003 의 1회성이 실행으로 성립한다. 표식을 손으로 지우면 백필이 다시 도는데, 그것은 D3 이 고른 설계 그대로이고 운영자가 DB 를 직접 건드린 경우다. **결함이 아니다.**

### 3.6 생존 변이 둘 — 「관측 불가」 주장을 반증하려 했으나 실패했다

sync 레인은 P5(`!Number.isInteger(roomId)` 제거)·P6(`!req.user` 제거)가 생존한 이유를 「`requireAuth` 뒤라 관측 가능한 행위 차이가 없다」고 적었다. 그 논거를 깨는 입력을 찾으려 했다 — 가드가 없을 때 `isRoomMember` 가 **던지면** 500 과 404 가 갈려 관측 가능해진다.

```
isRoomMember(db, NaN, alice)        => false (예외 없음)
isRoomMember(db, Infinity, alice)   => false
isRoomMember(db, -Infinity, alice)  => false
isRoomMember(db, 1e+308, alice)     => false
isRoomMember(db, 9007199254740992,) => false
isRoomMember(db, 1.5, alice)        => false
```

**하나도 던지지 않는다.** better-sqlite3 가 이 값들을 전부 무매치로 흡수하므로 가드가 있든 없든 응답은 같은 `404` 다. HTTP 로도 확인했다 — `abc`·`1abc`·`1.5`·빈 문자열·`%20`·`1e999`·`Infinity`·`-1`·`9007199254740995` 전부 `404`. **P5 의 생존 논거는 참이다.** P6 는 게이트 일곱 곳이 모두 `requireAuth` 를 앞에 두는 것을 §2.1 의 라우트 표와 소스 판독으로 확인했고, `requireRoomMember` 를 단독으로 쓰는 등록점은 없다 — 역시 관측 불가가 참이다.

**반증 시도가 실패했다는 것을 결함 없음의 증거로 적는다.** 다만 이것은 「지금 이 순간 관측 불가」이고, `requireAuth` 없이 이 preHandler 를 쓰는 라우트가 생기는 날 P6 는 즉시 관측 가능해진다.

### 3.7 열려 있는 두 경로 — 실제로 열려 있다

```
[첨부] alice 첨부 전송: 200, attachment id = 1
       비멤버 carol 다운로드: 200 content-type=text/plain body="TOP SECRET"

[보관] 비멤버 carol 보관 : 200 {"ok":true}
       보관 후 활성 봇 토큰 : 1 → 0
       멤버 alice 이후 전송: 409 {"error":"보관된 방에는 메시지를 보낼 수 없습니다"}
       멤버 alice 이후 초대: 409 {"error":"보관된 방에는 초대할 수 없습니다"}
       실재 오라클: 있는 활성 방 200 / 이미 보관된 방 409 / 없는 방 404
```

**둘 다 문서가 먼저 정확하게 적어 두었다.** 첨부 항목의 서술(«번호를 아는(또는 찍는) 비구성원은 남의 방 첨부를 여전히 내려받을 수 있습니다 … 지금 남아 있는 가장 큰 구멍»)은 내 관측과 정확히 일치한다. 보관 항목의 서술도 파괴적 쓰기·토큰 철회·실재 오라클 셋을 모두 적었다 — **다만 네 번째 결과(멤버가 그 뒤로 쓰지 못한다)가 빠져 있다. → F-02.**

**리드가 물은 질문에 답한다.** 보관 라우트의 `404`/`200`/`409` 갈래는 **REQ-ROOMAUTHZ-013 이 닫으려던 실재 오라클을 실제로 다시 연다.** 크기는 이렇다 — 계정 하나로 방 번호를 훑어 **실재는 알 수 있지만 내용은 못 읽는다.** §1.2 의 사슬(목록 → 읽기 → `request_id` → 승인)은 2·3단계에서 여전히 끊겨 있으므로 **권한 상승으로 이어지지 않는다.** 대신 이 오라클에는 사슬과 무관한 별도의 무게가 있다 — 오라클과 파괴적 쓰기가 **같은 요청**이라, 스캔하는 행위 자체가 남의 방을 하나씩 정지시킨다. 이것은 이 카드가 만든 회귀가 아니고(보관은 처음부터 무게이트였다) 문서가 알고 인수했지만, 후속 카드 우선순위에서 첨부 다음이 아니라 **첨부와 나란히** 놓일 만하다.

### F-01 [Medium] [비차단] — 「목록이 술어를 부른다」는 거짓 문장이 신고된 두 자리가 아니라 여섯 자리에 있다

**리드가 물은 질문에 답한다 — REQ-ROOMAUTHZ-007 이 자기 구현에 반증되는가.** **아니다.** 근거 둘이다.

1. SPEC §2 가 「게이트」를 «멤버십 술어를 걸어 **비멤버를 거르는** 지점»으로 정의한다. 목록은 아무도 거르지 않는다 — 로그인한 누구나 `200` 을 받고 행 집합만 좁아진다. 정의상 게이트가 아니므로 «모든 게이트가 함수 하나를 부른다»의 구속을 받지 않는다.

**§5.3 의 예외 처리는 「충분하지만 이유가 틀렸다」.** §5.3 은 목록을 AC-017 sweep 밖으로 이름 붙이면서 그 이유를 «상태 코드 하나로 방향이 드러나지 않아»라고 적는다 — **측정 가능성**의 문제로 설명한다. 진짜 이유는 그 자리에 **두 번째 멤버십 판정이 SQL 로 따로 쓰여 있다**는 구현상의 사실이고, 그것이야말로 REQ-007 이 막으려던 「같은 판정의 복사」다. 지금 문서를 읽는 사람은 그 두 번째 판정의 존재를 알 수 없다.

**완화 사정 셋** — 이것이 차단이 아닌 이유다.

### F-02 [Medium] [비차단] — 보관 라우트 공시가 네 번째 결과를 빠뜨렸다: 비멤버가 남의 방을 **정지**시킬 수 있다

### F-06 [Low] [비차단] — 멤버가 쓸 수 있는 사용자 존재 오라클이 공시되지 않았다

**위치**: `server/src/routes-rooms.ts:58-59`

```
없는 사용자 초대 : 400 {"error":"사용자를 찾을 수 없습니다"}
있는 사용자 초대 : 201 {"ok":true}
재초대(멱등)     : 200 {"ok":true,"already":true}
```

방 하나의 멤버는 `user_id` 를 훑어 **어느 번호에 계정이 있는지** 알아낼 수 있다. REQ-ROOMAUTHZ-005 표가 정한 동작 그대로이고 요구사항 위반이 아니다.

**크기가 작은 이유 둘.** (1) 멤버 자격이 선행 조건이라 §1.2 의 사슬을 늘리지 않는다. (2) 같은 종류의 누출이 이미 있다 — `POST /api/auth/register` 가 이름 중복에 `409` 를 돌려주므로 사용자 이름 열거는 원래 가능하다(다만 그쪽은 이름, 이쪽은 번호다). `POST /api/auth/login` 은 없는 사용자와 틀린 비밀번호를 같은 `401` 로 합쳐 열거를 막고 있는데(`auth.ts:52-55`), 초대 라우트는 같은 배려를 하지 않는다는 **내부 비일관**이 남는다.

**필요한 변경**: 없음(동작은 요구사항대로다). 후속 카드가 방 경계를 더 조일 때 함께 볼 자리로 §9 에 한 줄 기록하는 것을 권한다.

### F-07 [Low] [비차단] — 방 번호가 정규화되지 않는다 (관찰 — 우회로는 찾지 못했다)

**위치**: 게이트 전부 — `Number((req.params as {id:string}).id)`

```
GET id='+1'  (멤버 alice) => 200 {"messages":[]}
GET id=' 1'  (멤버 alice) => 200 {"messages":[]}
GET id='0x1' (멤버 alice) => 200
```

`+1`·` 1`·`0x1`·`1.0` 이 전부 방 1 을 가리킨다. **우회로는 아니다** — 게이트와 핸들러가 **같은** `Number()` 변환을 쓰므로 「게이트는 A 를 보고 핸들러는 B 를 보는」 갈라짐이 없고, 비멤버가 별칭을 써도 같은 `404` 다(프로브 B3 에서 확인). 감사가 찾은 것은 **결함이 아니라 성질**이다.

기록하는 이유는 하나다 — 나중에 방 번호를 로그·감사 기록·캐시 키로 쓰는 기능이 생기면 같은 방이 여러 문자열로 기록된다. 지금은 아무 결과도 없다.

**필요한 변경**: 없음. 관찰로만 남긴다.

## 7. Gaps — 이 감사가 **관측하지 못한** 것

정직하게 적는다. 아래는 통과가 아니라 **미관측**이다.

1. **변이 행렬 15종을 재현하지 않았다.** 디스패치가 `server/`·`channel/`·`web/` 소스 수정을 금지했으므로 변이를 넣지 않았다. 따라서 «스위트가 게이트 제거를 잡는가»는 sync 레인의 기록을 **신뢰한 것이지 관측한 것이 아니다.** 다만 그 기록이 증명하려던 다른 명제(«게이트가 실제로 막는가»)는 §3 의 블랙박스 프로브로 독립 확인했고, 복원 무결성은 `git status --short server/` 빈 출력로 확인했다.
2. **커버리지를 재지 않았다.** `server` 워크스페이스에 커버리지 스크립트가 없고 SPEC·acceptance 어느 쪽도 커버리지 임계를 요구하지 않는다. TRUST 5 의 85% 하한은 이 카드에서 **UNVERIFIED** 다.
3. **린트를 돌리지 않았다.** `server` 에 린트 스크립트가 없다 — Unified 축은 `tsc` 하나로만 관측된다.
4. **run 단계의 RED 원문·34-moment 전이를 재현하지 않았다.** 마일스톤을 되감아야 하는 관측이라 범위 밖에 두었다. `m3-post-gates-verbose.txt`·`m4-transition-34-verbose.txt` 를 읽지도 않았다 — §E.2 의 요약만 읽었다.
5. **REQ-ROOMAUTHZ-003 의 백필 트랜잭션 원자성을 재지 않았다.** 백필과 표식 기록이 갈라지는 상황을 만들지 않았다. SPEC §9 가 「미검증」으로 이름 붙인 그대로 남는다.
6. **실제 구버전 DB 파일을 상향해 보지 않았다.** «올려도 아무도 잠겨 나오지 않는다» 는 CHANGELOG 문장은 `db.ts:97-107` 판독과 새 DB 에서의 표식 동작 관측(§3.5)에 근거한다 — 진짜 옛 파일로 재현하지는 않았다.
7. **동시성을 재지 않았다.** 같은 사람을 같은 방에 동시에 넣는 두 요청, 방 생성 트랜잭션의 부분 실패를 만들지 않았다. 복합 기본키와 `db.transaction` 의 존재는 소스로 확인했으나 경합은 관측하지 않았다.
8. **게이트웨이 WebSocket 경로를 구동하지 않았다.** `history_request` 가 방 메시지 전체를 넘긴다는 것은 `gateway.ts:176-190` **판독**이고 실제 소켓을 붙여 보지 않았다. 토큰 발급 라우트가 게이트 뒤라는 것만 HTTP 로 실측했다.
9. **`web/` 을 전혀 건드리지 않았다.** diff 가 비었음만 확인했다.
10. **§6 표의 «파일→표» grep 35히트를 내가 다시 세지 않았다.** 표본 세 행만 대조했다. 나머지 22행의 참 여부는 재확인되지 않은 채 남는다.
11. **`t4` 재판정을 실행하지 않았다.** 이 카드의 범위 밖이다.
