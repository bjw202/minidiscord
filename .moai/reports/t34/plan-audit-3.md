- 왜 거짓이 되는가: **3회차 수리 자신이 만들었다.** N-06 이 실패 문구를 갈래 둘로 쪼갰으므로 브로커의 결과 본문은 **셋에서 넷**이 된다. `plan.md` M3-3 이 이를 명시한다 — 「**문구는 넷이고** 서로 모두 달라야 한다: 승인 전송됨 / 거절 전송됨 / (ㄱ) … / (ㄴ) …」. `acceptance.md:266` 3항도 「방에 저장될 수 있는 본문은 **넷**이 서로 모두 다르다」로 같은 값을 적는다. 즉 v0.2.0 에서 참이던 「세 템플릿」이 v0.3.0 에서 거짓이 된다.
- 왜 훑기가 못 잡았는가: §6.1 어간 열 가운데 「세 템플릿」을 잡는 것이 하나도 없다. 실패 문구 행의 어간은 `전달하지 못했습니다|접속해 있지|FAILED_BODY` 인데, `web-rich.test.ts:150` 은 셋 중 어느 것도 포함하지 않는다(직접 확인 — 그 파일에서 어간이 걸리는 줄은 `:19`·`:151`·`:197` 뿐). 개수 열거를 잡는 어간은 `다섯` 하나뿐이고 「셋/세」는 없다.
- 부수 상한: **`web/` 가 §6.1 범위 목록에 통째로 없다.** 범위 명령은 `.moai/specs/*/{spec,plan,acceptance,design,research}.md` + `server/src/*.ts` + `server/test/*.ts` + `channel/src/*.ts` 이고, `/usr/bin/grep -c 'web/' .moai/reports/t34/evidence/t34-scope-ex-self.txt` → `0`. 그런데 3회차 수리 자신이 `web/rich.js:67` 에서 **살아 있는 코드 결합**을 찾아 [HARD] 제약으로 올렸다 — 훑기가 볼 수 없는 표면에 이 SPEC 의 중심 제약이 걸려 있다. `web/` 의 노출은 내가 전수로 열거했고 넷이 전부다(`rich.js:59`·`:60`·`:62`·`:67`; `:60` 은 줄임표 인용이라 부류 4, `:67` 은 정규식이라 부류 4).
- 왜 차단인가: `AC-PERMROUTE-010` 의 통과 조건이 「뒤집힌 자리 중 표에 없는 것이 **0건**」이다. 표에 없는 뒤집힌 자리가 실재하므로 그 기준은 착지 시 **거짓으로 통과**한다 — 이 SPEC 이 스스로 세운 기준이 무너지는 자리다. 부류로 보면 1·2회차를 실패시킨 것과 같다(어간 목록은 상한이다).
- 요구 수리(전부 기계적):
  1. §6.1 어간 표에 개수 열거 어간 한 줄을 더한다 — 예 `/usr/bin/grep -rn '세 템플릿\|세 결과 템플릿'`, 적중과 분류를 함께 적는다.
  2. §6.2 에 `server/test/web-rich.test.ts:150` 을 행으로 싣는다(주석 1줄, 조용한 부류 — 17행과 같다). `plan.md` M4 목록에 그 편집을 더한다.
  3. §6.1 범위 명령에 `web/*.js` 를 더하거나, 더하지 않는다면 **왜 제외했는지와 그 대신 무엇이 `web/` 를 덮는지**를 §6.1 에 명시한다. `web/rich.js:59`·`:62` 는 부류 2(주석 1줄)로 실린다.
- **리드에게**: 이 항목은 차단으로 분류하지만 **결과 크기는 낡은 주석 셋**이고, 수리는 표 두 행 + 어간 한 줄이다. 「부채로 수용하고 run M4 에 명시 단계로 싣는다」가 완전히 합리적인 처분이며, 이 보고서가 자리를 전수로 열거했으므로 처분에 필요한 정보는 여기 다 있다. 4회차를 도는 값어치는 없다고 본다.

### N3-02 — §6.2 11행이 `spec.md:230` 을 넣은 **근거**가 SPEC 자신의 조항에서 도출되지 않는다 · **비차단**

- 자리: `.moai/specs/SPEC-PERMROUTE-001/spec.md:307` (11행)
- 표가 적은 근거: 「`:230` 의 「판정을 전달하지 못했습니다」는 새 문구에서 **「판정을」이 앞으로 빠져** 이어진 문자열로는 남지 않는다」
- 반증: 이 SPEC 이 새 문구에 거는 제약은 `spec.md:161` [HARD] 의 **꼬리 「전달하지 못했습니다 (`<request_id>`)」 유지** 하나뿐이다. 「판정을」을 뺄 것을 요구하는 조항은 어디에도 없다. 「⚠️ 요청한 세션이 끊겨 **판정을 전달하지 못했습니다** (id)」는 모든 조항을 만족하면서 「판정을 전달하지 못했습니다」를 이어진 채로 남긴다. 즉 표가 사실로 적은 인과는 **구현 선택에 종속된 추론**이며, 3회차가 닫으려던 부류(읽어서 얻은 것을 사실로 적기)와 같다.
- 실제 근거는 따로 있다: `:230` 은 「브로커의 **세 결과 템플릿**」이라는 개수 열거이고, 넷이 되는 순간 거짓이다(N3-01 과 같은 뿌리). 그러므로 **행 자체는 표에 있어야 하고, 「이 SPEC 이후」 칸의 문장만 교체하면 된다.**
- 비차단으로 두는 이유: 자리는 이미 표에 있고 처분(주석 1줄)도 옳으므로, 근거가 틀려도 run 이 그 줄에 주석을 단다. 잘못된 근거의 주석이 남는 것이 유일한 손해다. N3-01 을 고칠 때 같은 자리를 지나므로 함께 고쳐진다.

### N3-03 — `gateway.ts` 제거 범위의 하한 `:353` 이 착지 후에도 참인 줄이다 · **비차단**

- 자리: `spec.md:309` (13행) · `plan.md:189` (M2-5) — 둘 다 제거 범위를 `:353-360` 으로 적는다.

### N3-04 — [HARD] 파서 제약이 「꼬리 유지」만 요구하고 「한 줄」을 요구하지 않는다 · **비차단 (과잉 지적으로 분류)**

- `RESOLUTION_RE` 는 `/^.*(?:…) \((…)\)$/` 로 양끝이 고정돼 있고 `.` 이 줄바꿈을 건너지 못한다(`web/rich.js:62` 주석이 그 설계를 적는다). 따라서 새 실패 본문이 **두 줄**이면 꼬리를 유지해도 정규식이 걸리지 않아 버튼이 되살아난다. `spec.md:161` 의 [HARD] 는 꼬리만 요구하고 단일 행을 요구하지 않는다.

## 6. 착수 가능성 판정 (공격선 8)

**착수 가능하다.** 네 산출물을 받은 run 실행자가 만들 수 있고, 끝난 때를 알 수 있고, 무엇을 보고할지 안다.

- **만들 수 있는가**: `plan.md` §F 가 M1~M6 을 되돌리기 어려운 순서로 늘어놓고, 각 단계가 파일·줄·앵커 명령까지 지목한다. M2 가 RED 먼저를 명시하고(「현행 전원 발신 코드에서 이 시험이 **실제로 붉다**는 것을 관측하고 출력을 남긴다」), M3-2 가 `undefined` 좁히기 분기를 조항으로 못 박는다. 리드 처분 둘(§D-1 선택 필드 · §D-5 유지)이 닫혀 있어 미결로 멈출 자리가 없다.
- **끝난 때를 아는가**: AC 15건 전부 이진이고, 그중 값이 실제로 움직이는 것과 비회귀 불변식인 것을 **문서가 스스로 갈라 공시한다**(AC-007 · AC-008 · AC-014 의 (ㄱ)·(ㄷ)). 「오늘 이미 통과인 기준이 계획의 자기 검증을 떠받친다」는 1회차 F-03 의 함정이 구조적으로 닫혔다. 변이표 여섯 행이 판별력을 갖고, M6 이 중심 주장에 기계적 반증자를 붙인다.
- **무엇을 보고할지 아는가**: 재회부 방아쇠 둘이 값과 함께 명시돼 있다(typecheck 30 자리 이탈 / M1-6 실측이 14 와 다름). DoD 7항이 「빈 §Gaps 는 강한 주장이다」까지 적는다.
- **남는 위험은 이름이 붙어 있다**: 14 는 추론값이고 편집 목록은 실측이 정한다는 것, 판정 도착과 동시 절단 창은 이 SPEC 이 닫지 않는다는 것, `web/rich.js` 파서 결합이 살아 있는 코드 결합이라는 것 — 셋 다 문서가 스스로 적었다.

세 회차의 결함 크기가 단조 감소했다는 것이 판정의 근거 하나다: 1회차는 **살아 있는 거짓 네 부류**를 통째로 빠뜨렸고, 2회차는 **문서 하나**를 분류란에서 떨어뜨렸으며, 3회차가 남긴 것은 **주석 셋과 인과 한 문장**이다. 정체가 아니라 수렴이다.
