## 0. 요약 — 무엇이 닫혔고 무엇이 새로 열렸는가

**1회차의 차단 넷은 전부 닫혔다.** 특히 F-01(배제하지 못하는 상대를 «배제한다» 로 적었다)에 대한 응답은 이 프로젝트에서 본 것 중 가장 정직하다 — 배제표를 **전송 계층으로 갈라** 여덟 행으로 늘리고, «오늘 이 저장소에서 실제로 서는 행은 평문 행들이다» 를 [HARD] 로 못 박고, **공백을 초록으로 위장하지 않고 «상대가 이긴다» 를 매 실행마다 단언하는 기준**(AC-GWAUTH2-024)을 세웠다. 1회차가 요구한 것 이상이다.

**그런데 그 개정이 세 자리에서 자기 형제를 낡게 만들었고, 그중 하나는 개정의 핵심을 무력화한다.**

### G-03 — [Critical] [차단] 검증 층의 열쇠 유도 헬퍼 셋이 **`cb` 를 담지 않는다** — 요소 ④가 기준에서 사라졌다

**위치**: `acceptance.md:126-131`(헬퍼) 대 `spec.md:174-177`(§2.5 전사 정의)

**요구사항 층 (`spec.md:174-177`, 원문)**

```
challenge 전사 = `challenge|${client_nonce}|${server_nonce}|${room_id}|${bot_id}|${pub}|${cb}`

세션 열쇠      = HMAC-SHA256(k_srv, `session|${client_nonce}|${server_nonce}|${room_id}|${bot_id}|${cb}`)
```

**검증 층 (`acceptance.md:126-131`, 원문)**

```ts
const challengeProof = (t, cn, sn, room, bot) =>
  createHmac('sha256', ksrvOf(t)).update(`challenge|${cn}|${sn}|${room}|${bot}|${pubOf(t)}`).digest('hex')
const authSig = (t, cn, sn, room, bot) =>
  sign(null, Buffer.from(`auth|${cn}|${sn}|${room}|${bot}|${pubOf(t)}`), skOf(t)).toString('hex')
const sessKey = (t, cn, sn, room, bot) =>
  createHmac('sha256', ksrvOf(t)).update(`session|${cn}|${sn}|${room}|${bot}`).digest()
```

**셋 다 `cb` 가 없다.** 인자 목록에도, 문자열에도 없다.


**즉 스물네 기준 가운데 `cb` 를 전사에 넣어 계산하는 것은 0개다.** AC-022 는 두 바인딩 **값이 다르다**를 재고 등록 실패를 재지만, 그 실패가 «전사에 `cb` 가 들어갔기 때문» 임을 재는 계산은 어느 기준에도 없다.

**두 방향의 귀결을 함께 적는다.**

1. **정상 구현이 거짓 실패한다.** AC-005 의 Then 은 «각 `challenge.server_proof` 가 테스트가 독립 계산한 `challengeProof(T, client_nonce, server_nonce, room_id, bot_id)` 와 **정확히 같고**(`toBe`)» 다. §2.5 를 따른 구현은 전사 끝에 `|unbound` 를 붙이므로 **이 `toBe` 는 실패한다.** 이 문서 자신의 §「검증 원칙」 5번(«정상 구현을 거짓 실패시키지 않는다»)이 금지한 형태다.
2. **바인딩 없는 구현이 통과한다.** 헬퍼가 `cb` 를 모르므로, 세 전사 전부에서 `cb` 를 뺀 구현(= 변이 **T** + **V** 동시)은 005·007·009·010·011·013·014·015·016·020·023 을 **전부 초록으로** 지난다.

**왜 Critical 인가.** 채널 바인딩은 **1회차 Critical F-01 에 대한 이 개정의 답 전체**다. 그 답이 검증 층의 전사 정의에서 빠져 있으면, run 이 «바인딩을 붙였다» 고 보고해도 그 보고를 뒷받침하는 계산이 어디에도 없다. 그리고 이 문서 자신이 헬퍼를 «구현이 쓰는 코드를 부르지 않고 기준이 스스로 계산한다 — 공유하면 규칙이 함께 틀려도 기준이 그것을 알아채지 못한다» 로 세웠으므로, **사본이 규칙과 갈라진 것은 그 설계가 막으려던 바로 그 실패**다.

**필요한 수정** (셋 다 필요하다)
1. 세 헬퍼에 `cb` 인자를 더하고 문자열 끝에 `|${cb}` 를 붙인다 — `challengeProof(t, cn, sn, room, bot, cb)` · `authSig(…, cb)` · `sessKey(…, cb)`. `envOf` 는 `sessKey` 를 부르므로 함께 바뀐다.
2. 평문 하네스에서 그 인자가 리터럴 `'unbound'` 임을 **하네스 절에 명시한다** — 기본값으로 숨기면 다음 라운드가 「`cb` 가 없다」로 다시 읽는다.
3. **변이 T 의 예측을 다시 도출한다.** 지금 T 는 «022 만 무너진다» 로 적혀 있으나, 헬퍼가 `cb` 를 담으면 T 는 005·007·… 를 함께 무너뜨린다. **예측을 고치지 않으면 run 이 실측에서 어긋남을 만나고, 그것이 `SPEC-GWAUTH-001` 의 13행 중 7행 어긋남과 같은 자리다.**

### G-12 — [Minor] [비차단] §2.8.3 의 「성립하는 근거 **둘**」 중 둘째가 첫째와 독립이 아니다

**리드가 준 근거의 기각은 옳다.** `spec.md:176` 이 세션 열쇠를 `HMAC-SHA256(k_srv, …)` 로 정의하고, v2 의 `hello` 는 `pub`·`client_nonce` 만 싣는다(REQ-004). **중계자는 `k_srv` 를 갖지 않으므로 전사를 전부 보아도 세션 열쇠를 유도하지 못한다** — 「전사를 관측했으므로 전사에서 유도한 열쇠도 얻는다」는 이 설계에 성립하지 않는다. 개정의 정정은 정확하다.

**대체 근거 둘 가운데 첫째(층의 독립)는 건전하다.** 둘째(「투명한 전달 중계 자체가 성립하지 않게 된다」)는 **첫째의 따름정리다**: TLS 종단 배치에서는 중계자가 핸드셰이크에서 이미 걸리므로 「확립된 세션의 봉투를 흘려보내는」 상황 자체가 성립하지 않고, 평문 배치에서는 양쪽 `cb` 가 `unbound` 로 같으므로 유도에 넣어도 아무것도 달라지지 않는다. 둘째가 물리는 유일한 경우는 **첫째의 전제(핸드셰이크 게이트가 어떤 이유로든 뚫린다)가 성립할 때**다.

**이 SPEC 자신이 그것을 이미 기록했다** — 변이표 V 행이 「**하나도 없다** — 등록이 먼저 막히므로 관측되지 않는다」이고, 그 아래 [HARD] 가 「근거는 «층의 독립» 이지 «오늘의 관측» 이 아니다」라고 적는다. 즉 **표는 근거가 하나임을 알고 있고, §2.8.3 만 둘이라고 적는다.** 결정 자체는 옳으므로 비차단이며, 「성립하는 근거는 둘이다」를 「근거는 층의 독립 하나이며, 그 귀결로 투명 중계도 성립하지 않게 된다」로 바꾸면 표와 일치한다.

### G-13 — [Minor] [비차단] 시험 fixture 의 위험 경계 서술이 **네 가지를 비운다** (운영자 정책 결정 대기 항목)

**적혀 있는 것**: 「시험 전용 폐기 열쇠」 · 파일 머리 `@MX:WARN` · 「어떤 생산 경로도 그것을 읽지 않는다」 · 「fixture 가 없으면 건너뛰지 않고 **실패한다**」(건너뛰기 금지는 이 프로젝트의 규칙과 일치한다).

4. **재생성 시점이 없다** — 만료되면 어느 시점에 누가 다시 만드는가.

**«적으라는 것이지 닫으라는 것이 아니다»** — 이 SPEC 이 F-09 에 대해 쓴 어법을 그대로 돌려준다.

### G-14 — [Minor] [비차단] 공허성 집계 「B=0」은 문서 본문으로 지지되지 않는다

## 6. 디스패치가 지정한 중심 질문에 대한 판정

### 6-1. 「측정된 배치가 지지하지 않는 종결 주장이 한 문장이라도 있는가」 — **없다**

**어간으로 훑었다**(관용구가 아니라 어간 `배제` 로):

```
$ grep -n '배제' spec.md plan.md design.md acceptance.md research.md | grep -v '배제하지 못' | grep -v '배제 근거'
```

무조건 「배제한다」로 적는 자리는 §5 표 **세 행뿐**이고, 셋 다 조건이 **행 자신 안에** 있다:

- 1행 — 공격자 칸이 「(진짜 서버에 **닿지 못한다**)」로 상대를 한정한다.
- 2행·4행 — 전송 조건 칸이 「양쪽이 같은 TLS 연결을 종단」이다. 그리고 표 바로 아래 `spec.md:461` [HARD] 가 「**그 조건이 붙은 두 행은 오늘 성립하지 않는다** … 이 표를 근거로 «중계자를 배제했다» 고 보고하는 것은 조건을 지운 보고이며 **금지한다**」로 못 박는다.

그 밖의 「배제」 용례는 전부 부정형이거나(「배제되지 않는다」) 조건을 동반한다. **종결 과장은 찾지 못했다.**

### 6-2. AC-024 는 정말 「상대가 이긴다」를 매 실행 기록하는가 — **그렇다** (관측 함수 셋은 미정의, G-06)

핵심 줄이 **양성 단언**이다:

```
expect(gw.isOnline(roomId, botId)).toBe(true)   // ★ 중계자의 소켓이 봇으로 등록됐다 — 상대가 이겼다
```

「부정 단언은 누락에 초록이다」의 함정을 피한다 — 프레임이 오지 않거나 하네스가 죽으면 이 단언은 **붉어진다.** 그리고 `acceptance.md:698` 이 「**이 줄이 붉어지는 날은 결함이 생긴 날이 아니라 방어가 늘어난 날이며**, 그때는 이 기준과 `spec.md` §5 표를 **함께** 고쳐야 한다 — 기준만 고치면 표가 낡고, 표만 고치면 기준이 낡는다」로 적어, **이 감사가 반복해서 잡는 결함 부류에 대한 사전 방어를 기준 안에 넣었다.**

**「기록을 지우면 실패하는가」에 대한 정확한 답**: 기준을 삭제하면 아무것도 실패하지 않는다(테스트 삭제는 어떤 스위트에서도 붉어지지 않는다). 그러나 질문의 뜻이 「이 관측이 반증 가능한가」라면 **그렇다** — `isOnline === true` 와 `channelBinding() === 'unbound'` 둘 다 양성이고, 구현이 그 공백을 닫는 순간 붉어진다. **다만 넷 중 셋의 관측 함수가 미정의다(G-06)** — 반증 가능성은 설계에 있고 표면이 아직 없다.

### 6-3. AC-022 는 약화된 대역인가 — **아니다.** 선행 카드를 무너뜨린 형태와 정반대다

선행 카드의 실패 형태는 **「필요한 것을 다 쥐고도 쓰지 않기로 한 위조자」**였다. AC-022 의 상대는 다섯 축에서 그 반대다.

| 축 | AC-022 가 실제로 하는 것 |
|---|---|
| 진짜 TLS 종단 서버 | `Fastify({ https: { key, cert } })` 위에 **진짜 `createGateway`**. 생산 코드 무변경으로 `app.server` 가 `https.Server` 가 된다 |
| 진짜 채널 | `wire()` — 스텁 아님 |
| 진짜 전사 | 중계자가 `hello`·`challenge`·`auth` 를 **글자 그대로** 전달. 「고치는 것이 하나도 없다」 |
| **능력을 깎지 않았음을 단언한다** | `relayedFrames()` 의 up/down 타입 배열을 `toEqual` 로 — 「전달만 했다」가 **관측된다**. 이 줄이 「위조자가 실제로 읽었다」(AC-006 1단계)의 중계자 판본이다 |
| **왜 막혔는지를 함께 잰다** | `bindingToChannel() !== bindingToServer()` + 둘 다 64자 hex. 「나중에 다른 이유로 막히기 시작해도 그것을 바인딩의 효력으로 오독하지 않는다」 |
| **양성 짝** | ⑤ 중계자 없이 직접 붙으면 확립된다 — 「모든 TLS 접속을 거절하는 구현」을 배제한다 |

**하네스 절이 그 의도를 [HARD] 로 선언한다**: 「이 상대는 «약화된 대역» 이 아니라 진짜 중계자다. 무엇을 빠뜨리지도, 망가뜨리지도, 흉내내지도 않는다.」

**남는 결함은 능력이 아니라 계산이다** — G-03 이 지적한 대로 헬퍼가 `cb` 를 담지 않으므로, AC-022 가 관측하는 「막힘」이 **전사의 `cb` 때문임을 계산으로 뒷받침하는 자리가 없다.** 상대는 온전하고 대조가 반쪽이다.

### 6-4. 루프백 잔여의 조건부 분석 — **정확하고, 조건이 보이는 자리에 있다**

`spec.md` §2.8.5 의 세 성질을 코드로 대조했다.

1. 「`server_proof` 를 스스로 만들지 못한다」 — `k_srv = HMAC(T, 'minidiscord/v2/server-confirm')`(§2.3)이고 v2 `hello` 는 `pub`·`client_nonce` 만 싣는다(REQ-004, AC-003 이 키 집합 전체를 `toEqual` 로 잰다). **참.**
2. 「낡은 `challenge` 를 재생하지 못한다」 — 전사에 두 논스가 묶이고 논스는 소켓마다 새로 만들어진다(REQ-010, AC-011). **참.**
3. 「봉투를 만들지 못한다」 — `k_sess = HMAC(k_srv, …)`(§2.5). **참.**
4. 「그러나 진짜 서버에 닿을 수 있으면 중계는 한다」 — 양쪽 `cb` 가 `unbound` 라 두 소켓의 전사가 같다. **참.**

**조건은 두 자리에서 보인다**: ① §5 표 1행의 공격자 칸이 「(진짜 서버에 **닿지 못한다**)」로 한정하고, 닿는 경우는 2·3행이 별도로 진다. ② §2.8.5 가 「진짜 서버에 닿는 경로가 **없으면** 가용성뿐 / **있으면** 봇 사칭이 열린다」를 두 개의 불릿으로 갈라 적는다.

**그리고 그 상대의 전제까지 적는다** — 루프백 포트 선점 능력은 흔히 `MINIDISCORD_TOKEN` 읽기 능력을 함께 뜻하고, 그러면 평문 토큰 유출 행이 되어 전부 열린다. 그것을 「판정을 무르게 하는 근거가 아니라 위협 모형의 경계를 정확히 하는 관측」으로 규정한 것은 정확하다. **다만 그 문장이 가리키는 행 서수가 틀렸다(G-04 — 「넷째 행」이 아니라 일곱째).**

### 6-5. KDF 채널 바인딩 근거 — **정정은 옳고, 대체 근거 둘 중 하나는 독립이 아니다**

§4 G-12 에 적었다. 요약: **리드가 준 기제의 기각은 정확하다**(세션 열쇠가 전사가 아니라 `k_srv` 에서 유도되고 중계자는 `k_srv` 를 갖지 않는다 — `spec.md:176` 과 REQ-004 로 확인). 대체 근거 1(층의 독립)은 건전하고, 대체 근거 2(투명 중계 불성립)는 근거 1 의 전제 아래에서만 물리는 **따름정리**다. **이 SPEC 자신의 변이표 V 행이 그 사실을 이미 기록한다.** 결정 자체는 옳으므로 비차단이며, 문안만 표와 맞추면 된다.

### 6-7. Tier L 다섯 산출물 — `research.md` 는 **자리 채우기가 아니다**

**판정 방법**: 인용된 명령을 **글자 그대로 다시 돌려** 출력을 대조했다.

## 7. 내가 확인하지 **않은** 것 (Gaps)

정직하게 열거한다. 아래는 이 감사가 근거를 갖지 못하는 자리다.

1. **스위트를 돌리지 않았다.** `npm test`·`npm run typecheck` 를 실행하지 않았다. base 개수, 형제 하네스의 실제 파손 범위, `channel/dist` 상태에 대해 아무 주장도 하지 않는다.
2. **Ed25519 유도를 재실행하지 않았다.** DER 접두 상수 둘(`302e020100300506032b657004220420` · `302a300506032b6570032100`), 공개키 32바이트, 서명 64바이트는 **미검증 인용**이다. 1회차와 같은 공백이며, `plan.md` §C 5번이 run 착수 시 재확인한다. 나는 `exportKeyingMaterial` 과 Fastify 버전만 재실행했다.
3. **G-03 의 귀결을 실행으로 확인하지 않았다.** 「AC-005 의 `toBe` 가 정상 구현에서 실패한다」는 §2.5 의 전사 정의와 헬퍼 문자열을 **문서 대조**로 얻은 결론이다. 구현이 없으므로 실행 프로브를 만들 대상이 없다. 두 원문은 내가 직접 읽었고 위에 인용했다.
4. **형제 SPEC 일곱을 통독하지 않았다.** 따라서 `plan.md` §B-1 목록의 **완전성을 독립으로 판정하지 못했다.** 1회차와 같은 공백이며, DoD 가 재도출을 별도 항목으로 진 것(F-07 종결)이 그 자리를 대신한다.
5. **`.moai/reports/t15` 의 88건 인용을 개별 대조하지 않았다.** `plan.md` §B-8 의 처분(고치지 않는다)이 옳다고 판단했고, 그 판단에 개수가 영향을 주지 않는다.
6. **억제된 프레임의 채널 쪽 귀결을 확인하지 않았다.** `channel/src/channel-server.ts` 의 무판정 기본 동작을 읽지 않았다. 문서가 그 미확인을 스스로 공시하므로(§0-7·잔여 위험·design §E.0) 결함으로 세지 않았다.
7. **`design.md` §B·§C·§D(전선 형식·열쇠 일정·상태 기계)를 행 단위로 대조하지 않았다.** §A 표 17행과 §E·§E.0·§E.1·§F·§G 는 읽고 대조했다. `cb` 가 §B·§C 의 프레임·열쇠 정의에 어떻게 반영됐는지는 **재지 않았으므로 G-03 의 범위를 `acceptance.md` 헬퍼로 한정했다** — `design.md` 쪽에도 같은 누락이 있는지는 3회차 범위다.
8. **AC-022 가 처방한 TLS 하네스가 실제로 서는지 실행하지 않았다.** `Fastify({ https })` → `app.server instanceof https.Server` → 업그레이드 소켓이 `TLSSocket` 이라는 연쇄는 **문서의 주장**이며, 나는 Fastify 5.12.1 과 `exportKeyingMaterial` 의 존재만 쟀다.

## 9. 권고

1. **G-03 · G-02 · G-01 · G-04 · G-05 · G-06 을 닫기 전에 run 에 들어가지 않는다.** 특히 **G-03 은 단독으로 run 진입 차단이다** — 요소 ④를 재기로 한 계산이 검증 층에 없는 상태에서 구현이 착지하면, 「바인딩을 붙였다」는 보고가 바인딩 없는 구현 위에서 초록으로 나온다. 이 카드가 존재하는 이유가 정확히 그런 보고였다.

2. **세 결함(G-01·G-04·G-05)이 같은 형태임을 개정자에게 명시한다.** 1회차 처방이 자리를 **명명**했고 개정은 **명명된 자리만** 덮었다. 3회차는 각 수정을 **어간 grep 으로 시작해 적중 전건을 분류표로 남기고**, 처방이 명명한 자리 수와 실제 적중 수가 다르면 그 차이를 적어야 한다. 관용구가 아니라 어간으로 잡는다 — 「넷·다섯」이 아니라 `sendToBot`, 「셋째 행」이 아니라 `째 행`.

3. **G-04 는 서수를 고치지 말고 버린다.** 이 SPEC 은 줄 번호에 대해 이미 「앵커로 재도출한다」는 결론에 도달했다(§3.1 [HARD], `plan.md` §B-0 ③). **행 서수는 표가 자랄 때마다 낡는 줄 번호와 같은 것**이며, 이번 라운드가 그 증명이다. 같은 결론을 표의 행에도 적용한다.

4. **G-13(fixture)은 운영자 결정을 먼저 받는다.** 개인키를 버전 관리에 넣는 결정이며, 이 카드가 조용히 내릴 결정이 아니다. **결정이 「넣는다」로 나오더라도 G-13 의 네 공백(재는 기준 · 생성 파라미터 · 스캐너 취급 · 재생성)은 문서에 적혀야 한다** — 「어떤 생산 경로도 읽지 않는다」는 지금 강제되지 않는 가정이고, 그것이 1회차 F-08 이 §2.5 에서 잡은 것과 같은 형태다.

5. **점수 궤적: 0.83 → 0.83.** 하락이 아니므로 STOP 신호는 내지 않는다. **그러나 평행선 자체가 신호다** — 1회차 결함 열셋 중 열둘을 닫고도 총점이 오르지 않은 것은, **닫은 만큼 새로 열렸기 때문**이다. 3회차가 마지막 반복(`max_iterations: 3`)이므로, 3회차 개정은 **G-01~G-06 여섯만** 다루고 **범위를 넓히지 않아야 한다.** 이번 라운드처럼 개정이 새 요소(채널 바인딩)를 함께 들여오면 그 요소가 다시 여섯 자리의 형제를 낳는다. 3회차가 FAIL 이면 운영자에게 세 갈래(부채 동반 PASS · 범위 축소 · 반복 상한 연장)를 올린다.

6. **닫힌 것을 함께 적는다.** 이 개정은 이 감사가 이 프로젝트에서 본 가장 정직한 경계 서술을 만들었다 — **공백을 「재지 않는다」로 적는 대신 「상대가 이긴다」를 매 실행 단언하는 기준**(AC-024)은 여기서 처음 본 형태이고, `SPEC-GWAUTH-001` 이 무너진 자리에 대한 구조적 답이다. **판정이 FAIL 인 것은 그 답이 틀려서가 아니라, 그 답을 계산하는 자리가 검증 층에서 빠졌기 때문이다.**
