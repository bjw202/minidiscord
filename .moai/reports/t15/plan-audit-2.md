## 1. 주장 (Claim)

**1회차의 16건이 전건 닫혔고, 넷 중 셋은 문언 수선이 아니라 구조 교체로 닫혔다.**

- **C-02** 는 `plan.md` §F M3-3 이 `proofRejected` 를 `established` 와 분리하고 그 검사를 t9 게이트보다 **앞**에 두도록 [HARD] 로 처방하면서, 코드 블록·금지 형태·소켓 지역성까지 못 박아 닫혔다. 그 구조에서 변이 N 의 기대값은 실제로 성립한다 — 내가 구조를 따라가 다시 도출했다. **변이 O 는 장식이 아니다**: N 의 기대값이 구조에 의존한다는 것을 «구조를 어기면 N 이 뒤집힌다» 로 재는 메타 관측이고, 그런 관측을 두는 것 자체가 이 프로젝트에서 처음이다.
- **C-01·H-02** 는 형제 `settled` 센티넬 형태로 되돌리는 것에 더해, `deferWelcome` 손잡이로 **순서를 실제로 성립시켜** 닫혔다. 서술을 철회하는 값싼 길을 택하지 않았고, 그 결과 «스텁이 나가는 프레임에서 진짜 id 를 읽는다» 가 `expect(stub.readIds()).toEqual(['real-42'])` 로 **단언되는** 관측이 됐다.
- **C-03** 은 «공격자가 무엇을 가졌는가» 네 행 표로 다시 쓰였다. 네 행 전부 정직하고, 특히 «착지 전후 비교와 절대적 경계를 구분한다» 문단이 내가 1회차에 든 비대칭을 정면으로 다룬다. 잔여 문장을 전 트리에서 훑어 확인했다.
- **C-04** 는 `onWelcome` 단언을 «확립의 귀결» 로 바꾸고 통과 충실성을 AC-GWAUTH-015 로 떼어 냈다. 그 하네스가 실제로 콜백을 노출하는지 코드로 확인했고, 인용 줄번호 둘 다 정확했다.

**작성자가 나를 상대로 든 반박 셋은 전부 옳다.** 그중 하나는 내 1회차 보고가 **실행하지 않은 명령의 출력을 실행한 것처럼 적은** 경우다 — 이 보고서의 주제가 바로 그 부류의 결함이므로 §4에 분리해 적는다.

**그럼에도 세 자리가 열려 있다.** 전부 M-04 를 닫는 과정에서 새로 생긴 것이고, 셋 다 이 프로젝트가 반복해 온 «정정이 스스로 낡은 기록을 남긴다» 부류다 — 다만 어느 것도 Critical 이 아니고 설계·기준 층을 건드리지 않는다.

## 2. 증거 (Evidence)

### 2.1 (C-02 · 닫힘) 구조 처방이 모호하지 않고, 논증이 그 구조 위에서 다시 쓰였다

`plan.md` §F M3-3 은 [HARD] 표지와 함께 **실행 가능한 코드 블록**을 처방한다.

```ts
let established = false          // t9 소유 — 손대지 않는다
let proofRejected = false        // 이 SPEC 이 새로 들이는 소켓 지역 상태. established 와 별개다

ws.on('message', d => {
  …
  if (proofRejected) return                       // ① 이 SPEC 의 강제 지점
  if (msg.type === 'welcome') {
    if (!verifyProof(msg, nonce, opts.token)) {
      proofRejected = true                        // 플래그를 먼저 세우고
      console.error('minidiscord-channel: …')
      ws.close()                                  // 그 다음에 닫는다
      return
    }
    established = true
    opts.onWelcome?.(msg)
  } else if (!established) {                      // ② t9 게이트 — 한 글자도 바꾸지 않는다
```

**결합을 되살리면서 처방을 만족시킬 길이 막혀 있다.** 같은 절이 두 우회를 이름으로 금지한다 — «**①을 ② 뒤에 두거나 `proofRejected` 를 `established` 하나로 합치면 그 분리가 사라진다**». 그리고 `proofRejected` 의 소켓 지역성까지 별도 문단으로 못 박는다(클로저로 올리면 재접속이 영구히 막힌다). 코드 블록 + 금지 형태 둘 + 지역성 = 구현자가 처방을 지키면서 결합을 되살릴 여지가 실질적으로 없다.

**분리가 실제로 성립하는지 내가 다시 도출했다.** 부정 기준의 흐름은 이렇다 — 스텁이 증명 없는 `welcome` → ①은 아직 `false` 라 통과 → `welcome` 갈래에서 `verifyProof` 실패 → `proofRejected = true`, close → 뒤따르는 세 프레임은 **①에서 반환**된다. 변이 N(`!established` → `false`)은 ②를 지우지만 ①이 먼저 반환하므로 **다섯이 무너지지 않는다.** 변이 H(증명 대조 무력화)는 ①이 서지 않아 프레임이 흘러 **다섯이 무너진다.** 두 행이 갈린다. ✅

한편 t9 기준(AC-CHANAUTH-001·003·004·005)은 `welcome:false` 스텁을 쓰므로 `proofRejected` 가 서지 않고 `established` 도 `false` — 변이 N 은 그쪽을 무너뜨린다. 역방향 분리도 성립한다. ✅

`acceptance.md` §「검증 원칙」 4번은 표제부터 «강제 지점을 둘로 분리해서» 로 바뀌었고, «**v0.1.0 의 논증은 틀렸다 (1회차 감사 C-02)**» 를 먼저 적은 뒤 새 구조 위에서 2행 표(변이 H / 변이 N × 이 SPEC 기준 / t9 기준)로 다시 세운다. **기존 논증에 단서를 붙인 것이 아니라 논증을 교체했다.**

**변이 O 는 장식이 아니다.** O 는 구조를 어긴 뒤 «N 의 기대값이 뒤집히는가» 로 판정한다(`acceptance.md:406`). 즉 N 의 통과가 **구조 때문인지 우연인지**를 가른다 — 이 SPEC 이 «호칭이 아니라 구조가 분리를 만든다» 고 적은 문장을 실행으로 재는 유일한 관측이다. N 단독이라면 «어쩌다 통과했다» 와 구분되지 않으므로, O 는 실질을 더한다. 다만 그 지시가 완전히 모호하지 않은 것은 아니다 — N-03 을 보라.

### 2.2 (C-01 · H-02 · 닫힘) 부정 관측이 실행 가능한 형태가 됐고, 순서가 실제로 성립한다

`acceptance.md` 「이력 축 관측의 표준 형태」가 형제 AC-CHANAUTH-003 의 형태를 그대로 가져왔다. 그 형제 코드를 직접 대조했다.

```
$ sed -n '191p;212p' channel/test/transport-auth.test.ts
    let settled: 'pending' | 'resolved' | 'rejected' = 'pending'
    expect((await p).messages).toEqual([])
```

인용 `transport-auth.test.ts:191-212` 는 **정확하다** — 191 이 센티넬 선언, 212 가 그 기준의 마지막 단언이다.

새 형태는 `expect(settled).toBe('pending')` 를 잰다. 내가 1회차에 든 두 실패 갈래가 **둘 다 사라진다**: `'rejected'` 를 기대하지 않으므로 «연결 없음» 거부와 혼동되지 않고(`gateway-client.ts:113`), 10초를 기다리지 않으므로 vitest 기본 5,000ms 에 걸리지 않는다. 문서가 그 이유를 그대로 적었다(`acceptance.md:135`).

**H-02 의 순서는 `deferWelcome` 로 실제로 성립한다.** AC-GWAUTH-006·011 의 4단계를 `gateway-client.ts` 의 `send()` 조건에 대고 따라갔다.

1. 스텁이 `deferWelcome: true` 라 `hello` 에 답하지 않는다 → **소켓이 `OPEN` 으로 남는다.**
2. 세션이 승인 요청을 발신 → `send()` 의 `socket.readyState !== WebSocket.OPEN` 검사(`:47`)를 통과해 `true` → `permission_request` 가 **실제로 나간다** → 스텁이 `request_id` 를 읽는다.
3. `requestHistory` 도 같은 이유로 나가고 스텁이 `rid` 를 읽는다.
4. 그제서야 `pushWelcome()` 으로 위조 `welcome` + 세 프레임 → ①이 버린다.

1회차의 실패 원인(«소켓이 닫힌 뒤에 요청을 보내게 해 1번이 실행되지 않는다»)이 제거됐다. ✅ 그리고 `expect(stub.readIds()).toEqual(['real-42'])` 는 이 순서에서 **측정 가능하다** — 스텁이 실제로 프레임을 받았기 때문이다. 하네스가 `sent` 배열을 이미 갖고 있으므로 `readIds()` 는 그 위에서 구현된다. 다만 접근자 선언이 빠졌다 — N-04.

`acceptance.md` 「잔여 위험」이 이 의존을 스스로 든다: «`deferWelcome` 순서에 기대는 기준 … 구현이 `hello` 직후 무언가를 이유로 소켓을 먼저 닫으면 전부 함께 붉어진다». 대가를 감춘 곳이 없다.

### 2.3 (C-03 · 닫힘) 네 행 전부 정직하고, 잔여 문장이 트리에 없다

`spec.md` §5 의 표를 행 단위로 판정했다.

| 행 | 「증명을 만들 수 있는가」 | 내 판정 |
|---|---|---|
| 소켓 위치만 (프로브의 상대 · 루프백 선점 · 중간자) | **아니다** / 배제한다 | **옳다.** 열쇠는 `token_hash` 이고 이 상대는 그 값을 갖지 않는다 |
| `token_hash` **읽기만** (백업 유출 · 읽기 전용 SQLi · 파일 읽기) | **그렇다** / 배제하지 못한다 | **옳다.** `createHmac('sha256', keyHex)` 의 `keyHex` 가 정확히 그 값이다 |
| 평문 토큰 | 그렇다 / 배제하지 못한다 | **옳다.** 평문 → 해시가 자명하다 |
| 서버 장악 (DB 쓰기 포함) | 그렇다 / 배제하지 못한다 | **옳다.** 상위 집합이다 |

그리고 §5 가 내가 1회차에 든 비대칭을 정면으로 적는다 — «**해시 → 토큰은 256비트 역상 문제라 성립하지 않는다** … 해시 보유자는 더 약한 지식으로 증명 위조에는 충분하다». 나아가 «**착지 전후 비교와 절대적 경계를 구분한다**» 문단이 «해시 보유자가 통과하는 것은 이 SPEC 이 새로 연 공격면이 아니다. 그러나 §5 가 답해야 하는 물음은 그 비교가 아니라 «무엇이 닫혔는가» 이고, 그 답에 해시 보유자는 들어가지 않는다» 로 두 논점을 분리한다. **내가 1회차에 든 논증과 같은 구조이며, 더 정확하다.**

잔여 문장을 전 트리에서 훑었다.


**«토큰을 모르는 모든 상대를 닫는다» 로 읽히는 문장이 `spec.md`·`plan.md` 어디에도 남아 있지 않다.** 남은 두 자리는 그 표현을 **금지 대상으로 인용**하는 문장(`plan.md:174`·`:257`, `acceptance.md:423`)이고, `plan.md:106` 은 «별도 HMAC 비밀 컬럼» 기각 사유로 그 컬럼 역시 읽기 유출에 똑같이 노출되므로 «강도 이득이 없다» 는 결론이 여전히 참이다. ✅

§E.2 완료 조건(`plan.md:174`)과 DoD(`acceptance.md:423`)가 **줄여 적으면 미충족**을 명시해, run 단계가 이 경계를 다시 좁힐 수 없게 못 박았다.

### 2.4 (C-04 · 닫힘) 하네스가 실제로 콜백을 노출하고, AC-015 는 고아가 아니다

AC-GWAUTH-015 의 인용을 코드로 확인했다.

```
$ sed -n '86p' channel/test/gateway-client.test.ts
async function connected(srv: FakeServer, over: Partial<GatewayClientOpts> = {}) {
$ sed -n '112p' channel/test/gateway-client.test.ts
    await connected(srv, { onWelcome: w => got.push(w) })
```

**둘 다 정확하다.** `:86` 이 `over: Partial<GatewayClientOpts>` 로 `onWelcome` 을 받는 정의이고, `:112` 가 실제 사용례다. 그 파일은 `createGatewayClient` 를 직접 부르므로(`:88`) `wire()` 의 배선 부재와 무관하다. ✅

토큰 값도 맞다 — AC-015 가 `proofOf('tok123', …)` 를 쓰고, `connected()` 의 하드코딩 토큰이 `'tok123'` 이다(`:91`). `rogueGateway` 쪽 `'tok'` 과 혼동하지 않았다.

매트릭스에서 **AC-GWAUTH-015 → REQ-GWAUTH-007** 로 매핑돼 고아가 아니다. REQ 13 전건이 여전히 최소 1개 AC 로 덮이고, AC 15 전건이 유효 REQ 를 가리킨다. ✅

AC-GWAUTH-013 은 `onWelcome` 대신 «서버가 넣은 메시지가 세션 알림으로 도착한다» 를 잰다. **그 대체가 논리적으로 충분하다** — REQ-GWAUTH-011 이 미확립 소켓의 `message` 를 버리므로 «메시지 도착 ⟹ 확립» 이 성립하고, 「스텁도 흉내도 없다」 성질과 §3.5 의 워크스페이스 간 관측이 둘 다 살아 있다. ✅

### 2.5 (H-01 · 닫힘) 표제를 낮추고 6자리를 올렸으며, 미확인을 미확인으로 적었다

§3.3 의 표제가 «전건 열거» → **«확인한 범위»** 로 바뀌었고, 그 앞에 **SPEC별 확인 방법 표**가 새로 섰다 — `CHANCLIENT`·`CHANAUTH` 통독 / `GATEWAY` 부분 / `CHANPERM`·`CHANWIRE`·`CHANNEL` **«통독하지 않았다»**. 마지막 줄이 기준을 정확히 말한다: «**없다고 적지 않는다 — 보지 않았다고 적는다.**»

**이 공개는 적절하다.** 완전성을 주장하지 않고, 주장하지 않는 범위를 이름으로 열거하며, 후속(`plan.md` §B-6)으로 넘긴다. 감사가 요구할 수 있는 최대치다.

내가 든 6자리가 전부 표에 있고 **분류도 옳다.**

| 자리 | 부류 | 내 판정 |
|---|---|---|
| `CHANCLIENT/spec.md:92` `onWelcome` 타입 선언 | **B** | 옳다 — 산문이 아니라 타입 계약이다 |

## 4. 감사자 자기 정정 — 1회차 발견 2건이 틀렸다

**이 프로젝트는 반증된 발견을 폐기하지 않고 기록한다.** 작성자가 든 반박 셋을 판정한다.

### 4.1 반박 1 — C-03 의 «§7 서술» 인용: **작성자가 옳다. 내 발견이 틀렸다.**

1회차 발견표에 나는 C-03 의 위치를 «`spec.md` §5 «닫는다» 줄 · §1.3 · §2.2 · **§7 서술**» 로 적었다. v0.1.0 의 §7 은 «## 7. 수용 기준» 이고 본문은 «수용 기준 전체는 `acceptance.md` 에 있다 … **기준 수는 14건, 요구사항은 13건**» 이다 — **경계 진술이 한 문장도 없다.** 네 번째 자리는 `plan.md` §G 의 «정확한 진술은 «토큰을 모르는 상대를 배제했다» 다» 였고, 그것이 실제로 가장 위험한 자리였다(§G 는 run 단계가 읽는 안티패턴 목록이다).

**내 인용이 틀렸다.** 그리고 이것은 내가 M-03 으로 지목한 것과 같은 부류다 — **위치를 확인하지 않고 적은 인용.** 작성자는 틀린 인용을 그대로 따르지 않고 실제 자리를 찾아 고쳤다(`plan.md:257`). 감사가 잘못 짚은 자리를 작성자가 바로잡은 경우로 기록한다.

### 4.2 반박 2 — M-04 의 «9자리»: **작성자가 옳다. 내 계수가 하나 모자랐다.**

내가 빠뜨린 `CHANINJECT/progress.md:68` 을 확인했다 — «카드 t15 의 큐 본문이 … 범위 셋 중 둘(위조 permission_verdict·선착 판정, **F-A8**)을 담지 않는다». F-A8 을 t15 인계 범위로 적은 문장이 맞다. **내 9는 하나 모자랐다.**

다만 작성자의 10 도 맞지 않는다 — N-02 를 보라. 두 계수 모두 틀렸고 정답은 11 이다.

### 4.3 반박 3 — «44줄» vs «36줄»: **작성자가 옳다. 그리고 내 44는 측정된 값이 아니었다.**

작성자 말대로 두 질의는 다르다(작성자 쪽은 `| grep 소유` 가 더 붙는다). 모순이 아니다. 실측:

```
$ grep -rn 't15' .moai/specs --include='*.md' | grep -v SPEC-GWAUTH-001 | grep 소유 | wc -l
36                              ← 작성자의 질의. 값이 맞다
```

**그러나 더 무거운 사실이 있다.** 내 1회차 보고 §2.6 은 이렇게 적었다.

> `$ grep -rn 't15' .moai/specs/ --include='*.md' | grep -v SPEC-GWAUTH-001 | wc -l   → 44`

이 명령을 지금 그대로 실행하면 **67** 이 나온다.

```
$ grep -rn 't15' .moai/specs/ --include='*.md' | grep -v 'SPEC-GWAUTH-001' | wc -l
67
```

1회차에 나는 `wc -l` 을 **붙이지 않은** 목록 출력만 실행했고, 화면에 뜬 줄을 눈으로 세어 «44» 라고 적으면서 **명령 출력인 것처럼 표기했다.** 44 는 관측값이 아니라 오산이다.

**이것은 `verification-claim-integrity.md` §2 가 금지하는 무귀속 주장이며, 하필 그 결함 부류를 판정하는 보고서 안에서 저질렀다.** 1회차 §2.6 의 그 인용 블록을 **철회한다.** 그 문단이 뒷받침하려던 논지(«§3.3 이 다루지 않은 거짓 문장 부류가 하나 더 있다» = M-04)는 별도 근거로 성립하므로 논지 자체는 유지되지만, 근거 한 줄은 무효다.

**타당한 점.** 소유(누가 책임지는가)와 종결(어느 SPEC 이 닫는가)의 구분은 이 프로젝트에서 이미 쓰이는 축이다 — `SPEC-CHANAUTH-001` 이 `completed` 인데 F-01 이 t15 소유로 열려 있는 것이 같은 구조다. 그 축을 쓰면 형제 문장들이 **문자 그대로 참으로 남고**, 열 자리를 건드리지 않아도 된다. 자기모순 문장(«t15 소유 → 범위 밖»)도 «t15 소유이며 그 소유는 유지된다. 다만 그 카드의 첫 SPEC 은 닫지 않는다» 로 해소됐다. **소급 수정을 피하면서 참을 유지하는, 셋 중 가장 값싼 길이다.**

**그러나 명시되지 않은 대가가 하나 있다.** 이 SPEC 이 착지하면 카드 `t15` 는 큐에서 닫힌다. 그런데 A 부류 개정이 존재하는 이유가 바로 «**카드는 큐에서 닫히면 사라지므로 «이 잔여를 누가 닫았는가» 를 문서에서 따라갈 수 없다**» 였다. 소유를 카드에 남기면 **F-A8 만은 그 문제로 되돌아간다** — 다른 세 인계 항목은 SPEC·REQ 번호로 이어졌는데 F-A8 의 포인터는 곧 닫힐 카드를 가리킨 채 남는다. `spec.md` §5 는 «128 상한 자체의 재검토는 별도 SPEC 이 필요하다» 로 후속의 **형태**만 적고 **후속 소유자를 지목하지 않는다.** 이 자리를 문서가 인지하지 않은 것은 결함이다.

`plan.md` §B 에 «F-A8 의 후속 소유자를 지목하거나, `t15` 종료 시 포인터가 끊긴다는 사실을 기록한다» 한 줄이면 닫힌다.

## 8. 미검증 (Gaps)

- **변이표 A~M·N·O 의 실제 대응.** 구현이 없어 실행으로 재지 못했다. §2.1 의 N/H 분리 판정은 `plan.md` §F M3-3 코드 블록과 현행 `gateway-client.ts:63-86` 구조로부터의 **연역**이며 실행 관측이 아니다. N-03 이 든 (나) 해석에서 O 의 기대값이 성립하지 않는다는 판정도 연역이다.
- **AC-006~012 의 실제 통과.** 하네스가 아직 없다. `deferWelcome` 순서가 성립한다는 판정은 `send()` 의 `readyState` 검사(`gateway-client.ts:46-49`)를 읽은 연역이다. `readIds()`·`proof` setter 는 **명세에 없어** 실제 형태를 알 수 없다.
- **스위트 재실행.** 이번 라운드에 `npm test` 를 다시 돌리지 않았다. `git status --short` 로 `server/`·`channel/` 무변경을 확인하고 1회차 실행값(250/250)을 그대로 인용했다. 소스가 바뀌지 않았다는 사실은 관측했으나, 문서 편집이 스위트에 영향을 주지 않는다는 것은 자명한 가정이다.
- **`SPEC-CHANPERM-001`·`CHANWIRE-001`·`CHANNEL-001`·`SPEC-GATEWAY-001` 통독.** 나도 하지 않았다. 작성자의 «미확인» 공개가 적절한지만 판정했고, 그 안에 실제로 무엇이 있는지는 모른다. 1회차 §5의 같은 Gap 이 그대로 유효하다.
- **F-A8 11자리의 «참인가» 판정.** 소유/종결 축을 받아들이면 참이라고 판단했으나, 11자리를 한 줄씩 읽어 각각이 그 축과 정확히 맞는 문장인지는 대조하지 않았다. `grep` 으로 목록만 뽑았다.
- **`t15` 큐 카드 본문.** 이번에도 조회하지 않았다. B-4 의 불일치는 문서 기록 판독이다.
- **타이밍 부채널.** REQ-009 가 이제 «타이밍 무의존» 을 요구하지만 그것을 재는 AC 는 없다. 문서가 그 사실을 「잔여 위험」에 적었고, 나도 재지 않았다.

## 10. 잔여 위험

- **구조 처방이 [HARD] 인 대가.** `plan.md` §F M3-3 은 SPEC 이 HOW 를 규정하는 자리다. 문서가 그 대가를 인정하고 탈출구를 남겼다 — «구현이 더 나은 분리 구조를 찾으면 **변이 N 의 기대값이 유지되는 한** 그것을 택해도 된다». 탈출구의 조건이 관측 가능한 성질이라는 점이 좋으나, 그 판단을 내리는 주체가 run 단계이고 그것을 검사하는 것은 O 뿐이다 — N-03 이 O 를 모호하게 두면 이 탈출구가 위험해진다.
- **`deferWelcome` 에 여섯 기준이 걸린다.** 순서가 깨지면 여섯이 함께 붉어지고, 원인이 방어가 아니라 하네스라는 것을 알려면 「잔여 위험」 문단을 읽어야 한다. 문서가 그렇게 적었으므로 감춰진 위험은 아니나, 단일 실패점인 것은 사실이다.
- **REQ-009 의 타이밍 무의존 절에 관측이 없다.** L-04 를 닫으면서 함수 이름을 조항에서 뺐고, 그 결과 조항의 절반이 코드 리뷰에만 의존한다. 문서가 그것을 적었고 1회차의 판단과 같다.
- **형제 계약 개정이 미결인 채 run 이 시작되면** 카드 `t4` → `t9` 가 밟은 경로(«개정되지 않은 SPEC 과 실제 동작의 괴리» 로 sync 에서 되돌아옴)를 반복한다. `plan.md` §B-1·§B-2 가 차단으로 서 있는 것이 유일한 방어다.
- **이 워크트리는 미푸시다.** 브랜치 `WT-rogue-frame-defense` 의 작업과 두 형제 SPEC 개정이 이 나무에만 있다.
