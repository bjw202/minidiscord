# SPEC-LIVEENV-001 — 수용 기준

## 이 문서가 지키는 검증 원칙

이 저장소가 실제로 반복해 온 실패 부류 다섯을 기준마다 명시적으로 피한다.

1. **위조자가 실제 공격자보다 약하면 기준은 공허하다.** `status` 의 음성 대조군은 합성한 가짜가 아니라 **실제로 일어났던 사고**를 재현한다 — 무관한 프로세스가 같은 포트를 잡은 상태(`SPEC-LIVEVERIFY-001/progress.md:135`).
2. **셸 명령으로만 재는 기준은 동작을 통째로 지워도 초록이다.** 추출기의 각 기준은 셸 관측과 **인프로세스 회귀**를 짝으로 갖는다.
3. **부재 주장에는 대기 상한과 양성 대조군이 같은 증거 파일 안에 있어야 한다.**
4. **판별자가 상수 함수인지는 변이로 확인한다.** 각 기준은 「무엇을 망가뜨리면 빨개지는가」를 스스로 적고, `evidence/M01-mutation.txt` 가 그 실측을 담는다.
5. **「검사할 것을 찾지 못함」과 「검사해서 통과」는 다른 값이다.** 이 카드가 그 구별을 만들면서 스스로 그 결함을 재생산하면 아무것도 닫히지 않으므로, `AC-LIVEENV-004` 가 그 구별 자체를 잰다.

## Given-When-Then 시나리오

### AC-LIVEENV-001 — 스크립트가 자기 트리에 고정된다

- **Given** `scripts/live-env.sh` 가 놓인 트리와 다른 디렉터리에서 셸이 시작된 상태다.
- **When** 임의의 디렉터리에서 절대 경로로 `scripts/live-env.sh paths` 를 실행한다.
- **Then** 출력된 서버 디렉터리·데이터 디렉터리·봇 디렉터리·채널 `dist` 경로가 **전부 이 워크트리 아래**이며, 호출 셸의 작업 디렉터리는 실행 전후로 같다.
- **측정**
  ```
  ( cd /tmp && "$WT/scripts/live-env.sh" paths ) | tee evidence/E01-tree-pin.txt
  grep -cE '^[a-z_]+=' evidence/E01-tree-pin.txt        # 분모 — 출력된 경로 줄 수
  grep -cE "^[a-z_]+=$WT" evidence/E01-tree-pin.txt      # 분자 — 이 트리 아래인 줄 수. 분모와 같아야 한다
  grep -cE "^[a-z_]+=/Users/byunjungwon/Dev/my-project-04/minidiscord/scripts" evidence/E01-tree-pin.txt   # → 0 (기본 체크아웃 경로 부재)
  ```
- **[HARD] 분모를 내는 명령이 있어야 한다 — 두 수를 사람이 세지 않는다.** `paths` 는 경로를 `key=value` **한 줄씩** 찍고(형식을 여기서 못박는다), 위 첫 두 명령의 출력이 **같은 수**여야 한다. v0.1.0 은 분자만 명령으로 내고 분모를 「출력된 경로 줄 수」라는 산문으로 두었는데, 그러면 경로 줄이 넷인데 셋만 트리 아래인 경우를 **사람이 세어 비교**해야 한다 — 이 문서가 `AC-LIVEENV-007` 에서 금지한 것과 같은 부류다(1회차 감사 D15).
- **변이로 판별력을 확인한다** `git rev-parse --show-toplevel` 유도를 `pwd` 로 바꾸면 `/tmp` 가 뿌리가 되어 이 기준이 빨개진다. 그 diff 와 빨간 출력을 `M01-mutation.txt` 변이 ①로 남긴다.
- **[HARD] 미관측 조건** `paths` 가 아무 것도 찍지 않으면(스크립트 오류) 이 기준은 통과가 아니라 미관측이다 — 빈 출력에 `grep -c` 를 걸면 분모·분자가 모두 0 이라 우연히 「같다」가 성립한다. **분모가 `0` 이면 그 사실을 먼저 적고 미관측으로 처분한다.**

### AC-LIVEENV-002 — `up`/`down` 이 자기 프로세스만 다룬다

- **Given** 서버가 떠 있지 않다.
- **When** `up` → `status` → `down` → `status` 를 순서대로 실행한다.
- **Then** ㉠ `up` 이 상태 파일에 포트·데이터 디렉터리·봇 파일 뿌리·pid 를 적는다 ㉡ `down` 뒤 그 pid 가 사라진다 ㉢ **`down` 은 상태 파일이 적은 pid 만 신호를 받는다.**
- **측정**
  ```
  scripts/live-env.sh up      >> evidence/E02-lifecycle.txt
  cat "$STATE_FILE"           >> evidence/E02-lifecycle.txt   # port·data_dir·bot_files_dir·pid 네 열쇠
  PID=$(json port/pid 읽기);  ps -p "$PID" -o pid,command     >> evidence/E02-lifecycle.txt
  scripts/live-env.sh down    >> evidence/E02-lifecycle.txt
  ps -p "$PID" >/dev/null; echo "after-down exit=$?"          >> evidence/E02-lifecycle.txt   # → exit=1
  ```
- **[HARD] 남의 프로세스를 죽이지 않는 것은 부정형이므로 양성 대조군을 같은 파일에 둔다.** 상태 파일의 `pid` 를 **살아 있는 무관한 프로세스**(예: `sleep 600` 로 띄운 것)의 pid 로 바꾼 뒤 `down` 을 실행하고, ㉠ 그 프로세스가 **여전히 살아 있고** ㉡ `down` 이 「이 트리의 서버가 아니다」를 사유로 거부한 출력이 같은 파일에서 읽힌다. 대조군이 없으면 「아무 것도 안 하는 `down`」도 이 기준을 통과한다.

### AC-LIVEENV-003 — `status` 가 응답 코드가 아니라 세 축으로 판정한다

- **Given** `up` 으로 서버가 떠 있고 방·봇·초대가 세워진 상태다.
- **When** `status` 를 실행한다.
- **Then** 출력이 세 축을 각각 이름과 함께 싣고, 각 줄이 그 축의 측정 여부를 함께 싣는다: `listen_pid_cwd=<경로> measured=yes` · `db_rows=<수> measured=yes` · `principal=<봇이름>:api=<online 불리언>:conn=<확립 접속 수> measured=yes`. 세 축이 모두 이 트리의 값과 일치할 때만 통과다.
- **[HARD] `principal` 은 두 면을 함께 싣는다 — 형식이 결정을 조용히 뒤집지 못하게 한다.** `api=` 는 방의 초대 목록 `online` 필드(웹 API 를 거친다), `conn=` 은 같은 시각의 **확립 접속 수**(API 를 거치지 않는다)다. 한 면만 담는 `principal=<봇이름:online>` 형식은 **쓰지 않는다** — 그 형식은 두 면을 함께 읽기로 한 결정(`spec.md` REQ-003 ㉢)을 형식 차원에서 되돌린다.
  - **왜 두 면인가** — 형제 기준 `AC-LIVEVERIFY-012` 가 이미 둘 다 필요하다고 판정했다(㉠㉡ 은 API 면, ㉢ 은 접속 면). 그리고 `online` 은 게이트웨이의 `isOnline(roomId, botId)` 를 그대로 내보내는 값인데(`server/src/routes-bots.ts:103`), 그 함수는 그 방·그 봇으로 붙은 소켓이 **하나라도** 있으면 참이다(`server/src/gateway.ts:355-358` — `for (const c of conns.values()) if (c.roomId === roomId && c.botId === botId) return true`). 즉 **어느 프로세스가 붙었는지는 말하지 않는다** — 「이 실행이 띄운 봇 세션이 붙었다」와 「그 봇의 자격을 쥔 **다른** 프로세스(예: 낡은 토큰을 `export` 한 리드 세션)가 붙었다」를 가르지 못한다. t32 를 오염시킨 혼동이 정확히 그 모양이다. `conn=` 이 그 자리에 프로세스 면의 수를 놓는다.
  - **치르는 값** `status` 가 무거워지고, `lsof` 가 없는 환경에서 `2`(재지 못함)로 끝나는 경로가 넓어진다. **그 확장은 옳은 거동이지 회귀가 아니다** — 못 잰 것을 못 쟀다고 말하는 자리가 늘어난 것이다.
- **[HARD] 음성 대조군 — 실제로 일어났던 사고를 재현한다.** `down` 으로 서버를 내린 뒤, **같은 포트를 무관한 프로세스가 잡게** 하고(`python3 -m http.server <포트>` 한 줄) `status` 를 다시 실행한다. 그 실행은 **통과를 내서는 안 된다** — `listen_pid_cwd` 가 이 트리의 서버 디렉터리가 아니므로 `1`(실패) 또는 `2`(재지 못함)여야 한다. 같은 파일 안에 ㉠ 통과 실행 ㉡ 이 음성 실행 둘이 함께 있어야 한다.
  - **왜 이 대조군인가** — `SPEC-LIVEVERIFY-001/progress.md:135` 가 기록한 실제 사고가 바로 이 모양이다(remotion 프로세스가 `*:3000` 점유). 합성한 가짜보다 약하지 않다.
- **측정** `evidence/E03-status-axes.txt` 가 두 실행의 출력 전문과 각 실행의 종료 코드를 담는다. 대조군 프로세스는 관측 직후 종료하고 종료 확인 줄도 같은 파일에 남긴다.

### AC-LIVEENV-004 — 「재지 못함」이 「통과」와 다른 값으로 나온다

- **Given** 서버가 정상으로 떠 있어 `status` 가 `0` 을 내는 상태다(양성 기준선).
- **When** `status --unmeasured-paths` 가 **스스로 찍은** 「재지 못함」 경로 목록을 분모로 삼아, 그 목록의 **각 경로**를 하나씩 성립시킨 뒤 `status` 를 실행한다. 최소한 아래 여섯이 그 목록에 있어야 한다.
  1. ㉠ 축 · 도구 부재 — `PATH` 를 `lsof` 가 없는 값으로 좁혀 실행한다.
  2. ㉡ 축 · 파일 부재 — 상태 파일의 DB 경로를 존재하지 않는 경로로 바꾼다.
  3. ㉢ 축 · 조회 실패 — 초대 목록 조회가 실패하도록 상태 파일의 포트를 닫힌 포트로 바꾼다.
  4. ㉠ 축 · **부분 측정** — `lsof` 는 있고 LISTEN pid 도 잡히지만 그 pid 의 cwd 를 읽지 못한다.
  5. ㉡ 축 · **부분 측정** — DB 파일은 있으나 대상 테이블이 없다.
  6. ㉢ 축 · **부분 측정** — 초대 목록이 `200` 으로 오되 **비어 있다**(어느 봇도 실리지 않았다).
- **Then** 모든 실행이 **종료 코드 `2`** 이고, 출력이 **재지 못한 축의 이름**과 그 축의 `measured=no` 를 싣는다. 어느 하나라도 `0` 이면 이 기준은 실패다.
- **[HARD] 전칭을 재려면 분모를 스크립트에서 받아야 한다.** `REQ-LIVEENV-004` 는 「세 축 중 **어느 하나라도** 측정이 성립하지 않으면」이라는 **전칭**이다. 그런데 실걸이할 경로를 이 문서가 손으로 셋만 골라 적으면 전칭이 아니라 **표본 셋**을 잰 것이고, 이 저장소는 「표본 일치는 목록 크기를 세우지 않는다」로 그 부류를 이미 기록했다. 그래서 목록을 내는 주체를 스크립트로 옮긴다 — `status --unmeasured-paths` 의 출력 줄 수를 `N` 이라 하면 `evidence/E04-tristate.txt` 는 **`N` 건의 실행**을 담아야 하고, 실행 수가 `N` 보다 적으면 이 기준은 통과가 아니라 **미관측**이다. 위 여섯은 목록의 **하한**이지 목록 자체가 아니다.
  - **[HARD] 이 전칭의 범위를 정직하게 적는다 — 「모든 미측정 경로」가 아니라 「스크립트가 신고한 미측정 경로 전부」다.** 분모를 스크립트로 옮긴 것은 「문서가 표본 셋을 손으로 고른다」는 결함을 옳게 닫았지만(1회차 감사 D15), 그 대가로 남는 성질이 있다 — **스크립트가 모르는 미측정 경로는 목록에도 나오지 않으므로 이 기준에 보이지 않는다.** 이 기준을 「미측정 경로가 하나도 남지 않았다」의 증거로 읽어서는 **안 된다**. 그럼에도 이 기준이 공허로 가지 않는 이유는 목록의 **내용에 하한이 박혀 있기** 때문이다 — 위 여섯과 아래 엣지 케이스 넷, 합쳐 **열 자리**가 [HARD] 로 목록에 있어야 하고 그 열은 실제로 재어진다. 스크립트가 그중 하나를 빠뜨리면 이 기준이 빨개진다(2회차 감사 A-3).
- **[HARD] 부분 측정이 이 기준의 중심이다.** 「도구가 아예 없다」는 쉬운 경우이고, 실제로 `0` 이 새는 자리는 **재기 시작했으나 값을 얻지 못한** 상태다(4·5·6). 그 셋이 목록에 없으면 `status` 는 「절반만 재고 통과」를 낼 수 있고, 그것이 이 카드가 겨눈 결함의 원형이다.
- **[HARD] 엣지 케이스가 이 목록 안에 있어야 한다.** `E-1`(`up` 이 잡은 포트를 그 사이 남이 가져감)·`E-2`(승인 프롬프트에서 멈춤)·`E-3`(대화 기록 후보 다수)·`E-5`(실행 중 전역 항목 변경) 넷은 전부 「재지 못함」이므로 `--unmeasured-paths` 목록에 **이름이 있어야 하고**, 각각의 처분은 종료 코드 `2` 다. 엣지 케이스 표에만 있고 어느 기준도 걸지 않는 상태를 이 조항이 닫는다.
- **[HARD] 이 기준의 판별력은 반대 방향 변이로 확인한다.** 스크립트에서 「측정 불가 → `2`」 분기를 지우고 관례대로 `0` 을 내게 만든 변이를 넣으면 위 실행이 전부 `0` 이 되어 이 기준이 빨개져야 한다. 변이 diff·빨간 출력·복원 후 초록을 `M01-mutation.txt` 변이 ②로 남긴다.
- **측정** `evidence/E04-tristate.txt` — `status --unmeasured-paths` 의 출력 전문(분모 `N`) + 양성 기준선 1건 + `N` 건 각각의 명령·출력·`echo "exit=$?"`.
- **미관측이 아니라 실패인 경우** 세 실행 중 하나가 `1`(재서 실패)을 내면 그것도 실패다. `1` 은 「쟀고 틀렸다」인데 실제로는 재지 못했으므로, 값이 사실을 잘못 말한 것이다.

### AC-LIVEENV-005 — 토큰이 파일 한 곳에만 놓이고 그 파일은 커밋되지 않는다

- **Given** 방과 봇이 세워져 있다.
- **When** `scripts/live-env.sh invite <방> <봇>` 을 실행한다.
- **Then** ㉠ 표준출력에 64자 hex 가 **없고** `token_head=`·`issued_at=` 두 줄만 있다 ㉡ 토큰 파일의 권한이 `600` 이다 ㉢ 그 경로가 버전 관리에서 제외된다 ㉣ **`token_head=` 가 남긴 앞 8글자와 토큰 파일 내용의 앞 8글자가 같다**(전문은 어느 쪽에도 남기지 않는다) ㉤ **봇 작업 디렉터리도 버전 관리에서 제외된다**.
- **측정** — 토큰 파일은 `data/live-env/token` 이다(`spec.md` §7 10번).
  ```
  scripts/live-env.sh invite 1 pm > evidence/E05-token-file.txt 2>&1
  grep -cE '[0-9a-f]{64}' evidence/E05-token-file.txt              # → 0
  stat -f '%Lp' data/live-env/token  >> evidence/E05-token-file.txt   # → 600
  git check-ignore -v data/live-env/token >> evidence/E05-token-file.txt; echo "exit=$?" >> evidence/E05-token-file.txt   # → exit=0 (무시됨)
  # ㉣ 양성 대조군 — 이름표로 고르고 앞 8글자끼리만 맞댄다. 위치로 고르지 않는다
  cut -c1-8 data/live-env/token > /tmp/le-head-file
  sed -n 's/^token_head=//p' evidence/E05-token-file.txt > /tmp/le-head-out
  test "$(wc -l < /tmp/le-head-out)" -eq 1; echo "head-lines exit=$?" >> evidence/E05-token-file.txt   # → exit=0 (이름표가 정확히 한 줄)
  diff /tmp/le-head-file /tmp/le-head-out >> evidence/E05-token-file.txt; echo "exit=$?" >> evidence/E05-token-file.txt   # → exit=0 (같다)
  # ㉤ 봇 작업 디렉터리의 무시 — `.gitignore` 한 줄(REQ-009)의 효과를 잰다
  git check-ignore -v bot-01/.mcp.json >> evidence/E05-token-file.txt; echo "exit=$?" >> evidence/E05-token-file.txt      # → exit=0 (무시됨)
  ```
- **[HARD] ㉣ 가 이 기준의 양성 대조군이다 — 이 문서의 검증 원칙 3 이 요구하는 자리다.** ㉠ 은 **부재 주장**이라 `invite` 가 아무 것도 하지 못하고 조용히 끝나도 `grep -cE '[0-9a-f]{64}'` 는 `0` 을 내어 통과 방향으로 읽힌다. ㉡·㉢ 은 **파일이 만들어졌는가·추적되지 않는가**를 잴 뿐 **그 파일에 이번 초대의 토큰이 들었는가**를 재지 않는다. ㉣ 이 「이번 실행이 실제로 발급해서 그 파일에 넣었다」를 세운다. 앞 8글자만 맞대므로 전문 비노출은 유지된다 — `AC-LIVEENV-006` ㉡ 과 `AC-LIVEVERIFY-001` ㉢ 이 같은 규율을 쓴다. v0.1.0 은 이 자리를 비워 두었고 DoD 3 의 양성 대조군 목록에서도 빠져 있었다(1회차 감사 D7).
- **[HARD] ㉣ 는 값을 위치가 아니라 이름표로 고른다 — 그래서 출력 순서에 걸리지 않는다.** v0.2.0 은 `grep -oE '\b[0-9a-f]{8}\b' … | head -1` 로 「파일에서 **처음 나온** 8자리 16진수」를 골랐는데, 같은 파일에는 `invite` 가 함께 찍는 **발급 시각**이 있고 `20260906` 같은 8자리 숫자열은 `[0-9a-f]{8}` 에 글자 그대로 걸린다(실측: `echo "20260906" | grep -oE '[0-9a-f]{8}'` → `20260906`). 시각이 토큰 앞 8글자보다 먼저 찍히면 이 대조는 토큰이 아니라 **시각을 맞대고**, `diff` 가 `exit≠0` 을 내어 **옳은 구현에서 기준이 빨개진다** — 공허해지는 방향은 아니지만 판별자가 재려는 것과 다른 것을 재는 형태다(2회차 감사 B-4). 그래서 `REQ-LIVEENV-005` 가 `invite` 의 출력을 `token_head=`·`issued_at=` **두 `key=value` 줄**로 못박고, 이 대조는 `sed -n 's/^token_head=//p'` 로 이름표를 집는다. `AC-LIVEENV-001` 이 `paths` 의 형식을 못박아 분모를 명령으로 낸 것과 **같은 처방**이며, 형제 자리에 같은 규율을 준 것이다.
  - **`head-lines` 줄이 함께 필요한 이유** — 이름표가 없거나(형식 위반) 둘 이상이면 `sed` 출력이 0줄 또는 2줄이 되는데, 0줄일 때 `diff` 는 **빈 파일 대 한 줄**을 비교해 `exit≠0` 을 내므로 우연히 옳은 방향으로 실패한다. 그러나 그 실패는 「토큰이 다르다」로 읽혀 사유를 감춘다. 줄 수를 먼저 재어 **형식 위반과 값 불일치를 가른다.**
- **[HARD] ㉤ 는 이 카드가 편집하는 저장소 설정 파일 둘 가운데 첫째를 잰다.** `.gitignore` 의 `bot-01/` 한 줄은 계획이 지시하지만(`plan.md` M3), v0.2.0 에서는 **어느 요구사항도 어느 기준도 그것을 걸지 않았다**(2회차 감사 B-2). 실측으로 그 전제는 참이다 — `git check-ignore -v bot-01/.mcp.json` 은 지금 `exit=1` 을 내며, 그 줄이 없으면 세션 작업 디렉터리가 추적 대상으로 들어와 `AC-LIVEENV-011` 의 `git grep` 훑기 정의역까지 넓어진다. **검사 가능한 조건에 실행 주체를 붙였다.** 둘째(루트 `package.json`)는 `AC-LIVEENV-016` 이 진다.
- **변이** 토큰 파일 경로를 추적되는 디렉터리(예: `.moai/state/`)로 옮기면 `git check-ignore` 가 `exit=1` 을 내어 이 기준이 빨개진다 — `M01-mutation.txt` 변이 ③.
- **왜 `data/` 아래인가 (리드 처분)** `data/` 는 이미 `.gitignore` 2행에 있어 **`.gitignore` 편집 없이** 추적에서 빠진다(실측: `git check-ignore -v data/live-env/token` → `.gitignore:2:data/` · `exit=0`). 부작용 — 데이터 디렉터리를 통째로 지우는 정리 절차가 토큰도 함께 지운다 — 은 **의도된 것이다**: t32 의 사고 부류가 「낡은 토큰을 3회 다시 썼다」였고, 데이터와 토큰이 함께 죽으면 낡은 토큰이 살아남아 다시 쓰일 자리가 없어진다.
- **[HARD] 이 기준이 재는 것은 「파일에 놓였다」이지 「토큰이 안전하다」가 아니다.** §6 위협 모형의 `ps eww` 잔여는 이 기준이 닫지 않는다.

### AC-LIVEENV-006 — 세션 실행이 토큰을 명령행·이력·표준출력에 남기지 않는다

- **Given** 토큰 파일이 있고 채널 `dist` 가 빌드되어 있다.
- **When** `scripts/live-env.sh bot` 으로 세션을 띄운다.
- **Then** 셋이 함께 성립한다. ㉠ 그 세션 프로세스의 **명령행 인자**(`ps -o command`)에 64자 hex 가 없다 ㉡ 그 세션의 **환경**(`ps eww`)에는 `MINIDISCORD_TOKEN` 이 **있다** — 주입이 실제로 일어났다는 양성 확인이다 ㉢ 실행 출력에 64자 hex 가 없고, **셸 이력 파일의 64자 hex 줄 수가 이 실행 전후로 같다**(증분 0).
- **[HARD] ㉢ 의 판정 대상은 절대값이 아니라 이 실행이 만든 증분이다 — 기준선을 명시적으로 둔다.** v0.3.0 은 「셸 이력 파일에 64자 hex 가 없다」로 적었으나 **인도 시점에 이미 거짓이었다**: run 단계 실측으로 `~/.zsh_history` 에 그 패턴을 담은 줄이 **19건** 있고, 전부 t32 시절의 `export MINIDISCORD_TOKEN=…` 이다(이 카드가 만들지 않았고 이 카드가 지울 자리도 아니다 — 셸 이력은 저장소 밖이며 §5 가 편집을 금한다). 절대 0 을 판정선으로 쓰면 이 기준은 **이 카드가 무엇을 하든 영구히 빨갛고**, 그러면 「이번 실행이 토큰을 이력에 남겼는가」라는 이 기준이 실제로 재려던 것을 아무도 재지 않게 된다. 그래서 판정은 **before/after 두 수의 동일성**이다 — 이 실행이 한 줄이라도 남기면 after 가 커져 빨개진다.
  - **절대값은 판정선이 아니되 증거에는 남긴다.** 기계의 과거(19건)를 지우면 나중 회차가 「원래 0 이었다」고 오독한다.
- **측정** `evidence/E06-bot-launch.txt` 가 세 관측을 담는다. ㉡ 의 출력은 **값을 앞 8글자로 가려** 기록한다.
  ```
  HIST_BEFORE=$( cat ~/.zsh_history ~/.bash_history 2>/dev/null | grep -cE '[0-9a-f]{64}' )   # 기준선 (실측 19)
  scripts/live-env.sh bot --observe   >> evidence/E06-bot-launch.txt 2>&1
  HIST_AFTER=$(  cat ~/.zsh_history ~/.bash_history 2>/dev/null | grep -cE '[0-9a-f]{64}' )
  test "$HIST_BEFORE" -eq "$HIST_AFTER"; echo "hist-delta-zero exit=$?"   # → exit=0 (증분 0)
  grep -cE '[0-9a-f]{64}' evidence/E06-bot-launch.txt                      # → 0 (실행 출력의 전문 노출)
  ```
- **반대 방향 변이로 판별력을 확인한다** — 증분 판정이 「증분이 있어도 통과」로 무뎌지지 않았음을 보여야 한다. 이력 파일에 가짜 64자 hex 한 줄을 **덧붙인 뒤** 위 대조를 실행하면 `hist-delta-zero exit=1` 이 나와야 한다. 관측 직후 그 줄을 되돌리고, 되돌린 것을 같은 증거 파일에서 보인다 — `M01-mutation.txt` 변이 ⑦.
- **[HARD] ㉡ 을 빼면 이 기준은 공허하다.** 세션을 아예 띄우지 않아도 ㉠·㉢ 은 성립하기 때문이다. ㉡ 이 「띄웠고 토큰이 갔다」를 세우는 양성 대조군이다.
- **[HARD] ㉡ 은 동시에 잔여의 증거다** — 같은 사용자가 `ps eww` 로 읽을 수 있다는 사실이 여기서 그대로 관측된다. 이 카드는 그것을 닫았다고 **주장하지 않는다**(REQ-008).
- **이 절이 장차 빨개지는 방향을 미리 적어 둔다 — 지금은 고치지 않는다.** ㉡ 이 재는 **의도**는 「토큰이 자식 프로세스에 실제로 전달됐다」이고, 오늘 그 의도를 관측하는 수단이 `ps eww` 다. `SPEC-CHANWIRE-001`·`SPEC-CHANAUTH-001` 이 채널을 파일에서 토큰을 읽게 고치면(`spec.md` §5 가 그 소유를 그 SPEC 들에 넘겼다) 환경변수가 사라지면서 이 절은 **잔여가 닫혔다는 이유로** 빨개진다 — 개선을 벌하는 기준이다(1회차 감사 D13). 그때의 처분은 **관측 수단을 바꾸는 것**이지 절을 지우는 것이 아니다(예: 채널이 게이트웨이에 붙었다는 관측으로 대체). **오늘 바꾸지 않는 이유**: 오늘의 사실은 `channel/src/index.ts:121` 이 환경변수만 읽는 것이고(F-3), 아직 오지 않은 변경에 맞춰 기준을 미리 느슨하게 적으면 **오늘 재던 것을 오늘 놓친다.**

### AC-LIVEENV-007 — 토큰 소재 목록이 전건이고 실행된다

- **Given** `spec.md` §7 의 열두 행이 있다.
- **When** `scripts/live-env.sh token-sweep` 을 실행한다.
- **Then** 훑기 출력이 §7 의 **행 수와 같은 수의 자리**를 보고하고, 각 자리마다 「자리 이름 · 실행한 명령 · 적중 수」 셋을 싣는다.
- **측정**
  ```
  scripts/live-env.sh token-sweep > evidence/E07-inventory.txt

  # ① 개수 — 진단용. §7 표만 겨눈다
  grep -c '^site=' evidence/E07-inventory.txt                                             # → 12
  awk '/^## 7\. 토큰 소재 목록/,/^## 8\./' .moai/specs/SPEC-LIVEENV-001/spec.md \
    | grep -cE '^\| [0-9]+ \|'                                                            # → 12

  # ② 이름 집합 — 판정은 이쪽이다. 출력이 비어야 통과다
  sed -n 's/^site=\([a-z_]*\).*/\1/p' evidence/E07-inventory.txt | sort -u > /tmp/le-sites-sweep
  awk '/^## 7\. 토큰 소재 목록/,/^## 8\./' .moai/specs/SPEC-LIVEENV-001/spec.md \
    | sed -n 's/^| [0-9]\{1,\} | `\([a-z_]*\)` |.*/\1/p' | sort -u > /tmp/le-sites-table
  comm -3 /tmp/le-sites-sweep /tmp/le-sites-table | tee -a evidence/E07-inventory.txt | wc -l   # → 0
  ```
- **[HARD] 판정은 ②(이름 집합)이고 ①(개수)은 진단이다.** 개수만 맞추면 한 자리가 빠지고 다른 자리가 둘로 쪼개져도 통과한다(이 저장소의 「이름 집합이지 개수가 아니다」 교훈). **그리고 그 [HARD] 를 실행할 명령이 실제로 있어야 한다** — v0.1.0 은 이름 집합 대조를 산문으로만 못박고 실행 가능한 것은 개수 명령 하나만 남겨, run 단계가 쥘 수 있는 유일한 도구가 [HARD] 가 금지한 바로 그 개수 대조였다(1회차 감사 D4). `comm -3` 이 그 대조를 명령으로 내리고, **출력이 비어 있다**가 판정이다.
- **[HARD] ① 의 범위를 §7 로 좁힌 이유 — 인도 시점에 이미 틀린 값이었다.** v0.1.0 의 `grep -c '^| [0-9]* |' spec.md` 는 파일 **전체**를 세어 `19` 를 냈다(기준이 요구하는 값은 `12`). 차이 7건은 §3 D1 의 「카드 문언 일곱 자리」 표로, 그 표도 첫 열이 번호라 같은 정규식에 걸린다. 게다가 그 형태는 이 문서 어디에든 번호 열을 가진 표가 하나 더 생기면 값이 또 움직인다 — **자기 문서의 무관한 편집에 판정이 흔들리는 형태**다. `awk` 로 §7~§8 사이만 잘라 그 부류를 닫았다.

### AC-LIVEENV-008 — 상시 소재의 평문 토큰이 0건이다

- **Given** 봇 세션이 떠 있고 토큰이 실제로 쓰이는 중이다(부재가 「아무도 안 쓴다」 때문이 아님을 세우는 양성 대조군).

- **[HARD] 무편집의 판별자는 파일의 수정 시각이 아니라 `minidiscord-channel` 항목의 내용이다.** v0.3.0 은 실행 전후 `stat -f %m` 두 값의 동일성으로 무편집을 보이라고 적었으나, run 단계 실측이 그 판별자를 반증했다 — 그 파일은 **Claude Code 자신이 세션 기동·종료 때 쓴다**(관측: 평소 시각은 고정인데 `bot` 이 세션을 띄우는 순간 `1788630392` → `1788630396`). 즉 시각은 「항목이 바뀌었다」가 아니라 「세션이 떴다」를 재고, 하필 이 카드의 `bot` 단계가 정확히 세션을 띄우므로 **정상 실행이 늘 빨개진다.** 항목 내용(`args`·`env`)은 그 실행 동안 한 글자도 바뀌지 않았다. 같은 처방을 엣지 `E-5` 와 추출기에도 적용한다(추출기는 이미 내용 대조로 구현돼 있다).

- **측정** `evidence/E08-ambient-sweep.txt` — 여섯 자리의 명령·출력·적중 수 + `principal` 줄 + 아래 항목 내용 대조.

### AC-LIVEENV-009 — 봇 세션의 채널 왕복이 봇 디렉터리 `.mcp.json` 에서 온다

### AC-LIVEENV-010 — 추출기가 세 표면에서 다섯 항을 만든다

- **Given** 합성 fixture 셋(세션 jsonl · DB 파일 · 프로세스 목록 출력)이 `server/test/fixtures/` 에 있다.

  | 프로세스 신원 | 예행(`AC-LIVEENV-014`) | 예행이 진짜 프로세스를 만든다 |
  | **봇 세션 대화 기록 jsonl** | **실 세션 한 번(M8)이 단독으로 진다** | 예행은 `REQ-014`·`AC-LIVEENV-014` ㉢ 에 따라 Claude 세션을 **띄우지 않는다**. 세션이 없으면 jsonl 이 생기지 않으므로 예행은 그 파서를 **한 줄도 밟지 않는다** |

### AC-LIVEENV-011 — 산출물 어디에도 토큰 전문이 없다

- **Given** 추출기와 예행과 실 세션 한 번이 끝나 증거가 착지한 상태다.
- **When** 산출 디렉터리 전체와 추적되는 저장소 파일을 64자 hex 로 훑는다.
- **Then** ㉠ 이 카드가 만든 산출 디렉터리의 적중이 **절대 0건**이고, ㉡ 추적되는 저장소 파일의 적중이 **이 카드 이전과 같다**(증분 0).
- **[HARD] 두 측정의 판정선이 서로 다르며, 그것이 옳다.** ㉠ 의 정의역(`evidence/`)은 **이 카드가 새로 만드는 디렉터리**라 절대 0 이 옳은 판정선이다. ㉡ 의 정의역(추적되는 저장소 전체)은 **이 카드 이전부터 0 이 아니다** — run 단계 실측으로 **36건**이 적중하고, 전건 열거해 확인한 결과 전부 정당한 SHA-256 이다(`.moai/state/verify/**` 의 변이·검증 기록 31 · `.moai/specs/**` 2 · `.moai/reports/**` 의 CI 로그 2 · `.moai/manifest.json` 의 `template_hash` 꼴 1). 토큰은 하나도 없다.
  - **`package-lock.json` 제외와 같은 부류를 v0.3.0 이 다 세지 못했다.** 그 제외의 근거는 「npm 무결성 해시가 64자 hex 를 정당하게 담는다」였는데, 같은 성질의 자리가 `.moai/` 아래에도 있었다. **그렇다고 그 경로들을 제외 목록에 넣지는 않는다** — 제외를 넓히면 그 안에 실제로 토큰이 새도 이 기준이 침묵한다. 대신 **정의역은 그대로 두고 판정선을 증분으로 옮긴다**: 새로 생긴 적중 파일이 하나라도 있으면 빨개진다.
  - **이것이 「제외는 부류이지 자기 면제가 아니다」를 어기지 않는 이유**: 이 SPEC 자신의 파일도 정의역 안에 그대로 있고, 이 카드가 그 안에 토큰을 남기면 `comm -13` 이 그 파일 이름을 낸다.
- **측정** — `<BASE>` 는 `progress.md` §E.2 가 귀속시킨 리터럴 SHA 다.
  ```
  # ㉠ 이 카드의 산출 — 절대 0
  grep -rEl '[0-9a-f]{64}' .moai/specs/SPEC-LIVEENV-001/evidence/ ; echo "exit=$?"   # → exit=1
  # ㉡ 추적 파일 — 증분 0. 절대값은 함께 남기되 판정선이 아니다
  git grep -lE '[0-9a-f]{64}' -- . ':!package-lock.json' | wc -l                     # 절대값 (기준선 36)
  git grep -lE '[0-9a-f]{64}' <BASE> -- . ':!package-lock.json' | sed 's/^<BASE>://' | sort > /tmp/le-hex-before
  git grep -lE '[0-9a-f]{64}' HEAD   -- . ':!package-lock.json' | sed 's/^HEAD://'   | sort > /tmp/le-hex-after
  comm -13 /tmp/le-hex-before /tmp/le-hex-after | tee -a evidence/E11-no-full-token.txt | wc -l   # → 0
  ```
- **[HARD] 양성 대조군은 두 벌이다 — 측정이 둘이기 때문이다.** 정규식이 애초에 아무것도 잡지 못하는 형태였다면 「0건」은 검사가 아니라 침묵이다. 그런데 `git grep` 은 **추적되는 파일만** 본다 — 추적되지 않는 임시 파일 하나만 세우면 `git grep` 쪽 정규식은 대조군 없이 남아, 두 명령 중 **하나만** 그 침묵을 배제한다(1회차 감사 D14). 그래서 둘을 각각 세운다.
  - ㉠ **추적되지 않는** 임시 파일에 가짜 64자 hex 한 줄 → `grep -rEl` 이 적중 1건.
  - ㉡ **`git add` 로 스테이징한** 임시 파일에 같은 한 줄 → `git grep -lE` 이 적중 1건이고, **`comm -13` 이 그 파일 이름을 낸다**(증분 판정도 함께 빨개진다).
  - 관측 직후 되돌린다(`git rm --cached` + 파일 삭제). 되돌린 것을 같은 증거 파일의 마지막 줄에서 `git status --porcelain` 으로 보인다.
  - **㉡ 이 곧 증분 판정의 반대 방향 변이다** — 「증분이 있어도 통과」로 무뎌지지 않았음을 이 한 번의 관측이 함께 보인다. `M01-mutation.txt` 변이 ⑨.
- `package-lock.json` 제외 근거: npm 무결성 해시가 64자 hex 를 정당하게 담는다. **제외는 부류이지 자기 면제가 아니다** — 이 SPEC 자신의 파일은 제외하지 않는다.

- **측정** `evidence/E14-dry-run.txt` — 예행 표준출력 전문 · 산출 파일 목록 · 두 `pgrep` 출력(예행 중 `0`) · **양성 대조군 두 줄(`1` 이상)과 그 프로세스의 종료 확인** · 종료 코드.

### AC-LIVEENV-015 — `SPEC-LIVEVERIFY-001` 이 한 글자도 바뀌지 않았다

- **Given** 이 카드 착수 직전의 커밋을 기준선 `<BASE>` 로 잡는다(run 단계가 그 SHA 를 이 문서에 적고, 이후 모든 측정이 그 리터럴을 쓴다).
- **When** 착지 후 diff 를 뜬다.
- **Then** 그 경로의 변경이 **0건**이다.
- **측정**
  ```
  git rev-parse --short <BASE>                                             # 기준선 생존 가드 — 비면 이 기준은 미관측
  git diff --name-only <BASE>..HEAD -- .moai/specs/SPEC-LIVEVERIFY-001/ | wc -l   # → 0
  git status --porcelain -- .moai/specs/SPEC-LIVEVERIFY-001/ | wc -l              # → 0 (미커밋 변경도 없다)
  ```
- **[HARD] 기준선 생존 가드가 필요한 이유** 이 저장소는 `$BASE` 가 비어 `HEAD..HEAD` 로 해석돼 **무조건 초록**이던 결함을 이미 겪었다(`SPEC-E2E-001` 감사 N-01). 변수 대신 **리터럴 SHA** 를 쓰고, 그 SHA 가 실제로 해소되는지를 먼저 잰다.
- **두 명령이 모두 필요한 이유** 첫째는 커밋된 변경을, 둘째는 작업 트리의 미커밋 변경을 잡는다. 하나만으로는 「커밋 안 했으니 0건」이 성립한다.

### AC-LIVEENV-016 — 형제 기준 `AC-E2E-016` 이 여전히 초록이다

- **Given** 이 카드가 `scripts/` 에 새 파일을 놓았고, 그 디렉터리가 `AC-E2E-016` 의 훑기 범위다(실측 F-11).
- **When** `AC-E2E-016` 의 **무조건 측정 넷**을 그 문서에 적힌 명령 그대로 다시 실행한다.
- **Then** ① `exit=1` · ①-b `7` **이하** · ①-c `0` · ② `exit=1` — 네 값이 모두 그 문서가 못박은 판정을 만족한다. 다섯째 측정 ③ 은 **「해당 없음」**이다.
- **[HARD] 측정은 넷이 아니라 다섯이고 범위가 서로 다르다 — 형제 원문에 대고 확인했다**(`SPEC-E2E-001/acceptance.md:214-245`). ①·①-b 는 `README.md` `scripts/` `.moai/specs/SPEC-E2E-001/` 셋을 범위에 넣고, ①-c 는 `README.md` `scripts/` 둘, **② 는 `scripts/` 하나뿐이다** — `README.md` 는 ② 의 범위가 **아니다**. ③ 은 `README.md` 의 수동 체크리스트 절 안을 조건부로 재며, 이 카드는 체크리스트를 싣지 않으므로 「해당 없음」으로 명시한다(형제 문서가 `:245` 에서 그 처분을 허용하되 **①②는 그대로 돈다**고 못박았다).
  - v0.1.0 은 이 자리를 「네 측정이 `scripts/` 와 `README.md` 를 범위에 넣는다」로 적어 **② 의 범위를 넓게, 측정의 수를 적게** 옮겼다(1회차 감사 D12). 오류의 방향이 보수적이라 기준이 공허해지지는 않았지만, **실측했다고 제시된 사실이 실제와 다른 것 자체가 결함이다** — 측정 ③ 의 존재를 SPEC 이 모르면 run 단계는 그것이 「해당 없음」인지 「빠뜨린 것」인지 판단할 근거가 없다.
- **①-b 의 판정은 등가가 아니라 상한이다.** 형제 문서가 `:226` 에서 그렇게 못박았다 — `7` **초과**면 누군가 새 주장을 면제로 덮은 것이므로 조사하고, **미만은 빨강이 아니다**(그 SPEC 자신의 인용 문장을 줄이면 값이 정당하게 내려간다).
- **[HARD] 이 기준은 형제 SPEC 을 편집해 만족시키지 않는다.** `SPEC-E2E-001` 도 `completed` 다. 값을 맞추는 방법은 **이 카드의 산출물 쪽 문언을 고치는 것**뿐이다 — 특히 `scripts/` 아래 새 파일의 주석에 「실 세션으로 확인」류 문구나 `AC-016-EXEMPT` 표지를 쓰지 않는다.
- **[HARD] 이 기준은 루트 `package.json` 의 기존 열쇠가 바뀌지 않은 것도 함께 잰다 — 이 카드가 편집하는 저장소 설정 파일 둘 가운데 둘째다.** 예행은 루트 `package.json` 에 실행 스크립트 **한 줄**로 걸리는데(REQ-014 · `plan.md` M6), v0.2.0 은 그 편집을 계획만 지시하고 **어느 기준도 재지 않았다**(2회차 감사 B-2). 기존 `test`·`e2e` 는 품질 게이트와 형제 기준이 딛는 자리이므로, 한 줄을 **더하는 것**과 있는 줄을 **바꾸는 것**을 갈라야 한다.
  ```
  git diff -- package.json | grep -cE '^[-+][[:space:]]*"(test|e2e)":'   # → 0 (두 열쇠의 값이 그대로다)
  git diff --stat -- package.json                                        # 더해진 줄이 하나임을 눈으로 확인할 자리
  ```
  첫 명령이 `0` 이 아니면 기존 열쇠가 움직인 것이며 이 기준은 실패다. 첫째 설정 파일(`.gitignore` 의 `bot-01/` 한 줄)은 `AC-LIVEENV-005` ㉤ 가 진다.
- **측정** `evidence/E16-sibling-e2e016.txt` — 네 명령과 각 출력·종료 코드, 위 `package.json` 두 명령의 출력, 그리고 `git status --porcelain -- .moai/specs/SPEC-E2E-001/ | wc -l` → `0`.
- **왜 이 기준이 필요한가** 이 저장소는 「계약 개정이 형제 하네스를 빠뜨린다」를 반복 기록했다. 새 파일을 놓는 디렉터리가 남의 기준의 정의역일 때, 그 사실을 SPEC 안에 기준으로 내리지 않으면 run 단계가 알 방법이 없다.
