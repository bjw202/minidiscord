## 1. 배경과 목적

minidiscord 에서 사람이 방에 쓴 메시지는 **전부** 봇에게 가지 않는다. 방에 봇이 셋 붙어 있어도 사람끼리의 잡담까지 세 세션이 모두 받아 읽으면, 각 세션의 컨텍스트가 자기 일과 무관한 대화로 가득 찬다. 그래서 `spec-v2.md` 2장은 **멘션 없는 메시지는 봇에게 전달하지 않는다**를 기능 요구사항으로 못 박았다.

그 판정을 하는 것이 이 SPEC 이 만드는 함수 하나다. 메시지 본문 문자열을 받아, 누구에게 전달할지와 그 전달이 **응답 의무가 있는지**를 돌려준다.

| 형식 | 뜻 |
|------|-----|
| `@TO(봇이름)` | 그 봇에게 전달하고, 그 봇은 **응답할 의무가 있다** |
| `@CC(봇이름)` | 그 봇에게 전달하지만, 그 봇은 **응답하지 않는다** (참고용) |
| 멘션 없음 | 어떤 봇에게도 전달하지 않는다 |

이 함수가 작아 보이는데도 별도 SPEC 인 이유는 **소비자가 둘**이기 때문이다. 같은 카드 `t3` 안에서 게이트웨이(Task 8)와 메시지 API(Task 9)가 이 함수의 반환 타입에 직접 결합한다. 타입을 나중에 바꾸면 두 곳이 함께 바뀐다. 그래서 반환 타입은 여기서 확정되고, §4.2 에 그대로 적힌다.

`plan-v2.md` 의 파일 구조 주석도 같은 말을 한다 — *"`mention.ts` 는 순수 함수로 분리해 파서만 단독 테스트한다."* 순수 함수라는 것이 이 SPEC 의 설계 제약이지 우연이 아니다. DB 도 네트워크도 보지 않으므로, 파서 테스트는 서버를 띄우지 않고 문자열만 넣어 돌릴 수 있다.

근거 문서: `.moai/plan/2026-08-26-minidiscord/plan-v2.md` Task 6 및 파일 구조, `spec-v2.md` 2장(기능 요구사항)·6장(게이트웨이 프로토콜)·7장(사람 → 봇 흐름).

## 2. 용어

| 용어 | 뜻 |
|------|-----|
| 멘션 | 메시지 본문 안의 `@TO(이름)` 또는 `@CC(이름)` 한 조각 |
| 봇 이름 | 멘션의 `(` 와 `)` 사이 문자열. 괄호와 공백이 없는 1자 이상 |
| delivery | 그 멘션이 요구하는 전달 방식. `'to'`(응답 의무) 또는 `'cc'`(응답 금지) |
| 순수 함수 | 같은 입력에 항상 같은 출력을 내고, 외부 상태를 읽거나 쓰지 않는 함수 |
| 스텁 | 시그니처만 맞고 본문이 비어 있는 가짜 구현. 이 SPEC 의 수용 기준은 스텁을 통과시키지 않아야 한다 (§7) |

## 4. 요구사항 (GEARS)

### 4.1 멘션 인식

**REQ-MENTION-001** (Ubiquitous)
멘션의 형식은 정확히 `@TO(이름)` 과 `@CC(이름)` 두 가지여야 한다. 키워드 `TO` / `CC` 는 **대문자**이고, 이름은 여는 괄호와 닫는 괄호 사이의 문자열로서 **괄호(`(`, `)`)와 공백 문자를 포함하지 않는 1자 이상**이어야 한다.

**REQ-MENTION-002** (When — 이벤트 구동)
본문에서 형식에 맞는 멘션이 감지되면, 함수는 그것을 **본문에 나타난 순서 그대로** 결과에 담아야 한다. 같은 봇이 여러 번 언급되면 **중복을 합치지 않고 전부** 담아야 한다 — `@TO(coder)` 와 `@CC(coder)` 는 delivery 가 서로 다른 별개의 멘션이므로, 합치면 응답 의무 정보가 사라진다.

**REQ-MENTION-005** (Ubiquitous)
봇 이름은 ASCII 로 제한되지 않아야 한다. 한국어 이름(`@TO(코드리뷰어)`)이 ASCII 이름과 동일하게 인식되어야 한다. 봇 이름은 사람이 UI 에서 붙이는 이름이고 이 프로젝트의 UI 문구는 한국어다.

### 4.2 반환 타입 계약 (교차 태스크)

**REQ-MENTION-003** (Ubiquitous)
`server/src/mention.ts` 는 다음 두 가지를 **이 시그니처 그대로** 내보내야 한다.

```ts
export interface Mention {
  bot: string
  delivery: 'to' | 'cc'
}

export function parseMentions(body: string): Mention[]
```

세 가지가 계약의 핵심이며 하나라도 다르면 소비자가 깨진다.

| 항목 | 확정 값 | 왜 고정하는가 |
|------|---------|--------------|
| 반환은 **배열** | `Mention[]` | 한 메시지가 봇 여럿을 언급할 수 있다 (`spec-v2.md` 2장 "복수 지정을 허용한다"). 단일 객체 반환은 그 요구사항을 표현할 수 없다 |
| `delivery` 는 **리터럴 유니온** | `'to' \| 'cc'` | Task 8 게이트웨이가 `message` 이벤트의 `delivery` 필드에 그대로 실어 보낸다 (`spec-v2.md` 7장). `string` 으로 넓히면 세 번째 값이 조용히 흘러 들어간다 |
| 키워드→값 사상 | `TO`→`'to'`, `CC`→`'cc'` (소문자) | 프로토콜 표면의 값이 소문자로 확정돼 있다 |

이 계약의 소비자는 카드 `t3` 안의 Task 8(게이트웨이)과 Task 9(메시지 API)다. 두 태스크가 이 SPEC 과 같은 카드에 있으므로, 여기서 확정하지 않으면 두 곳이 서로 다른 가정으로 짜인다.

### 4.3 배제와 경계

**REQ-MENTION-004** (Unwanted — shall not)
아래 후보는 결과에 들어가서는 안 된다.

| 입력 조각 | 왜 배제되는가 |
|-----------|--------------|
| `@pm` | 괄호가 없다. 평문 `@이름` 은 멘션이 아니다 |
| `@토(pm)` | 키워드가 `TO` / `CC` 가 아니다 |
| `@to(pm)` | 키워드가 소문자다 (REQ-MENTION-001 이 대문자로 한정) |
| `@TO()` | 이름이 0자다 |
| `@TO( )` | 이름에 공백이 있다 |

**REQ-MENTION-006** (Unwanted — shall not)
`parseMentions` 는 순수 함수여야 한다. 파일·네트워크·DB·전역 변수를 읽거나 써서는 안 되고, `server/src/mention.ts` 는 프로젝트 내부 모듈이든 외부 패키지든 **아무것도 import 해서는 안 된다**.

특히 이 함수는 **봇의 존재 여부를 검증하지 않는다.** `@TO(없는봇)` 도 그대로 `{ bot: '없는봇', delivery: 'to' }` 로 파싱된다. `spec-v2.md` 8장이 "알 수 없는 봇 멘션은 서버가 거부하고 안내"라고 적었으나, 그 판정은 등록된 봇 목록을 알아야 하므로 DB 를 읽는 호출자(Task 9 메시지 API)의 몫이다. 파서가 그것을 하면 순수 함수가 아니게 된다 — §9 2번 참조.

**REQ-MENTION-007** (Unwanted — shall not)
이 SPEC 의 구현은 `server/src/mention.ts` 와 `server/test/mention.test.ts` 두 파일만 만들어야 하며, `server/src` 의 기존 파일을 **한 줄도** 고쳐서는 안 된다. 특히 `server/src/db.ts` 의 `SCHEMA` 상수와 `server/src/index.ts` 의 조립 코드를 건드리지 않는다. 이 파서를 실제로 배선하는 것은 Task 9(메시지 API)이지 이 SPEC 이 아니다.

## 5. 범위 밖 (Exclusions)

아래 항목은 이 SPEC 에서 **만들지 않는다**. 각 항목에 소유자를 명시한다.

### Out of Scope — 파서를 호출하는 쪽 (Task 9, 메시지 API)

- `server/src/routes-messages.ts` — 메시지 전송(multipart)·목록·다운로드 라우트
- 파싱 결과를 실제 전달로 옮기는 배선. 이 SPEC 은 문자열 → 구조체 변환까지만 하고, 그것으로 무엇을 하는지는 모른다
- **알 수 없는 봇 멘션의 거부와 안내** (`spec-v2.md` 8장). 등록된 봇 목록 조회가 필요하므로 DB 를 아는 호출자의 몫이다
- 멘션 텍스트를 본문에서 지우거나 표시용으로 바꾸는 일. 저장되는 본문은 원문 그대로다

### Out of Scope — 봇에게 실제로 보내는 쪽 (Task 8, 게이트웨이)

- `server/src/gateway.ts` — WebSocket 서버, `hello { token }` 인증, 방 구독
- `message` 이벤트의 `delivery` 필드 전송. 이 SPEC 은 그 필드에 들어갈 **값의 타입**을 정할 뿐 전송하지 않는다
- 봇 온라인/오프라인 판정, 놓친 메시지 재전송(`missed_after_id`)

### Out of Scope — 웹 UI (카드 `t5`)

- 입력창의 **봇 자동완성** (`spec-v2.md` 2장). 사용자가 `@TO(` 를 치면 등록된 봇을 제안하는 기능은 브라우저 쪽이며, 등록 봇 목록을 알아야 한다
- 이미 보낸 메시지에서 멘션을 강조 표시하는 렌더링

### Out of Scope — 파서 기능 심화

- 멘션 형식의 확장 — `@ALL`, `@here`, 별칭, 공백 포함 이름의 따옴표 표기. 원본 `plan-v2.md` Task 6 의 형식이 전부이고, 늘리려면 소비자 둘이 함께 바뀐다
- 대소문자 무시 매칭(`@to(pm)` 허용). REQ-MENTION-004 가 명시적으로 배제한다
- 코드 블록·인용 안의 멘션을 무시하는 문맥 인식 파싱. 마크다운 파서가 필요해지고, 이 함수의 순수성·단순성과 맞바꿀 만한 가치가 지금은 없다
- 봇 이름 중복·유효성 검사, 정규화(공백 제거·소문자화)

## 6. 제약

- Node.js 20 이상, TypeScript strict 모드, `module: NodeNext`. 상대 import 는 `.js` 확장자를 붙인다 (이 SPEC 의 소스 파일 자체는 import 가 없다 — REQ-MENTION-006).
- 이 SPEC 은 **새 의존성을 추가하지 않는다.** 구현은 `RegExp` 와 `String.prototype.matchAll` 만 쓴다.
- 테스트 프레임워크는 vitest. 실행 명령은 워크스페이스 루트에서 `npm test -w server`.
- 코드 주석은 한국어 (`code_comments: ko`).
- 커밋 메시지는 영어 관례(`feat:`, `test:`).
- 원본 `plan-v2.md` Task 6 의 테스트 본문과 구현 스켈레톤을 규범으로 삼는다. 테스트 이름은 그 문서의 것을 그대로 쓴다 — 수용 기준이 그 이름을 관측 대상으로 지목하기 때문이다.

## 7. 수용 기준

수용 기준 전체는 `acceptance.md` 에 있다. 각 기준은 **명령 하나와 관측 가능한 결과 하나**로 이루어진다.

이 SPEC 의 수용 기준에는 추가 규범이 하나 걸려 있다. **스텁을 통과시키는 기준은 기준이 아니다.**

```ts
export function parseMentions(_body: string): Mention[] { return [] }   // 스텁
```

본문이 빈 이 구현에 대해서도 통과하는 검사는 아무것도 검증하지 못한다. 특히 "형식에 맞지 않는 것을 배제한다"류의 부정 기준은 기대값이 `[]` 라서 스텁에게 자동으로 통과된다 — 이 SPEC 에서 가장 빠지기 쉬운 함정이다. 그래서 모든 부정 기준은 **같은 입력 문자열 안에 정상 멘션을 하나 섞어** 두고, 그 하나가 잡히는 것까지 함께 단언한다. `acceptance.md` 의 「스텁 대조」 표가 기준별로 어떤 잘못된 구현을 잡아내는지 명시한다.

## 9. 원본 문서 사이의 모순

작성 중 근거 문서 사이에서 모순 3건을 찾았다. 전부 이 SPEC 에서 해소했고, 근거를 남긴다.

### 1. 멘션 표기 — 공백형 대 괄호형

`spec-v2.md` 는 같은 문서 안에서 두 표기를 쓴다.

| 위치 | 표기 |
|------|------|
| 2장 기능 요구사항 | `@TO <봇>` — 공백으로 이름을 잇는 형태 |
| 4-A 컴포넌트 표 | `@TO(봇)` / `@CC(봇)` — 괄호 형태 |

**괄호형으로 확정한다.** `plan-v2.md` Task 6 이 정규식(`/@(TO|CC)\(([^()\s]+)\)/g`)과 테스트 여섯 개로 괄호형을 구체화했고, 공백형은 서술 한 줄뿐이다. 게다가 공백형은 이름의 끝을 판정할 수 없다 — `@TO 코드 리뷰어 봐줘` 에서 이름이 `코드` 인지 `코드 리뷰어` 인지 결정하는 규칙이 어디에도 없다. 괄호형은 닫는 괄호가 그 경계를 준다. REQ-MENTION-001 이 괄호형이다.

### 2. 알 수 없는 봇 멘션의 거부 — 파서의 일인가

`spec-v2.md` 8장 에러 처리 표는 *"알 수 없는 봇 멘션 | 서버가 거부하고 안내"* 라고 적는다. 이것을 파서가 하면 등록된 봇 목록을 알아야 하고, 그러면 DB 를 읽게 되어 `plan-v2.md` 파일 구조가 요구한 **순수 함수** 제약이 깨진다.

**모순이 아니라 층위 문제로 해소한다.** "서버가 거부"의 주어는 파서가 아니라 메시지 API(Task 9)다. 파서는 문자열에서 이름을 뽑기만 하고, 그 이름이 실재하는지는 DB 를 아는 호출자가 판정한다. REQ-MENTION-006 과 §5 에 소유자를 명시했다.

### 3. 리드 지시와 `plan-v2.md` 의 파일명·반환 타입 불일치

이 SPEC 작성 지시는 파일을 `server/src/mentions.ts`(복수형), 반환을 `{ bot, delivery }`(단일 객체)라고 적었다. `plan-v2.md` 는 둘 다 다르게 적는다.

| 항목 | 리드 지시 | `plan-v2.md` | 채택 |
|------|-----------|--------------|------|
| 파일명 | `server/src/mentions.ts` | `server/src/mention.ts` | **`mention.ts`** |
| 반환 타입 | `{ bot, delivery }` | `Mention[]` | **`Mention[]`** |

**`plan-v2.md` 를 채택한다.** 파일명은 그 문서의 세 곳(파일 구조 트리, Task 6 Files, 테스트의 `import ... from '../src/mention.js'`)이 모두 단수형으로 일치한다. 반환 타입은 단일 객체로는 `spec-v2.md` 2장의 **"복수 지정을 허용한다"** 를 표현할 수 없다 — `@TO(pm) @TO(coder)` 를 하나의 `{ bot, delivery }` 로 담을 방법이 없다. 리드에게 보고한다.
