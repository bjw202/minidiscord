## 1. 배경 — 무엇이 관측됐나

`server/test/gateway.test.ts` 의 `history_request applies limit before since_id, speaker, since and until`(`:713`) 이 **전체 워크스페이스 병렬 실행(`moai gate`)에서만** 실패한다.

```
Error: Unexpected server response: 404      ← 접속 시도 약 7ms 뒤
```

관측 원본은 `.moai/reports/t37/sync-audit.md:179-194` 다. 그 자리가 함께 적는 실측은 이렇다 — **단독 실행 3/3 통과**, **게이트 2회차 exit=0**, **같은 head 의 CI 2건 SUCCESS**. 즉 이 실패는 재현이 어렵고 **스스로 꺼진다**.

### 1.1 이 카드가 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 404 를 **누가** 냈는지 관측으로 확정할 수 있는 **관측 설계**를 세운다 | 원인을 고르지 않는다. 경쟁 설명 둘 이상을 열어 둔 채 «무엇을 보면 갈라지는가» 만 적는다 |
| 그 관측이 실제로 잡히는 **재현 조건**(병렬/직렬 대조)을 규정한다 | **수리를 설계하지 않는다.** 응답자가 밝혀진 뒤가 수리의 자리다 |
| 각 수용 기준에 **그것을 깨뜨리는 변이**를 붙인다 | 부하를 인위로 만들지 않는다(§6 제약) |

### 1.2 종결 정의

이 SPEC 은 다음 둘이 함께 성립할 때 닫힌다.

1. 404 응답 하나 이상의 **원문 바이트**(상태 줄 · 헤더 전건 · 본문), **소켓 주소 양끝**, 그리고 **자기 앱 수신 카운터의 포획 구간 증감**이 기록으로 남았고, §5 의 지문표가 그 바이트를 **하나의 응답자 부류**로, 2차 판정이 그 카운터를 **하나의 갈래**로 기계로 사상했다.
2. 20회 대조 실행의 **병렬 N통과/M실패**와 **직렬 N'통과/M'실패**가 기록됐고, §5.2 의 세 갈래 규칙이 그 수를 하나의 분류로 사상했다.

**포획 0건은 통과가 아니다.** 20회 안에서 404 가 한 번도 나오지 않으면 판정은 `미관측`이며, `PASS` 로 적는 것을 이 SPEC 이 금지한다(AC-WSUPGRADE-009).

## 2. 용어와, 옮기지 말아야 할 전제

| 용어 | 뜻 |
|------|-----|
| 응답자 (responder) | 404 상태 줄을 실제로 소켓에 써 넣은 프로세스·서버 객체. 이 문서가 규명하려는 대상이며, 현재 **미상**이다 |
| 지문 (fingerprint) | 응답 바이트에서 응답자 부류를 가르는 관측 가능한 특징. 헤더 집합·본문 모양·상태 줄 |
| 병렬 팔 / 직렬 팔 | 같은 명령을 파일 병렬 스위치만 달리해 돌린 두 실행. §5.2 |
| 자기 포트 | 실패한 시험의 `build()` 가 돌려준 포트 값. 그 시험이 «내 것» 이라고 믿는 포트 |
| 자기 앱 수신 카운터 | 실패한 시험의 Fastify 앱이 **자기 프로세스 안에서** 센 요청 수. `onRequest` 훅 한 줄이 올리는 값이며, 포획 시점에 그 값이 올라갔는지가 «내 앱이 이 요청을 받았는가» 를 답한다. 소켓 주소가 아니라 **응답자 신원**을 재는 값이다 |

### 2.1 반증된 선행 판독 — 전제로 옮기지 않는다

`.moai/reports/t37/sync-audit.md:192` 는 이 실패를 «즉시 404 (서버가 아직 듣지 않는 상태)»[반증된-선행-판독] 로 적었다. **그 판독은 반증됐다.** 근거 둘을 직접 확인했다.

1. `server/test/gateway.test.ts:54` 가 `await app.listen({ port: 0 })` 이고, **그 다음 줄**에서 `app.server.address()` 로 포트를 읽어 돌려준다(`:55`). 리슨 완료가 포트 획득보다 앞선다. 실패한 시험(`:714-716`)은 그 돌려받은 포트로 접속한다.
2. **아무도 듣지 않는 포트는 ECONNREFUSED 를 낸다. 404 는 응답이다** — 응답이 왔다는 것은 그 포트에 **응답자가 있었다**는 뜻이다.

그러므로 이 문서의 어떤 요구사항·기준·계획도 «서버가 서기 전»[반증된-선행-판독] 을 전제로 세우지 않는다.

**표지 규약.** 이 어간은 이 SPEC 디렉터리 안에서 **언제나 고정 리터럴 토큰 `[반증된-선행-판독]` 을 같은 줄에 달고** 등장한다. 「반증」 같은 낱말을 표지로 삼지 않는 이유는 동의어와 의역이 새기 때문이고, 「규칙의 정의문은 면제」 같은 예외를 두지 않는 이유는 그 예외가 감시 대상 공간을 삼키기 때문이다. **면제는 0건이며, 이 문장 자신도 토큰을 단다.** `AC-WSUPGRADE-008` 이 이것을 훑기로 잰다.

## 3. 이 SPEC 이 근거로 삼은 측정 (F1~F6)

각 항목은 **명령 또는 파일 자리**를 이름으로 단다. 재확인은 이 나무(`.claude/worktrees/t39` @ `620af7a`)에서 했고, `node_modules` 가 없는 항목은 주 체크아웃(`/Users/byunjungwon/Dev/my-project-04/minidiscord`)에서 읽었다.

### F1 — `ws` 는 이 404 의 응답자가 될 수 없다

`node_modules/ws/lib/websocket-server.js`(ws **8.21.3**, 주 체크아웃에서 읽음)에서:

- `shouldHandle(req)` 는 `options.path` 와 요청 경로가 다르면 `false` 를 돌려준다(`:224-232`).
- `completeUpgrade` 는 `if (!this.shouldHandle(req)) { abortHandshake(socket, 400); return }` (`:277-280`).

**400 이지, 404 가 아니다.** 그리고 서버 쪽 `WebSocketServer` 는 `server/src/gateway.ts:98` 의 `new WebSocketServer({ server: app.server, path: '/bot' })` 하나뿐이다. 그러므로 **응답자는 `ws` 의 WebSocketServer 가 아니다.**

> 참고: t36 보고(`.moai/reports/t36/nonce-flake.md:§4`)는 이 자리를 «ws 는 경로 미스 시 응답 없이 무시한다(가설 등급)» 로 적었다. **그 가설은 이 소스 판독으로 정정된다 — 무시가 아니라 400 응답이다.** 결론(«응답자는 다른 무엇이다»)은 같은 방향으로 유지되지만, 근거가 바뀌었으므로 그 문장을 인용하지 않고 F1 을 인용한다.

### F2 — upgrade 리스너가 **0개**인 HTTP 서버는 업그레이드 요청을 평범한 HTTP 요청으로 답한다

통념은 «업그레이드 리스너가 없으면 소켓이 끊긴다(ECONNRESET)» 이다. **실행으로 반증했다.**

- 탐침: `.moai/reports/t39/probe-upgrade.mjs` (증거로 커밋됨)
- 출력: `.moai/reports/t39/probe-upgrade.log`

```
upgrade 리스너 수 = 0
--- 받은 응답 ---
HTTP/1.1 404 Not Found | Date: ... | Connection: keep-alive | Keep-Alive: timeout=5
```

**이 사실이 응답자 부류를 이름 짓는다 — «`/bot` 에 업그레이드 리스너를 달지 않은 HTTP 라우터».**

### F3 — 그런 서버가 server 스위트 안에 실재한다

`server/test/` 에서 `.listen(` 을 부르는 파일은 일곱이고, 그중 `createGateway` 를 한 번도 부르지 않는 파일은 **셋**이다.

```
$ grep -ln '\.listen(' server/test/*.ts      → gateway, permissions, restart-persistence, sse, room-members, web-visual, web-permission-contract
$ grep -ln 'createGateway' server/test/*.ts  → gateway, gateway-v2(하네스), permissions, messages, room-members, web-permission-contract
```

| 게이트웨이를 붙이는 파일 | 붙이지 않는 파일 (= `/bot` 업그레이드 리스너 없음) |
|---|---|
| `gateway.test.ts` · `permissions.test.ts` · `room-members.test.ts` · `web-permission-contract.test.ts` | **`sse.test.ts` · `restart-persistence.test.ts` · `web-visual.test.ts`** |

### F4 — 응답자를 볼 수 있는 관측 창이 이미 있다

`node_modules/ws/lib/websocket.js:929`:

```js
} else if (!websocket.emit('unexpected-response', req, res)) {
  abortHandshake(websocket, req, `Unexpected server response: ${res.statusCode}`);
}
```

`unexpected-response` 는 **던지기 전에** 발생하고, 두 번째 인자 `res` 는 날것 `IncomingMessage` 다. 그러므로 **상태 줄 · 헤더 전건 · 본문 · 소켓 주소 양끝**이 전부 읽힌다. 리스너를 달면 던짐도 가로챌 수 있다(`emit` 이 참을 돌려주면 `abortHandshake` 가 건너뛰어진다) — 관측을 먼저 남기고 나서 스스로 실패시키는 설계가 가능하다는 뜻이다.

지문이 응답자 부류를 가른다: Fastify 의 기본 404 는 특유의 JSON 모양이고, 맨 `http.createServer` 의 404 는 그렇지 않으며(F2 의 탐침 응답이 그 예다), 정적·Vite 계열의 404 는 HTML 이다.

### F5 — 병렬성의 모양

- 루트 `package.json:4,7` — `"workspaces": ["server","channel"]`, `"test": "npm test --workspaces --if-present"`.
- `server/package.json:7`, `channel/package.json:13` — 각각 `"test": "vitest run"`.
- `server/` 와 `channel/` 에 `vitest.config.*` 가 **없다**(`ls` 로 확인, 무결과). 그러므로 vitest 기본값이 적용되고, **테스트 파일들은 여러 워커에서 동시에 돌아간다.**
- 모든 앱이 `port: 0`(OS 임시 포트)으로 붙고 시험 끝에 닫히므로, **임시 포트가 계속 반납되고 재배정된다.**

한 가지 관측된 비대칭을 그대로 적는다 — 바인드 주소 인자가 파일마다 다르다.

| 자리 | 인자 |
|---|---|
| `gateway.test.ts:54`, `sse.test.ts:37`, `sse.test.ts:232` | `{ port: 0 }` (host 미지정 → Fastify 5 기본값) |
| `web-visual.test.ts:58`, `restart-persistence.test.ts:43` | `{ port: 0, host: '127.0.0.1' }` |

**이 비대칭이 어떤 결과를 낳는지는 이제 측정됐다 — F6 이 그 측정이다.**

### F6 — 두 바인드는 같은 포트 번호 위에 공존하고, 그 상태에서 관측된 404 서명이 그대로 재현된다

1회차 plan-audit 이 이것을 측정했고(`.moai/reports/t39/plan-audit.md` D1), 독립 탐침이 같은 결과를 재현했다(`.moai/reports/t39/probe-coexist.mjs` · 출력 `.moai/reports/t39/probe-coexist.log`). 셋으로 나눠 적는다.

**(1) Fastify 5 의 host 기본값은 `localhost` 이고, 그것은 두 번 바인드한다.** `node_modules/fastify/lib/server.js:32,66` 이 `host` 기본값을 `'localhost'` 로 두고, `:151-211`(`multipleBindings`)이 **두 번째 `http.Server`** 를 만들어(`:190` `getServerInstance`) 같은 포트의 남은 주소에 붙인 뒤 그 서버의 `upgrade` 사건을 주 서버로 넘긴다(`:206`). 두 번째 바인드의 실패는 **조용히 삼켜진다**(`:176-181`, `_ignoreErr` 폐기). 이 기계에서 `dns.lookup('localhost',{all:true})` 는 `::1` 을 먼저 돌려주므로, `{ port: 0 }` 앱의 **주 리스너는 `::1`** 이고 `127.0.0.1` 쪽이 삼켜질 수 있는 **부차 리스너**다.

**(2) 공존은 성립하며 한 방향뿐이다.** 게이트웨이 없는 앱을 `127.0.0.1:P` 에 **먼저** 붙이고 게이트웨이 있는 앱을 host 미지정으로 같은 P 에 붙이면 **둘이 공존한다**(뒤 앱의 주 리스너는 `::1:P`). 순서를 뒤집으면 `EADDRINUSE` 로 막힌다.

**(3) 그 상태에서 `ws://127.0.0.1:P/bot` 은 관측된 것과 같은 서명을 받는다.**

```
타앱(게이트웨이 없음) : {"address":"127.0.0.1","family":"IPv4","port":60971}
내앱(게이트웨이 있음)  : {"address":"::1","family":"IPv6","port":60971}
*** 상태 404 본문 {"message":"Route GET:/bot not found","error":"Not Found","statusCode":404}
```

**이 측정이 세우는 것과 세우지 않는 것을 갈라 적는다.** 세우는 것: 이 기제는 **기계적으로 재현된다**. 세우지 않는 것: 실제 게이트 실행에서 **누가 답했는지는 아무도 보지 않았고**, `{ port: 0 }` 이 이미 IPv4 로 잡힌 포트를 무는 **빈도도 재지 않았다**. 그러므로 이 측정은 §4 의 갈래를 하나로 좁히지 **않는다** — 가능성이지 발생 사실이 아니다(§7-3).

### 3.1 재지 않은 것

- `moai gate` 가 두 워크스페이스를 동시에 돌리는지 순차로 돌리는지 **확인하지 않았다.** npm 은 워크스페이스를 순차 실행하는 것이 기본이므로, 문제되는 동시성은 **server 워크스페이스 안**(gateway 대 sse/web-visual/restart-persistence)일 가능성이 크지만 이는 추론이고 관측이 아니다.
- 이 나무에는 `node_modules` 가 없어 **스위트를 한 번도 돌리지 않았다.** F1·F4 는 주 체크아웃의 소스 판독이고, F2 는 주 체크아웃에서 돌린 탐침이다.

## 4. 경쟁 설명 — 하나로 좁히지 않는다

t36(`.moai/reports/t36/nonce-flake.md:§4`)이 **포트 재할당 경합**을 후보로 올렸다. F2·F3·F5 는 그것을 **기계적으로 가능한** 이야기로 만든다 — 게이트웨이 없는 앱이 실재하고, 그런 앱은 404 로 답하며, 임시 포트는 계속 돌려 쓰인다.

**그러나 그 설명은 아직 한 자리에서 막힌다.** 실패한 클라이언트는 **자기 `build()` 가 방금 돌려준 포트**로 붙고, 그 앱은 게이트웨이를 붙인다. 살아 있는 리스너 둘이 같은 포트를 나눠 갖지 못하는 한, 「엉뚱한 앱에 닿았다」는 설명은 그 사실과 긴장한다. 이 SPEC 은 그 긴장을 문구로 덮지 않고 **열어 둔다.**

| 갈래 | 이야기 | 이것을 참으로 만드는 관측 |
|---|---|---|
| **H-1 포트 재배정** | 접속이 이 시험의 앱이 아닌 다른 앱(게이트웨이 없는 셋 중 하나)에 닿았고, **이 시험의 앱은 그 포트를 더는 들고 있지 않다** | 지문이 **Fastify** 이고, **자기 앱 수신 카운터가 오르지 않았으며**, 포획 시점에 자기 앱이 그 포트 번호를 들고 있지 않다(`app.server.listening === false` 또는 `app.server.address().port ≠ 자기 포트`) |
| **H-2 같은 포트 번호 위의 주소별 공존** | 두 리스너가 서로 다른 주소로 같은 포트 번호에 공존했고, `127.0.0.1` 로의 접속이 다른 앱 쪽 리스너로 갔다 | 지문이 **Fastify** 이고, **자기 앱 수신 카운터가 오르지 않았으나**, 포획 시점에도 자기 앱이 **그 포트 번호를 들고 있다**. F5 의 인자 비대칭이 씨앗이고, F6 이 이 기제를 실제로 재현했다 |
| **H-3 자기 앱이 답했다** | 응답자가 실제로 이 시험의 앱이며, 업그레이드가 게이트웨이에 닿기 전에 Fastify 404 로 처리됐다 | 지문이 Fastify 이고 **자기 앱 수신 카운터가 그 포획 구간에서 올랐다**. 이 갈래가 참이면 원인은 경합이 아니라 **배선 순서**다 |

**H-3 을 목록에 남기는 것이 중요하다.** H-1·H-2 는 둘 다 «다른 서버» 를 요구하지만, 같은 지문이 자기 서버에서도 나올 수 있다. **응답 바이트만으로는 셋이 같아 보이고, 소켓 주소로도 갈리지 않는다** — 자기 포트와 원격 포트는 TCP 정의상 항상 같고 주소 계열 대조는 이 스위트에서 상수이기 때문이다(F6·§5.4). 갈래를 가르는 것은 **자기 앱이 그 요청을 받았는가**뿐이다.

**한 가지 비대칭을 공시한다.** F6 은 H-1·H-2 의 기제가 재현 가능함을 보였고, H-3 의 성립 조건은 **아직 실행으로 시험되지 않았다** — `WebSocketServer` 가 `upgrade` 리스너를 이미 붙인 Fastify 서버(`server/src/gateway.ts:98`)가 `/bot` 업그레이드에 404 를 낼 수 있는 경로가 있는지는 미관측이다(§7-7). 그럼에도 H-3 을 지우지 않는 이유는 이 카드가 규명 카드이기 때문이다 — 시험되지 않은 갈래를 목록에서 빼는 것은 관측이 아니라 선택이다.

이 SPEC 은 어느 갈래도 참으로 적지 않는다. §5 의 관측이 이 표를 기계로 가르게 하는 것이 전부다.

## 5. 요구사항 (GEARS)

### 5.1 §A — 응답자 식별 (카드의 (ㄱ))

- **REQ-WSUPGRADE-001** — **When** server 스위트의 WebSocket 클라이언트가 101 이 아닌 핸드셰이크 응답을 받으면, 시험 하네스는 그 응답의 **상태 코드 · 상태 줄 · 헤더 전건 · 본문 전체**를 기록물로 남겨야 한다(shall).
- **REQ-WSUPGRADE-002** — **When** 같은 사건이 일어나면, 하네스는 다음 셋을 같은 기록에 남겨야 한다(shall): (가) **소켓 양끝**(`localAddress`·`localPort`·`remoteAddress`·`remotePort`와 각각의 주소 계열), (나) **자기 앱 수신 카운터**의 포획 구간 증감(`onRequest` 훅이 세는 값의 포획 전후 두 값), (다) **포획 시점의 자기 앱 포트 보유 상태**(`build()` 가 돌려준 자기 포트, `app.server.listening`, `app.server.address()`). (가)는 기록 항목이고, 갈래를 가르는 것은 (나)·(다)다(§5.4).
- **REQ-WSUPGRADE-003** — 하네스는 §5.4 의 지문표를 **기계로 평가 가능한 술어 목록**으로 들고 있어야 하며(shall), 기록된 바이트를 **정확히 하나의 응답자 부류**로 사상해야 한다. 어느 술어에도 걸리지 않는 응답은 `미분류`로 남기고 **추측으로 채우지 않는다**.
- **REQ-WSUPGRADE-004** — 하네스는 관측을 남긴 뒤 **원래의 실패를 그대로 재현해야 한다**(shall) — 관측이 시험을 초록으로 바꾸는 일은 없어야 한다.

### 5.2 §B — 재현 (카드의 (ㄴ))

- **REQ-WSUPGRADE-005** — **When** 재현 실행이 요청되면, 절차는 **병렬 팔과 직렬 팔**을 돌려야 한다(shall). 두 팔의 명령은 **파일 병렬 스위치 하나를 빼면 글자 그대로 같아야** 한다.
- **REQ-WSUPGRADE-006** — 각 팔은 **20회** 반복하고, `N 통과 / M 실패`를 팔별로 보고해야 한다(shall). (선례: t36 `.moai/reports/t36/nonce-flake.md:§2.3` 의 20회 보고 형식.)
- **REQ-WSUPGRADE-007** — 판정은 §5.5 의 **세 갈래**(「병렬에서만 실패」/「항상 실패」/「한 번도 실패하지 않음」) 중 하나여야 하며(shall), 규칙은 두 팔의 실패 수만으로 결정돼야 한다.
- **REQ-WSUPGRADE-008** — **When** 두 팔 합쳐 404 포획이 0건이면, 판정은 `미관측`이어야 한다(shall). 하네스는 그 경우를 `PASS` 로 사상해서는 **안 된다**(shall not).

### 5.3 §C — 규율

- **REQ-WSUPGRADE-009** — 이 SPEC 의 어떤 절차도 **배경 부하 프로세스를 스폰해서는 안 된다**(shall not). 경합이 진정 필요하면 **바깥에서 경계 지어진 수단**(테스트 프레임워크의 정리 훅에 등록된 종료, 또는 `timeout` 래퍼)만 허용되며, 뒤에 붙인 `kill` 한 줄은 정리가 아니다.
- **REQ-WSUPGRADE-010** — 이 SPEC 은 **수리를 설계하지 않는다**(shall not). 응답자가 밝혀지기 전의 어떤 코드 변경 제안도 이 범위 밖이다.
- **REQ-WSUPGRADE-011** — 이 SPEC 의 어떤 요구사항·기준도 **«서버가 아직 듣지 않는 상태»[반증된-선행-판독]를 전제로 삼아서는 안 된다**(shall not) — §2.1 에서 반증됐다. 그리고 이 어간이 등장하는 **모든** 줄은 고정 리터럴 토큰 `[반증된-선행-판독]` 을 같은 줄에 달아야 한다(shall) — 면제 0건.

### 5.4 지문 → 응답자 사상표

기록된 바이트를 아래 술어에 차례로 걸어 **첫 적중**을 응답자 부류로 삼는다.

| # | 술어 (기록된 응답에 대해) | 응답자 부류 | 이 부류가 뜻하는 것 |
|---|---|---|---|
| ① | 상태 400 **이고** `Sec-WebSocket-Version` 헤더가 있거나 본문이 비어 있다 | `ws` 의 WebSocketServer (경로 미스) | F1 의 경로다. **관측된 실패는 404 이므로 이 부류가 아니다** — 대조군으로 표에 남긴다 |
| ② | 상태 404 **이고** 본문이 `{"message":...,"error":"Not Found","statusCode":404}` 모양의 JSON | **Fastify 기본 404** | 게이트웨이 **없는** Fastify 앱이거나, 게이트웨이 있는 앱이 업그레이드를 라우터로 흘린 경우. H-1·H-2·H-3 이 여기서 갈린다 — **자기 앱 수신 여부가 가른다** |
| ③ | 상태 404 **이고** 본문이 JSON 이 아니며 헤더에 프레임워크 표지가 없다 | 맨 `http.createServer` | F2 탐침의 응답 모양 |
| ④ | 상태 404 **이고** `Content-Type` 이 `text/html` | 정적·Vite 계열 서버 | 스위트 밖 프로세스일 수 있다 |
| ⑤ | 위 어느 것에도 걸리지 않음 | `미분류` | 추측으로 채우지 않고 기록만 남긴다 |

**②가 적중했을 때의 2차 판정**(H-1/H-2/H-3 을 가르는 자리). 판별의 축은 **응답자 신원**이다 — 소켓 튜플이 아니라 «내 앱이 이 요청을 받았는가».

| # | 관측 (기록된 값에 대해, 차례로) | 갈래 |
|---|---|---|
| ㉮ | 포획 구간에서 **자기 앱 수신 카운터가 증가했다** | **H-3** (자기 앱이 답했다) |
| ㉯ | 증가하지 않았고, 포획 시점에 자기 앱이 그 포트 번호를 **더는 들고 있지 않다** (`app.server.listening === false` **또는** `app.server.address().port ≠ 자기 포트`) | **H-1** (포트가 다른 앱에 넘어갔다) |
| ㉰ | 증가하지 않았고, 포획 시점에도 자기 앱이 **그 포트 번호를 들고 있다** | **H-2** (같은 포트 번호 위의 주소별 공존) |
| ㉱ | 카운터 값이 기록되지 않았거나 포획 구간을 특정할 수 없다 | **`미분류`** — 추측으로 채우지 않는다 |

**버린 판별자와 그 이유를 남긴다**(같은 설계가 다시 제안되는 것을 막기 위해서다).

| 버린 관측 | 왜 못 쓰는가 |
|---|---|
| 원격 포트 대 자기 포트 대조 | 클라이언트가 자기 포트로 걸므로 소켓의 `remotePort` 는 **TCP 정의상 언제나 자기 포트와 같다.** 상수 「같음」이며 판별력 0 (`.moai/reports/t39/plan-audit.md` D1 관측 1) |
| 소켓 계열 대 `app.server.address().family` 대조 | 대상 시험은 `{ port: 0 }`(기본 호스트 → 주 리스너 `::1`)로 붙고 클라이언트는 리터럴 `127.0.0.1` 을 거므로, **경합이 전혀 없어도 언제나 불일치**다. 상수 「불일치」이며 판별력 0 (F6·`probe-coexist.log`) |

두 값은 **기록 항목으로는 그대로 남긴다**(REQ-002 (가)). 판별에 쓰지 않을 뿐, 나중에 다른 물음이 생겼을 때 되읽을 수 있어야 한다.

### 5.5 세 갈래 분류 규칙

병렬 팔 실패 `Mp`, 직렬 팔 실패 `Ms` (각 팔 20회):

| 조건 | 분류 |
|---|---|
| `Mp ≥ 1` **이고** `Ms = 0` | **병렬에서만 실패** |
| `Mp ≥ 1` **이고** `Ms ≥ 1` | **항상 실패** (병렬성은 원인이 아니다) |
| `Mp = 0` **이고** `Ms = 0` | **한 번도 실패하지 않음** → 이 실행은 `미관측`이며 `PASS` 가 아니다 |
| `Mp = 0` **이고** `Ms ≥ 1` | **뒤집힘** — 예상 밖이며 그대로 기록한다 |

## 7. 미검증 / Gaps

이 SPEC 을 쓰면서 **관측하지 않은 것**을 그대로 적는다.

1. **응답자를 아직 아무도 보지 못했다.** 이 문서 전체가 «어떻게 보는가» 이며 «누구였는가» 가 아니다.
2. **스위트를 이 나무에서 한 번도 돌리지 않았다**(C-3). 404 를 스스로 재현한 적이 없고, `.moai/reports/t37/sync-audit.md:179-194` 의 기록에 의존한다.
3. **F5 의 바인드 비대칭은 측정됐다(F6) — 그러나 닫힌 것은 「기제」뿐이다.** 측정 결과: Fastify 5 의 host 기본값은 `localhost` 이고 두 번 바인드하며(`node_modules/fastify/lib/server.js:32,66,151-211`), 두 바인드는 「IPv4 명시 먼저 → 기본 호스트 나중」 한 방향에서 같은 포트 번호 위에 공존하고, 그 상태에서 `ws://127.0.0.1:P/bot` 은 관측된 것과 같은 Fastify 404 를 받는다(`.moai/reports/t39/probe-coexist.mjs` · `.log`). **여기서 세워진 것은 「이 기제가 재현 가능하다」이지 「이것이 일어난 일이다」가 아니다.** 남은 미검증 셋 — (가) 실제 게이트 실행에서 **누가 답했는지 아무도 보지 않았다**, (나) `{ port: 0 }` 이 이미 IPv4 로 잡힌 포트를 무는 **빈도를 재지 않았다**(가능성은 확인했고 확률은 확인하지 않았다), (다) 모든 측정이 **Darwin 25.5.0 · Node v24.12.0 · fastify 5.12.1 · ws 8.21.3 한 기계**에서 나왔고 Linux·CI 에서 같은 규칙인지 재지 않았다. CI 에서 404 가 재현된 적이 없다는 관측(§1)과 함께 읽으면 (다)는 그 자체로 다음 회차의 관측 항목이다.
4. **`moai gate` 의 워크스페이스 동시성이 미확인이다**(§3.1). 문제되는 동시성의 범위를 아직 모른다.
5. **7ms 라는 시각이 무엇을 뜻하는지 재지 않았다.** 그것이 TCP 연결 성립부터인지 요청 전송부터인지, 그리고 그 값이 갈래를 가르는지 여부에 대한 관측이 없다.
6. **`gateway.test.ts:209` 의 기존 경로 격리 시험이 400 과 404 를 구별하지 않는다** — `error` 이벤트가 났는지만 본다. 즉 이 스위트는 지금까지 **응답 코드를 한 번도 재지 않았다**. 이것은 미검증 항목이자 §5 관측 설계의 필요 근거다.
7. **H-3 의 성립 조건을 실행으로 시험하지 않았다.** `WebSocketServer` 가 이미 `upgrade` 리스너를 붙인 Fastify 서버(`server/src/gateway.ts:98`)가 `/bot` 업그레이드 요청에 404 를 낼 수 있는 경로가 있는지 재지 않았다. 그러므로 H-3 을 「반증됐다」고 적지 않고 **시험되지 않은 갈래**로 열어 둔다(§4).
8. **「다른 앱」 역할에 실제 시험 파일을 쓰지 않았다.** F6 의 게이트웨이 없는 앱은 합성 Fastify 앱이었다. 실제 `sse` · `restart-persistence` · `web-visual` 앱을 띄워 확인한 것이 아니므로, 그 셋의 404 본문이 정말 Fastify 모양이라는 것은 **판독이 아니라 추론**이다(`plan.md` §B 도 같은 추론 위에 선다).
9. **AC-008 의 가드는 리터럴 두 구절에만 걸린다.** 훑기가 실제로 잡는 것은 고정 구절이고, 「포트만 잡히고 서버는 준비되지 않은」 같은 **의역은 기계로 잡히지 않는다.** 의역 누수는 사람이 읽는 검토 항목으로 남기며, 기준 이름도 재는 범위에 맞춰 좁혔다(`acceptance.md` AC-008).

## 8. 범위 밖 (exclusions)

### Out of Scope — 404 의 수리

- 응답자가 밝혀지기 전의 어떤 코드 변경도 담지 않는다. 재시도·대기·포트 고정·바인드 주소 통일 — 전부 후속 카드의 것이다.
- 이 SPEC 이 낼 수 있는 유일한 「고침」은 **관측 하네스의 추가**이며, 그것은 생산 코드가 아니다.

### Out of Scope — 다른 플레이크

- `channel/test/transport-auth.test.ts` 의 논스 건은 `t36` 이 이미 닫았다(`.moai/reports/t36/nonce-flake.md:§2.6`). 이 카드는 그 수리를 다시 열지 않는다.
- 두 건은 **다른 워크스페이스·다른 서명**이다(값 동일 실패 대 404). 하나의 원인으로 묶는 서술을 담지 않는다.

### Out of Scope — 부하 정량화

- 「부하가 끼임 확률을 얼마나 넓히는가」는 담지 않는다. C-1 이 그 실험 수단을 금지하기 때문이며, 그 하나로 충분하다. (t36 의 무부하 재현은 **다른 시험**의 관측이므로 이 배제의 근거로 들지 않는다 — C-1 의 괄호 참고.)

### Out of Scope — 스위트 전반의 포트 정책

- 임시 포트 대신 고정 포트를 쓰는 설계, 워커 수 제한, 파일 격리 정책 — 전부 수리 영역이며 이 카드 밖이다.
