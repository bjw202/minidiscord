### 세 갈래 결정에 대한 판단 — 셋 다 내 제안보다 낫거나 같다

1. **N3 을 헬퍼가 아니라 §B.6 에서 고친 것 — 내 제안보다 낫다.** 나는 「`cssRuleBlock` 에 마지막 매치 옵션」을 셋째 선택지로 제시했는데, 그 함수는 기존 호출 세 자리(`cssRuleBlock(css, '#auth-view')`·`'#auth-error'`·`'[hidden]'`)가 이미 의미에 기대는 **공유 자산**이다. 소비자 쪽 규약을 고치려고 공유 헬퍼의 동작을 바꾸는 것은 방향이 위험하다. `plan.md:230` 이 그 이유를 명시적으로 적었다 — `[HARD] **동작을 바꾸지 않는다.** … 기존 호출 세 자리가 그 의미에 기대고 있다.` 게다가 제자리 편집은 §B.6 의 원래 의도(덮어쓰기 층 금지)와 같은 방향이고, 산문에 그치지 않고 **AC-015 (4) 라는 기계적 가드**를 함께 세웠다.
2. **`[[:space:]]` 를 고른 것 — 옳다.** `\s` 는 POSIX ERE 에 없고 GNU 확장이다. 이 저장소는 darwin 이라 BSD `grep -E` 가 기본이고, 그 위에서 `\s` 는 보장되지 않는다. 오늘 열 0 인 앵커 셋까지 함께 바꾼 것도 비용 0 의 방어라 반대할 근거가 없다.
3. **`-t` 를 고치지 않고 버린 것 — 옳다.** 나는 2회차에 「vitest 가 필터 0개에서 어떤 종료 코드를 내는지 **측정하지 않았다**」고 적었다. 측정하지 않은 동작 위에 관측을 세우는 것은 이 저장소가 금지하는 **미관측 주장**이다. describe 실재를 따로 세고 파일 전체 종료 코드를 보는 형태는 관측이 둘로 늘어 오히려 강하다.

## 4. 남은 결함 — 전부 산문 요약의 수치 드리프트 (blocking 0)

세 라운드를 거치며 **규범 층(요구사항·명령·가드)은 정확한데 서술 층(요약·매트릭스·카운트)이 뒤처지는** 패턴이 생겼다. 다섯 건이고, 어느 것도 실행이나 판별력에 닿지 않는다.

### D1 — [minor / optional] `acceptance.md:84` 가 「여섯」이라 적고 **일곱을 열거한다**

> `이 SPEC 의 기준이 관측하는 선택자 가운데 `style.css` 에 **이미 있는** 것은 실측으로 여섯이다 — `.room-item`(…)·`.room-item.active`·`.archive-btn`·`.message:not(.turn-cont)`·`#autocomplete`·`.ac-kind.to`·`#msg-input`.`

세어 보면 일곱이고, `plan.md` §B.6 의 같은 문장은 **일곱**이라 옳게 적었다. 내 독립 대조도 일곱이다. `acceptance.md` 쪽 숫자만 갱신되지 않았다.

### D2 — [minor / optional] 「뒤 넷은 이 SPEC 이 바꾸지 않는 자리」가 **둘에 대해 거짓이다**

같은 문장(그리고 `plan.md` §B.6 의 마지막 실측 문단)이 `.message:not(.turn-cont)`·`#autocomplete`·`.ac-kind.to`·`#msg-input` 넷을 「바꾸지 않는 자리」로 묶는다. 둘이 틀렸다:

- **`#msg-input`** — REQ-WEBUI-009(`spec.md:263`)가 `background: none; border: none; outline: none` 을 **더하라고** 하고, N5 교정으로 **AC-010 이 바로 그 둘을 단언한다**(`acceptance.md:522-523`). 「바꾸지 않는 자리」가 아니라 §B.6 둘째 행(선언을 더하는 자리 → 제자리 편집)이다.
- **`.message:not(.turn-cont)`** — REQ-WEBUI-005 가 `border-top` 을 **없앤다.** §B.6 셋째 행이 그것을 명시적으로 열거하므로, 같은 문서가 스스로 반증한다.

**왜 blocking 이 아닌가.** 결론(일곱 다 첫 매치가 관측 대상)은 옳고, 그 결론을 떠받치는 것이 이 문장이 아니라 세 기계다: ① §B.6 둘째 행의 일반 규칙(「이미 있는 선택자에 선언을 더할 때 → 제자리」)이 `#msg-input` 을 이름 없이도 덮는다, ② AC-015 (4) 의 가드 정규식이 `#msg-input` 과 `.message:not(.turn-cont)` 를 **명시적으로 포함한다**(축자 확인), ③ REQ-009 자체가 무엇을 더하는지 목록으로 적는다. 구현자가 이 문장에 속아 끝 블록에 쓰더라도 (2)가 잡는다.

`audit-rubric-scope.md` §4(d) 대로 — 한 뜻으로 읽히면서 거짓인 문장이므로 Clarity 에서 깎지 않고 여기 적는다.

### D3 — [minor / optional] AC 매트릭스의 AC-016 칸이 **옛 앵커 형태**를 보여 준다

`acceptance.md:145` — `` 새 계약문 넷이 **주석 줄**(`^// …§5.1 — 꼬리는 줄이지 않는다` 등)로 각 1건 ``. 실행 블록(`:838`)은 `^[[:space:]]*//` 다. N1 교정이 명령은 고쳤고 요약 칸은 두고 갔다.

### D4 — [minor / optional] §5.3 은 **열 행**인데 두 곳이 「아홉 자리」라 적는다

`awk '/^### 5.3/,/^### 5.4/' spec.md | grep '^| '` → 헤더 1 + **데이터 10행**. 그런데 `plan.md:245` 와 `acceptance.md:866`(Definition of Done)이 「§5.3 표의 **아홉** 자리를 전부 열어 보고」라고 한다. 2회차에 아홉이었고 이번에 한 행이 늘었는데 두 참조가 따라오지 않았다. 실무 영향: 구현자가 아홉만 열고 하나를 빠뜨릴 여지.

### D5 — [minor / optional] `progress.md` 의 「부류 훑기」 요약 수치 셋이 내 재측정과 어긋난다

`progress.md:31` — `선언 중복 0건(24개 ts 블록 전수 파싱) … 행 번호 인용 0건. cssRuleBlock 대상 선택자 열셋을 …`

| 주장 | 내 재측정 | 차이 |
|---|---|---|
| ts 블록 24개 | **25개** | −1 |
| 행 번호 인용 0건 | `plan.md:243`·`:257` 에 맨 행 번호 **2건**(+ 「작성 시점」 한정 3건) | 과소 |
| 선택자 열셋 | 리터럴 **14개** | −1 |

**결론(충돌 0 · 기존 블록 일곱)은 전부 옳다.** 틀린 것은 모집단 크기 셋뿐이다. 다만 `verification-claim-integrity.md` 기준으로 「0건」은 관측 주장이므로, 2건이 남아 있는 상태에서 0 을 적는 것은 과대주장이다.

## 5. 왜 이 다섯이 또 한 번의 저작 라운드를 필요로 하지 않는가

셋을 나눠 답한다.

1. **어느 것도 명령·가드·요구사항 본문에 없다.** D1·D2·D5 는 설명 문단, D3 은 요약표 칸, D4 는 숫자 하나다. 열여섯 기준의 실행 경로에 이 다섯 중 무엇도 놓여 있지 않다 — 나는 관측 기계(chk/le 아홉 줄, 앵커 정규식 다섯, AC-015 가드, tsc)를 **축자로 돌려** 그것을 확인했다.
2. **D2 는 세 기계가 이미 잡는다**(위 D2 참조). 나머지 넷은 잘못 읽어도 잘못된 코드로 이어지지 않는다 — D4 만이 「하나를 덜 열어 볼」 여지를 만드는데, 그것도 §5.3 표 자체를 열면 즉시 드러난다.
3. **저작 라운드의 비용이 이득을 넘는다.** 세 라운드가 12 → 4 → 0(실행 결함)으로 수렴했고, 2회차가 보여 준 대로 **교정 자체가 새 결함을 만든다.** 문장 다섯 줄을 고치려고 네 산출물을 다시 여는 것은 지금 시점에서 순손실이다. 이 다섯은 M0 을 여는 김에, 또는 sync 단계에서 쓸어 담으면 된다.

권고 형태로만 적는다(조건 아님): D1 「여섯」→「일곱」, D2 문장을 「뒤 넷 가운데 `#autocomplete`·`.ac-kind.to` 는 이 SPEC 이 바꾸지 않고, `#msg-input`·`.message:not(.turn-cont)` 는 제자리 편집 대상이라 어느 쪽이든 첫 매치가 관측 대상이다」로, D3 매트릭스 칸을 `^[[:space:]]*//` 로, D4 「아홉」→「열」(두 곳), D5 셋을 25 / 2 / 14 로.

## 6. Tier 판정

**Tier M 유지에 동의한다.** 파일 **9개**(소스 4 + 시험 4 + `css-rule.ts`) — Tier M 구간 5~15 안이고 L 문턱에 한참 못 미친다. LOC 600~700 추정은 구간 300~1000 안. 스키마·마이그레이션·아키텍처 변경 0.

**16/16 이 지금 무언가를 덜 관측하는가 — 아니다.** 2회차에 내가 지목한 두 하위 주장(폭·초기 상태)에 관측이 붙었고, 이번 라운드도 요구사항·기준 개수를 늘리지 않은 채 단언과 가드만 늘렸다. 열여섯 기준이 전부 판별력을 갖는 것을 §1·§2 에서 확인했다.

**따라서 「16/16 은 구조적으로 관측이 모자라니 Tier L 이나 3분할이 옳다」는 진단은 이 SPEC 에 해당하지 않는다.** 그 진단이 성립하려면 관측되지 않은 주장이 남아 있어야 하는데, 지금은 없다. `plan.md:118` 이 적은 전환 조건(「요구사항을 하나라도 더 쪼개야 한다면 그때는 L」)이 정확한 형태이고, 그 시점은 아직 오지 않았다.

다만 2회차에 적은 경고는 유지한다 — 여유 0 은 실재하는 압력이고, 2회차의 N2(변수 재선언)가 그 압력의 산물이었다. **다음에 무엇이든 더할 때는 예산부터 다시 본다.**

## 8. 검증하지 못한 것

1. **시험 스위트를 돌리지 않았다** (읽기 전용 제약). N4 는 추출 코드로 `tsc` 를 **실제로** 돌려 닫았고, N1·N8·N9 와 AC-015 가드는 명령을 **축자로** 돌려 닫았다. 남은 것은 구현 후에만 관측 가능하다: `cd server && npm run typecheck && npm test`.
2. **`bootVisual()` 추출 결과물은 M0 산출물이라 지금 없다.** 계약(`acceptance.md:88-92`)과 M0 2번의 「기존 단언 넷 불변」 지시는 확인했다. 닫는 명령: M0 후 `cd server && npx vitest run test/web-visual.test.ts`.
3. **Playwright 존재 여부를 확인하지 않았다** — AC-003·006·010 의 뒤 겹이 실제로 도는지는 J3 실행이 필요하다. `plan.md` 가 [HARD] 로 「한 번 이상 실제로 돌리고 못 돌렸으면 Gap 으로 적는다」를 이미 요구하므로 이 공백은 SPEC 이 스스로 관리한다.
4. **AC-015 (4) 가드는 구현 전이라 공허 참이다.** 사후 가드로 설계된 것이라 정상이지만, 「지금 PASS」가 「그 부류가 실제로 막힌다」의 증거는 아니다. 닫는 명령: 구현 후 같은 줄을 다시 돌린다.
5. **LOC 600~700 추정은 구현 전이라 원리적으로 검증 불가.**
6. **아트보드 캔버스는 여전히 접근 불가**(세션 스크래치패드). 「SPEC 이 아트보드를 정확히 옮겼는가」는 세 라운드 내내 판정 불가였다. 다만 §1.1 [HARD] 의 자립성 요구는 §4 본문이 실제로 충족한다.
7. **vitest 가 `-t` 필터 0개에서 내는 종료 코드**는 이번에도 측정하지 않았다 — 그러나 `-t` 가 제거돼 **더 이상 아무것도 그것에 의존하지 않으므로** 미결로 남겨도 무해하다.
