## 3. 새 경계에 대한 공격 — 뚫지 못했다

리드가 가장 알고 싶어 할 자리이므로 먼저 적는다. **나는 ㉯ 경계를 우아함이 아니라 소스로 검증했고, 열거된 어떤 들어오는 통로도 그것을 무너뜨리지 못했다.**

### 3.1 「들어오는 것은 전부 결과 아니면 알림」이 이 저장소에서 참인가 — 참이다

세 자리를 직접 읽었다.

`channel/src/channel-server.ts` § `CallToolRequestSchema` 처리기:

```ts
if (req.params.name === 'reply') {
  const { text, files } = req.params.arguments as { text: string; files?: string[] }
  await deps.sendToChat({ text, files })
  return { content: [{ type: 'text', text: 'sent' }] }
}
if (req.params.name === 'fetch_history') {
  const args = req.params.arguments as { … }
  const text = await deps.fetchHistory(args)
  return { content: [{ type: 'text', text }] }
}
```

`reply` 는 **호출 인자**를 읽어 채팅으로 내보내고, `fetch_history` 는 **반환값**으로 이력을 준다. 같은 파일 § `pushChatMessage` 는 `mcp.notification({ method: 'notifications/claude/channel', … })` 로 **알림**을 민다. 즉 세션으로 들어오는 것은 두 형태뿐이고, 둘 다 호출 인자가 아니다.

`grep -n 'inner.type ===' channel/src/gateway-client.ts` 실행 출력:

```
194:          if (inner.type === 'welcome') opts.onWelcome?.(inner)
197:        if (inner.type === 'message') opts.onMessage?.(inner)
198:        else if (inner.type === 'permission_verdict') opts.onVerdict?.(inner)
199:        else if (inner.type === 'history_response') {
```

네 갈래 전부 `wire()`(`channel/src/index.ts`)에서 알림 또는 `fetch_history` 반환으로 귀결한다 — `onMessage` → `pushChatMessage`(알림), `onVerdict` → `handlePermissionVerdict`(알림), `history_response` → `requestHistory` 의 프로미스(결과), `welcome` → 세션으로 가지 않는다.

**결론: 「호출 인자냐, 결과·알림이냐」는 이 코드베이스에서 실제로 배타적이다.** 판정이 통로 목록의 완전성에 걸려 있지 않다는 SPEC 의 주장은 참이다.

### 3.2 「다른 소켓이 답했는데 사진 속 세션이 그것을 받아 되뇐다」 — 경로는 실재하고, 판정은 무너지지 않는다

내가 만들 수 있는 가장 강한 시나리오다.

1. `server/test/gateway-v2.ts` 의 `connectV2(port, token)` 를 쓰는 위조 소켓이 같은 토큰으로 함께 붙는다(hello 처리기는 **같은 소켓만** 축출한다 — `server/src/gateway.ts:166` 주석 실측 확인).
2. 운영자의 `@TO` 메시지는 `deliver` 가 **일치하는 모든 소켓**에 배달한다(같은 파일 `:331`, 루프가 `return` 하지 않는다 — 직접 판독).
3. 위조 소켓이 먼저 `A1B2C3D4` 를 붙여 답한다.
4. 사진 속 세션은 지시문 7행(「사람이 나를 부르면 **답하기 전에** `fetch_history` 로 놓친 대화를 먼저 확인하세요」)에 따라 이력을 먼저 부른다. `handleHistory` 는 방의 **모든** 메시지를 돌려주므로(봇이 쓴 것 포함 — `server/src/gateway.ts` § `handleHistory` 직접 판독) 그 답이 결과에 실려 들어온다.
5. 사진 속 세션이 그 값을 자기 `reply` 인자에 그대로 실어 답한다.

이때 ㉣ 의 두 절(방 화면의 `X` · 그 세션의 `reply` 호출 인자의 `X` · 두 값 동일)이 **모두** 선다.

**그런데 이것은 ㉣ 가 막으려는 위협이 아니다.** ㉣ 의 Then 절이 세우려는 명제는 「그 칩이 가리키는 세션이 그 방의 답을 **만든다**」이고, 이 시나리오에서 그 세션은 **실제로 `reply` 를 냈다** — 즉 답하고 있다. ㉣ 가 배제하려던 셋(「기동 화면 찍고 죽인 세션」 · 「살아 있되 답하지 않는 세션」 · 「받기만 한 세션」)은 전부 배제된 채로 남는다. 무너지는 것은 「`X` 를 그 세션이 **지어냈다**」뿐이고, 그것은 판정의 결론이 아니라 매개의 성질이다.

그래서 나는 이것을 **차단 결함이 아니라 공시되지 않은 잔여**로 본다(O-C5). SPEC 의 「남는 노출」 셋 중 1번(복사 위조)은 **방이 세션을 베끼는** 방향만 적고, **세션이 이력을 베끼는** 역방향은 적지 않았다. 4회차를 깨뜨린 통로가 정확히 그 이력 통로였으므로 목록에 있어야 한다.

### 3.3 「운영자가 두 소켓을 가를 수 없는」 시나리오 — 이미 공시된 잔여로 환원된다

사진 속 세션이 `reply` 를 냈으나 그 프레임이 게이트웨이에 닿지 못하고, 방에 뜬 답은 위조 소켓의 것인 경우를 따져 봤다. 두 값이 같으려면 위조 소켓이 8자리를 **우연히** 맞히거나(≈ 1/2.8×10¹²) **베껴야** 하는데, 베끼는 쪽은 SPEC 이 이미 「남는 노출 1 — 복사 위조, 운영자 자신의 능동적 위조를 요구하므로 수동 수용 실행의 위협 모형 밖」으로 공시한 자리다. 새 구멍이 아니다.

**요약: ㉯ 는 실체가 있는 구조 변경이고, 네 라운드의 실패 형태(목록이 하나 빠짐)는 이 SPEC 에서 은퇴했다.**

## 4. 미뤄진 판독 절차 — 리드가 운영자에게 전할 답

리드가 명시적으로 물은 자리다. 에두르지 않고 적는다.

### 4.1 이 기준은 판정 불가능한가 — **아니다. 미뤄진 것은 기준이 아니라 절차다**

기준 자체는 무엇이 참이어야 하는지를 정확히 말한다: 「`X` 가 `reply` 도구 **호출의 인자**에 나타나고, 방 화면의 답변과 같으며, 도구 **결과**·**알림**에 나타난 것은 세지 않는다」. 이것은 반증 가능한 명제다 — 반례(결과에만 나타난 `X`)를 특정할 수 있고, 무엇을 보면 참인지도 특정할 수 있다.

미뤄진 것은 **그 명제를 사진 한 장에서 읽어 내는 절차**다. SPEC 은 이것을 숨기지 않고 [HARD] 로 공시했으며, 세 가지(호출/결과를 가르는 화면상 표지 · 인자 전문이 보이는지 접히는지 · 접히면 무엇을 눌러 펼치는지)를 이름으로 지목해 run 첫 실행에 넘겼다. 그리고 **그 전까지 이 항은 미관측**이라고 못 박았다.

이 처분이 안전한 이유는 `acceptance.md` 「미관측의 처분」이 「미관측은 통과로 셈하지 않으며, 종결 보고는 `통과 N / 실패 M / 미관측 K` 셋을 나누어 적는다. 「12/12」는 K = 0 일 때만 쓸 수 있다」로 이미 닫혀 있기 때문이다. **절차를 모른다는 사실이 통과로 둔갑할 길이 없다.**

### 4.2 그러나 이 미룸은 **강제된 것이 아니었다** — 더 강한 증거 면이 이미 존재한다

이것이 이 감사가 새로 찾아낸 것 중 가장 쓸모 있는 항목이다(O-C6).

**따라서 정직한 판정은 이렇다: 미룸은 허용 가능한 부채이되, 저작 시점에 검토되지 않은 대안이 있었다.** SPEC 이 「의존성이 없어 세션을 띄울 수 없었다」로 미룬 것은 **화면**을 재려 했기 때문이고, 화면이 아닌 면은 세션을 띄우지 않고도 그 존재와 형태를 확인할 수 있었다(내가 방금 했다).

### 4.3 그래서 부채인가, 판정 불가인가 — **부채다. 조건 하나가 붙는다**

- **부채인 이유** 기준은 반증 가능하고, 미관측 처분이 거짓 통과를 막으며, run 이 확정할 것이 셋으로 이름 붙어 있고, 그 셋을 확정 못 해도 §5 의 「실 세션으로만 닿는 실패 → 관측을 붙인 잔여, 처분은 리드」가 출구를 준다.
- **붙는 조건** 만약 run 첫 실행에서 터미널이 호출과 결과를 육안으로 가르지 못한다고 밝혀지면, 이 SPEC 은 자기 중심 기준을 **영구히 미관측**으로 닫게 된다. 그 경우 §4.2 의 transcript 면으로 갈아타는 것이 유일하게 값싼 길이고, 그것은 SPEC 편집이 아니라 **증거 형태의 교체**라 §5 의 「이 카드 안에서 고친다」 원칙과 충돌하지 않는다.
- **권고** run 첫 실행에서 **두 면을 함께** 남길 것 — 화면 캡처 `A01-liveness.png` 와 그 세션의 transcript 에서 `reply` 호출 한 건을 뽑은 발췌. 둘 다 남기면 화면이 가르든 못 가르든 ㉣ 가 선다. 이것은 새 AC 가 아니라 기존 ㉣ 의 증거 형태를 하나 더 인정하는 것이므로 예산(16/16)을 건드리지 않는다.

### 6.5 §C 경계 fixture — 산술로 판별력 재확인 (실행 아님)

`channel/src/truncate.ts` 실측 상수: `MAX_NAME_BYTES = 256`, `MAX_BODY_BYTES = 4000`. `'<channel'` = 8바이트, `neutralizeEnvelope` 이 `'&lt;channel'` = 11바이트로 늘린다(`s.replace(/<\/?channel/gi, m => \`&lt;${m.slice(1)}\`)` 직접 판독).

| 값 | 반복 수 | 날것 | 중화 뒤 | 전제(㉠) |
|---|---|---|---|---|
| `author_name` | `floor(256/8)` = 32 | 256 ≤ 256 ✓ | 352 > 256 ✓ | 성립 |
| `body` | `floor(4000/8)` = 500 | 4000 ≤ 4000 ✓ | 5500 > 4000 ✓ | 성립 |

**변이 상태에서 ㉡ 이 실제로 붉어진다.** `truncateToBudget(raw, 256)` 은 `totalBytes <= budgetBytes` 에서 **원문 그대로 반환**하고(같은 파일 ②), 그 뒤 중화가 352 로 늘리므로 `author ≤ MAX_NAME_BYTES` 단언이 깨진다. ㉢(날것 시길 0건)은 두 순서 모두에서 참이므로 판별자가 아니고, ㉡ 이 판별자라는 SPEC 의 지목은 옳다.

**기존 fixture 가 순서를 가르지 못한다는 §6.3 의 근거도 참이다.** `channel/test/index-wiring.test.ts` 의 이력 fixture 를 읽었다 — `author_name: 'alice'`(5바이트) · `'과거'`(6바이트) · 오염 문자열(약 180바이트) 은 전부 상한에서 멀고, `bigBody = '가'.repeat(MAX_HISTORY_BYTES)` 는 날것으로도 상한을 넘는다. 어느 쪽도 `raw ≤ 상한 < 중화` 구간에 들지 않는다.

**부분 변이 결과는 보고 가능한가 — 그렇다.** AC-016 ㉡ 이 「실패한 기준의 **전체 집합**을 이름으로 적는다 — 형제 기준이 함께 붉어졌는지는 실측 대상이며, 「새 기준만 실패했다」를 미리 단정하지 않는다」로 적어 두었고, 변이가 아무것도 붉히지 못하는 경우는 엣지 E-8 이 「AC-016 은 실패이며 AC-015 도 함께 무효」로 처분한다. **두 방향 다 닫혀 있다.**

## 10. 리드가 운영자에게 전할 답

### 10.1 남은 것은 구조적 재천공인가, 잔여 점수인가 — **잔여 점수다**

에두르지 않고 답한다. **접근을 다시 볼 자리는 남아 있지 않다.**

네 라운드를 깨뜨린 것은 하나의 구조적 오류였다 — 「그 세션이 만들었다」를 **터미널 화면**으로 재려 한 것. 화면은 들어온 것과 만든 것이 섞이는 면이고, 그 면의 들어오는 통로는 이 SPEC 이 통제하지 못하므로, 매 라운드 수리가 통로를 하나 막으면 다음 통로가 나왔다. 이번 수리는 그 통로를 하나 더 막은 것이 **아니라**, 관측 지점을 면에서 **행위**로 옮겼다. 나는 그 주장을 믿지 않고 소스에서 검증했고, 결과는 이렇다:

- 세션으로 들어오는 것은 이 코드베이스에서 **전부** 도구 결과 아니면 알림이다(§3.1, 세 파일 직접 판독).
- `reply` 는 `req.params.arguments` 를 읽는다 — 그 자리는 세션 밖에서 채워질 수 없다.
- 내가 만든 가장 강한 공격(위조 소켓 + 이력 되뇌기)은 「`X` 를 그 세션이 지어냈다」만 무너뜨리고 「그 세션이 답을 만든다」는 무너뜨리지 못한다(§3.2).

**그래서 「목록이 하나 빠졌다」로 여섯 번째가 열릴 길은 닫혔다.** 남은 두 차단 결함은 각각 **한 줄 편집**이다 — 낡은 문장 하나 교체(F-C1), 마일스톤에 빌드 한 줄 추가(F-C2). 나머지 열은 전부 비차단이고, 보통의 run 단계가 흡수하는 크기다.

### 10.2 함께 통과하는 부채

PASS 와 함께 넘어가는 것을 이름으로 적는다. 리드가 이것을 모르고 승인해서는 안 된다.

1. **AC-001 ㉣ 의 판독 절차가 미확정이다 — 판정 불가가 아니라 부채다.** 근거는 §4 에 전부 적었다: 기준은 반증 가능하고, 미관측 처분이 거짓 통과를 막고, run 이 확정할 것 셋이 이름 붙어 있고, 확정 못 해도 §5 가 출구를 준다. **다만 이 미룸은 강제된 것이 아니었다** — 세션 transcript 라는 더 강한 면이 이미 존재하고 이 저장소의 `CLAUDE.md` 가 그 면을 이름으로 안다. **권고: run 첫 실행에서 화면 캡처와 transcript 발췌를 함께 남긴다.** 그러면 화면이 호출과 결과를 가르든 못 가르든 ㉣ 가 선다. 새 AC 가 아니므로 16/16 예산을 건드리지 않는다.
2. **세 기준(AC-001 ㉣ · AC-013 ㉣ · AC-014)이 분류 판단을 요구한다.** 기계 검사가 아니다. 각각 실패 예시를 이름으로 들고 결과를 표로 남기게 해서 사후 감사는 가능하지만, 판정자가 성실해야 선다. 검증가능성 0.75 의 실질이 이것이다.
3. **§A 열두 항·§C 변이·전 스위트 초록은 다섯 라운드 내내 아무도 실행하지 않았다.** 이것은 결함이 아니라 계획 단계의 정상 상태이며, `spec.md` §6.4 와 `progress.md` 의 「미검증 인수」가 그것을 정확히 공시한다 — **실행한 척하는 자리는 어느 산출물에도 없다**(전건 대조했다). 다만 리드는 이 SPEC 이 아직 **한 번도 돌아 보지 않았다**는 것을 알고 run 에 넘겨야 한다.
4. **비차단 열 건**(O-C1~O-C10)은 리드 재량이다. 그중 O-C1(죽은 명령)과 O-C5(공시되지 않은 잔여)는 F-C1·F-C2 와 함께 처리하면 비용이 거의 없다.

### 10.3 권고하는 처리 순서

1. **F-C1** — `spec.md` §7 의 ㉣ 절을 `plan.md` §G R-8 문언으로 교체(한 줄).
2. **F-C2** — `plan.md` M1 첫 단계에 `npm run build -w channel` 추가(한 줄).
3. 여력이 있으면 **O-C1**(죽은 `awk` 줄 삭제) · **O-C5**(잔여 넷째 항 추가) · **O-C6**(transcript 를 ㉣ 증거 형태로 함께 인정) 을 같은 편집에서 닫는다.
4. **재감사 없이 run 으로 넘긴다.** 이 셋은 판정을 바꾸지 않는 편집이며, 여섯 번째 감사를 정당화하지 않는다. 리드가 편집 착지를 직접 판독하는 것으로 충분하다.
