## §B 전선 형식

### B.1 핸드셰이크 세 프레임

```jsonc
// ① 채널 → 서버. 비밀이 없다 — 이것이 v2 의 전부다
{ "type": "hello", "pub": "<64자 hex>", "client_nonce": "<64자 hex>" }

// ② 서버 → 채널. 서버가 논스를 먼저 낸다
{ "type": "challenge", "server_nonce": "<64자 hex>", "room_id": 1, "bot_id": 2,
  "server_proof": "<64자 hex>" }

// ③ 채널 → 서버. ②를 통과시킨 뒤에만 나간다
{ "type": "auth", "signature": "<128자 hex>" }
```

`signature` 가 128자인 것은 Ed25519 서명이 64바이트이기 때문이다(§A 아래 실측 확인).

**[HARD] 위 세 프레임 어디에도 `cb` 가 없다는 것이 관측 대상이다.** 채널 바인딩 값은 전사와 세션 열쇠 유도에만 들어가고 **전선에는 나타나지 않는다**(REQ-GWAUTH2-021). 실으면 중계자가 자기 값 대신 상대의 값을 실어 보낼 수 있고, «전달할 수 없는 값» 이라는 성질 자체가 사라진다.

**그것을 재는 자리는 AC-GWAUTH2-004 ㉡ 이다.** 그 기준이 `hello`·`challenge`·`auth`·`env` 의 키 집합을 각각 `toEqual` 로 고정하므로, 이 네 종류의 어디에 어떤 이름으로 실어도 붉어진다. **AC-GWAUTH2-003 은 `hello` 하나만 잰다** — 3회차까지 이 자리는 AC-003 이 «이 성질도 함께 지킨다» 고 적었고 **그 문장은 거짓이었다**(3회차 감사 H-02). `challenge`·`auth`·`env` 에 `cb` 를 실어도 붉어지는 기준이 그때는 없었다. 4회차가 AC-004 를 넓혀 그 공백을 닫았다. **다만 이 문단이 말하는 넓이는 전선 위 네 종류까지다** — 봉투 `payload` 안의 내부 프레임은 AC-GWAUTH2-004 가 재지 않는다(`acceptance.md` 그 기준의 [HARD] 절이 그 사실을 적는다). 4회차 개정은 이 자리에 «어느 프레임에 어떤 이름으로 실어도» 라고 적어 **다시 재는 것보다 넓게 말했고**, 4회차 감사 J-01 이 그것을 잡았다 — **같은 형태의 결함이 같은 자리에서 두 번 났다는 것을 기록으로 남긴다.**

### B.2 확립 후 봉투

```jsonc
{ "type": "env", "seq": 1, "mac": "<64자 hex>",
  "payload": "{\"type\":\"welcome\",\"room_id\":1,\"bot_id\":2,\"bot_name\":\"pm\",\"missed_after_id\":0}" }
```

`payload` 는 **문자열**이다. MAC 은 그 문자열 자체에 걸리므로 정규화 규칙이 존재하지 않는다(`plan.md` §D-6). 채널은 대조 **후에** 파싱하며, 파싱 실패는 프레임을 버리는 것으로 끝난다(예외를 던지지 않는다 — REQ-GWAUTH2-016).

`welcome` 도 봉투 안에 들어간다. 예외를 하나라도 두면 그 종류가 주입 통로가 된다.

## §C 열쇠 일정

```
T  (평문 토큰 — 채널만 안다. 서버는 발급 순간에만 보고 저장하지 않는다)
│
├─ HMAC-SHA256(T, "minidiscord/v2/sign")           → seed  ──→ Ed25519 sk    [채널 전용]
│                                                              └→ pub        [서버 저장 · 공개]
└─ HMAC-SHA256(T, "minidiscord/v2/server-confirm") → k_srv                   [양쪽]
                                                     │
                 HMAC-SHA256(k_srv, "session|cn|sn|room|bot|cb") → k_sess    [소켓마다 새로]

cb  (전송 연결에서 각자 유도 — 토큰과 무관한 독립 축이다. 프레임에 실리지 않는다)
 └─ tlsSocket.exportKeyingMaterial(32, "EXPORTER-minidiscord/v2/channel-binding")
    또는 리터럴 'unbound'                                     [양쪽 각자]
```

**라벨 두 개가 이 그림의 «열쇠» 축을 진다.** `k_srv` 를 아는 것이 `sk` 를 알려 주지 않는 이유가 그것뿐이며, 라벨을 같게 만들거나 한쪽을 다른 쪽에서 유도하면 `spec.md` §5 표 **`DB읽기만`** 행의 봇 사칭 칸이 다시 열린다 — 그것이 REQ-GWAUTH2-002 이며, **AC-GWAUTH2-009 가 그 상대의 무능력으로 그것을 잰다**(변이 AA). 3회차까지 이 자리는 행을 이름이 아니라 서술(«DB 유출 행»)로 가리켰고, `spec.md:459` 의 [HARD] 가 형제 문서까지 이름 사용을 구속하므로 그 규칙의 유일한 미적용 지점이었다(3회차 감사 H-05).

**`cb` 는 그 축에 속하지 않는다 — 토큰에서 나오지 않는 두 번째 축이다.** 그래서 토큰을 다 아는 상대도 `cb` 를 «맞출» 수는 없고, 반대로 `cb` 를 아는 것이 어떤 열쇠도 알려 주지 않는다. **`cb` 의 방어력은 비밀성이 아니라 연결마다 다르다는 성질에서 나온다**(`spec.md` §2.8).

**전사 넷** (`plan.md` §D-10 과 `spec.md` §2.5 가 정본):

```
challenge|${cn}|${sn}|${room}|${bot}|${pub}|${cb}   ← server_proof 의 메시지
auth|${cn}|${sn}|${room}|${bot}|${pub}|${cb}        ← signature 의 메시지
session|${cn}|${sn}|${room}|${bot}|${cb}            ← k_sess 유도
${seq}|${payload}                                   ← 봉투 mac (k_sess 가 이미 cb 를 진다)
```

앞의 둘이 라벨만 다른 이유: 라벨이 없으면 한쪽 증명이 다른 쪽 자리에서 통한다.

**셋 모두에 `cb` 가 들어가는 이유는 `spec.md` §2.8.3 이 정본이며, 그 절이 «성립하지 않는 근거» 하나를 명시적으로 기각한다** — «중계자가 전사를 관측했으므로 세션 열쇠도 유도한다» 는 이 설계에서 성립하지 않는다(유도의 열쇠가 `k_srv` 이고 중계자는 그것을 갖지 않는다). **성립하는 근거는 «두 층이 독립으로 실패해야 한다» 하나이며, «투명한 전달 중계 자체를 깨뜨린다» 는 그 따름정리다** — 후자가 물리는 것은 전자의 전제(핸드셰이크 게이트가 뚫린다)가 성립할 때뿐이기 때문이다(2회차 감사 G-12; `spec.md` §2.8.3 이 정본).

## §D 상태 기계 (채널 쪽 소켓 하나)

```
                    ┌──────────────┐
   connect() ──────▶│  OPENING     │  sk·k_srv 유도, client_nonce 생성,
                    │              │  open 이후 cb 유도 (실패하면 'unbound' + stderr 공시)
                    └──────┬───────┘
                     hello │ 발신 (비밀 없음)
                    ┌──────▼───────┐
                    │  AWAIT_CHAL  │  이 상태에서 나가는 프레임은 없다 (REQ-GWAUTH2-008)
                    └──────┬───────┘
              challenge 도착 │
             ┌──────────────┴──────────────┐
    대조 실패 │                              │ 대조 통과
    ┌────────▼────────┐            ┌────────▼────────┐
    │ PROOF_REJECTED  │            │  AWAIT_WELCOME  │  auth 서명 발신
    │ stderr 1줄·close│            └────────┬────────┘
    └─────────────────┘             봉투 welcome │
                                    ┌──────────▼──────────┐
                                    │    ESTABLISHED      │  lastSeq = 그 welcome 의 seq
                                    └──────────┬──────────┘
                                     봉투 도착   │
                          ┌────────────────────┴────────────────────┐
                mac·seq 실패 │                                        │ 통과
                ┌───────────▼───────────┐                 ┌──────────▼──────────┐
                │   FRAME_REJECTED      │                 │ payload 파싱 → 분배 │
                │   stderr 1줄·close    │                 │ lastSeq = seq       │
                └───────────────────────┘                 └─────────────────────┘
```

- **세 거절 상태가 서로 다른 플래그다** — `proofRejected` · `frameRejected` · (`!established`). `plan.md` §D-8 이 그 순서를 처방한다.
- **전부 소켓 지역이다.** `connect()` 안에서 만들어지고 소켓과 함께 사라진다. 클로저 밖으로 올리면 재접속이 영원히 막히거나 게이트가 영구히 열린다.
- **`AWAIT_CHAL` 에서 아무 프레임도 나가지 않는 것**이 AC-GWAUTH2-008 이 재는 성질이다.
- **거절은 예외를 던지지 않는다.** 소켓을 닫고 기존 백오프 재접속 경로에 맡긴다 — 봇이 «조용히 아무 일도 하지 않는» 상태로 남는 것이 이 프로젝트에서 가장 비싼 실패 형태이기 때문이다(`SPEC-GWAUTH-001` REQ-GWAUTH-008 의 근거를 그대로 잇는다).

서버 쪽은 대칭이며 한 자리만 다르다: **접속 목록 등록이 `auth` 검증 통과 시점**이다. v1 은 `hello` 조회 성공에서 등록했고(`server/src/gateway.ts:101`, 앵커 `conns.set`), 그 자리에서는 서명이 아직 오지 않았으므로 등록이 인증보다 앞섰다.

## §E 위협별 실패 지점 — 어디서 막히는가

각 행은 «그 상대가 무엇을 갖고 어디서 걸리는가» 를 적는다. **막히지 않는 행을 표에서 빼지 않는다.**

**[HARD] 중계형 상대의 두 행은 전송 조건을 함께 적는다.** 초판은 조건 없이 «막힌다» 로 적었고 1회차 감사(F-01)가 그것을 반증했다.

| 상대 | 전송 조건 | 가진 것 | 봇 사칭 시도 → 어디서 걸리는가 | 게이트웨이 사칭 시도 → 어디서 걸리는가 |
|---|---|---|---|---|
| 위조 종단 (진짜 서버에 **닿지 못한다**) | 무관 | `pub`, `client_nonce` | 해당 없음 (서버에 붙지 않는다) | **② `challenge` 대조** — `k_srv` 를 유도하지 못한다 |
| 위조 종단 (진짜 서버에 **닿는다** — 오라클 중계) | 양쪽 TLS 종단 | 위 + 진짜 서버가 내준 `challenge` | 해당 없음 | **② `challenge` 대조** — 받아 온 증명이 **자기 연결의 `cb`** 로 계산되어 채널의 `cb` 와 어긋난다 |
| 〃 | **평문 / TLS 미종단** | 〃 | **막히지 않는다** — 전달한 서명이 서버에 등록된다 | **③ 봉투 `mac`** — `k_srv` 가 없어 `k_sess` 를 유도하지 못한다. **②는 통과한다**(증명이 진짜다) |
| 중계형 중간자 | 양쪽 TLS 종단 | 오간 모든 프레임 | **서버의 서명 검증** — 두 연결의 `cb` 가 달라 전달한 서명이 거절된다 | **② 와 ③ 둘 다** — 중계한 `challenge` 가 채널에서 거절되고, `k_sess` 도 `cb` 에 묶여 있다 |
| 〃 | **평문 / TLS 미종단** | 〃 | **막히지 않는다** — `spec.md` §2.8.1 의 다섯 단계 | **③ 봉투 `mac`** — `k_srv` 가 없다 |
| 읽기 전용 DB 유출 | 무관 | `verifier_pub`, `server_confirm_key` | **서버의 `auth` 서명 검증** — 개인키가 DB 에 없다 | **막히지 않는다.** `challenge` 도 봉투도 만든다. **중계 위치에 서면 채널의 `cb` 도 자기 값으로 알므로 채널 바인딩이 보태는 것이 없다** |
| 평문 토큰 유출 | 무관 | `T` | 막히지 않는다 | 막히지 않는다 |
| 서버 장악 | 무관 | 전부 | 막히지 않는다 | 막히지 않는다 |

> **[HARD] 오늘 이 저장소에서 서는 행은 «평문 / TLS 미종단» 행들이다.** `server/src/index.ts:34` 가 `Fastify({ logger: false })` 이므로 서버 쪽 `cb` 는 언제나 `'unbound'` 다(§A 실측, `spec.md` §2.8.4). **«중계자를 배제했다» 는 조건을 지운 보고다.**

**DB 유출 행의 두 칸이 다르다는 것이 이 설계의 정직한 결과다.** 「검증자 저장으로 DB 유출을 닫았다」는 왼쪽 칸에만 참이다. 오른쪽 칸을 닫으려면 서버가 자기 키쌍을 갖고 채널이 그 공개키를 고정해야 하며, 그것은 공개키 배포·회전·초기 신뢰 확립이라는 새 문제를 연다 — `spec.md` §5 가 밖에 두었다.

### E.0 억제 축 — 봉투가 **보증하지 않는** 것

**봉투는 출처와 순서를 인증하지 전달을 보증하지 않는다.** 경로에 선 상대는 임의의 봉투를 **흔적 없이 삼킬 수 있다.** `seq` 는 재생을 막지만 삭제를 탐지하지 못한다 — 채널은 «직전에 받아들인 값 이하» 를 버리므로(REQ-GWAUTH2-013·014), `seq=5` 를 삼키고 `6` 을 넘기면 `6 > 4` 라 정상 수용된다. 순서 뒤바꾸기도 같은 것으로 환원된다(먼저 넘긴 큰 `seq` 가 나중의 작은 것을 버리게 만든다).

**세션 절단(순수 DoS)과 다르다** — 선택적 억제는 표적이 있고 눈에 보이지 않으며 세션은 계속 건강해 보인다. 억제된 `permission_verdict` 나 `history_response` 가 채널 쪽에서 어떤 기본 동작으로 귀결되는지는 **이 패스가 확인하지 않았다**; 확인 없이 심각도를 주장하지 않는다.

**채널 바인딩은 이 축에 아무것도 보태지 않는다.** TLS 종단 배치에서는 중계자가 애초에 세션을 세우지 못하므로 이 축이 열리지 않지만, 그 밖의 배치와 **경로 상의 순수 폐기**(패킷 드롭)에는 무력하다. 탐지에는 연속 `seq` 요구·하트비트·수신 확인이 필요하며 **별도 카드다.**

### E.1 재생 축

| 무엇을 재생하는가 | 왜 통하지 않는가 |
|---|---|
| 다른 소켓의 `challenge` | 전사에 두 논스가 묶여 있고 둘 다 소켓마다 새로 만들어진다 (AC-GWAUTH2-011) |
| 다른 소켓의 `auth` 서명 | 같은 이유 (AC-GWAUTH2-010) |
| **같은 소켓의 유효한 봉투** | `seq` 가 직전에 받아들인 값 이하다 (AC-GWAUTH2-015) |
| 다른 소켓의 유효한 봉투 | `k_sess` 가 두 논스와 `cb` 에 묶여 소켓마다 다르다 |
| **중계자가 전달한 진짜 서명** | **재생이 아니므로 논스가 막지 못한다.** 두 연결의 `cb` 가 달라 서버의 검증에서 걸린다 (AC-GWAUTH2-022) — **TLS 종단 배치에서만** |

**«같은 소켓의 유효한 봉투» 행이 `seq` 의 존재 이유다.** (서수가 아니라 행의 내용으로 가리킨다 — 2회차 감사 G-04 가 §5 표에서 잡은 부류를 이 표에도 적용한다.) MAC 만으로는 이 재생이 열리고, 판정 축에서 그것은 실질 위험이다 — 같은 `permission_verdict` 를 두 번 흘려보내는 것이 그 자체로 상태를 바꾼다(`channel/src/channel-server.ts` 의 발신 집합 소진).

## §F 이 설계가 만들지 않는 것

`spec.md` §5 가 정본이며 여기서는 **설계 층의 이유**만 덧붙인다.

- **서버 키쌍과 공개키 고정** — 배포·회전·초기 신뢰 확립이 새 문제로 열린다. `k_srv` 는 그 자리의 대용이다.
- **채널 → 서버 방향의 봉투** — 서버는 핸드셰이크에서 소켓에 신원을 묶으므로 관문이 하나 있다. 「닫혔다」가 아니라 「관문 하나에 의존한다」이며, 중계형 중간자가 채널의 프레임 내용을 바꾸는 것은 막지 않는다.
- **토큰 회전·만료** — 결정적 유도는 **토큰이 곧 개인키**임을 뜻하므로 회전의 필요가 v1 보다 커졌다. 그럼에도 이 카드가 소유하지 않는다 — 발급·폐기 절차 전체를 다시 여는 범위다.
- **128 축출(F-A8)의 상한 자체** — 도달 범위만 좁아진다. `SPEC-CHANAUTH-001` §5 «승인 요청의 수명 관리» 와 함께 열려야 한다.

## §G 남은 설계 질문 — 상위 회부

1. **`server_confirm_key` 를 서버 쪽에서 한 번 더 감쌀 것인가.** 예: 서버 프로세스가 환경변수로 받은 마스터 열쇠로 그 컬럼을 암호화해 저장한다. 그러면 DB 만 읽은 상대는 게이트웨이 사칭도 하지 못한다. **비용**: 마스터 열쇠의 배치·회전 문제가 생기고, 열쇠 없는 개발 환경의 동작을 정해야 한다. 이 패스는 **범위에 넣지 않았다** — 리드 디스패치가 연 요소들에 없고, 넣으면 카드가 다시 커진다.

2. **`welcome` 을 봉투에 넣을 것인가, 밖에 둘 것인가.** 이 문서는 **넣는다**로 정했다(예외를 두면 그 종류가 주입 통로가 된다). 대가는 형제 하네스 전부가 `welcome` 을 풀어야 한다는 것이다. 되돌리기 쉬운 결정이므로 M2 에서 재검토해도 된다.
   **[HARD] 되돌리면 함께 바뀌는 자리는 셋이다** — ① `spec.md` §1.3 의 ⑥ 줄(«`welcome` 부터 봉투»), ② `acceptance.md` AC-GWAUTH2-004 ㉡ 의 전선 위 종류 목록(`welcome` 이 다섯째 바깥 종류가 되어 네 `toEqual` 이 다섯이 된다), ③ **AC-GWAUTH2-016** 의 `seq` 배열 `[1,2,3,4]`(`welcome` 이 봉투 밖이면 재전송 셋만 남아 `[1,2,3]` 이 된다). 「되돌리기 쉽다」는 **이 셋을 함께 고칠 때만** 참이며, 셋을 적지 않으면 되돌림이 조용히 세 자리를 거짓으로 만든다(4회차 감사 J-04).
   **[HARD] 그리고 이 편입을 명령하는 요구사항은 아직 없다.** REQ-GWAUTH2-012 는 「확립 이후」를 구속하는데 `welcome` 도착이 확립의 성립 조건이므로(§2 용어표 「세션 확립됨」 행) `welcome` 자신을 덮지 않는다. 4회차 감사 J-04 는 대안 둘을 제시했다 — `spec.md` §1.3 ⑥ 을 맞추거나 REQ-GWAUTH2-012 를 넓히거나. **이 패스는 앞의 것을 택했다**: 문서 사이의 모순을 없애는 쪽이고, 요구사항 문언을 열지 않으므로 형제 기준의 포섭 관계를 건드리지 않는다. **그러므로 요구사항 층의 공백은 닫히지 않았고, 이 항목이 그 공백의 소유자다** — M2 재검토는 «넣을 것인가» 와 «어느 요구사항이 그것을 명령하는가» 를 함께 답해야 한다.
3. **기존 DB 파일의 스키마 갱신을 어떻게 처리할 것인가** — `plan.md` §D-3 이 M1 의 판정 항목으로 올렸다. 개발용 DB 재생성으로 끝낼지, 마이그레이션 문을 쓸지.

4. **[HARD] 서버가 TLS 를 종단하게 만들 것인가 — 그리고 그 전에 채널 바인딩을 착지시키는 것이 옳은가.** §A 가 실측한 대로 서버는 오늘 TLS 를 종단하지 않으므로, 채널 바인딩은 **실제 배치에서 아무것도 막지 않는다**(시험 안에서는 AC-GWAUTH2-022 가 실재를 잰다). 두 갈래가 있다: (a) 지금 착지시켜 프로토콜 문제를 배치 문제로 바꾸고, 서버 TLS 종단을 후속 카드로 연다 — 이 문서가 택한 안이다. (b) 서버 TLS 종단까지 한 카드로 묶는다 — `server/src/index.ts` 와 인증서 배치가 들어오므로 카드가 크게 커지고 REQ-GWAUTH2-018 의 파일 경계를 다시 연다.
   **[해소 — 3회차 운영자 결정] (a)를 택했다.** 이 카드의 범위는 «TLS 배치 조건부 종결» 이고, 서버 TLS 종단과 §1.1 의 무조건 종결은 후속 카드 **`t23`** 이 소유한다(`spec.md` §1.4·§5, `plan.md` §B-0c). **생산 배치를 막는 조건도 이 카드가 아니라 `t23` 이다.**
