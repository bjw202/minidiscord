# SPEC-COVERAGE-001 구현 계획

> 이 문서는 `spec.md` 의 요구사항을 **어떻게** 세울지를 정한다. 무엇을 만들지는 `spec.md`, 무엇으로 판정할지는 `acceptance.md` 가 소유한다.

바꾸기 어려운 결정을 앞에 둔다 — 사람이 검토할 때 되돌리기 비싼 것부터 보게 하려는 배치다. §B·§C 가 계약이고, §D 부터는 그 계약을 세우기 위한 기술적 처리다.

## §A 실행 순서와 의존

이 SPEC 은 선행 SPEC 이 없다. 다른 카드의 코드에 기대지 않고, 다른 카드를 막지도 않는다.

| 전제 | 상태 |
|------|------|
| 워크트리 루트에 `npm install` 이 끝나 있음 | **충족** — 233 패키지, 종료 0 (이 워크트리, 오케스트레이터 실측) |
| `server` 테스트 스위트가 초록 | **충족** — 10 파일 / 104 테스트 통과 (같은 실측) |
| 커버리지 제공자가 루트 `node_modules` 에 존재 | **충족, 그러나 우연** — `channel` 의 선언 덕이며 그것이 이 카드가 닫는 결함이다 (`spec.md` §1.2) |

후행: 이 카드가 서면 sync 단계 감사가 Craft 임계를 실측으로 판정할 수 있게 된다. 그것이 이 카드의 존재 이유다.

## §B 되돌리기 어려운 결정 — 임계를 «전역 라인 85» 로 건다

운영자 결정 D1 이 «임계를 강제한다, 라인 85» 를 정했다. 그 위에서 이 계획이 정하는 것은 **어느 범위에 거는가** 하나이며, 그것이 이 SPEC 에서 가장 되돌리기 비싼 결정이다.

| 안 | 내용 | 판정 |
|----|------|------|
| (가) | `thresholds: { lines: 85 }` — 프로젝트 전체 합계 | **채택.** 오늘 97.01% 로 여유 있게 선다 |
| (나) | `thresholds: { perFile: true, lines: 85 }` — 파일마다 | **기각.** `server/src/index.ts` 가 오늘 83.33% 다. 아무 결함도 없는 트리에서 게이트가 실패한다 |
| (다) | 라인 외 세 차원에도 임계 | **기각.** Craft 기준이 말하는 것은 라인 하나다. 근거 없는 숫자는 나중에 아무도 왜 그 값인지 설명하지 못한다 |

(나)를 기각한 것이 핵심이다. **정상 구현을 거짓 실패시키는 게이트는 곧 무시된다** — 이 저장소는 그 부류로 이미 여러 번 대가를 치렀다(형제 SPEC 의 기본 포트 점유 사례, `set-cookie` 하네스 사례). 게이트가 «환경 탓» 으로 읽히기 시작하면 그것은 게이트가 아니라 잡음이다.

되돌리기 어려운 이유: 임계값 `85` 는 sync 감사의 Craft 임계와 **같은 숫자로 맞춘 것**이라, 나중에 이 값을 바꾸면 두 숫자가 갈라지고 «어느 쪽이 진짜인가» 라는 질문이 생긴다. 값을 바꾸려면 감사 기준 쪽을 함께 다뤄야 한다.

## §C 되돌리기 어려운 결정 — 진입점을 제외하지 않는다

`server/src/index.ts` 의 진입점 블록(65-74행, 미커버로 잡히는 구간은 66-68·71-72)은 프로세스 직접 구동에서만 실행되므로 인프로세스 계측에 잡히지 않는다. 두 갈래가 있었다.

| 안 | 내용 | 판정 |
|----|------|------|
| (가) | 제외 없이 미커버로 두고, 사유를 한국어 주석으로 남긴다 | **채택** |
| (나) | `exclude: ['src/index.ts']` 로 제외한다 | **기각** |

**(가)를 고른 세 가지 근거.**

1. **선례가 이미 있다.** `channel/vitest.config.ts` 가 자기 `src/index.ts` 의 **같은 상황**을 제외 없이 주석으로 처리했다. 형제 두 워크스페이스가 같은 문제를 다르게 처리하면 나중에 읽는 사람이 어느 쪽이 규범인지 알 수 없다.
2. **제외는 사유보다 오래 산다.** 카드 `t4` 의 sync 감사 F-10 이 정확히 그 사례다 — 제외의 명시 사유가 반증되었는데 헤드라인 숫자는 제외 덕에 계속 좋아 보였다(`SPEC-CHANWIRE-001/progress.md` §E.4). 주석은 틀렸을 때 그냥 틀린 주석이지만, 제외는 틀렸을 때 **숫자를 조용히 부풀린다.**
3. **부풀릴 이유가 없다.** 전역 97.01% 는 임계 85 위에 크게 여유가 있다. 여기서 제외를 만들면 그것은 필요가 아니라 습관이다. (여유가 없었더라도 답은 제외가 아니라 테스트를 더하는 것이며, 그것은 이 카드의 범위 밖이다.)

이 결정의 대가: `index.ts` 의 **미커버 5행**(66·67·68·71·72 — 라인 25/30 = 83.33%)이 총계를 계속 끌어내린다. 그 대가를 받아들이는 대신, **총계가 임계 아래로 내려가면 그것이 진짜 신호**가 된다 — 제외를 쓰면 그 신호가 사라진다.

(구문 기준으로는 미커버 구문이 6개이고 그중 55행 하나는 진입점 블록 밖이다. 이 SPEC 의 임계는 라인이므로 계약에는 영향이 없다 — `spec.md` §4.4.)

## §D 판단이 필요했던 자리

### 1. 회귀 짝을 위해 `server/test/` 에 파일 하나를 더한다 (승인됨 — 리드 판정, 2026-08-29)

카드는 run 단계가 `server/src/**` 와 `server/test/**` 의 **동작을 바꾸지 말라**고 했다. 그런데 이 SPEC 이 세우는 것은 전부 설정이고, **설정은 지워져도 테스트 스위트가 초록으로 남는다.** 이 저장소는 그 부류를 이미 기록해 두었다(`criteria-outside-the-regression-suite` — 셸 명령으로만 재는 기준은 그 동작을 통째로 지워도 초록이다).

| 안 | 내용 | 판정 |
|----|------|------|
| (가) | `server/test/coverage-contract.test.ts` 한 개를 새로 만들어 계약을 단언한다 | **채택 (리드 승인, 2026-08-29)** |
| (나) | 기존 테스트 파일 안에 단언을 끼워 넣는다 | **기각.** 그것이야말로 «기존 파일의 동작을 바꾸는» 일이다 |
| (다) | 회귀 짝 없이 셸 기준만 둔다 | **기각.** 임계가 지워져도 아무것도 빨개지지 않는 상태를 수용하는 것이다 |

(가)로 읽은 근거: 금지의 대상은 «기존 동작의 변경» 이고, 새 파일 추가는 기존 테스트가 하는 일을 하나도 바꾸지 않는다. 이 독해는 작성 시점에는 해석이었으므로 조용히 승인하지 않고 판정을 요청했고, **리드 세션이 2026-08-29 에 승인으로 확정했다.** 조건부 조항은 이 SPEC 어디에도 남기지 않는다.

판정 기록의 본문은 `spec.md` §4.5 에 있고 이 항목은 대안 비교를 담는다. 두 자리는 **같은 사실**(승인)을 적으며, 어느 쪽도 판정 유무에 따라 분기하지 않는다.

### 2. `npm ls` 의 기본형은 이 결함을 재지 못한다 (실측으로 확인)

의존성 선언을 재는 자연스러운 명령은 `npm ls @vitest/coverage-v8 -w server` 인데, **이 명령은 오늘 이미 종료 0 이다.**

```
$ npm ls @vitest/coverage-v8 -w server
└─┬ @minidiscord/server@ -> ./server
  └─┬ vitest@4.1.11
    └── @vitest/coverage-v8@4.1.11
EXIT=0
```

끌어올려진 사본을 `vitest` 아래 전이 의존성으로 찾아 주기 때문이다. 이 명령을 기준으로 삼았다면 **결함이 그대로 있는 채로 통과하는 기준**을 쓸 뻔했다 — 이 SPEC 이 막으려는 부류 그 자체다. `--depth=0` 은 직접 선언만 보므로 오늘 종료 `1` 이고, 선언 후 `0` 이 된다. `channel` 을 같은 명령으로 재 대조군까지 확보했다(`acceptance.md` AC-COVERAGE-001).

**교훈의 일반형**: 명령이 종료 0 을 낸다는 사실은 그 명령이 무언가를 쟀다는 증거가 아니다. 기준을 쓰기 전에 **결함이 있는 현재 트리에서 그 명령이 실패하는지** 먼저 재야 한다.

### 3. 파일별 관측을 텍스트 리포터로 하면 판정이 뒤집힌다 (실측에서 마주침)

기준선 측정에서 텍스트 리포터의 파일 목록에 `auth.ts`·`config.ts` 등이 보이지 않았다. 파일이 측정되지 않은 것이 아니라 **텍스트 리포터가 100% 파일의 행을 숨긴다.** 그 목록으로 «제외가 있다» 고 판정했다면 없는 결함을 만들어 낼 뻔했다. 파일별 관측은 `json-summary` 로만 한다(`acceptance.md` AC-COVERAGE-002).

### 4. 임계 강제는 «걸었다» 로 끝낼 수 없다

임계를 설정에 적는 것과 게이트가 실제로 막는 것은 다르다. 키 이름을 틀리거나 리포터만 켜진 설정은 임계를 조용히 무시하고 종료 0 을 낸다. 그래서 **run 단계의 의무로 프로브를 명시**했다 — 임계를 실측값(97.01) 바로 위인 98 로 올려 실패를 관측하고, 85 로 통과를 관측한다(AC-COVERAGE-003).

98 을 고른 것은 경계가 **측정값에 붙어 있음**을 함께 보이기 위해서다. 100 같은 큰 값으로 재면 «무엇이든 실패시키는 설정» 과 «실측값을 비교하는 설정» 이 구분되지 않는다.

**임계를 어디서 올리는가 — 설정 파일이지 명령줄이 아니다(감사 F-01 반영).** 초안은 프로브가 `--coverage.thresholds.lines=98` 을 명령줄로 넘기게 했다. 감사가 실행으로 보인 것은 두 가지다. 첫째, **그 형식은 이 vitest 버전에서 실제로 인식된다** — 초안의 §E 가 «미확인» 으로 적어 두었던 위험은 해소됐고, 그 행은 지금의 사실로 다시 쓰였다. 둘째, 그런데 바로 그 때문에 그 프로브는 **이 카드가 만드는 것을 재지 않는다**: vitest 는 넘겨받은 값으로 판정하므로 `server/vitest.config.ts` 의 `lines: 85` 는 한 번도 읽히지 않고, 설정 파일이 아예 없는 오늘의 트리에서도 두 프로브가 그대로 «통과» 한다. REQ-COVERAGE-004 를 통째로 지워도 초록인 기준이다.

그래서 주·부를 맞바꾼다. **주경로는 설정 파일의 `lines` 를 임시로 98 로 바꿔 오버라이드 없이 재는 것**이고(되돌린 뒤 해시 대조로 복원 증명), CLI 오버라이드는 «vitest 의 임계 기능 자체가 살아 있다» 는 보조 관측으로만 남는다. 보조 관측은 REQ-COVERAGE-004 의 근거로 쓰지 않는다.

### 5. 검증 명령이 프로세스를 띄우거나 부하를 만들지 않는다

이 저장소에는 검증이 만든 배경 부하가 다른 검증을 오염시킨 전례가 있다. 이 SPEC 의 모든 관측은 `npm`·`git`·`shasum` 호출과 파일 읽기·쓰기뿐이고, 자식 프로세스를 남기지 않으며 서버를 띄우지 않는다. 임계 프로브와 변이가 설정 파일을 잠시 고치지만 그 되돌림은 매번 해시 대조로 증명한다. 정리할 좀비가 없다는 것이 이 카드의 검증이 가진 장점이다 — 유일한 부작용은 `server/coverage/` 산출물인데 `.gitignore` 의 `coverage/` 가 이미 덮는다.

## §E 알려진 위험

| 위험 | 증상 | 완화 |
|------|------|------|
| `--coverage.thresholds.lines=<n>` CLI 오버라이드는 **인식된다**(plan 감사가 실행으로 확인 — 위험 해소). 그러나 **그 형식은 설정 파일을 재지 않는다** | 오버라이드로 재는 프로브는 `server/vitest.config.ts` 가 아예 없어도 동일하게 통과한다 — «게이트가 섰다» 는 오독이 그 자리에서 생긴다 | AC-COVERAGE-003 의 주경로를 **설정 파일 임시 변경(85→98) + 오버라이드 없는 실행 + 해시 대조 되돌림**으로 바꿨다. CLI 오버라이드는 보조 관측으로만 남으며 REQ-COVERAGE-004 의 근거가 아니다 (§D 4) |
| 새 devDependency 선언이 `package-lock.json` 을 예상보다 크게 바꾼다 | 리뷰가 어려워지고 형제 워크스페이스가 흔들린다 | 이미 루트에 설치된 정확한 버전(`4.1.11`)을 범위로 선언한다. 품질 게이트에 `npm test -w channel` 을 두어 형제 무회귀를 확인한다 |
| `coverage-summary.json` 의 파일 키 형식(절대 경로/상대 경로)이 가정과 다르다 | AC-COVERAGE-002 의 `HAS_INDEX` 판정이 거짓 실패한다 | 판정을 `endsWith('src/index.ts')` 로 써 경로 형식에 의존하지 않게 했다 |
| `server/src/` 의 파일 수가 앞으로 바뀐다 | AC-COVERAGE-002 의 `FILE_COUNT=11` 이 정상 변경에서 거짓 실패한다 | run 단계 한정 관측으로 쓴다. 이 숫자는 **이 카드의 착지 시점**을 재는 것이며, 이후 카드가 파일을 더하면 이 기준이 아니라 그 카드가 갱신 대상이다 — §E.2 에 그 사실을 적는다 |
| 계약 테스트(`coverage-contract.test.ts`)가 임계 프로브의 판정을 **막는다** («가린다» 가 아니다 — 아래) | 프로브 주경로가 설정의 `lines` 를 98 로 바꾸면 그 테스트의 단언 4(`lines === 85`)가 함께 실패한다. 그리고 **테스트가 하나라도 실패하면 vitest 4.1.11 은 커버리지 보고와 임계 판정을 아예 건너뛴다** — plan 감사 2회차가 실행으로 확정했다(E13): `--exclude` 없이 돌린 실행의 출력에는 `Statements/Branches/Functions/Lines` 요약도, `does not meet global threshold` 메시지도 **없었다** | AC-COVERAGE-003 이 프로브 실행에서 그 파일을 `--exclude` 로 빼도록 명문화했다. **이 완화는 방어적 군더더기가 아니라 필수다** — 제외가 없으면 프로브 A' 는 임계 미달 메시지 **없이** 종료 1 을 내고 `acceptance.md` 의 관측 1(«임계 미달 메시지가 있다»)이 성립하지 않는다. 나중에 «불필요한 복잡성» 으로 읽고 제거하면 이 기준이 무너진다. 제외된 파일은 `src/**` 를 임포트하지 않으므로 총계에 영향이 없으며, 그 확인은 단계 7 뒤의 **재프로브** 출력으로 한다 |
| `.moai/reports/t7/sync-audit.md` §T5 를 직접 읽지 않았다 | 이 SPEC 의 배경 서술이 카드 인용에만 근거한다 | 배경(§1.1)에 그 사실을 명시했다. 이 SPEC 의 **요구사항은 그 보고서가 아니라 운영자 결정 D1·D2 와 이 워크트리 실측에서 나온다** — 보고서 내용이 다르더라도 요구사항은 흔들리지 않는다 |

## §F 마일스톤

시간 추정은 쓰지 않는다. 이 카드는 마일스톤 하나로 충분하다.

### M1 — 커버리지 도구 도입 (우선순위 High)

**단계 0 — 전제 확인 (구현 전).**
1. `git rev-parse HEAD` 를 `.moai/specs/SPEC-COVERAGE-001/.spec-base-sha` 에 기록한다.
2. 회귀 짝 파일 추가는 리드 승인(2026-08-29)으로 확정돼 있다 — 판정을 기다리는 절차는 없다. 단계 7 을 무조건 수행한다.
3. `npm ls @vitest/coverage-v8 -w server --depth=0` 과 `-w channel --depth=0` 을 실행해 §3 의 실측값(`1` / `0`)이 이 시점에도 그대로인지 확인한다. 다르면 멈추고 보고한다.

**단계 1 (RED — 전이 1).** `npm run coverage -w server` 를 실행해 `Missing script: "coverage"` 로 실패하는 것을 원문으로 기록한다.

**단계 2 — 설정과 스크립트.** `server/vitest.config.ts` 를 만들고 `server/package.json` 에 `coverage` 스크립트를 더한다. **의존성 선언은 아직 하지 않는다.**

설정 파일이 담아야 하는 것 넷 — (a) `provider: 'v8'`, (b) `include: ['src/**']`, (c) `reporter: ['text', 'json-summary']`, (d) `thresholds: { lines: 85 }`. 형태는 `channel/vitest.config.ts` 를 따르되 그 파일에 없는 (c)·(d)가 더해진다. 그리고 **파일 상단 다섯 줄 안**에 진입점을 제외하지 않는 사유를 한국어 주석으로 적으며, 그 주석은 `index.ts` 와 `process.argv` 를 함께 언급해야 한다(REQ-COVERAGE-005, AC-COVERAGE-004 단언 7 이 잰다).

(c)를 빠뜨리면 AC-COVERAGE-002 가 `coverage-summary.json` 부재로 실패한다 — 기본 리포터는 그 파일을 만들지 않는다.

**단계 3 (RED — 전이 2).** `npm run coverage -w server` 가 이제 **돌아간다**. 그러나 `npm ls @vitest/coverage-v8 -w server --depth=0` 은 여전히 종료 `1` 이다. 두 관측을 함께 원문으로 남긴다 — 「돌지만 아직 결함이 남은」 중간 상태를 명시하는 것이 이 단계의 목적이다.

**단계 4 — 의존성 선언.** `server/package.json` 의 `devDependencies` 에 `"@vitest/coverage-v8": "^4.1.11"` 을 더하고 워크트리 루트에서 `npm install` 을 돌린다. `package-lock.json` 변경을 확인한다.

**단계 5 (GREEN — 전이 3).** AC-COVERAGE-001·002 를 실행해 원문을 남긴다.

**단계 6 — 임계 프로브.** AC-COVERAGE-003 의 프로브 A'·B'(설정 파일 임시 변경 경로)와 보조 관측을 실행한다. 프로브 A' 가 실패하지 **않으면** 게이트가 서지 않은 것이므로 멈추고 진단한다 — 통과로 적지 않는다. 이 단계는 단계 7 보다 먼저 오므로 계약 테스트가 **아직 없다.** 따라서 이 시점의 `--exclude` 는 없는 파일을 빼는 무동작이고, AC-COVERAGE-003 의 관측 2(«실패한 테스트가 없다»)와 «제외해도 `Lines :` 가 기준선과 같다» 도 자명하게 참이라 아무것도 재지 못한다. **이 단계가 재는 것은 관측 1·3·4 다**; 나머지 둘은 단계 7 뒤의 재프로브가 잰다(감사 2회차 NEW-02). `--exclude` 는 두 실행에 같은 형태로 쓴다(§E 의 «계약 테스트가 판정을 막는다» 위험).

**단계 7 — 회귀 짝.** `server/test/coverage-contract.test.ts` 를 만들고 AC-COVERAGE-004 를 실행한다. 리드 승인으로 확정된 단계이며 조건부가 아니다.

이어서 변이를 **셋** 돌린다. 각 변이마다 실패 테스트 이름 집합을 원문으로 남기고, 되돌린 뒤 해시 대조로 복원을 증명한다.

| 변이 | 조준하는 단언 | 되돌림 증명 |
|------|---------------|-------------|
| `server/package.json` 의 `devDependencies` 에서 `@vitest/coverage-v8` 줄 **하나만** 삭제 | 단언 1 (의존성 선언, REQ-001) | `shasum -a 256 server/package.json` |
| `server/package.json` 의 `"@vitest/coverage-v8"` 범위를 `"^3.0.0"` 으로 변경 | 단언 6 (메이저 대역 일치, REQ-001 — 감사 F-07) | 같은 파일 해시 |
| `server/vitest.config.ts` 의 `reporter` 배열에서 `'json-summary'` **하나만** 삭제 | 단언 3b (리포터, REQ-002 — 감사 F-02) | `shasum -a 256 server/vitest.config.ts` |

세 변이 각각에서 실패하는 테스트가 **`coverage-contract.test.ts` 하나뿐**이어야 한다. 실패가 없으면 그 단언이 아무것도 재지 않는 것이고, 다른 테스트까지 무너지면 기준이 이 계약이 아닌 다른 것을 재고 있는 것이다.

**단계 7 마무리 — 재프로브 (감사 2회차 NEW-02).** 변이 셋을 되돌린 뒤, 설정의 `lines` 를 다시 98 로 올려 `npm run coverage -w server -- --exclude 'test/coverage-contract.test.ts'` 를 **한 번 더** 돌리고 85 로 되돌린다(해시 대조로 복원 증명). 이번에는 계약 테스트가 **존재하므로** 제외가 실제로 동작하고, 그 출력으로 AC-COVERAGE-003 의 관측 2(«실패한 테스트가 없다»)와 «`Lines :` 가 기준선 `97.01% (325/335)` 와 같다» 를 판정한다. 단계 6 의 프로브 출력과 이 재프로브 출력을 **둘 다** `progress.md` §E.2 에 남긴다.

**단계 8 — 품질 게이트와 범위 경계.** `npm run typecheck -w server` / `npm test -w server` / `npm test -w channel` / AC-COVERAGE-005 의 네 관측(명령 여덟 줄)을 그 문서에 적힌 블록 **그대로** 실행한다 — 형태를 바꾸면 워크트리 격리 가드가 거부한다(감사 2회차 NEW-01).

**단계 9 — 커밋.** `chore(SPEC-COVERAGE-001): server 커버리지 도구 도입 및 라인 85% 임계 강제 (card t13)`.

## §H 안티패턴 (하지 말 것)

- **커버리지를 올리려고 테스트를 더하거나 소스를 고치기.** 이 카드는 재는 도구를 들이는 것이다. 숫자를 움직이면 도구가 무엇을 재는지가 흐려진다.
- **`index.ts` 를 제외해 숫자를 좋게 만들기.** 오늘 여유가 충분하므로 필요가 아니라 습관이다. 그리고 제외는 사유가 낡아도 숫자를 계속 좋아 보이게 한다(§C).
- **임계를 `perFile` 로 걸기.** 정상 트리에서 게이트가 깨지고, 곧 «환경 탓» 으로 무시된다(§B).
- **`npm ls @vitest/coverage-v8 -w server` 를 `--depth=0` 없이 기준으로 쓰기.** 오늘 이미 종료 0 이다 — 아무것도 재지 않는 기준이 된다(§D 2).
- **파일별 커버리지를 텍스트 리포터로 세기.** 100% 파일이 숨겨져 없는 결함을 만들어 낸다(§D 3).
- **임계를 적어 놓고 프로브 없이 «게이트가 선다» 고 적기.** 관측하지 않은 것은 통과가 아니라 Gap 이다.
- **임계 프로브를 CLI 오버라이드로만 돌리고 «게이트가 선다» 고 적기.** 그 형식은 인식되지만 설정 파일을 읽지 않으므로, 설정이 아예 없어도 같은 결과가 나온다 — 아무것도 재지 않는 기준이다(§D 4, 감사 F-01).
- **루트 `package.json` 에 합산 스크립트 더하기.** 운영자 결정 D2 가 명시적으로 배제했다.
- **`channel/` 을 «참고삼아» 한 줄 고치기.** 운영자 결정 D2 이고, AC-COVERAGE-005 관측 2 가 실패한다.
- **`server/coverage/` 를 커밋하기.** `.gitignore` 가 이미 덮으므로, 나타난다면 무언가 잘못된 것이다.
- **AC-COVERAGE-005 의 명령을 «간결하게» 한 줄로 합치기.** 중괄호 그룹 파이프라인과 `$(…)` 명령 치환은 워크트리 격리 가드가 거부한다. 거부당한 자리에서 즉석으로 형태를 지어내는 것도 금지다 — `acceptance.md` 의 블록을 그대로 쓴다(감사 2회차 NEW-01).
- **변경 파일 목록을 `git diff --name-only` 로만 재기.** 이 카드가 만드는 파일 둘은 미추적 신규이므로 그 명령에 보이지 않는다 — 올바른 구현을 거짓 실패시킨다(AC-COVERAGE-005, 감사 F-04).
