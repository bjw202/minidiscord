# SPEC-CHANAUTH-001 구현 계획

> 이 문서는 `spec.md` 의 요구사항을 **어떻게** 세울지를 정한다. 무엇을 만들지는 `spec.md`, 무엇으로 판정할지는 `acceptance.md` 가 소유한다.

바꾸기 어려운 결정을 앞에 둔다 — 사람이 검토할 때 되돌리기 비싼 것부터 보게 하려는 배치다. §B 가 계약 개정이고, §C·§D 가 그 개정을 어디에 놓을지의 결정이며, §E 부터는 그것을 지키기 위한 기술적 처리다.

## §B 되돌리기 어려운 결정 — 무상태 원칙을 좁힌다

카드 `t4` 는 이 질문을 **열어 둔 채** 넘겼다. 두 갈래가 있었다.

| 갈래 | 내용 | 고르지 않은 이유 |
|------|------|-----------------|
| (가) 무상태 유지 | 인증을 전송 계층에서만 해결한다 — `welcome` 게이트 + `wss://` 강제. 채널은 계속 아무것도 기억하지 않는다 | **서버 자신이 손상되거나 토큰이 유출된 경우의 승인 주입을 막지 못한다.** 승인은 사람의 의사를 대신하는 값이므로 그 한 축만은 채널이 자기 눈으로 확인할 수 있어야 한다 |
| (나) 발신 id 를 기억한다 | 채널이 내보낸 `request_id` 집합을 프로세스 메모리에 두고 그 안의 판정만 중계한다 | **고른 쪽.** 값의 비용이 비대칭이다 — 잘못 막으면 사람이 승인을 한 번 더 눌러야 하고, 잘못 통과시키면 `rm -rf` 가 승인 없이 실행된다 |

**(나)를 고르되 (가)도 함께 세운다.** 셋 중 어느 하나도 단독으로는 F-01 을 닫지 못한다(`spec.md` §1 의 세 겹 그림).

**개정의 범위를 좁게 못 박는다.** 디스크 무상태·설정의 환경변수 한정·요청 내용 미보관·타임아웃 부재·재전송 부재는 전부 그대로다. 새로 인정되는 것은 **`request_id` 문자열들의 상한 있는 목록 하나**뿐이다. 이 문장이 개정의 경계이며, 이보다 넓은 상태를 들이려는 변경은 이 SPEC 이 아니라 새 SPEC 의 일이다.

이 결정의 귀결로 `SPEC-CHANPERM-001` 의 다음이 바뀌었다 (그쪽 v0.3.0 HISTORY 참조).

- REQ-CHANPERM-008 — 무상태 조항 → 발신 집합 대조 조항
- AC-CHANPERM-008 — "모르는 id 도 중계된다"를 정상으로 못 박던 기준 → "발신하지 않은 id 는 중계되지 않는다"
- **AC-CHANPERM-005·006·009 — 발신 한 줄 추가** (v0.4.0). 셋 다 발신 없이 판정을 밀어 넣던 형태라 개정된 계약에서 거짓 실패한다
- **AC-CHANPERM-007 — 관측 형태 변경** (v0.4.0). 두 방향을 다른 값으로 재던 형태는 발신 집합 대조와 원리상 양립 불가 — 같은 id 로 재고, 잃은 관측은 카드 `t7` 소관임을 명시
- **`SPEC-CHANCLIENT-001` REQ-CHANCLIENT-004·005 — 세션 확립 전제 추가** (v0.4.0). 그쪽의 무조건 분배 의무가 REQ-CHANAUTH-001 과 정면 충돌한다. 하네스 `autoWelcome` 과 AC-CHANCLIENT-002·005 본문이 함께 바뀌었다
- §2 용어 "무상태", §4.3 절 제목, §5 범위 밖 한 줄, 엣지 케이스 두 줄, 검증 원칙 표 한 줄
- `plan.md` §B 상태 표와 §H 안티패턴 한 줄

## §C 되돌리기 어려운 결정 — 발신 집합은 `channel-server.ts` 에 둔다

후보는 둘이었다.

| 후보 | 문제 |
|------|------|
| `index.ts` 의 `wire()` 클로저 | 발신(`sendPermissionRequest`)과 수신(`onVerdict`)이 서로 다른 클로저라 그 사이에 상태를 끼워야 한다. 그리고 **`SPEC-CHANPERM-001` 의 수용 기준 하네스가 이 게이트를 관측하지 못한다** — 그쪽은 `attach()` 로 채널 서버를 직접 만들고 `handle.handlePermissionVerdict` 를 부른다 |
| `channel-server.ts` | **고른 쪽.** 발신과 수신을 둘 다 보는 유일한 지점이고, 기존 하네스가 그대로 관측한다 |

**기준이 재지 못하는 방어는 회귀에서 사라진다.** 감사 §3.2 가 이 프로젝트에서 이미 확인한 부류이며(변이 M1·M4 생존), 같은 실수를 되풀이하지 않으려고 자리를 이렇게 골랐다.

부수 효과 하나를 명시한다 — 발신 집합이 `channel-server.ts` 에 있으므로, `wire()` 의 `onVerdict` 는 **한 글자도 바뀌지 않는다.** 배선은 여전히 받은 판정을 그대로 `handlePermissionVerdict` 에 넘기고, 거를지 말지는 채널 서버가 판단한다.

## §D 되돌리기 어려운 결정 — 전송 검사는 `resolveUrl` 밖에 둔다

`resolveUrl(env)` 는 **순수 해석 함수로 남는다.** 검사는 새로 내보내는 `isTransportAllowed(url: string): boolean` 이 하고, 진입점이 `gw.start()` 앞에서 그것을 부른다.

세 가지가 이 배치를 고정한다.

1. **형제 기준.** AC-CHANWIRE-011 이 `MINIDISCORD_SERVER=ws://example/bot` 의 반환값을 글자 그대로 단언한다. 검사를 `resolveUrl` 안에 넣으면 정상 구현이 형제 기준을 거짓 실패시킨다.
2. **stdio 를 잠그지 않는다.** `SPEC-CHANWIRE-001` v0.2.0 이 같은 이유로 토큰 게이트를 게이트웨이 접속에만 걸었다(REQ-CHANWIRE-003·004). 이 검사도 같은 형태를 따른다 — 형제 SPEC 의 토큰 없는 dist 프로브(AC-CHANNEL-002·004·005, AC-CHANWIRE-014)가 계속 실행 가능해야 한다.
3. **판정만 하는 함수는 표로 잴 수 있다.** 순수 함수라 AC-CHANAUTH-010 이 8행 판정표를 한 번에 단언할 수 있고, 진입점이 그것을 실제로 부르는지는 AC-CHANAUTH-011 (a)가 자식 프로세스로 따로 잰다. 둘로 나눠야 "판정은 맞는데 아무도 안 부른다"가 드러난다.

**진단은 stderr 한 줄.** stdout 은 MCP 전송 통로이므로 한 글자도 쓸 수 없다(REQ-CHANAUTH-004). 프로세스를 종료시키지는 않는다 — 종료시키면 stdio 로 말을 걸던 상대가 이유 없이 끊긴 것으로 본다.

## §E 알려진 위험

| 위험 | 증상 | 완화 |
|------|------|------|
| `welcome` 을 인증 증거로 쓰는 것이 완전한 상호 인증이 아니다 | 토큰이 유출되면 게이트가 통째로 무의미해진다 | 완화하지 않는다. 그 경우의 방어는 발신 집합 대조 한 겹뿐이며, 이 한계를 `spec.md` §2·§5 에 명시했다 |
| `welcome` 이 두 번 오는 경우를 관측하지 않는다 | 서버 구현이 바뀌어 중복 `welcome` 을 보내면 `onWelcome` 이 두 번 불린다 | 미완화. 현재 서버는 한 번만 보낸다. 엣지 케이스 표에 "미검증"으로 기록 |
| 상한 128 이 실사용 분포와 맞는지 재지 않았다 | 승인 요청을 129건 이상 쌓아 둔 사용자의 오래된 승인이 조용히 무시된다 | 증상이 REQ-CHANAUTH-006 의 정상 동작과 같아 진단이 어렵다. 값의 근거를 `spec.md` REQ-CHANAUTH-008 에 적고 §E.2 Gaps 에 남긴다 |
| 부정 관측의 대기 시간이 원리상 완벽하지 않다 | 부하 걸린 기계에서 "늦게 온 것"을 "안 온 것"으로 읽을 수 있다 | 짝이 되는 양성 기준이 같은 하네스에서 수십 ms 안에 통과하므로 `settle()` 400ms 는 그 여러 배다. 인프로세스가 아니라 소켓을 건너는 관측이므로 이 여유를 둔다 |
| 실 게이트웨이와의 왕복을 시험하지 않는다 | 실제 서버가 `welcome` 을 보내는 시점이 스텁과 다르면 초기 프레임이 버려질 수 있다 | 실서버는 `hello` 검증 직후 `welcome` 을 보내고 그전에는 아무 프레임도 보내지 않는다(`server/src/gateway.ts`). 그래도 이 SPEC 은 스텁 대상이며, 실결합은 E2E 소관으로 남긴다 |
| 커버리지 제외가 `index.ts` 를 계속 가린다 | 전송 검사의 진입점 호출부가 수치 근거 0 으로 남는다 | AC-CHANAUTH-011 (a)의 자식 프로세스 관측이 실질 근거다. 감사 F-10 의 정정(제외 제거 또는 사유 정정 + 헤드라인 병기)을 품질 게이트에 적었다 |
| 세 파일을 동시에 고친다 | 형제 SPEC 이 같은 패키지를 만지면 충돌한다 | 카드 `t9` 는 이 워크트리에서 단독으로 돈다. 병렬 카드가 생기면 리드에게 보고한다 |
| **F-01 의 절반이 열린 채 남는다** | `welcome` 한 줄로 답할 수 있는 상대는 사칭 채팅과 이력 오염을 그대로 밀어 넣는다 | **완화하지 않는다.** 닫으려면 `server/` 서명·논스가 필요하고 REQ-CHANAUTH-013 이 금지한다. `spec.md` §5 가 카드 `t15` 로 인계했고, §E.2 Gaps 에 다시 남긴다. **이 카드의 성과를 «F-01 을 닫았다»로 보고해서는 안 된다** |
| 형제 스위트 두 곳을 같은 run 에서 고친다 | `permission-relay.test.ts` 5건 + `gateway-client.test.ts` 7건 = 12건이 한 번에 붉어진다 | 마일스톤을 나눠 관측한다 — CHANCLIENT 쪽은 M1 단계 1b, CHANPERM 쪽은 M3 단계 1. 두 무리를 섞어 고치면 어느 개정이 어느 실패를 닫았는지 증거가 갈린다 |

## §F 마일스톤

시간 추정은 쓰지 않는다. 우선순위와 순서만 정한다. 순서는 **바깥 겹부터** 다 — 전송 계층을 먼저 닫아야 그다음 겹의 관측이 오염되지 않는다.

### M1 — `welcome` 게이트 (우선순위 High)

**단계 0 — 전제 확인 (구현 전).**
1. `git rev-parse HEAD` 를 `.moai/specs/SPEC-CHANAUTH-001/.spec-base-sha` 에 기록한다.
2. `channel/src/gateway-client.ts` 의 프레임 분배(60-75행)와 `connect()`/`retry()` 의 실제 형태를 읽어 `spec.md` §3 의 기술과 같은지 확인한다. 다르면 멈추고 보고한다.
3. `.moai/state/verify/t4-sync-audit/probe-rogue.ts` 를 그대로 한 번 돌려 **현재 트리에서 F-01 이 여전히 재현되는지** 확인하고 원문을 §E.2 에 남긴다. 재현되지 않으면 그 사실이 먼저 설명되어야 한다.

**단계 1 (RED).** `channel/test/transport-auth.test.ts` 에 공통 하네스와 AC-CHANAUTH-001·002·003·004·005 를 쓴다. 001·003(가)·004·005 가 **단언 실패**로 실패하는 것을 확인한다. **002 와 003(나)는 이 시점에 통과하지 않아도 정상이다** — 둘 다 §4.2 의 발신 집합(M3)을 전제하는 왕복이므로, M1 시점에는 002 의 판정 갈래가 게이트 없이도 도달해 통과하고 003(나)는 확립 전제가 없으므로 통과한다. 두 기준의 최종 판정은 M3 GREEN 에서 함께 관측한다.

**단계 1b — 형제 스위트 개정 (`SPEC-CHANCLIENT-001` v0.4.0).** 게이트를 세우기 **전에** `channel/test/gateway-client.test.ts` 를 한 번 그대로 돌려 초록을 확인하고, 단계 2 구현 **직후** 다시 돌려 **일곱 건이 깨지는 것을 눈으로 관측한 뒤** 원문을 §E.2 에 남긴다(전건 목록: `spec.md` §3.2). 그 실패를 확인한 뒤에야 하네스에 `autoWelcome` 을 달고 AC-CHANCLIENT-002·005 본문을 개정본으로 교체한다. **개정본을 먼저 넣으면 계약 충돌이 실재했다는 증거가 남지 않는다** — M3 단계 1 과 같은 원칙이다.

**단계 2 (GREEN).** `connect()` 안에 소켓 지역 상태 하나(`established` — `authenticated` 라 부르지 않는다, `spec.md` §2)를 두고, `welcome` 에서 참으로 바꾼 뒤 나머지 세 분기 앞에 검사를 건다. 상태는 `connect()` 호출마다 새로 만들어지므로 재접속 시 자동으로 미확립으로 돌아간다 — 이것이 REQ-CHANAUTH-003 을 코드 구조로 보장하는 형태다.

**단계 3.** `npm test -w channel` 통과 + `npm run typecheck -w channel` 종료 코드 `0`.

**단계 4 — 변이 A·B·C 관측.** `acceptance.md` §품질 게이트의 변이 표대로 적용·실행·되돌린다.

**단계 5.** 커밋: `feat(t9): gate gateway frames behind welcome authentication`.

### M2 — 비루프백 `wss://` 강제 (우선순위 High)

**단계 1 (RED).** AC-CHANAUTH-010·011 을 쓴다. 010 은 `isTransportAllowed` 미수출로, 011 (a)는 단언 실패로 실패한다. **두 사유를 구분해 기록한다.** 판정표는 **9행으로 이미 확정돼 있다** — `ws://127.0.0.1.evil.com/bot → false` 행 추가 여부를 run 단계에서 정하던 v0.1.0 의 미결은 계획 단계에서 닫았다(계획 감사 M-02). 이 단계에서 새로 정할 것은 없다.

**단계 2 (GREEN).** `index.ts` 에 `isTransportAllowed(url)` 를 내보내고 — 내장 `URL` 로 파싱, 실패하면 `false`, `hostname` 이 루프백 **네 값**(`127.0.0.1`·`localhost`·`::1`·`[::1]`) 중 하나면 `true`, 아니면 `protocol === 'wss:'` — 진입점의 `if (token) gw.start()` 를 `if (token && isTransportAllowed(url)) gw.start()` 형태로 바꾼다. 거부하는 갈래에서 stderr 한 줄을 낸다.

**단계 3.** 빌드(`npm run build -w channel`)가 AC-CHANAUTH-011 의 전제다. 빌드 뒤 실행하고, 끝나면 `pgrep -f 'channel/dist/index.js'` 로 남은 프로세스가 없음을 확인한다.

**단계 4 — 형제 비회귀.** `--reporter=verbose` 출력에서 AC-CHANWIRE-011·014, AC-CHANNEL-002·004·005 의 `✓` 줄을 확인해 §E.2 에 남긴다.

## §H 안티패턴 (하지 말 것)

- **세션 확립 상태를 클라이언트 단위로 두기.** 한 번 인증되면 게이트가 영구히 열려, 재접속 시점에 포트를 선점한 상대가 그대로 통과한다. F-01 이 그대로 되살아나고 AC-CHANAUTH-001·002 는 계속 통과한다 (변이 B).
- **게이트에서 예외 던지기.** 소켓이 끊기고 봇이 끝없이 재접속을 돈다. 증상이 결함처럼 보이지 않고 간헐적인 느림으로만 나타난다 (변이 C).
- **인증 전 프레임 버퍼링해 두었다가 인증 후 재전달하기.** 게이트가 무의미해진다 — 인증 전 주입이 인증 후에 되살아난다.
- **발신 집합을 `wire()` 에 두기.** `SPEC-CHANPERM-001` 의 수용 기준 하네스가 그 게이트를 관측하지 못한다. 기준이 재지 못하는 방어는 회귀에서 사라진다 (§C).
- **조회만 하고 지우지 않기.** 한 번 발신된 id 가 영구 통행권이 되어, 같은 id 로 `deny` 를 `allow` 로 덮어쓰는 재생이 가능해진다 (변이 E).
- **`request_id` 를 정규화해 집합에 넣기.** REQ-CHANPERM-007 위반이고, 서버 쪽 결함(카드 `t7`)을 여기서 덮으려는 유혹이 실제로 생기는 자리다.
- **상한 없는 집합.** 만료가 범위 밖이므로 답을 받지 못한 요청마다 문자열이 영원히 남는다.
- **전송 검사를 `resolveUrl` 안에 넣기.** 형제 기준 AC-CHANWIRE-011 이 정상 구현에서 거짓 실패한다 (§D).
- **전송 검사로 stdio 까지 잠그기.** 형제 SPEC 의 토큰 없는 dist 프로브가 조용히 실행 불가가 된다.
- **진단을 stdout 으로 내기.** stdout 은 MCP 전송 통로다. 한 줄이 프로토콜을 깨뜨린다.
- **개정본을 먼저 넣고 구현하기.** 개정 전 AC-CHANPERM-008 이 실패하는 순간이 관측되지 않으면, 계약 충돌이 실재했다는 증거가 남지 않는다 (M3 단계 1).
- **셸 명령으로만 재는 기준 만들기.** 감사 §3.2 가 지목한 부류다 — 한 번 관측되고 회귀에서 사라진다.
- **`toContain` / `indexOf` 로 단언하기.** 접두만 맞아도 참이 된다. 배열은 `toEqual` 로 통째로 잰다.
- **고정 `sleep` 으로 소켓 왕복 기다리기.** 부하 걸린 기계에서 정상 구현이 거짓 실패하고, 그 사유가 진짜 결함과 구분되지 않는다. 양성 관측은 `waitFor`, 부정 관측만 `settle()`.
- **자식 프로세스 수거를 명령 끝의 `kill` 한 줄에 맡기기.** 단언이 먼저 실패하면 그 줄에 닿지 않고, 남은 프로세스가 다음 기준의 연결 수를 오염시킨다.
- **`welcome` 게이트를 «인증» 이라 부르기.** v0.1.0 이 그렇게 부르다 근거까지 지어냈다(계획 감사 C-01). 코드 식별자도 `established` 로 둔다 — 이름이 다음 독자의 추론을 만든다.
- **`CHANGELOG.md` 를 이 카드에서 고치기.** 구현이 착지하기 전에 고치면 아직 없는 동작을 기술하게 되고, 그 파일은 `manager-docs` 소유다. sync 단계 정정 목록으로만 넘긴다 (`spec.md` §5).
- **`server/` 를 "잠깐만" 고치기.** AC-CHANAUTH-012 가 실패한다. 서버 쪽 수정이 필요해 보이면 멈추고 보고한다 — F-14 는 별도 카드다.
- **디스크에 파일 쓰기.** 개정 뒤에도 디스크 무상태는 그대로다.
