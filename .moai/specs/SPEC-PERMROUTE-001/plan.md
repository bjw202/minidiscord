## §D 결정 — 각 항목은 결론 · 고르지 않은 갈래 · 그 갈래가 지는 이유

### §D-1 접속 신원을 무엇으로 표현하는가 (가장 되돌리기 어렵다)

**결론.** `ConnInfo` 에 **불투명 문자열 필드 `connId`** 를 더한다. 값은 `randomUUID()` 로 등록 자리 하나(`gateway.ts` `conns.set`)에서 발급하고, `Established` 는 그 필드를 **필수로 좁혀** 발급 누락이 타입에서 잡히게 한다(`Established = ConnInfo & { connId: string; … }`).

**고르지 않은 갈래.**

| 갈래 | 지는 이유 |
|---|---|
| `WebSocket` 참조를 그대로 `open` 맵에 넣는다 | 대기 항목이 소켓 객체를 붙들어, 접속이 끊겨도 소켓과 그 버퍼가 회수되지 않는다(§D-4 와 정면 충돌). 게다가 `permissions.ts` 가 `ws` 타입에 결합되고, 봉투를 입히는 유일한 통로(`sendEstablished`)를 우회해 보낼 능력을 브로커에 준다 |
| 불투명 발신 콜백(클로저)을 `open` 에 넣는다 | 같은 소켓 붙듦에 더해 `Established`(세션 열쇠·`seq`)를 통째로 클로저에 가둔다. 무엇보다 **발신 권한이 게이트웨이 밖으로 나간다** — 오늘 게이트웨이가 지는 (방, 봇) 대조와 봉투 규칙이 그 통로에서만 사라진다 |
| `ConnInfo` 를 그대로 두고 `ConnInfo & { connId }` 별도 타입을 핸들러 인자로 쓴다 | `connId` 가 필수가 되어 형제 시험 30자리가 타입 검사에서 깨진다. 개정 범위만 넓히고 얻는 것이 없다 — REQ-GW-020·021 개정은 어느 갈래에서도 어차피 필요하므로 「개정을 피한다」는 이 갈래의 장점이 아니다 |

**`Established` 가 `ConnInfo` 위에 얹혀 있다는 성질을 어떻게 쓰는가.** `type Established = ConnInfo & { … }` 이므로 `ConnInfo` 에 더한 필드는 `Established` 로 자동 전파된다. 필수로 더하면 **생산 두 자리**(`gateway.ts:142` 핸들러 호출 · `:204` `Established` 구성 — 실측값)만 고치면 되므로 이 방향의 비용은 작다. 비용의 **대부분**은 반대편 — 30자리 시험 리터럴 — 에 있고, 그래서 `ConnInfo` 쪽을 선택으로 두고 `Established` 쪽에서만 좁히는 비대칭이 나온다.

**「전부 반대편」은 아니다.** 선택 필드를 골라도 그 30자리 가운데 여럿은 실행으로 깨져 편집해야 한다(§D-1 정정). 비교는 「30 대 0」이 아니라 **「30(타입, 실측) 대 14(실행, 읽기 추론)」**이며, 비대칭의 방향은 그대로지만 폭은 이만큼 좁다. **두 수의 자격이 다르다** — 30 은 `npm run typecheck -w server` 를 돌려 얻었고, 14 는 아직 없는 구현의 동작을 문서에서 읽어 도출했다.

#### §D-1 처분 — **선택 필드** (리드 처분으로 확정, 미결 닫힘)

**결정 주체: 운영자 (리드 `AskUserQuestion` 경유).** 기록: `.moai/reports/t34/lead-decisions.md`. 이 결정은 이 레인의 추론이 아니라 리드 처분이며, 뒤에 오는 독자가 누가 정했는지 읽을 수 있게 그 파일을 출처로 적는다.

처분이 붙인 조건: **감사 F-07 대로 `undefined` 좁히기 분기를 재는 수용 기준 1건을 세울 것** → `AC-PERMROUTE-013` 으로 이행했다. 선택 필드는 생산 코드에서 조용히 빠질 수 있고 그때 판정은 REQ-PERMROUTE-007 의 실패 갈래로 떨어져 **사용자에게 보이는 오작동**이 되므로, 타입이 막지 않는 갈래를 기준 하나가 직접 잰다.

**측정한 것 — 필수로 두었을 때의 파급 (실측, 결정의 근거가 아니라 결정에 붙은 기록).**

```
$ (스크래치) export interface ConnInfo { roomId: number; botId: number; connId: string }
$ npm run typecheck -w server        → exit 1
   2 src/gateway.ts          (:142 핸들러 호출 · :204 Established 구성)
  27 test/permissions.test.ts
   2 test/room-members.test.ts
   1 test/web-permission-contract.test.ts
= 형제 시험 30 + 생산 2
$ (되돌림) git status --short -- server/ → 빈 출력 · npm run typecheck -w server → exit 0
```

전문 출력·되돌림 기록: `.moai/reports/t34/evidence/D1-connid-required-typecheck.txt`.

**판독: 형제 시험 파급은 정확히 30자리로, 계획이 `grep` 으로 센 분모와 일치한다.** 리드가 건 재회부 조건(「30자리와 다르게 나오면 리드에 재회부」)은 **발동하지 않는다.**

**[HARD] 정정 (2판) — 「선택 필드는 30자리를 건드리지 않는다」는 타입 검사에 대해서만 참이고, 그 파급의 크기는 이 SPEC 이 두 번 틀렸다.**

위 결론은 그 문장을 근거로 삼았는데, 실행에 대해서는 거짓이다. 형제 시험 30자리 가운데 일부는 `connId` 없이 요청을 만든 뒤 **실제 소켓이 판정을 받는다**고 단언하므로, 선택 필드에서 `info.connId` 가 `undefined` 가 되면 REQ-PERMROUTE-007 의 실패 갈래로 떨어져 붉어진다.

**그 자리 수를 plan 2회차는 7 로 적었고, 그것은 부분 계수였다.** 2회차 감사가 전수로 세어 **14** 를 냈고(배달을 단언하는 12 + 성공·실패 문구가 서로 다름을 단언하는 `:303`·`:304` 둘), 리드가 그 값을 수용했다(`.moai/reports/t34/lead-decisions.md` 「정정 — 회부 방아쇠 «7» 은 거짓」). 리드는 자기 귀속도 함께 적었다 — 표본 두 자리만 대조하고 7 을 통과시켰다는 것.

**[HARD] 14 는 실측값이 아니다.** 2회차 감사관의 독립 계수이며, 감사관 스스로 그 보고서 §6 Gaps 에서 **「실행 관측이 아니라 읽기 추론」**이라고 공시했다. 전제는 아래 M3-2 가 지시한 동작(「`info.connId` 가 `undefined` 인 대기 항목은 `sendToOrigin` 을 부르지 않고 곧바로 실패 갈래로 보낸다」)이고, 구현이 없으므로 지금 실행으로 확인할 방법이 없다. **이 문서는 14 를 사실로 주장하지 않는다** — 자리 목록과 판정선을 `spec.md` §6.2 **18행**에 적어 두고, 실측은 run 에 넘긴다.

즉 **선택/필수의 비용 차이는 「30 대 0」이 아니라 「30(타입, 실측) 대 14(실행, 추론)」이다.** 그래도 처분은 뒤집지 않는다 — 결정은 리드의 것이고, 14 < 30 이라 처분 방향과 같은 쪽이며(리드가 그 판단을 명시 유지했다), 무엇보다 `AC-PERMROUTE-013` 이 처분이 걱정한 갈래를 직접 잰다.

### §D-2 게이트웨이 공개 계약의 모양

**결론.** `Gateway` 에 **새 메서드** `sendToOrigin(connId: string, payload: object): boolean` 을 더한다. `sendToBot` 의 시그니처는 건드리지 않는다.

**고르지 않은 갈래 — `sendToBot(roomId, botId, payload, connId?)` 로 넷째 인자를 더한다.** 지는 이유 둘. (1) 표적 발신이 브로드캐스트의 **인자 모양**이 되어, 호출자가 `connId` 를 `undefined` 로 넘기면 조용히 전원 발신으로 떨어진다 — 이 카드가 없애려는 실패 모양 바로 그것이다. (2) 두 발신은 주소 공간이 다르다(`(방, 봇)` 대 접속 하나) 그리고 `false` 의 뜻이 다르다(「그 봇이 아무 데도 없다」 대 「그 접속이 없다」). 한 시그니처에 두 뜻을 겹치면 REQ-PERMROUTE-007 의 문구 분화가 호출부에서 판별 불가능해진다.

「개정을 피할 수 있다」는 이 결정의 논거가 **아니다.** REQ-GW-021 이 `Gateway` 인터페이스를 글자 그대로 고정하므로 메서드를 더하든 시그니처를 고치든 개정은 똑같이 일어난다. 그러니 순수하게 API 자체의 옳고 그름으로만 갈랐다.

**이름.** `sendToConn` 은 쓰지 않는다 — `gateway.ts:324` 의 비공개 전원 발신 함수가 이미 그 이름이다(§B-4).

### §D-3 요청한 접속이 이미 사라졌을 때

**결론.** `false` 를 돌려주고 **브로드캐스트로 대체하지 않는다.** REQ-PERM-009 의 기존 실패 안내 경로가 그대로 발동하되, **문구를 고친다**(REQ-PERMROUTE-007).

**이 갈래는 드문 예외가 아니다.** 운영자는 방을 읽고 몇 분 뒤에 답하고, 그 사이 봇 세션이 재접속하면 새 소켓이 된다. 둘 다 정상 동작이므로 이 경로는 **흔하다.**

**그래서 대체 갈래가 지는 이유가 결정적이다.** 브로드캐스트 대체는 흔한 경로에서 채널 가드 의존을 되살린다 — 즉 목표 2(의존 해제)가 **달성되지 않고 조건부로 남는다.** 조건부로 남은 의존은 코드를 읽는 사람이 「이제 안 쓴다」고 읽으므로 없는 의존보다 위험하다. 이 판단을 SPEC 본문(REQ-PERMROUTE-008)에 명시적으로 적었다.

**사람이 보는 것.** 방에 「⚠️ 판정을 요청한 세션이 끊겨 전달하지 못했습니다 (`<id>`)」 계열의 한 줄이 뜬다. 대기 항목은 이미 소비됐으므로 같은 답을 다시 쳐도 아무 일이 없고, 사람은 봇 터미널에서 직접 승인하거나 도구를 다시 호출해야 한다. 이것은 `SPEC-PERM-001` REQ-PERM-003 이 재시작 갈래에서 이미 받아들인 것과 같은 모양의 결과다.

낡은 문구(「봇이 접속해 있지 않아」)를 그대로 두면 이 흔한 경로에서 사람에게 **틀린 진단**을 준다 — 봇은 멀쩡히 붙어 있다.

**실패 문구는 하나가 아니라 둘이다 (2회차 감사 N-06).** REQ-PERMROUTE-007 이 갈래를 둘로 나눴다 — (ㄱ) `sendToOrigin` 이 `false` → 「요청한 세션이 끊겼다」, (ㄴ) 대기 항목에 `connId` 자체가 없음 → 「요청한 세션의 **신원이 기록되지 않았다**」. (ㄴ) 에 (ㄱ) 의 문구를 쓰면 아무것도 끊기지 않은 갈래에 「끊겼다」를 적는 것이고, 그것은 위 문단이 낡은 문구를 비판한 것과 **같은 부류의 틀린 진단**이다. 초판은 `AC-PERMROUTE-013` 의 판정선을 (ㄷ) 와 같게 두어 정확히 그 실수를 했다.

**[HARD] 두 문구 모두 꼬리 「전달하지 못했습니다 (`<request_id>`)」를 유지해야 한다 — 이것은 문서 결합이 아니라 살아 있는 코드 결합이다.** `web/rich.js` 의 `RESOLUTION_RE` 가 이모지와 앞부분을 쓰지 않고 그 꼬리만으로 판정 결과 메시지를 인식한다(실물 확인):

```
$ grep -n 'RESOLUTION_RE =' web/rich.js
67:const RESOLUTION_RE = /^.*(?:승인 전송됨|거절 전송됨|전달하지 못했습니다) \(([a-km-z]{5})\)$/
```

꼬리를 끊으면 `permissionResolutionId` 가 `null` 을 돌려주고, 이미 끝난 요청에 승인·거절 버튼이 다시 살아난다(`SPEC-WEBRICH-001` REQ-WEBRICH-010). 이 제약은 **문구를 새로 지을 때 넘어야 할 선**이며, `server/test/web-rich.test.ts:196-197` 이 그 인식을 실제로 재고 있다. 3회차 수리가 §6.2 11행의 세 자리를 다시 열어 대조하다가 찾았다.

### §D-4 대기 항목이 무엇을 얼마나 오래 쥐는가

**결론.** 불투명 문자열 `connId` 만 쥔다. 접속 종료를 듣는 훅도, 축출 장부도 만들지 않는다. 낡은 `connId` 는 아무 접속에도 맞지 않아 §D-3 의 갈래로 떨어진다.

**새는 것이 있는가 — 없다, 그리고 그 근거는 세 갈래다.** (1) `connId` 는 `randomUUID()` 문자열이라 소켓 객체·버퍼·세션 열쇠 어느 것도 붙들지 않는다. (2) 값 자체로는 아무 권한도 아니다 — 게이트웨이의 살아 있는 접속 목록 안에서만 접속으로 해석되고, 목록에 없으면 그냥 맞지 않는 문자열이다. (3) 대기 항목의 수명은 이 카드가 바꾸지 않는다 — 답이 오거나 프로세스가 재시작할 때까지 남는 성질은 `SPEC-PERM-001` REQ-PERM-003 이 이미 수용한 설계이고, 이 카드는 그 항목이 담는 **내용**만 넓힌다. 즉 **새 누수를 들이지 않는다**가 이 결정이 넘어야 할 기준이고, 넘는다.

**고르지 않은 갈래 — 접속 종료 시 그 `connId` 의 대기 항목을 지운다.** 지는 이유: 게이트웨이가 브로커의 내부 자료구조를 알아야 하거나 새 콜백 계약이 생긴다. 얻는 것은 「짧은 문자열 하나가 조금 일찍 사라진다」뿐이고, 사람이 보는 동작은 어느 쪽이든 같다(둘 다 §D-3 의 안내로 끝난다). 부품 사이의 결합을 늘려 사용자에게 보이지 않는 개선을 사는 거래다.

### §D-5 전원 발신은 남는가

**결론.** `sendToBot` 은 전원 발신 그대로 **남긴다.** 첫 일치 `return` 으로 되돌리지 않는다. 이 SPEC 착지 뒤 그 메서드의 **생산 호출자가 0** 이 된다는 사실을 SPEC 본문(REQ-PERMROUTE-011)에 명시한다.

**분모를 명령으로 셌다.**

```
grep -rc 'sendToBot' . | grep -v node_modules | grep -v '/dist/' | grep -v '^\./\.git/' | grep -v ':0$'
```

- 생산 호출자 **1**: `server/src/permissions.ts:99` — 이 카드가 `sendToOrigin` 으로 옮긴다
- 자기 자신 **3**: `server/src/gateway.ts` 의 인터페이스 선언(`:28`) · 주석(`:261`) · 구현(`:361`)
- 시험 **8**: `gateway.test.ts` 6 · `room-members.test.ts` 1(`{type:'ping'}` 로 범용 사용) · `permissions.test.ts` 1(주석)

**되돌리는 갈래가 지는 이유.** 첫 일치 `return` 으로 되돌리면 `deliver`(전원)와 갈래가 다시 어긋나고, D-5 의 뿌리 — 두 발신 지점의 배달 방식이 다르다 — 가 미래의 호출자에게 되살아난다. `t32` 가 갈래를 맞춘 것 자체는 옳은 정정이다.

- **[HARD] 대조 전에 집계 기준 제외 규칙을 적용한다** (변이표 머리, 2회차 감사 N-02). `AC-PERMROUTE-012` **전체**와 `AC-PERMROUTE-007` 의 「파일 전체 초록」 **절반**은 다른 기준의 통과 여부를 합산하므로 셈에서 뺀다 — 빼지 않으면 여섯 행 중 다섯이 자동으로 「어긋남」으로 보고된다. 실제 실행에서는 그 둘도 함께 붉어질 것이고 **그것이 정상이다**; 보고서에는 「집계 기준 둘은 예상대로 함께 붉었고 셈에서 제외했다」를 적어 남긴다

- **M6(채널 `emitted` 가드 제거)의 기대 집합은 `008` 하나다.** 「서버 쪽 0건」은 판정값에서 뺐다 — 서버 패키지가 `channel/` 을 import 하지 않아(`grep -rn "from .*channel" server/src server/test` → 무출력·`exit 1`) 그 값은 변이 전에 이미 정해져 있다(1회차 sync 감사 F-04). REQ-PERMROUTE-010 의 측정은 `AC-PERMROUTE-003b` 와 `AC-PERMROUTE-009` (가) 가 진다
- M6 은 `channel/` 을 건드리므로 되돌림을 `git hash-object` 로 확인하고, `git diff --stat -- channel/` 이 다시 빈 출력임을 관측해야 완료된다 — 그 관측이 `AC-PERMROUTE-008` 의 재실행이다

## §G 안티패턴 — 하지 않을 것

- **`channel/` 을 고치지 않는다.** `emitted` 가드를 「이제 필요 없으니 지우자」로 읽으면 재생 방어(REQ-CHANAUTH-007)가 함께 사라진다. 이 카드는 가드의 **임무 하나를 덜어낼 뿐** 가드를 없애지 않는다. **예외 아님 — 변이 M6:** 이 금지는 **착지하는 편집**을 금지하며, M6 은 변이 창 안에서만 존재하고 되돌린다. 되돌림을 `git hash-object` 로 확인하고 `git diff -- channel/` 이 다시 빈 출력임을 관측해야 M6 이 완료된다
- **`sendToOrigin` 에 브로드캐스트 대체를 넣지 않는다**(§D-3). **`connId` 가 `undefined` 인 갈래에서도 마찬가지다** — 그 갈래를 대체 발신으로 「구제」하면 선택 필드가 연 구멍이 곧바로 가드 의존의 재생이 된다(REQ-PERMROUTE-008 · AC-PERMROUTE-013)
- **「요청한 쪽이 받는다」만 재는 기준을 추가하지 않는다** — 이미 있고, 이 카드의 목표를 재지 않는다(§B-1)
- **`REQ-PERMROUTE-006` 을 약화하거나 지우지 않는다** — `sendToBot` **유지**가 리드 처분이고(§D-5), 그 조항이 유지의 조건으로 붙은 재생산 방지 장치다
- **`spec.md` §6.3 목록의 이력 문서를 고치지 않는다** — CHANGELOG 의 지난 항목, `SPEC-LIVEVERIFY-001` 의 감사·증거 궤적, `t32` 감사 보고서
- **`spec.md` §6.2 의 「주석 1줄」 처분 자리를 본문 재작성으로 넘기지 않는다** — 리드 범위 상한(`.moai/reports/t34/lead-decisions.md`)이며, 과잉도 AC-PERMROUTE-010 의 어긋남이다
- **완료된 형제 문서(`SPEC-LIVEVERIFY-001`)에 D-5(B) 종결을 적지 않는다.** 종결은 이 SPEC 의 `progress.md` 와 sync 단계의 `CHANGELOG` 항목이 진다
- **변이 실험을 감사가 도는 동안 하지 않는다**
