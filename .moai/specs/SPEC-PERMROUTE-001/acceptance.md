# SPEC-PERMROUTE-001 — 수용 기준

기준은 **15개**다 — 라벨은 `AC-PERMROUTE-001`..`014` 이고 그중 `003` 이 `003a`/`003b` 둘로 갈리므로 **14 + 1 = 15** 개가 된다. Tier M 상한 16 안이다. (초판은 「12개」라 적었는데 003 의 분할을 반쪽으로 셌기 때문이며, 하필 `003b` 는 이 SPEC 스스로 「무게중심」이라 부르는 기준이라 그 회계가 무게를 반대로 표현했다 — 1회차 감사 F-06. 0.2.0 이 `013` 을 더해 14, 0.3.0 이 `014` 를 더해 15가 됐다.)

재현 명령 둘 — 둘 다 `15` 를 내야 하고, 어긋나면 표와 본문이 갈라진 것이다:

```
$ grep -cE '^### AC-PERMROUTE' acceptance.md
15
$ sed -n '/^## §D 기준표/,/^---$/p' acceptance.md | grep -cE '^\| \*{0,2}AC-PERMROUTE'
15
```

(둘째 명령의 범위를 §D 절로 좁힌 이유: `AC-PERMROUTE-007` 아래의 귀속 표가 003b·005 를 다시 행으로 적으므로, 파일 전체로 세면 17이 나온다. 범위를 적지 않은 계수 명령은 자기 문서의 다른 표를 함께 센다.)

각 기준은 Given-When-Then 으로 쓰고, **이진으로 판정 가능**해야 한다. 요구사항 자체(GEARS 표기)는 `spec.md` §4 가 진다 — 이 문서는 그것을 **재는 층**이며 요구사항을 다시 쓰지 않는다.

## Given-When-Then

### AC-PERMROUTE-001 — 접속마다 하나, 사는 동안 하나

**Given** 같은 초대 토큰으로 두 소켓 A·B 가 v2 인증을 통과해 붙어 있다.
**When** A 가 `permission_request` 를 두 번 보내고 B 가 한 번 보낸다.
**Then** 핸들러가 받은 세 `info` 중 A 의 두 `connId` 는 **같고**, B 의 `connId` 는 그 값과 **다르다**.

한 접속 안의 불변성과 접속 사이의 유일성을 한 시험에서 함께 재는 이유는, 둘 중 하나만 재면 「매번 새 값을 발급한다」와 「모두 같은 상수를 쓴다」 중 한쪽이 통과하기 때문이다.

### AC-PERMROUTE-002 — 요청한 접속의 신원이 핸들러까지 온다

**Given** 소켓 하나가 붙어 있고 핸들러가 등록돼 있다.
**When** 그 소켓이 `permission_request` 를 보낸다.
**Then** 핸들러가 받은 `info.roomId`·`info.botId` 가 그 소켓의 방·봇이고, `info.connId` 가 **비어 있지 않은 문자열**이다.

`toEqual` 로 객체 전체를 정확 일치시키지 않는다 — `connId` 값은 실행마다 다르므로 `roomId`·`botId` 는 값으로, `connId` 는 **존재와 타입**으로 잰다.

### AC-PERMROUTE-003a — 요청한 소켓이 받는다

**Given** 같은 (방, 봇) 에 소켓 A·B 가 이 순서로 붙어 있다(A 가 먼저).
**When** **B** 가 `permission_request` 를 보내고, 그 요청의 `connId` 로 `sendToOrigin` 이 판정을 보낸다.
**Then** B 가 `{ type: 'permission_verdict', request_id, behavior: 'allow' }` 를 정확히 1건 받는다.

### AC-PERMROUTE-003b — 요청하지 않은 소켓은 받지 않는다 (이 SPEC 의 무게중심)

**Given** AC-PERMROUTE-003a 와 같은 배치.
**When** 같은 판정이 나간다.
**Then** **A 가 받은 `permission_verdict` 프레임의 수가 0 이다.**

**[HARD] 이 기준의 부정 절반을 약화하지 말 것.** 「B 가 받는다」만 재는 기준은 **오늘의 전원 발신 코드 아래에서도 통과한다** — 즉 아무것도 재지 않는다. 실제로 `server/test/gateway.test.ts:855-884` 의 기존 D-5 시험이 정확히 그 모양이며, 이 SPEC 의 변경 전후 모두 초록이다. 이 카드가 존재하는 이유가 그 부정 단언 하나이므로, 이후 어떤 라운드도 이 절반을 「중복이다」·「긍정으로 충분하다」로 지워서는 안 된다.

관측 방법: A 소켓에 도착한 모든 프레임을 수집해 `type === 'permission_verdict'` 인 것을 센다. 「일정 시간 안에 오지 않았다」가 아니라 **판정이 B 에 도착한 것을 관측한 뒤** A 의 수집함을 센다 — 그래야 「아직 안 왔을 뿐」과 「오지 않는다」가 갈린다.

### AC-PERMROUTE-004 — 살아 있지 않은 신원으로는 아무 데도 가지 않는다

**Given** 같은 (방, 봇) 에 소켓 A·B 가 붙어 있다.
**When** 어느 접속의 것도 아닌 `connId` 로 `sendToOrigin` 을 부른다.
**Then** 반환값이 `false` 이고, A·B 가 받은 `permission_verdict` 프레임 수가 **둘 다 0** 이다.

반환값만 재면 「`false` 를 돌려주면서 그래도 보낸다」가 통과한다.

### AC-PERMROUTE-005 — 브로드캐스트 대체가 없다

**Given** 같은 (방, 봇) 에 소켓 A·B 가 붙어 있고, **B** 가 승인 요청을 냈다.
**When** B 를 닫아 서버가 그 접속을 목록에서 지운 뒤, 사람이 방에서 `yes <id>` 로 답한다.
**Then** A 가 받은 `permission_verdict` 프레임 수가 **0** 이고, 방에 실패 안내 system 메시지가 한 행 저장된다.

이 기준이 AC-PERMROUTE-004 와 다른 점: 004 는 게이트웨이 메서드를 직접 재고, 005 는 **사람의 답에서 시작하는 전 경로**를 잰다. 브로커가 실패를 만나 `sendToBot` 으로 되돌아가는 구현은 004 를 통과하고 005 에서 죽는다.

### AC-PERMROUTE-006 — 세 문구가 갈린다

**Given** 요청 하나가 대기 중이다.
**When** (ㄱ) 요청 소켓이 살아 있는 채 `yes`, (ㄴ) 살아 있는 채 `no`, (ㄷ) 요청 소켓이 끊긴 뒤 `yes` — 세 갈래를 각각 재현한다.
**Then** 저장된 세 system 본문이 **서로 모두 다르다.** 그리고 (ㄷ) 의 본문은 원인이 요청한 세션·접속 쪽에 있음을 담고, 「봇이 접속해 있지 않」 계열 문구가 **아니다.**

부정 단언을 함께 두는 이유: 문구를 고치지 않고 그대로 둔 구현은 「셋이 서로 다르다」를 여전히 통과한다(옛 문구도 성공 문구와는 다르므로). 이 SPEC 이 요구하는 것은 「다르다」가 아니라 「원인이 옳게 적혔다」이다.

**넷째 갈래는 이 기준이 재지 않는다.** REQ-PERMROUTE-007 은 되돌리지 못하는 갈래를 둘로 나눈다 — (ㄱ) `sendToOrigin` 이 `false`(여기 (ㄷ) 가 그것이다)와 (ㄴ) `connId` 부재. (ㄴ) 은 소켓을 거치지 않고 브로커를 직접 부른 경우에만 생기므로 이 기준의 세 갈래 재현으로는 도달하지 않으며, **`AC-PERMROUTE-013` 이 그 갈래를 따로 잰다.** 두 기준을 합치면 방에 저장될 수 있는 본문 넷이 전부 서로 다름이 요구된다.

### AC-PERMROUTE-007 — 판정 라우팅 시험이 채널을 import 하지 않는다 (**비회귀 불변식**)

**Given** 판정 라우팅을 재는 시험 파일(AC-PERMROUTE-003a·003b·004·005 를 담은 `server/test/gateway.test.ts`).
**When** 그 파일에서 `channel` 패키지 경로를 import 하는 줄을 훑고, 그 파일을 실행한다.
**Then** import 적중이 **0건**이고, 그 파일이 전부 초록이다.

**[HARD] 이 기준은 「가드 해제」를 재지 않는다 — 이름을 낮춘 이유.** 초판은 이 기준을 「해제했다를 **재는** 방식」이라 적었고 `plan.md` §E 의 자기 검증 한 항목이 그 위에 서 있었다. 1회차 감사가 그 훑기 명령을 **변경 이전 나무에서 그대로 돌려** 반증했다 — 적중 0건, 종료 코드 1. 즉 이 기준은 **오늘 이미 통과**이며, 이 SPEC 의 변경 전후로 값이 바뀌지 않는다. 아무것도 측정하지 않는 기준이 계획의 자기 검증을 떠받치고 있었다(감사 F-03).

그래서 역할을 **비회귀 불변식**으로 낮춘다: 「판정 라우팅 시험에 채널 결합이 **새로 들어오지 않는다**」를 지키는 자리다. 그 임무에서는 공허하지 않다 — 미래의 누군가가 이 시험에 채널 import 를 들이면 붉어진다. AC-PERMROUTE-008 이 같은 성격이며 스스로 그렇게 선언돼 있다.

**「가드 해제」의 측정 책임은 다음 둘에 있다 (명시 귀속).**

| 기준 | 무엇으로 해제를 재는가 |
|---|---|
| **AC-PERMROUTE-003b** | 요청하지 않은 소켓이 판정 프레임을 **0건** 받는다 — 남의 세션에 판정이 도착하는 사건 자체가 없으므로, 그것을 버리는 가드가 불필요해진다 |
| **AC-PERMROUTE-005** | 요청 소켓이 사라진 뒤에도 **대체 발신이 없다** — 가드 의존이 되살아나는 유일한 갈래를 닫는다 |

이 둘은 변경 이전 나무에서 **붉다**(전원 발신 코드가 003b 를 무너뜨린다). 그것이 「무엇인가를 재고 있다」의 증거다.

훑기 명령:
```
grep -n "from '\.\./\.\./channel\|from 'channel\|channel/src" server/test/gateway.test.ts
```
적중 0건(종료 코드 1)이 통과다. **이 명령은 착지 전에도 통과한다는 것을 알고 쓴다** — 위 [HARD] 문단이 그 사실을 공시한다.

**[HARD] 이 기준은 절반이 집계다.** 「그 파일이 전부 초록이다」는 `gateway.test.ts` 안의 003a·003b·004·005 를 합산하므로, 변이 판정에서 그 절반은 셈에서 제외된다(변이표 머리의 집계 기준 제외 규칙). import 훑기 절반은 집계가 아니므로 셈 안에 남는다. **비회귀 불변식으로서의 임무는 두 절반 모두 그대로 진다** — 제외는 변이 셈에 한정되고, 통과 판정 자체는 두 절반을 모두 요구한다.

**잔여 위험 — 「가드를 지워도 서버 쪽 결과가 바뀌지 않는다」를 M6 이 재지 못한다** (1회차 sync 감사 F-04, 이 절의 정정). 서버 패키지가 `channel/` 을 import 하지 않으므로(`grep -rn "from .*channel" server/src server/test` → 무출력·`exit 1`) M6 의 서버 쪽 결과는 변이를 돌리기 전에 이미 정해져 있고, **실패할 수 없는 변이는 아무것도 재지 않는다.** 중심 주장(REQ-PERMROUTE-010)의 근거는 M6 이 아니라 **`AC-PERMROUTE-003b`**(요청하지 않은 소켓 0건 수신)와 **`AC-PERMROUTE-009` (가)**(전원 발신 생산 호출자 0)이며, 그 둘은 서버 안에서 실제로 붉어질 수 있는 기준이다. M6 이 남아서 재는 것은 채널 쪽 절반(`008` — 가드가 재생 방어 임무를 여전히 진다)뿐이다.

### AC-PERMROUTE-008 — 채널의 재생 방어는 값 하나 바뀌지 않는다

**Given** 이 SPEC 의 모든 변경이 착지한 트리.
**When** `npm test -w channel` 과 `git diff --stat -- channel/` 을 돌린다.
**Then** `Tests 126 passed (126)` · 실패 0 이고, `channel/` 의 diff 가 **빈 출력**이다.

`AC-CHANPERM-008`(발신하지 않은 id 판정에서 알림 0건)과 `AC-CHANAUTH-007`(재생 판정 폐기)이 126 안에 그대로 살아 있다는 것이, 가드가 임무 하나를 덜었을 뿐 없어지지 않았다는 관측이다.

### AC-PERMROUTE-009 — `sendToBot` 은 전원 발신인 채로 남고, 아무도 부르지 않는다

**Given** 같은 (방, 봇) 에 소켓 A·B 가 붙어 있다.
**When** `sendToBot(room, bot, { type: 'ping' })` 을 부른다.
**Then** A·B **둘 다** 그 프레임을 받고 반환값이 `true` 다.

- **M4 → 013 추가.** 013 은 실패 문구가 REQ-PERMROUTE-007 의 형태임을 함께 단언하므로, 문구를 성공 문구와 같게 만들면 붉어진다.
- **M4 → 005 의 문구 절반 추가 (sync 재도출).** 위 「뿌리는 하나다」와 같은 결합이 005 시험에도 걸린다 — 005 시험은 실패 안내 행이 **(ㄱ) 「요청한 세션이 끊겨」** 형태임을 단언하는데(`:589`), 실패 문구를 성공 문구와 같게 만들면 그 자리에 `✅ 승인 전송됨 (abcde)` 이 저장돼 붉어진다. **고유 관측 `:586` 은 통과한다** — 문구만 바꾸는 변이는 배달 대상을 바꾸지 않으므로 남은 소켓은 여전히 0건이다. 그래서 005 **전부**가 아니라 **문구 절반**이다.
- **M6 → 008.** 가드 제거는 `channel/` 을 건드리므로 `git diff --stat -- channel/` 이 비지 않고(008) `npm test -w channel` 의 126 이 깨진다 — `AC-CHANPERM-008`(발신하지 않은 id 판정에서 알림 0건)과 `AC-CHANAUTH-007`(재생 판정 폐기)이 정확히 그 가드를 재기 때문이다. **012 의 channel 절반도 실제로는 함께 무너지지만 집계 기준이므로 셈에 적지 않는다** — 그 사실은 008 이 이미 같은 관측으로 담고 있다.
- **집계 기준을 적용한 뒤에도 여섯 행이 서로 다르다 (sync 재도출, 2026-09-04 — 여섯을 전부 다시 냈다).**

  | 변이 | 집합 |
  |---|---|
  | M1 | `003b` |
  | M2 | `001 · 003a · 006` |
  | M3 | `005 전부 · 006 · 013` |
  | M4 | `006 · 013 · 005 문구 절반` |
  | M5 | `001 · 002 · 003a · 006 · 005 문구 절반` |
  | M6 | `008` |

  여섯 집합이 **전건 서로 다르며**, 그것이 이 표가 판별력을 갖는다는 뜻이다. **[HARD] 이 구별은 「서버 쪽 0건」을 M6 에서 뺀 뒤에도 그대로다 — 열다섯 쌍을 다시 냈다**(1회차 sync 감사 F-04 이 그 원소를 지우게 했으므로, 「전건 서로 다르다」가 그 원소에 기대고 있었는지 다시 세야 한다). `008` 을 담은 집합은 M6 하나뿐이므로 M6 은 나머지 다섯 전부와 그 한 원소로 갈리고, M1(`003b` 하나)과도 갈린다. **빠진 원소는 애초에 판별에 쓰이지 않았다** — 「서버 쪽 0건」은 무너지는 기준이 아니라 무너지지 **않는다**는 서술이어서 집합의 원소가 된 적이 없다. 나머지 열 쌍(M1~M5 사이)은 이 편집이 건드리지 않았다. 가장 가까운 두 쌍은 이렇게 갈린다. **M3 대 M4** — 나머지 원소(`006`·`013`)가 같으므로 판별은 오직 005 의 어느 절반이냐에 달려 있고, 그 구별은 실패한 단언 줄(`:586` 대 `:589`)로 기계가 낸다. **M4 대 M5** — `013`(M4 에만) 과 `001·002·003a`(M5 에만) 로 양방향으로 갈린다.

  **[HARD] M3 대 M4 는 시험 이름 단위로는 구별되지 않는다.** 두 변이 모두 같은 시험 하나(`AC-PERMROUTE-005` 시험)를 붉히므로, 「붉은 시험의 집합」만 비교하면 두 행이 같아 보인다. **이 표를 대조할 때는 실패 출력의 단언 줄 앵커를 함께 읽는다** — 그것이 이 쌍의 유일한 판별 근거다. 대조 보고에 붉은 시험 이름만 적고 앵커를 빠뜨리면 M3 과 M4 를 갈랐다고 주장할 수 없다.

  012 를 여섯 행에 더했다면 여섯 집합의 차이는 그대로지만 열 하나가 상수가 되어 읽는 사람이 「012 가 무너졌다」를 신호로 오독하게 된다.

**M1 이 003b 하나만** 무너뜨린다는 것이 이 표의 핵심이다 — 003a 가 M1 에서 살아남는다는 사실이 곧 「긍정 단언만으로는 이 카드를 잴 수 없다」의 기계적 증명이다. M3 이 003b 를 무너뜨리지 **않는** 것도 의도된 값이다: 대체 발신은 요청 소켓이 사라진 뒤에만 일어나므로 003b 의 배치에는 걸리지 않고, 그래서 005 가 따로 필요하다. M3 이 **004 를 무너뜨리지 않는 것**도 의도된 값이다: 대체 발신을 `sendToOrigin` 안이 아니라 **브로커 쪽**에 두었으므로 게이트웨이 메서드를 직접 재는 004 는 초록으로 남는다 — 그 비대칭이 004 와 005 를 나누어 둔 이유다.

### M6 이 이 SPEC 의 중심 주장에 붙이는 반증자

**[HARD] 「서버 쪽 0건」은 M6 의 판정값에서 뺐다 — 그 값은 위상 때문에 변이 전에 이미 정해져 있었다** (1회차 sync 감사 F-04). 서버 패키지는 `channel/` 을 한 줄도 import 하지 않는다:

```
$ grep -rn "from .*channel" server/src server/test
(무출력)   exit=1
```

따라서 `channel/src/channel-server.ts` 의 두 줄을 지우는 변이가 **서버 기준을 무너뜨리는 일은 애초에 일어날 수 없다.** 실패할 수 없는 변이는 아무것도 재지 못하므로, 「서버 쪽 0건」의 관측은 REQ-PERMROUTE-010 을 지지하는 증거가 아니다 — 그것이 재는 것은 「서버 스위트가 채널 가드를 **볼 수 없다**」는 모듈 위상 하나뿐이다. **주장은 옳고 인용된 증거가 공허했다**(이 프로젝트가 세 번째로 기록하는 부류).

**REQ-PERMROUTE-010 의 측정 책임은 다음 둘에 있다** (리드 처분, 2026-09-04):

- **`AC-PERMROUTE-003b`** — 요청하지 않은 소켓이 판정 프레임을 **0건** 받는다. 가드가 버릴 프레임이 애초에 도착하지 않음을 **서버 안에서** 직접 관측하며, 변이 M1(전원 발신 복원)이 이 기준 **하나만** 무너뜨린다 — 즉 공허하지 않다.
- **`AC-PERMROUTE-009` (가)** — 판정 경로에 `sendToBot`(전원 발신) 생산 호출자가 **0**이다. 전원 발신 통로가 코드에 없으므로 요청하지 않은 접속에 판정이 **도착하는 사건 자체가 없다.**

둘을 합치면 「도착하지 않는 프레임은 버릴 가드가 필요 없다」가 서버 패키지 안에서만 성립하며, 그것이 REQ-PERMROUTE-010 이 실제로 기대고 서 있는 근거다. **M6 이 남아서 재는 것은 반대 방향 하나** — 가드가 채널 쪽 임무(재생 방어)를 여전히 지고 있다는 것(`008`)이다.

M6 을 AC-PERMROUTE-008 과 **짝으로** 둔 이유는 그대로다: 008 이 붉어짐으로써 「가드가 실재하고 채널 쪽 임무(재생 방어)를 여전히 지고 있다」가 관측된다. 그것이 없으면 「가드가 애초에 아무것도 안 했다」와 구별되지 않는다. **다만 「가드는 남았고 임무 하나만 덜었다」의 나머지 절반 — 서버 쪽이 그 가드에 기대지 않는다 — 은 M6 이 아니라 위의 `AC-PERMROUTE-003b`·`AC-PERMROUTE-009` (가) 가 잰다.** 서버 스위트는 채널 가드를 볼 수 없으므로 M6 의 서버 쪽 결과로는 그 절반을 세울 수 없다.

**§5 의 `channel/` 무편집 금지와 충돌하지 않는다.** 그 금지는 **착지하는 편집**을 금지하며, 되돌리는 변이 탐침은 금지 대상이 아니다. M6 은 변이 창 안에서만 존재하고 되돌린 뒤 `git diff -- channel/` 이 다시 빈 출력임을 확인해야 완료된다. 그 확인 자체가 AC-PERMROUTE-008 의 재실행이다.

기준선 오염 방지: 변이 전후 `git hash-object` 로 대상 파일을 대조하고, 변이 창 동안 다른 세션의 쓰기가 없었음을 확인한다. **M6 은 `channel/` 을 건드리므로 이 대조를 특히 엄격히 한다** — 되돌림이 불완전하면 이 카드가 「`channel/` 한 글자도 고치지 않는다」는 자기 선언을 깬다.

### AC-PERMROUTE-012 — 기준선 비회귀

**Given** 착지한 트리.
**When** 다음을 실행한다.
```
npm run build -w channel
npm test -w server
npm test -w channel
npm run typecheck -w server
npm run typecheck -w channel
```
**Then** `build` exit 0, server 통과 수가 **210 이상**이고 실패 0, channel 통과 수가 **정확히 126**이고 실패 0, 두 `typecheck` 모두 exit 0.

server 는 이 SPEC 이 시험을 더하므로 하한으로, channel 은 한 글자도 고치지 않으므로 등호로 잰다.

### AC-PERMROUTE-013 — `connId` 없는 대기 항목의 갈래 (선택 필드가 여는 구멍)

**Given** 같은 (방, 봇) 에 소켓 A·B 가 붙어 있고, **`connId` 를 담지 않은 `ConnInfo`** 로 `broker.onGatewayRequest({ roomId, botId }, …)` 가 직접 호출돼 대기 항목이 생겼다(소켓을 거치지 않은 경로 — 선택 필드에서 실제로 가능한 모양이다).
**When** 사람이 방에서 `yes <id>` 로 답한다.
**Then** 셋 모두 성립한다.

1. A 와 B 가 받은 `permission_verdict` 프레임 수가 **둘 다 0** 이다 — 어느 접속으로도 대신 보내지 않는다 (REQ-PERMROUTE-008).
2. 방에 **실패 안내 system 메시지가 한 행** 저장된다.
3. 그 본문이 REQ-PERMROUTE-007 의 **(ㄴ) 갈래** 형태다 — 원인이 「요청한 세션의 **신원이 기록되지 않았다**」임을 담고, 「봇이 접속해 있지 않」 계열 문구가 **아니며**, **AC-PERMROUTE-006 (ㄷ) 의 「세션이 끊겼다」 문구와도 다르다.** 성공 두 문구와도 다르므로 이 갈래를 포함해 방에 저장될 수 있는 본문은 **넷이 서로 모두 다르다.** 꼬리 「전달하지 못했습니다 (`<request_id>`)」는 유지한다(REQ-PERMROUTE-007 [HARD] — 화면 파서 결합).

**[HARD] 왜 (ㄷ) 의 문구를 빌려 쓰지 않는가 (2회차 감사 N-06).** 초판은 이 조항의 판정선을 AC-PERMROUTE-006 (ㄷ) 와 **같게** 두어 「요청한 세션이 끊겼다」를 요구했다. 그런데 이 갈래에서는 **아무것도 끊기지 않았다** — 대기 항목에 `connId` 가 애초에 없었을 뿐이고, 요청한 세션은 멀쩡히 살아 있을 수 있다. 「끊겼다」는 사람에게 틀린 진단을 주며, 그것은 이 SPEC 이 낡은 문구(「봇이 접속해 있지 않습니다」)를 비판한 근거(`spec.md` REQ-PERMROUTE-007)와 **정확히 같은 부류**다. 이 SPEC 이 자기 논거를 자기 기준에서 어기고 있었다.

**판정선을 느슨하게 만든 것이 아니다.** 초판은 「(ㄷ) 와 같은 문구」를 요구했고, 지금은 「(ㄷ) 와 **다른**, 신원 부재를 말하는 문구」를 요구한다 — 구별해야 할 문구가 셋에서 넷으로 늘었으므로 기준은 **강해졌다.** 변이 M4(실패 문구를 성공 문구와 같게 만든다)가 여전히 013 을 무너뜨리고, 여기에 「두 실패 문구를 서로 같게 만드는」 구현도 이제 붉어진다.

**왜 이 기준이 있는가 — 리드 처분이 붙인 조건이다.** `plan.md` §D-1 의 미결은 리드 처분으로 **「선택 필드」**로 닫혔고(`.moai/reports/t34/lead-decisions.md`, 운영자 결정 · 리드 경유), 그 처분은 감사 F-07 을 조건으로 달았다: **선택 필드는 생산 코드에서 조용히 빠질 수 있고, 그때 판정은 사용자에게 보이는 오작동이 된다** — 그러니 그 갈래를 재는 기준을 하나 세울 것.

초판은 이 갈래를 「미결이 풀리기 전에는 기준을 쓰지 않는다」로 공시만 하고 비워 두었다(감사 F-07). 미결이 닫혔으므로 공백도 닫는다. **이 갈래가 도달 불가라고 주장해 닫는 것은 허용되지 않는다** — 선택 필드인 이상 타입이 그것을 막지 않으며, 실제로 형제 시험이 정확히 이 모양으로 브로커를 직접 부른다 — 자리 목록과 그 수의 귀속은 `spec.md` §6.2 **18행**에 있다.

AC-PERMROUTE-004 와 다른 점: 004 는 **어느 접속의 것도 아닌 `connId`** 를 게이트웨이 메서드에 직접 넘겨 재고, 013 은 **`connId` 자체가 없는 대기 항목**을 사람의 답에서 시작하는 전 경로로 잰다. 004 는 타입이 있는 값의 실패, 013 은 값의 부재다 — 좁히기 분기(`info.connId` 가 `undefined` 일 때 `sendToOrigin(connId: string, …)` 앞에서 반드시 갈라져야 하는 자리)를 재는 것은 013 뿐이다.

### AC-PERMROUTE-014 — 새 훅도, 새 장부도 생기지 않았다

**Given** 착지한 트리.
**When** 다음 셋을 돌린다.

```
# (ㄱ) PermissionBroker 의 공개 메서드가 정확히 둘 — 접속 종료를 듣는 새 훅이 늘지 않았다
sed -n '/^export interface PermissionBroker {/,/^}/p' server/src/permissions.ts | grep -cE '^  [a-zA-Z_]+\('

# (ㄴ) Gateway 의 공개 메서드가 정확히 여섯 — sendToOrigin 하나만 늘고 종료 콜백 등록자는 없다
sed -n '/^export interface Gateway {/,/^}/p' server/src/gateway.ts | grep -cE '^  [a-zA-Z_]+\('

# (ㄷ) 접속 종료 두 경로에 브로커·대기 레지스트리 참조가 0건
sed -n "/ws.on('close'/,/})/p" server/src/gateway.ts | grep -icE 'permission|broker|pending'
sed -n '/function dropConn/,/^  }/p' server/src/gateway.ts | grep -icE 'permission|broker|pending'
```

**Then** (ㄱ) = `2`, (ㄴ) = `6`, (ㄷ) = `0` · `0`.

**착지 전 나무에서 그대로 돌린 출력** — 워크트리 `.claude/worktrees/t34` · HEAD `6a359f8`:

```
$ sed -n '/^export interface PermissionBroker {/,/^}/p' server/src/permissions.ts | grep -cE '^  [a-zA-Z_]+\('
2
$ sed -n '/^export interface Gateway {/,/^}/p' server/src/gateway.ts | grep -cE '^  [a-zA-Z_]+\('
5
$ sed -n "/ws.on('close'/,/})/p" server/src/gateway.ts | grep -icE 'permission|broker|pending'
0
$ sed -n '/function dropConn/,/^  }/p' server/src/gateway.ts | grep -icE 'permission|broker|pending'
0
```

**왜 이 기준이 있는가.** `REQ-PERMROUTE-009`(「접속 종료를 듣는 새 장부나 새 훅을 만들어서는 안 된다」)를 재는 기준이 하나도 없었다(2회차 감사 N-05). 부정형 설계 조항이지만 기계로 잴 수 있는 종류이며, 재지 않으면 §D-4 가 고르지 않은 갈래로 적어 둔 「접속 종료 시 대기 항목을 지운다」가 구현 중에 조용히 들어와도 아무 신호가 나지 않는다.

**세 절반의 성격을 정직하게 공시한다.** (ㄱ)·(ㄷ) 는 **오늘 이미 통과**이며 값이 착지로 바뀌지 않는다 — `AC-PERMROUTE-007`·`008` 과 같은 **비회귀 불변식**이고, 그 임무(새 결합이 들어오면 붉어진다)에서는 공허하지 않다. (ㄴ) 는 오늘 `5` 이고 착지 후 `6` 이므로 **값이 바뀐다** — 이 기준이 이 카드의 변경을 실제로 관측하는 절반이다. 셋을 함께 두는 이유: (ㄴ) 만이면 메서드를 여섯으로 늘리면서 종료 훅을 함께 들인 구현이 통과하고, (ㄱ)·(ㄷ) 만이면 아무것도 재지 않는다.

**여섯 변이 중 어느 것도 이 기준을 무너뜨리지 않는다** — 변이 정의가 인터페이스 표면과 종료 경로를 건드리지 않기 때문이며, 그래서 변이표 어느 행에도 014 가 없다. `AC-PERMROUTE-010` 과 같은 자리다.

## 예상 실패 갈래 (edge cases)

- **같은 프로세스에서 두 소켓이 같은 `randomUUID()` 를 받는 경우** — 실질적으로 불가능하나, AC-PERMROUTE-001 이 두 값의 부등을 직접 재므로 발생하면 붉어진다
- **요청 소켓이 판정 도착과 동시에 끊기는 경우** — `sendToOrigin` 이 목록에서 찾지 못하면 `false` 이고 AC-PERMROUTE-006 (ㄷ) 의 갈래로 간다. 찾았으나 소켓이 이미 닫힌 상태면 `ws.send` 가 조용히 실패할 수 있고 반환값은 `true` 가 된다 — 이 창은 이 SPEC 이 닫지 않으며 §잔여 위험에 적는다
- **대기 항목에 `connId` 가 없는 경우**(선택 필드일 때) — **미결은 리드 처분으로 「선택 필드」로 닫혔고, 이 갈래는 `AC-PERMROUTE-013` 이 잰다.** 더 이상 공시된 공백이 아니다
