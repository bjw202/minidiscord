## §B 알려진 문제

### [HARD] B-0 — 정정 후 **전역** 재도출 (상시 절차)

**형제 문서를 편집한 뒤에는 그 문서를 인용하는 모든 자리를 파일 단위가 아니라 트리 단위로 다시 뽑는다 — 편집한 파일만 훑는 것이 네 라운드 연속 재현된 결함의 원인이다.**

이 한 줄이 §B 의 맨 앞에 있는 이유를 적는다. 카드 `t15` 의 계획 감사 네 라운드에서 **매번 직전 정정을 닫는 편집이 같은 부류의 다음 인스턴스를 만들었다** — 1회차 M-03(`:465`/`:471` 인용 다섯 자리), 2회차 N-01(HISTORY 행이 본문과 정반대)·N-06(세 자리를 네 자리로), 3회차 R-01·R-02·R-03·R-04. 3회차 감사의 진단이 정확하다: 이것은 개별 부주의가 아니라 **작성 절차에 전역 재도출 단계가 없다**는 신호이며, 라운드를 더 도는 것으로 닫히지 않는다.

R-02 가 그 증거다 — 형제 여덟 자리의 줄 번호가 `spec.md` §3.3 에서는 **전부 정확했고** `plan.md` §B 에서는 **전부 개정 이전 값**이었다. 훑기 자체는 옳게 수행됐으나 **한 파일에만** 적용됐기 때문이다.

**실행 형태** (편집 대상이 아니라 트리 전체를 훑는다):

```bash
# ① 형제 문서를 인용하는 자리를 트리 단위로 뽑는다 — .moai/specs 와 .moai/reports/t15 둘 다
grep -rn --include "*.md" "SPEC-[A-Z]*-001/\(spec\|progress\|acceptance\|plan\)\.md:[0-9]" .moai/specs .moai/reports/t15

# ② 인용된 각 줄 번호를 대상 파일에서 실제로 열어 내용이 맞는지 대조한다 (sed -n '<N>p')
# ③ 어긋난 자리는 대상 파일에서 앵커 문자열로 재도출한다 (grep -n '<고유 문구>')
```

**«편집한 파일만 훑었다» 는 훑지 않은 것과 같다.** 인용은 편집한 파일이 아니라 **인용하는 쪽 파일**에 있기 때문이다.

**v0.3.0 기준 상태**: 1·2회차에 «차단» 이던 형제 계약 개정 두 건은 **이 패스에서 해소됐다**(B-1·B-2). 남은 항목은 전부 **기록 또는 sync 인계**이며 run 진입을 막지 않는다.

### B-1 · B-2 (해소됨) 형제 계약 개정 — **이 패스에서 수행했다**

**운영자 결정 D3 = (a) (2026-08-29): run 으로 미루지 않고 plan 단계에서 개정한다.** 근거는 카드 `t9` 의 교훈이다 — 계약을 거짓인 채 run 에 넘기면 형제 하네스가 무더기로 무너지고 sync 감사에서 «개정되지 않은 SPEC 과 실제 동작의 괴리» 로 되돌아온다. 소유 SPEC(이 문서)이 이미 서 있으므로 소비자를 지금 고칠 수 있다. **여덟 자리를 한 세션에서 직렬로** 고쳤다 — 이 프로젝트에는 «동시 작성 SPEC 은 이음매에서 깨진다» 는 기록이 있고, 단일 세션 직렬 편집이 그 대책이다.

| 대상 | 자리 | 결과 |
|---|---|---|

**개수의 사실관계**: 리드에게 처음 보고된 수는 4였고, 레인 실측은 7 이상이었으며, **실제로 개정한 것은 8자리**다(`:240` 이 여덟 번째 — 운영자 판정으로 C → B. 같은 문단이 아래에서 `239 → 240` 을 적고 있으므로 여기도 개정 후 값으로 맞춘다). **위 줄 번호는 전부 개정 *후* 실측값이다** — 개정으로 줄이 밀리므로 개정 전 값을 그대로 두면 인용이 빈 줄을 가리킨다. **이 값들은 3회차 교정 중에 한 번 더 밀렸다** — R-07 이 `SPEC-CHANCLIENT-001` 에 HISTORY 한 행(v0.6.1)을 더해 43·63·93·118·130·134·239 → **44·64·94·119·131·135·240** 이 됐고, §B-0 의 트리 단위 재도출이 그것을 잡았다(3회차 감사 R-02). 요구사항·수용 기준의 **개수는 양쪽 모두 그대로**이며, 바뀐 것은 계약 문장뿐이다.

**남는 것 — run 단계 몫이다.** 계약은 참이 됐지만 **테스트는 아직 옛 계약을 잰다.** 재측정 결과는 `spec.md` §3.2 표에 있다: 하네스 수정 **6자리**, 본문까지 바뀌는 기준 **3건**(AC-CHANCLIENT-001·002·011), 영향 집합 상한 **55건**. 이 셋은 **차단이 아니라 M4 작업 항목**이다 — 계약이 이미 옳으므로 sync 감사가 되돌릴 근거가 없어졌다.

### B-3 (기록) 붕괴 상한 55는 여전히 상한이지 실측이 아니다

`spec.md` §3.2 의 재측정 표를 보라 — 하네스 자리 6·본문 개정 기준 3은 **파일 판독으로 확정**했으나, 실제로 몇 건이 붉어지는지는 **구현 없이 잴 수 없다.** 55는 `it()` 개수의 산술 합이다. **§C 사전 점검이 하네스를 고치기 전에 한 번 실행해 실측한다** — 상한과 실측이 크게 다르면 하네스 이해가 틀렸다는 신호다.

### B-4 (기록) 인계 카드 본문과 실범위가 다르다

큐 카드 `t15` 의 본문은 인계 범위 셋 중 둘만 담고 있다(`SPEC-CHANINJECT-001/spec.md:475` 이 그 불일치를 기록했다). 큐에 카드 본문 편집 verb 가 없으므로 **실범위의 정본은 `SPEC-CHANAUTH-001` §5 와 이 SPEC 문서**다. 착수자는 카드 본문만 보지 않는다.

### B-5 (기록) `SPEC-CHANAUTH-001` §2.1 은 착지 후 현재형으로 거짓이 된다

**고치지 않는다.** 근거는 `spec.md` §2.1·§3.3 C 부류. 대신 §5 인계 절이 이 SPEC 을 가리키므로 독자가 순서를 따라갈 수 있다.

### B-7 (sync 인계) F-A8 의 포인터가 카드 종료와 함께 끊긴다

`spec.md` §5 가 F-A8 의 **소유를 카드 `t15` 에 유지**하기로 했다 — 그래야 그 소유를 적은 15자리가 참으로 남는다(§3.3 — 내용 축 단일 실측). **그 대가는 이 카드가 닫히면 그 포인터가 가리킬 대상이 사라진다는 것이다.**

**후속 소유자를 지금 지목하지 않는 이유**: F-A8 은 감사도 이 SPEC 도 **도달성을 실측하지 않은 추정**이다. 실재가 확인되지 않은 항목에 소유 SPEC 을 붙이면 이 카드가 고치러 온 «근거 없이 적기» 를 반복한다.

**그러므로 조치를 sync 단계로 인계한다.** 카드를 닫기 전에 둘 중 하나를 한다 — ① 128 상한의 도달성을 실측해 결과에 따라 새 카드를 열거나 항목을 기각한다, 또는 ② «소유 카드가 닫혔고 후속 소유자가 없다» 를 `progress.md` §E.4 에 명시적으로 남긴다. **아무것도 하지 않고 닫으면 F-A8 은 조용히 사라진다.**

### B-6 (기록) 형제 SPEC 셋을 통독하지 않았다

`spec.md` §3.3 의 표제를 «전건 열거» 에서 **«확인한 범위»** 로 낮췄다(1회차 감사 H-01). 통독한 것은 `SPEC-CHANCLIENT-001` 과 `SPEC-CHANAUTH-001` 둘뿐이고, **`SPEC-CHANPERM-001`·`SPEC-CHANWIRE-001`·`SPEC-CHANNEL-001` 은 `t15` 문자열 grep 만 했다.** `SPEC-GATEWAY-001` 도 `welcome` 관련 자리만 봤다.

**착지 후 거짓이 되는 문장이 그 넷에 더 있을 수 있다.** 없다고 적지 않는다 — 보지 않았다고 적는다. B-1·B-2 의 계약 개정을 수행하는 패스가 그 통독을 함께 하는 것이 자연스럽다.

## §D 설계 결정과 기각한 대안

되돌리기 가장 비싼 순서로 적는다.

### D-1 증명 열쇠 = **저장된 `token_hash`** (평문 토큰이 아니다)

**근거는 실측이다.** `server/src/routes-bots.ts:63-65` 가 `randomBytes(32)` 로 만든 평문을 응답에 한 번만 싣고 `bot_tokens` 에는 `sha256Hex(token)` 만 넣는다. `gateway.ts:92-94` 는 그 해시로 조회한다. **서버는 평문을 저장하지 않는다.**

| 대안 | 기각 사유 |
|---|---|
| 평문 토큰을 열쇠로 | 서버가 저장하지 않는다. `hello` 로 방금 받은 평문을 쓸 수는 있으나 그것은 «상대가 준 값» 이라 증명이 되지 않는다 |
| `bot_tokens` 에 별도 HMAC 비밀 컬럼 추가 | DB 스키마 변경 + 마이그레이션 + 기존 발급 토큰 전건 무효화. 강도 이득이 없다 — 토큰을 아는 상대는 이미 그 봇이다(§1.3) |
| 서버 전역 비밀(환경변수) | 방·봇마다 다른 증명이 나오지 않아 «어떤 봇의 서버인가» 를 인증하지 못한다 |

**채택안의 대가**: 해시 규칙의 **생산 코드 사본이 하나 는다**(서버 공유 함수 + 채널 사본 = 둘). `gateway.ts:93` 은 `gateway.ts:7` 이 import 하는 호출 지점이라 사본이 아니다 — v0.1.0 은 이 자리를 «세 자리» 라 적었다(1회차 감사 M-01). 진짜 증식은 **테스트 여섯 자리**이며, 완화 셋의 겨냥은 `spec.md` §3.5 표에 층별로 적었다. 생산 두 자리의 분기를 잡는 것은 AC-GWAUTH-013 하나뿐이다.

### D-2 하위 호환 — 증명 없는 `welcome` 은 **fail-closed** (거절)

| 대안 | 기각 사유 |
|---|---|
| 유예 기간(증명 없으면 경고만 내고 통과) | **이 SPEC 이 닫으려는 공격을 그대로 남긴다** — 공격자는 증명을 «생략» 하면 그만이다. 방어를 세우면서 그 우회로를 문서에 적어 두는 꼴이다 |
| 환경변수로 강제 여부를 켠다 | 기본값이 무엇이든 한쪽은 뚫려 있고, 위험이 코드가 아니라 운영자의 환경변수 위에 얹힌다 — `SPEC-CHANAUTH-001` §1 이 지적한 바로 그 모양이다 |

**채택 근거**: 서버와 채널은 **한 저장소의 한 워크스페이스 쌍**(`package.json` `workspaces: ["server","channel"]`)에서 함께 빌드·배포된다. 버전 스큐는 지원되는 구성이 아니다. 구버전 채널이 신버전 서버에 붙는 경우는 D-3 이 답한다.

### D-3 논스 없는 `hello` — 서버는 **증명 없는 `welcome` 을 보내고 끊지 않는다**

| 대안 | 기각 사유 |
|---|---|
| 접속을 끊는다 | 보호받는 쪽(채널)이 아니라 **서버의 기존 계약**만 좁아진다. `server/test/` 의 **4개 파일**이 논스 없이 `hello` 를 보내며(실측 `grep -rln "type: 'hello'" server/test/` → `gateway.test.ts`·`permissions.test.ts`·`room-members.test.ts`·`web-permission-contract.test.ts`), 그 기준들이 방어와 무관하게 붉어진다. v0.1.0 은 «5개» 로 적고 `sse.test.ts` 를 넣었으나 그 파일은 `hello` 를 보내지 않는다 (1회차 감사 L-03) |
| 논스가 없으면 빈 문자열로 계산해 증명을 싣는다 | 예측 가능한 증명을 만들어 재생 공격의 여지를 연다 |

**하향 협상 공격이 되지 않는 이유**(`spec.md` REQ-GWAUTH-004 에 명문화): 이 위협 모형의 공격자는 **서버 쪽에 서는 상대**이고, 채널은 항상 논스를 싣고 항상 증명을 요구한다. 논스 없는 `hello` 는 공격자가 만들 수 있는 상태가 아니다. **거절 결정은 보호받는 쪽이 내린다.**

### D-4 논스의 신선도와 생성 위치

- **크기**: `randomBytes(32)` → 64자 hex. `randomUUID()`(122비트) 를 기각한 이유는 자릿수다 — 논스가 이 설계의 유일한 신선도 원천이므로 열쇠와 같은 자릿수로 둔다.
- **위치**: `connect()` **안**의 지역 변수. `established` 와 나란히 둔다(`gateway-client.ts:56-58`).
- **기각한 대안**: 클로저 변수(`createGatewayClient` 스코프). 그 자리의 기존 주석이 이미 경고한다 — "상태를 클로저로 올리면 한 번 확립된 뒤 게이트가 영구히 열린다". 논스에 같은 실수를 하면 직전 왕복의 `(nonce, proof)` 재생이 통한다. **AC-GWAUTH-005 가 정확히 이 변이를 잰다.**
- **서버 쪽 논스 캐시를 두지 않는다**: 논스는 **클라이언트의 챌린지**이므로 신선도의 책임은 클라이언트에 있다. 서버가 본 논스를 기억하면 무상태성이 깨지고 재시작마다 초기화돼 실효도 없다.

### D-5 증명 메시지 = `` `${nonce}|${room_id}|${bot_id}` ``

| 대안 | 기각 사유 |
|---|---|
| `nonce` 하나만 서명 | 증명이 «어떤 welcome 이 왔다» 만 인증하고 «무엇을 말하는가» 는 인증하지 않는다. 공격자가 유효한 증명을 그대로 두고 `room_id` 를 바꾼다 — **AC-GWAUTH-009 가 이 변이를 잰다** |
| `welcome` 전체를 정규화해 서명 | 정규화 규칙(키 순서·수 표기)이 두 워크스페이스에 각각 생겨 §3.5 위험이 커진다. 이득은 `bot_name` 인증 하나뿐이고 그 필드는 소비자가 없다 |
| 구분자 없이 이어 붙이기 | `(nonce, 1, 23)` 과 `(nonce, 12, 3)` 이 같은 문자열이 된다 |

`room_id`·`bot_id` 는 **토큰이 결정한 DB 값**을 쓴다 — 요청이 실어 보낸 값을 쓰면 증명이 상대의 주장에 서명한다.

### D-6 대조 실패 시 **소켓을 닫는다**

| 대안 | 기각 사유 |
|---|---|
| 소켓을 열어 둔 채 게이트만 잠근다 | 봇이 조용히 아무 일도 하지 않는 상태로 남는다 — 이 프로젝트에서 가장 비싼 실패 형태이며, 사람은 봇이 죽은 줄도 모른다 |
| `process.exit` | stdio 로 말을 걸던 MCP 상대가 이유 없이 끊긴다(`SPEC-CHANWIRE-001` REQ-003·004 와 같은 논리) |

**대가**: 거절이 반복되면 재접속 루프가 돈다(백오프 상한 30초 → 분당 약 2회). stderr 가 접속당 한 줄이므로 폭주하지 않는다. AC-GWAUTH-010 이 «접속 수 = stderr 줄 수» 로 그 성질을 잰다.

### D-7 상수 시간 대조 — 길이 확인이 먼저

`timingSafeEqual` 은 길이가 다르면 **예외를 던진다**. 길이 확인 없이 부르면 짧은 `proof` 한 줄이 REQ-GWAUTH-010 위반(잡히지 않은 예외)이 된다. AC-GWAUTH-012 가 그 순서를 동작으로 잰다.

**한계를 적는다**: `===` 로 바꾼 구현은 예외를 던지지 않으므로 AC-GWAUTH-012 를 통과한다. 타이밍 측정은 테스트 환경에서 신뢰할 수 없어 기준으로 두지 않았고, **이 자리는 코드 리뷰가 지킨다**(§G).

### M3 — 채널 쪽 논스와 대조 (REQ-GWAUTH-001·002·006~012)

**[HARD] 이 마일스톤의 구현 구조는 자유가 아니다.** 아래 3번이 요구하는 **«거절 플래그를 `established` 와 분리하고 그 검사를 `!established` 게이트보다 앞에 둔다»** 는 SPEC 이 HOW 를 규정하는 드문 자리이며, 그 이유는 «무엇을 관측할 수 있는가» 가 이 구조에 직접 달려 있기 때문이다 — 구조가 다르면 이 SPEC 의 부정 기준 다섯 건이 `SPEC-CHANAUTH-001` 의 게이트와 이 SPEC 의 게이트를 **구분하지 못한다**(1회차 감사 C-02). 대가는 `acceptance.md` §「검증 원칙」 4번과 「잔여 위험」에 적었다.

1. `connect()` 안에 `const nonce = randomBytes(32).toString('hex')` 를 `established` 옆에 둔다 (REQ-GWAUTH-002 — 클로저로 올리지 않는다).
2. `hello` 에 `nonce` 를 싣는다.
3. **`welcome` 갈래를 고치되, 아래 구조를 그대로 따른다.**

```ts
let established = false          // t9 소유 — 손대지 않는다
let proofRejected = false        // 이 SPEC 이 새로 들이는 소켓 지역 상태. established 와 별개다

ws.on('message', d => {
  let msg: any
  try { msg = JSON.parse(String(d)) } catch { return }

  // ① 이 SPEC 의 강제 지점. t9 게이트보다 앞이며, 그 게이트와 독립이다 (REQ-GWAUTH-011·012).
  //    버퍼에 이미 들어와 있던 프레임도 여기서 걸린다 — close() 가 디스패치를 앞지르지 못하기 때문이다.
  if (proofRejected) return

  if (msg.type === 'welcome') {
    if (!verifyProof(msg, nonce, opts.token)) {   // 길이 확인 → timingSafeEqual (4번)
      proofRejected = true                        // 플래그를 먼저 세우고
      console.error('minidiscord-channel: …')     // stderr 한 줄 (stdout 금지)
      ws.close()                                  // 그 다음에 닫는다
      return
    }
    established = true
    opts.onWelcome?.(msg)
  } else if (!established) {
    // ② t9 게이트 — welcome 이 오기 전 프레임을 버린다. 한 글자도 바꾸지 않는다.
  } else if (msg.type === 'message') opts.onMessage?.(msg)
  // …
})
```

**두 게이트가 분리되는 이유를 정확히 적는다.** 이 구조에서 «증명에 실패한 상대가 민 프레임» 을 버리는 주체는 ①이다 — ②는 그 프레임에 닿지 않는다. 그러므로 ②를 지우는 변이(**변이 N**)는 이 SPEC 의 부정 기준을 하나도 무너뜨리지 못하고, ①을 지우는 변이(**변이 H**)는 이 SPEC 의 기준만 무너뜨린다. **①을 ② 뒤에 두거나 `proofRejected` 를 `established` 하나로 합치면 그 분리가 사라진다** — v0.1.0 의 계획이 그 구조를 지시했고, 그래서 §「검증 원칙」 4번의 단언이 거짓이었다.

`proofRejected` 도 **소켓 지역**이다(REQ-GWAUTH-002 와 같은 이유). 클로저로 올리면 한 번 거절당한 뒤 재접속이 영원히 막힌다.

4. 대조 함수 `verifyProof`: `typeof proof === 'string'` → **길이 확인**(64자) → `timingSafeEqual(Buffer.from(a,'hex'), Buffer.from(b,'hex'))`. 길이 확인이 먼저인 이유는 §D-7.
5. **상호 참조 주석 (§3.5 완화 2 — 생산 두 자리를 겨눈다)** — 채널의 증명 계산 자리에 규칙의 정본 `server/src/routes-bots.ts:11` 과 그 사용 지점 `server/src/gateway.ts` 를 가리키는 `@MX:ANCHOR` 를 달고, 서버 쪽 기존 `@MX:ANCHOR`(`routes-bots.ts:9-10`)의 «발급과 조회가 갈라지지 않는다» 에 «그리고 채널 사본» 을 더한다. **«세 자리» 가 아니다** — `gateway.ts` 는 import 호출 지점이지 사본이 아니다(1회차 감사 M-01).

**이력 축은 `await` 로 재지 않는다** — 형제 AC-CHANAUTH-003(`transport-auth.test.ts:252-273`)의 `settled` 센티넬 + `settle()` 형태를 그대로 쓴다. `rejects.toThrow(/timed out/)` 는 정상 구현을 10초 타임아웃으로 죽인다(1회차 감사 C-01).

### M6 — 변이표 실행과 경계 확인 (AC-GWAUTH-014)

변이 A~M 을 실행하고, 이어서 **변이 N**(t9 게이트 제거 → AC-GWAUTH-* 가 하나도 무너지지 않아야 한다)과 **변이 O**(`proofRejected` 검사를 `!established` 뒤로 이동 → 그 상태에서 N 을 다시 넣으면 **여섯(AC-GWAUTH-005·006·008·009·011·012)** 이 무너져야 한다 — `005` 는 확립 경로를 공유해 따라온다: ①이 뒤로 밀리고 ②가 지워지면 거절돼야 할 `welcome` 이 확립을 세운다. 이 수는 **2차 sync 감사 G-04 의 실측**(`11 failed | 70 passed` = N 자신의 5건 + 이 여섯)이며 v0.4.0 의 「다섯」은 예측이었다). **[HARD] O 의 형태를 한 문장으로 못 박는다**: `if (proofRejected) return` 을 **체인 밖 독립 문장으로 if/else 체인 뒤에** 옮긴다 — `else if (proofRejected) return` 로 **체인 분기에 끼우는 형태가 아니다.** 후자로 구현하면 `message` 프레임이 ②를 지운 뒤 그 분기에 걸려 변이 N 으로도 **O 가 지목한 기준들이 무너지지 않고**, run 이 «구조가 틀렸다» 로 오진한다 (2회차 감사 N-03).를 실행한다. N·O 두 관측이 짝으로 성립해야 «분리가 구조에서 나온다» 가 확인된다. 마지막으로 `git diff --name-only` 로 경계를 확인한다.

## §G 안티패턴 — 하지 않는다

- **성과를 과장한다.** «전송 계층을 신뢰할 수 있게 만들었다» 로도, **«토큰을 모르는 상대를 배제했다» 로도** 보고하지 않는다 — 후자는 `bot_tokens.token_hash` 만 읽어 간 상대를 놓친다. **그리고 «토큰 또는 그 저장 해시를 모르는 상대를 배제했다» 로도 보고하지 않는다** — v0.4.0 까지 이 자리가 정답으로 적었던 문장이지만, `hello` 를 받는 상대는 미리 몰라도 그 자리에서 토큰을 얻으므로 거짓이다(sync 감사 F-01). 정확한 진술은 «그 소켓의 `hello` 를 읽을 수 없고 토큰도 그 저장 해시도 모르는 상대를 배제했다. `hello` 를 받는 자리에 있는 상대는 닫지 못하며(후속 카드 `t22`), `bot_tokens.token_hash` 가 읽기 전용으로 유출된 배치도 닫지 않는다» 다(`spec.md` §5 의 다섯 행 표). 이 카드는 과장이 만들어 낸 카드이고, v0.1.0 은 그 과장을 한 칸 줄인 형태로 반복했다(1회차 감사 C-03).
- **형제 SPEC 을 고치지 않고 테스트만 고친다.** B-1 을 건너뛴 run 은 sync 감사에서 되돌아온다.
- **`SPEC-CHANAUTH-001` §2.1·REQ-CHANAUTH-002 를 소급 수정한다.** 완료된 SPEC 의 정직성 조항이다(§3.3 C 부류).
- **REQ-CHANAUTH-013 / REQ-CHANINJECT-015 에 예외 조항을 넣는다.** 두 조항은 자기 SPEC 만 구속하므로 예외가 필요 없다(`spec.md` §3.4). 넣으면 존재한 적 없는 제약을 기록으로 만든다.
- **`===` 로 증명을 대조한다.** AC 가 잡지 못하는 자리이므로(§D-7) 리뷰가 지킨다.
- **`git add -A` 로 커밋한다.** 경로를 명시해 스테이징한다.
- **`channel/dist` 를 빌드하지 않고 테스트한다.** 자식 프로세스 기준이 방어와 무관하게 붉어진다.
