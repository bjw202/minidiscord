## §A 실행 순서와 의존

카드 `t5` 안에서 이 SPEC 은 **세 번째**다.

```
SPEC-WEBSHELL-001 (Task 15)  →  SPEC-WEBCHAT-001 (Task 16)  →  SPEC-WEBRICH-001 (Task 17)
   api()·state·$()·showMain()    renderMessage·openRoom·SSE       decorate 공급·초대·권한 버튼
   §4.8 공유 표면 계약 소유       장식 훅 호출 자리·등록 지점 소유   훅에 끼울 함수만 공급
```

**두 선행 SPEC 이 아직 존재하지 않아도 이 SPEC 의 상당 부분은 진행할 수 있다.** `web/rich.js` 는 DOM 과 주입된 `api` 함수 말고는 아무것도 의존하지 않는 순수 모듈이기 때문이다. 실제로 수용 기준 열여섯 중 **열셋**은 `rich.js` 와 실제 서버만 있으면 성립한다. 나머지 **셋**(AC-013 다이얼로그 닫기, AC-015 시각 확인, AC-016 — 관측 3·5 가 base 시점과 현재 시점의 `web/app.js`·`web/index.html` 을 요구한다)은 형제 둘의 산출물이 있어야 한다.

[HARD] **그 셋은 형제가 없으면 *실패*한다. 공허하게 통과하지 않는다.** 0.2.0 의 AC-016 은 base 에 `web/app.js` 가 없으면 셀 것이 없어 조용히 통과했다(감사 MF-10 둘째 경로). 0.3.0 은 base 파일 존재와 `renderMessage` 범위 비어 있지 않음을 관측 3의 **선행 조건**으로 올려, 순서가 어긋난 실행이 초록이 되는 길을 막았다.

run 단계 진입 시 두 선행 SPEC 의 산출물이 트리에 없으면, `rich.js`·`rich.d.ts`·테스트까지 만들고 이음매 배선은 블로커로 보고한다 — 없는 훅에 함수를 끼울 수는 없다.

**0.1.0 은 이 블로커를 "예고"만 했고, 그것이 감사가 잡은 결함이었다**(MF-5). 예고된 블로커의 해결자가 이미 카드에서 손을 뗀 형제였기 때문에, 규율이 있어도 출구가 없었다. 0.2.0 에서 이음매의 소유가 뒤집혔다 — **호출 자리와 등록 지점을 `SPEC-WEBCHAT-001` 이 자기 요구사항·수용 기준으로 선언**하고, 이 SPEC 은 그 훅에 끼울 함수(`createRichContext(...).decorate`)만 공급한다. 그러면 형제가 마감하는 시점에 이음매가 이미 존재하므로, 위 블로커는 "선행 SPEC 이 아직 착수되지 않은 경우"에만 남는다.

## §B 되돌리기 어려운 결정 — 모듈 경계와 상태의 자리

가장 되돌리기 어려운 결정 두 가지를 먼저 놓는다. 나머지는 이 둘의 귀결이다.

### 1. Task 17 의 로직을 `app.js` 가 아니라 `web/rich.js` 에 둔다

원본은 세 기능을 전부 `app.js` 안에 인라인으로 넣는다. 그러면 두 가지가 동시에 깨진다.

- **소유권** — `renderMessage` 는 `SPEC-WEBCHAT-001` 의 산출물인데 원본은 그것을 통째로 바꾸라고 한다. 형제 SPEC 이 같은 함수를 각각 최종본이라고 주장하는 상태가 된다.
- **검증 가능성** — `app.js` 는 최상위에서 `$('invite-btn').onclick = …` 처럼 DOM 을 즉시 만진다. jsdom 에서 import 하는 순간 그 배선이 전부 실행되므로, 첨부 노드 하나를 검사하려고 index.html 전체를 흉내 내야 한다.

그래서 부작용 없는 모듈 `web/rich.js` 를 만들고, `app.js` 는 그것을 불러 쓴다. 테스트는 `rich.js` 만 import 한다.

이 결정을 뒤집으려면 테스트 열 몇 개를 전부 다시 써야 한다.

**이음매의 소유는 0.2.0 에서 뒤집혔다 (감사 MF-5).** 0.1.0 은 "`renderMessage` 끝에 이 SPEC 이 한 줄을 끼운다"고 적었다. 그것은 **소비자가 생산자의 함수 안에 코드를 넣겠다고 일방적으로 선언한 것**이고, 형제 문서 어디에도 그 자리가 규정돼 있지 않았다. 게다가 그 계약 자체가 불완전했다 — `decorate` 라는 이름이 이 SPEC 의 export 목록에도 없었고, `RichContext` 는 참조만 되고 정의가 없었으며, `rich` 인스턴스를 누가 어디서 만드는지도 미정이었다(§B 2 는 "방을 열 때마다 새로"라고 하는데 방을 여는 코드는 형제 소유이고, 이 SPEC 은 스스로 "한 줄 밖은 건드리지 않는다"고 묶여 있었다 — 한 줄로는 방마다 재생성을 실현할 수 없다).

새 소유 배치는 이렇다.

| 조각 | 소유자 | 왜 |
|------|--------|-----|
| `renderMessage` 안의 훅 호출 자리 | `SPEC-WEBCHAT-001` | 함수의 소유자가 자기 함수의 확장점을 선언해야 한다. 소비자가 발명한 확장점은 생산자가 마감한 뒤에는 고칠 사람이 없다 |
| 훅 미등록 시의 무동작 | `SPEC-WEBCHAT-001` | 형제가 단독으로 마감·검증될 수 있어야 한다 |
| 훅 등록 지점(방마다 새 컨텍스트) | `SPEC-WEBCHAT-001` | 방을 여는 코드가 그 SPEC 안에 있다. §B 2 의 "방마다 새 인스턴스"는 그 자리에서만 실현된다 |
| 등록되는 값 = 팩토리 `createRichContext` **그 자체** | **이 SPEC** | 노드 조립과 판정 상태는 이 SPEC 의 본질이다. 호출 결과(`.decorate`)가 아니라 팩토리를 넘겨야 방마다 새 인스턴스가 생긴다 |
| 등록을 수행하는 배선 한 줄과 그 `import` | **이 SPEC** | `spec.md` REQ-WEBRICH-002 「배선 계약」이 전문. `web/app.js` 모듈 최상위, 정확히 한 번 |

이 SPEC 이 `web/app.js` 에 더하는 것은 전부 `renderMessage` **밖**이다 — `import { createRichContext } from './rich.js'`, 모듈 최상위의 `registerMessageDecorator(createRichContext)` 한 줄, 그리고 초대 다이얼로그 핸들러들. AC-016 관측 3이 `renderMessage` 불가침을, 관측 4·5 가 그 배선의 존재와 **넘기는 값의 형태**를 기계적으로 판정한다.

[HARD] **넘기는 값은 팩토리 `createRichContext` 그 자체다.** 0.2.0 은 세 곳에서 `createRichContext({ api, doc: document }).decorate` 를 넘긴다고 적었는데, 형제의 `registerMessageDecorator(factory)` 는 **팩토리**를 요구한다(`SPEC-WEBCHAT-001` `spec.md` REQ-WEBCHAT-016 등록 계약, `AC-WEBCHAT-002` 의 `expect(factoryCalls).toBe(2)`). 그대로 구현하면 `openRoom` 이 `factory({ api, doc })` 를 부를 때 실제로는 `decorate({ api, doc }, undefined)` 가 불리고, 반환 `undefined` 가 그 방의 컨텍스트가 되어 첫 메시지에서 `TypeError` 로 죽거나 — 널 가드가 있으면 — 첨부와 권한 버튼이 **아무 오류 없이 영원히 안 뜬다.** 게다가 인스턴스가 하나뿐이라 `resolved`·`pending` 이 방을 넘어 살아남아, §B 2 가 배제한 바로 그 상태로 되돌아간다. 이것이 감사 MF-9 이며 0.3.0 에서 정정했다.

`decorate` 가 건네받은 요소에 무엇을 해도 되고 무엇을 하면 안 되는지는 `spec.md` REQ-WEBRICH-002 아래 「요소 계약」이 전문이다. 그 가운데 run 단계에서 가장 틀리기 쉬운 둘을 여기 옮겨 둔다. **첫째, 호출 시점에 `el` 은 아직 문서에 붙어 있지 않다** — `#messages` 삽입 직전이므로 `getComputedStyle`·`closest` 처럼 연결을 전제하는 API 를 쓰면 조용히 틀린다. **둘째, `decorate` 는 동기 함수이고 `void` 를 돌려준다** — `async` 로 만들면 `renderMessage` 의 동기 렌더 경로에서 노드가 붙기 전에 반환돼, 첨부가 가끔 보이고 가끔 안 보이는 모양이 된다.

### 2. 판정 완료 상태는 팩토리 인스턴스 안에만 산다

`REQ-WEBRICH-010` 을 만족하려면 "어떤 `request_id` 가 이미 끝났는가"를 어딘가 기억해야 한다. 모듈 최상위 `const resolved = new Set()` 이 가장 짧지만 틀렸다 — 방을 옮겨도 남고, 테스트끼리 샌다. `createRichContext({ api, doc })` 팩토리가 자기 클로저에 두 개의 지도를 들고, 방을 열 때마다 새로 만든다.

```js
export function createRichContext({ api, doc }) {
  const resolved = new Set()                 // 판정이 끝난 request_id
  const pending = new Map()                  // request_id → [승인 버튼, 거절 버튼]
  return {
    decorate(el, m) { /* 첨부 + 권한 버튼 */ },
  }
}
```

`decorate` 는 매 메시지마다 두 가지를 한다 — 판정 결과 메시지면 `resolved` 에 넣고 `pending` 에 있는 버튼을 비활성한다. 요청 메시지면 `resolved` 에 이미 있는지 보고 살아 있는 버튼을 붙일지 말지 정한다. **순서 양방향이 다 필요하다**: REST 이력은 요청→결과 순으로 오지만, SSE 는 요청만 먼저 오고 결과가 나중에 온다.

## §C 되돌리기 어려운 결정 — 검증 방식과 개발 환경

### 원본의 "수동 확인"을 계약 합치 검사로 바꾼다

원본 Task 17 Step 3 은 "파일 첨부해서 전송 → 📄 링크 → 클릭 시 다운로드. 봇 초대 → 명령 안내 표시·복사"라는 사람 눈 확인을 유일한 검증으로 둔다. 이 SPEC 은 그것을 **보조**로 내리고, 세 가지 기계 검증을 주력으로 올린다.

| 층 | 무엇을 재나 | 환경 |
|----|-------------|------|
| 순수 함수 | 정규식·URL 조립·확장자 판정 | 환경 무관 |
| DOM 조립 | 어떤 노드가 어떤 속성으로 붙는가 | `jsdom` |
| **계약 합치** | UI 가 만든 페이로드를 **실제 서버**에 먹였을 때 의도한 결과가 나는가 | `node` + 실제 Fastify + 실제 WebSocket |

계약 합치가 이 SPEC 의 중심이다. 권한 판정은 UI 가 만든 문자열이 서버 정규식과 **글자 단위로** 맞아야만 성립하고, 어긋나면 200 이 돌아오면서 조용히 실패한다. "버튼을 눌렀더니 fetch 가 불렸다"를 재는 검사는 이 실패를 전부 통과시킨다. 그래서 AC-001·002·003·004 는 `server/test/permissions.test.ts` 의 하네스를 그대로 재사용해, 가짜 봇 WebSocket 이 `permission_verdict` 를 **실제로 받는지**를 관측한다.

### 개발 환경 선행 조건 (run 단계 첫 스텝)

> **[NEEDS CLARIFICATION 아님 — 확정된 설치 스텝]** 아래 두 줄은 추정이 아니라 이 워크트리에서 확인한 사실에 근거한다. `ls node_modules` → 부재. `server/package.json` → `vitest ^4.1.11`, `jsdom`·`happy-dom` 없음. `server/` 아래 vitest 설정 파일 없음.

```js

```

전역 `vitest.config.ts` 에 `environment: 'jsdom'` 을 넣으면 형제 SPEC 들이 남긴 서버 테스트 여덟 파일이 전부 jsdom 위에서 돌게 된다. 그 테스트들은 실제 소켓과 파일 시스템을 쓰므로 환경을 바꾸면 무엇이 깨질지 이 SPEC 이 통제할 수 없다. 설정 파일을 새로 만들지 않는 것이 이 SPEC 의 범위 경계와도 맞는다.

### `tsc --noEmit` 을 통과시키는 방법

`server/tsconfig.json` 은 `include: ["src","test"]` 에 `allowJs` 가 없다. 테스트가 `../../web/rich.js` 를 import 하면 TypeScript 는 같은 이름의 `.d.ts` 를 찾는다. 그래서 `web/rich.d.ts` 를 **산출물로 만든다** — `@ts-ignore` 한 줄로 덮는 것보다 낫다. 형이 실제로 검사되므로 이음매의 시그니처 불일치가 타입 검사에서 잡힌다.

### 브라우저 사실 하나 (검증 불가, 위험으로 남긴다)

`GET /api/attachments/:id` 는 `content-disposition: attachment` 를 붙인다(`routes-messages.ts`). 브라우저가 `<img src>` 에서 이 헤더를 무시하고 이미지를 렌더한다는 것이 통설이지만 **이 SPEC 은 그것을 기계로 재지 못한다** — jsdom 은 이미지를 가져오지 않는다. 그래서 AC-007 은 "`<img>` 노드가 올바른 `src` 로 만들어진다"까지만 단언하고, "실제로 그려진다"는 AC-015(사람 눈)로 넘긴다. 그려지지 않으면 run 단계에서 블로커로 보고하고 서버 쪽 헤더 조정(별도 SPEC)을 제안한다.

## §D 원본 문서 모순과 해결

원본 Task 17 의 코드 블록을 실제 서버 코드와 대조해 찾은 결함 열 건이다. **전부 의도적으로 이탈했다.**

### 1. `renderMessage` 를 통째로 교체하라는 지시

원본은 "실행자는 Task 16 의 `renderMessage` 를 다음 완성본으로 교체한다"고 쓴다. 그러면 `SPEC-WEBCHAT-001` 과 이 SPEC 이 같은 함수의 최종본을 각각 주장하게 되고, 카드 안 실행 순서에 따라 뒤에 오는 쪽이 앞의 것을 조용히 덮는다.

**해결 (0.2.0 교정)**: `web/rich.js` 로 분리하고, `renderMessage` 안의 장식 훅 호출 자리와 그 등록 지점은 **`SPEC-WEBCHAT-001` 이 자기 요구사항으로 선언한다.** 이 SPEC 은 그 훅에 끼울 함수만 공급하고 `renderMessage` 본체는 한 줄도 건드리지 않는다 (REQ-WEBRICH-002). 두 SPEC 이 겹치는 코드가 **0 줄**로 줄어든다.

0.1.0 의 해결("이 SPEC 이 한 줄을 끼운다")은 방향이 반대였다 — 자세한 것은 §B 1 에 적었다.

### 2. **[가장 무거움]** `request_id` 파서가 본문 아무 데서나 다섯 글자를 집는다

원본:

```js
const rid = /[a-km-z]{5}/.exec(m.body)?.[0]
```

브로커가 만드는 본문은 이렇다 (`server/src/permissions.ts`).

```
🔒 봇이 도구 사용 승인을 요청합니다: {tool_name}
{description}
{input_preview}
승인하려면 "yes {request_id}", 거절하려면 "no {request_id}" 라고 답해주세요.
```

앞 세 조각은 **봇이 보낸 임의 문자열**이다. `[a-km-z]{5}` 는 그 안의 아무 다섯 글자 소문자 러닝에나 맞는다 — `input_preview` 에 `command` 가 있으면 첫 일치는 `comma` 다. 그러면 UI 는 `yes comma` 를 보내고, 서버 정규식은 형식상 통과하지만 `open.get('comma')` 가 비어 `tryHandleUserReply` 는 `false` 를 돌린다. 그 답은 평범한 사용자 메시지로 방에 저장되고, **진짜 대기 항목은 그대로 열려 있다.** 승인을 기다리던 세션은 영원히 멈춘다.

이 실패에는 어떤 신호도 없다 — 버튼은 눌렸고, 요청은 200 이고, 화면에는 `yes comma` 라는 줄이 하나 늘 뿐이다.

**해결**: 마지막 줄 템플릿 전체를 역참조까지 포함해 일치시키고 마지막 일치의 캡처를 쓴다 (REQ-WEBRICH-006·007).

```js
/^승인하려면 "yes ([a-km-z]{5})", 거절하려면 "no \1" 라고 답해주세요\.$/m
```

역참조가 있어야 "앞뒤 ID 가 같은 줄"만 통과한다. AC-003 이 오염된 `input_preview` 로 이 성질을 회귀 검사한다.

**대가**: UI 가 서버의 한국어 템플릿 문자열에 결합한다. `permissions.ts` 는 이미 그 결합을 주석으로 인정하고 있고(`카드 t5 UI 의 … 파서가 이 형식에 결합한다`), 대안(서버가 `request_id` 를 구조화 필드로 실어 보내는 것)은 `SPEC-PERM-001` 의 계약 변경이라 이 SPEC 의 범위 밖이다. §E 위험으로 남긴다.

### 3. 판정이 끝난 요청에 버튼이 다시 살아난다

원본은 클릭 시 버튼을 비활성하지만, 그 상태는 DOM 노드에만 있다. 방을 다시 열면 `openRoom` 이 REST 이력을 전부 다시 그리므로 이미 끝난 요청에 **살아 있는 버튼이 다시 뜬다**. 누르면 §D 2 와 같은 경로로 방에 쓰레기 메시지만 남는다.

**해결**: 브로커가 남기는 판정 결과 메시지에서 ID 를 뽑아 `resolved` 집합을 만들고, 양방향(선렌더·후도착)으로 버튼을 잠근다 (REQ-WEBRICH-010, AC-011).

### 4. 첨부에 `mime` 이 없는데 이미지 판정이 필요하다

카드 지시는 "이미지는 인라인, 그 밖은 링크"인데, 서버가 메시지 봉투에 싣는 첨부는 `{ id, filename }` 뿐이다. `routes-messages.ts` 는 `stored_path` 와 함께 `mime` 도 응답에서 **의도적으로 뺐다**(경로 노출 감사 F-02 의 귀결). `att.mime` 을 읽는 구현은 언제나 `undefined` 를 보고 전부 링크로 떨어지며, 그 실패는 "이미지가 링크로 보인다"는 약한 신호로만 나타난다.

**해결**: 파일명 확장자로만 판정한다 (REQ-WEBRICH-003). 확장자와 실제 내용이 다른 파일은 깨진 이미지로 보인다 — 수용한다(§E).

### 5. 첨부 URL 을 검증 없이 문자열로 조립한다

원본은 `a.href = \`/api/attachments/${f.id}\`` 다. 현재 서버는 `id` 를 정수로 넣지만, 클라이언트가 서버 값의 형을 신뢰해 URL 을 만드는 습관 자체가 위험하다 — 값이 문자열이 되는 날 `href` 는 임의 문자열이 된다.

**해결**: `attachmentUrl(id)` 가 `Number.isInteger` + 음수 배제를 거쳐 통과한 값만 십진수로 적고, 아니면 `null` 을 돌려 노드를 만들지 않는다 (REQ-WEBRICH-004, AC-009).

### 6. `navigator.clipboard` 가 없을 때 조용히 실패한다

원본: `navigator.clipboard.writeText($('invite-command').textContent)`. `clipboard` 는 보안 컨텍스트에서만 있다. 기본 `127.0.0.1` 은 보안 컨텍스트지만 같은 서버를 LAN 주소(`http://192.168.x.x:3000`)로 열면 `undefined` 이고, 이 줄은 처리되지 않은 `TypeError` 로 끝난다. 사용자는 **토큰을 복사했다고 믿고 다이얼로그를 닫는다** — 그리고 토큰은 영영 사라진다.

**해결**: `copyText(text, { nav, onFail })` 이 부재·거부를 모두 잡아 `false` 를 돌리고 화면에 실패를 표시한다 (REQ-WEBRICH-014, AC-006).

### 7. 다이얼로그를 닫아도 토큰이 DOM 에 남는다

원본은 다이얼로그를 **열 때** `#invite-result` 를 숨기지만 `#invite-command` 의 내용은 지우지 않는다. 닫힌 `<dialog>` 의 자식 노드는 그대로 살아 있으므로 평문 토큰이 페이지 수명 내내 DOM 에 남고, 개발자 도구·확장 프로그램·`document.body.innerText` 를 읽는 어떤 코드에도 노출된다.

**해결**: 닫을 때 비운다 (REQ-WEBRICH-015, AC-013).

### 8. CSS 가 디자인 토큰을 무시하고 색을 직접 적는다

원본 CSS 는 `#2b2d31`(= `--md-bg-panel`), `#00a8fc`(= `--md-text-link`), `#1e1f22`(= `--md-bg-sidebar`), `#4e5058`(토큰에 없음)을 직접 적는다. `web/design-tokens.css` 가 M5 의 구속력 있는 시각 표준이고 `style.css` 는 그것을 소비하기로 되어 있다.

**해결**: 전부 `var(--md-*)` 로 옮긴다. 토큰에 없는 `#4e5058` 은 가장 가까운 역할인 `--md-bg-input`(`#383a40`)으로 대체한다 (REQ-WEBRICH-016, AC-014).

### 9. 초대 버튼이 실패를 삼킨다

원본의 봇 선택 핸들러는 `await api(...)` 를 `try` 없이 부른다. 보관된 방(409)·없는 봇(404)이면 처리되지 않은 거부가 되고 다이얼로그는 아무 반응 없이 열린 채로 남는다.

**해결**: 실패를 `#invite-result` 영역에 오류 문구로 표시한다. 이것은 화면 문구라 별도 REQ 를 두지 않고 §F M3 의 작업 항목으로 둔다.

### 10. [미해결 — 보존] `<dialog>.showModal()` 은 jsdom 에서 신뢰할 수 없다

jsdom 의 `<dialog>` 지원은 버전마다 다르고 `showModal()` 이 없는 판이 있다. 이 SPEC 은 그것을 우회하지 않는다 — 대신 `showModal()`/`close()` 호출을 `app.js` 에만 두고 `rich.js` 는 노드 조립과 상태만 다루게 해서, 어떤 수용 기준도 `showModal()` 을 부르지 않게 설계했다. 다이얼로그가 실제로 뜨는지는 AC-015(사람 눈)가 본다.

이 프로젝트에는 **구현이 옳든 그르든 통과하는 수용 기준**이 반복해서 나온 기록이 있다(카드 `t2`·`t3` 에서 같은 부류가 세 번). 그래서 이 SPEC 의 열여섯 기준을 하나씩이 아니라 **부류로** 훑었다. 훑은 축과 결과를 남긴다.

**이 표의 훑기는 한 방향뿐이었고, 범위가 이 SPEC 안이었다.** 독립 감사는 방향 A 에서 0건을 확인해 위 주장을 사실로 인정했지만, 반대 방향에서 두 건을 잡았다. 왜 놓쳤는지와 다시 훑은 결과는 §E.2 에 있다.

## §E.2 수용 기준 전수 훑기 (0.2.0) — "형제가 옳게 구현하면 실패하는가?"

[HARD] 0.1.0 의 훑기는 **"빈/스텁 구현이 통과하는가"** 한 방향만 물었고, 물은 범위가 이 SPEC 안이었다. 반대 방향 — **형제 SPEC 이 자기 요구사항대로 옳게 구현했을 때 이 기준이 실패하는가** — 은 정의상 자기 SPEC 안에서는 보이지 않는다. 실패를 일으키는 것이 형제의 변경이기 때문이다. 독립 감사(`.moai/reports/t5/plan-audit.md`)가 정확히 그 지점을 짚었다: *"남은 것은 방향 B 이고, 그것은 정의상 자기 SPEC 안에서는 보이지 않는다."*

그리고 감사는 하나를 더 짚었다 — 0.1.0 의 훑기 축에 **"어떤 기준으로도 관측되지 않는 요구사항이 있는가"** 가 없었다. 그래서 REQ-WEBRICH-002 를 놓쳤다.

그래서 질문을 셋으로 늘려 열여섯 기준을 **카드 전체 범위에서** 다시 훑었다.

- **방향 A** — 본문이 비어 있는 구현이 이 기준을 통과하는가?
- **방향 B (신설)** — **형제 SPEC(`SPEC-WEBSHELL-001`·`SPEC-WEBCHAT-001`)이 자기 요구사항대로 옳게 구현했을 때 이 기준이 실패하는가?**
- **축 C (신설)** — 이 기준이 매핑됐다고 적힌 REQ 를 **실제로 관측하는가?**

### 두 부류를 가른 원리

방향 B 의 다섯 건에는 공통 성질이 하나 있었다 — **이 SPEC 이 소유하지 않은 것에 대해 단언했다.** AC-014 는 `index.html` 의 내용을 단언했는데 그 파일의 토큰 로딩 방식은 `SPEC-WEBSHELL-001` 소유다. AC-004·007·008·009 는 형이 어떻게 좁혀지는지를 암묵적으로 가정했는데 그 형은 이 SPEC 이 아직 정의하지 않은 것이었다. 교정 원리는 하나다 — **소유한 것만 단언하고, 소유하지 않은 것은 계약을 참조한다.**

축 C 의 한 건은 성질이 다르다. 관측 대상을 **파일 단위**로 잡으면, 그 파일 안에서 무엇이 일어나든 관측되지 않는다. 소유 경계가 파일보다 가는 곳(`web/app.js` 안의 `renderMessage`)에서는 관측도 그만큼 가늘어야 한다.

## §E.3 수용 기준 전수 훑기 (0.3.0) — "실패가 아니라 *공허*로 무너지는 입력이 있는가?"

[HARD] 앞의 두 라운드는 기준마다 두 가지를 물었다 — **빈 구현이 통과하는가**(방향 A), **형제가 옳게 구현하면 실패하는가**(방향 B). 두 번째 독립 감사(`.moai/reports/t5/plan-audit-b.md` 권고 3)는 그 둘로도 안 잡히는 세 번째 부류를 짚었다.

> **방향 C — 이 기준이 실패가 아니라 *공허*로 무너지는 입력이 있는가?** 절차를 건너뛴 실행, 파일이 없는 base, 표준 오류로만 실패하고 표준 출력은 비는 명령.

이 부류가 위험한 이유는 방향 A 와 겉모습이 같지만 원인이 반대이기 때문이다. 방향 A 는 **구현**이 비어서 통과하는 것이고, 방향 C 는 **관측 대상**이 비어서 통과하는 것이다. 방향 A 는 기준을 더 엄격하게 만들면 막히지만, 방향 C 는 기준을 더 엄격하게 만드는 바로 그 순간에 생긴다 — 0.2.0 이 MF-8 을 메우려고 AC-016 에 관측 3을 더하면서 그 관측의 선행 조건은 더하지 않은 것이 정확히 그것이다.

```bash
grep -nE "#[0-9a-fA-F]{3,8}\b" web/style.css   # 이 SPEC 이 추가한 블록 안에 일치 없음
```

### 변이 검증 (필수)

카드 `t3` 이 남긴 방법론을 따른다 — 테스트를 읽어 안심하지 말고 **구현을 되돌려 테스트가 우는지 본다**. 최소 네 건:

1. `permissionRequestId` 를 원본의 `/[a-km-z]{5}/.exec(body)?.[0]` 로 되돌린다 → AC-003 이 울어야 한다.
2. `decorate` 안의 `resolved` 확인을 지운다 → AC-011 이 울어야 한다.
3. `attachmentUrl` 의 정수 검사를 지운다 → AC-009 가 울어야 한다.
4. **(0.2.0 신설)** `renderMessage` 를 원본 Task 17 의 완성본으로 통째로 교체한다 → AC-016 관측 3이 울어야 한다. 0.1.0 의 기준으로는 이 변이가 **아무것도 울리지 않았다**(감사 MF-8) — 그것이 이 변이를 추가한 이유다.
5. **(0.3.0 신설)** 배선을 `registerMessageDecorator(createRichContext({ api, doc: document }).decorate)` 로 되돌린다 → AC-016 관측 4(둘째 명령이 `1`)와 관측 5(첨부 노드 0개 또는 `TypeError`)가 **둘 다** 울어야 한다. 0.2.0 의 기준으로는 이 변이가 아무것도 울리지 않았고, 세 SPEC 48개 기준이 전부 초록인 채로 실제 앱에서는 첨부가 안 뜨는 상태가 됐을 것이다(감사 MF-9).
6. **(0.3.0 신설)** `.spec-base-sha` 를 지우고 AC-016 을 실행한다 → 관측 0 이 울어야 한다. 0.2.0 의 기준으로는 세 관측이 **전부 통과**했다(감사 MF-10).

울지 않는 것이 있으면 그 기준이 공허한 것이며, 고치기 전에는 카드를 닫지 않는다.

## §H 안티패턴 (하지 말 것)

1. `renderMessage` 본체를 **한 줄도 건드리지 않는다** — 호출 자리도 등록 지점도 `SPEC-WEBCHAT-001` 소유다. 이 SPEC 은 훅에 끼울 함수만 공급한다.
2. `request_id` 를 본문 아무 데서나 정규식으로 집지 않는다.
3. 판정 결과 메시지의 한국어·이모지 리터럴을 테스트에 손으로 타이핑하지 않는다 — 실제 서버 출력을 입력으로 쓴다.
4. 토큰·명령을 어떤 저장소·주소·콘솔에도 남기지 않는다.
5. `navigator.clipboard` 를 무조건 있다고 가정하지 않는다.
6. `att.mime` 을 읽지 않는다 — 응답에 없다.
7. `innerHTML` 로 첨부 목록을 만들지 않는다.
8. 전역 `vitest.config.ts` 를 **이 SPEC 이** 앞질러 새로 만들지 않는다 — 1순위는 파일 단위 도크블록이다. 형제가 먼저 만들었다면 지우거나 바꾸지 않고 따른다(0.2.0 교정, 감사 O-5). **다만 도크블록이 실제로 듣지 않고 형제도 만들어 두지 않았다면, 이 SPEC 이 만드는 것이 허용된다** — 이 SPEC 은 골격 A(`node`)와 골격 B(`jsdom`) 두 환경을 동시에 쓰는 유일한 SPEC 이라 그럴 가능성이 형제보다 높다. 그 파일은 AC-016 허용 집합에 있고(0.3.0, 감사 MF-11), 만들거나 고쳤으면 그 사실과 이유를 `progress.md` 에 적는다.
9. `server/` 아래 어떤 파일도 고치지 않는다 (`server/test/` 의 새 테스트 파일 제외).
10. 원시 16진 색을 `style.css` 에 새로 적지 않는다.
11. 버튼 비활성을 `await` 뒤로 미루지 않는다 — 첫 동작이어야 한다.
12. 판정 완료 상태를 모듈 전역에 두지 않는다.
12-1. **등록 지점에 `createRichContext(...)` 의 호출 결과를 넘기지 않는다.** 넘기는 것은 팩토리 함수 그 자체다 — `registerMessageDecorator(createRichContext)`. `.decorate` 를 넘기면 자동 기준은 조용히 통과하고 실제 앱에서만 깨진다(감사 MF-9, `spec.md` REQ-WEBRICH-002 「배선 계약」).
12-2. **관측을 강화할 때 그 관측의 선행 조건을 함께 넣지 않는 일을 하지 않는다.** 기준 SHA 가 없거나 base 파일이 없거나 대상 파일이 없을 때 명령이 표준 오류로만 실패하면, 그 관측은 실패가 아니라 **공허**로 무너진다(감사 MF-10).
13. "테스트가 통과했다"를 실행 없이 적지 않는다 — 원문 출력을 남긴다.
14. 시각 확인 기준을 자동 검사처럼 위장하지 않는다.
15. `decorate` 를 `async` 로 만들지 않고, 건네받은 `el` 이 문서에 연결돼 있다고 가정하지 않는다 — 호출 시점은 `#messages` 삽입 **직전**이다.
16. `web/index.html` 에 `design-tokens.css` `<link>` 를 더하지 않는다 — 토큰은 `style.css` 의 `@import` 하나로만 실린다(§4.8 계약 5). AC-014 가 붉으면 `index.html` 을 고칠 것이 아니라 명령의 대상을 확인한다.
