1. 요약

minidiscord는 2026-08-26의 설계 문서 네 장(제품·기술·구조·로드맵)에서 출발해, 여섯 장의 칸반 카드(큐에서 하나씩 꺼내 처리하는 작업 항목)로 전체를 지을 예정이었습니다. 지금은 SPEC(작업 단위의 설계·요구사항 문서) 21건이 만들어져 19건이 완료됐고, 카드 진행은 t22에 이르렀으며 t23이 큐에서 대기 중입니다.

늘어난 작업의 대부분은 새 기능이 아닙니다. 기능 구축 파도(t1~t5, SPEC 16건)가 지나간 뒤 이어진 보안 강화 파도(t7·t9·t10·t11·t15·t22·t23)가 뒤를 받았고, 그 중심에는 채널-서버 사이 인증이 있습니다. 원래 설계의 봇 접속은 «평문 토큰을 hello 프레임에 실어 보내는» 단순한 방식이었는데, 이것이 네 세대에 걸쳐 다시 지어졌습니다. 전송 계층 방어(t9) → 상호 인증 v1(t15) → 상호 인증 v2(t22, 진행 중) → 서버 TLS(t23, 예정)의 순서입니다.

카드가 늘어난 두 번째 이유는 검증이 정밀해진 것입니다. 각 보안 카드는 독립 감사(별도 심사자가 설계 문서와 구현을 결함 기준으로 검토하는 절차)를 통과해야 하고, 감사는 «방어가 닫은 것보다 넓게 닫았다고 적지 않았는가», «수용 기준이 명명한 공격자를 실제로 재는가»를 따집니다. t15와 t22는 이 질문 앞에서 각각 세 번 이상의 감사-개정 반복을 겪었습니다.

남은 큰 구멍은 하나로 정리됩니다. 이 저장소의 서버는 TLS(HTTPS 뒤에 있는 암호화 전송 계층)를 종단하지 않아서, t22가 새로 세운 «채널 바인딩»이 오늘의 배치에서는 서지 않습니다. 이를 닫는 t23이 큐에 있으며, t23이 닫히기 전까지 생산 배치는 불가하다는 경고가 설계 문서에 명시되어 있습니다. 그리고 t23 외에도 큐에는 여덟 장이 더 남아 있습니다 — 계획상 마지막 단계인 검증 카드 t6(아직 수행 전)과, 감사가 만들어 낸 잔여를 처분하는 일곱 장(t8·t12·t14·t16·t17·t19·t20)입니다.

2. 원래 설계 — 2026년 8월 26일의 네 장

2.1 만들려던 것

제품 문서(product.md)가 그린 그림은 단순합니다. 디스코드를 쓸 수 없는 회사 네트워크 같은 환경에서, 클로드코드 세션을 봇으로 참여시켜 대화할 수 있는 자체 호스팅 채팅 서버 — «내 PC에서 도는 나만의 디스코드»입니다. 사용자는 어디서든 브라우저로 내 PC의 서버에 접속하고, 세션들은 채널 플러그인(Claude Code 세션과 서버를 잇는 다리 역할 프로그램)을 통해 봇으로 접속합니다. 성공 기준 여섯 개 — 방 만들고 봇 초대, 서버 재시작 후에도 대화 보존, 파일 송수신, 한 방에 여러 봇, @TO/@CC 멘션 라우팅, 기록 따라잡기 — 가 전부입니다.

기술 문서(tech.md)는 비기능 요구사항을 분명히 했습니다. Node.js + TypeScript, 단일 서버 프로세스, SQLite 하나, 완성된 답변을 한 번에 보내는 응답 방식, 그리고 HTTP + 단순 로그인으로 시작한다는 것입니다. 여기에 두 문장이 이후 모든 이야기의 씨앗이 됩니다.

  • «HTTPS는 이후 업그레이드 경로로만 남겨두고 v1 범위에는 포함하지 않는다» (product.md)
  • «HTTP 평문: v1은 HTTP만 지원하므로 공용망에서 도청 위험이 있다 — 이 위험을 인지하고 v1에서는 수용한다» (tech.md)

2.2 세 컴포넌트와 연결 흐름

구조 문서(structure.md)는 세 개의 독립 컴포넌트로 시스템을 정의했습니다. 세션은 정확히 한 방에만 접속하고, 서버는 세션을 직접 조종하지 않으며, 서버는 봇의 페르소나를 모른다 — 이 세 원칙이 전체를 관통합니다.

봇 접속 프로토콜도 이 문서에 정의되어 있습니다. 채널이 hello { token }으로 인증을 요청하면 서버가 welcome으로 답하며, 전체 프로토콜은 아홉 가지 프레임 형식으로 정의되어 있습니다. 봇 인증은 «초대 때 한 번 발급한 (방, 봇) 조합 토큰을 hello에 실어 보낸다»가 전부였습니다. 서버는 토큰을 해시로만 저장한다는 보안 원칙(tech.md)은 있었지만, 전송되는 토큰이 평문이라는 사실은 두 설계 문서 어디에도 문제로 기록되어 있지 않습니다.

2.3 원래 설계가 «나중으로 미룬 것»

해설 원래 설계를 다시 읽으면, 이후 카드들이 갈 곳이 이미 표시되어 있었습니다. 설계가 게으른 것이 아니라 «먼저 만들 것»과 «나중에 닫을 것»을 나눈 기록이 남아 있고, 보안 파도는 그 표시된 자리를 순서대로 닫은 것이라고 읽힙니다.

원래 설계의 판단출처이후에 일어난 일
HTTPS는 v1 범위 밖, 업그레이드 경로만 확보product.md·tech.mdt23(서버 TLS 종단, 예정)이 돌아와 닫아야 할 자리가 됨
방별 접근 권한은 두지 않는다(YAGNI — 쓰지 않을 기능을 미리 만들지 않는다는 설계 원칙)product.md권한 릴레이가 들어오면서 «로그인한 누구나 아무 방이나 읽는다»가 권한 상승 경로로 변해 t11(SPEC-ROOMAUTHZ-001)이 이 판단을 뒤집음
봇 인증은 (방,봇) 토큰 하나, hello에 평문으로 실어 보냄structure.md·tech.mdt9 → t15 → t22의 인증 강화 사슬이 이 한 장을 다시 지움
채널 계약은 연구 단계(research preview) 기능이라 바뀔 수 있음tech.md계약 변경을 채널 플러그인 패키지 하나로 국한하라는 원칙이 유지되는 가운데 보안 카드들이 이 경계 위에서 작업

3. 단계별 성장 기록 — 두 파도와 인증 사슬

3.1 개관 — 카드 여섯 장의 계획이 어디까지 늘어났나

로드맵(ROADMAP.md)은 마일스톤 M1~M6 여섯 단계를 여섯 장의 카드(t1~t6)로 나누었습니다. 실제로 작업이 늘어난 경로는 두 파도로 요약됩니다.

파도시기(문서 기준)카드무엇을 했는가산출
파도 1 · 기능 구축 08-26 ~ 08-27 t1 ~ t5 서버·채널 플러그인·웹 UI 전체를 지어 올림. 카드 다섯 장이 SPEC 열여섯 건을 낳았습니다(t2 하나가 상한 초과로 셋으로 쪼개지는 등) SPEC 16건 (전부 완료)
파도 2 · 보안 강화 08-28 ~ (진행 중) t7 · t9 · t10 · t11 · t15 · t22 · t23 t4 감사가 잡은 전송 계층·채널 주입·방 인가 결함에서 시작해, 게이트웨이 인증을 v1·v2로 다시 지음 SPEC 5건 (완료 3 · 진행 2)

16 + 5 = SPEC 21건입니다. 해설 대칭이 눈에 띕니다 — 기능은 카드 다섯 장이 SPEC 열여섯 건을 만들었고, 보안은 카드 다섯 장이 SPEC 다섯 건을 만들었습니다. 카드 번호가 t23에 이른 것은 t6 이후의 보안·교정 카드들 때문입니다. 큐 파일(.moai/state/kanban/backlog.json)을 보면 지금도 카드 아홉 장이 남아 있습니다 — 아직 수행되지 않은 검증 카드 t6, 감사 잔여를 처분하는 일곱 장(t8·t12·t14·t16·t17·t19·t20), 그리고 t23입니다. 반면 닫힌 카드는 큐에서 사라지므로 t13·t18·t21처럼 이 파일에 흔적이 남지 않는 경우도 있고, 카드 작업은 나무(워크트리 — 같은 저장소를 별도 폴더에 꺼내 놓은 작업 사본)마다 흩어져 있습니다. 부록의 대응표는 이 나무의 문서와 큐 파일로 확인되는 것만 적습니다.

3.2 파도 1 — 기능 구축 안에서도 늘어난 이유

기능 구축 파도는 «계획대로 지으면 끝»이 아니었습니다. 완성된 SPEC들의 작성 기록(HISTORY)에는 세 가지 반복 패턴이 남아 있습니다.

첫째, 한 카드가 여러 SPEC으로 쪼개졌습니다. 카드 t2는 인증·방·봇 등록·봇 초대를 한 SPEC으로 묶으려다 요구사항 33개로 상한(Tier당 문서 분량 규칙)을 넘겨 SPEC-AUTH-001·SPEC-ROOM-001·SPEC-BOT-001 셋으로 갈라졌습니다. t3와 t4도 각각 5건·4건의 SPEC으로 나뉘었습니다.

둘째, 원래 설계 문서에 적힌 코드가 실제 코드와 어긋나 있었습니다. 웹 UI 세 SPEC은 원본 계획서의 HTML·JS·CSS 코드 블록을 이미 지어진 서버 코드와 대조해 각각 결함 열 건·일곱 건·열 건을 발견했고, 그중 «자동완성이 만드는 멘션 문자열을 서버 파서가 해석하지 못한다» 같은 것은 그대로 옮겼다면 실제 결함이 될 것이었습니다. 메시지 API SPEC은 원본 두 문서 사이의 모순 일곱 건을, 채널 배선 SPEC은 «구현이 완벽해도 테스트가 TypeError로 죽는» 차단급 하네스 결함을 잡았습니다.

셋째, 기능이 다 지어진 뒤 감사가 보안 결함을 들춰냈습니다. 카드 t4(채널 플러그인)의 동기화 감사가 Critical 한 건을 포함한 결함들을 보고했고, 이것이 보안 파도의 문을 열었습니다 — t9(전송 계층), t10(채널 주입), t11(방 인가)이 같은 감사 보고서의 서로 다른 발견에서 태어났습니다.

3.3 인증 강화 사슬 — 네 세대의 기록

보안 파도의 중심인 인증 사슬을 각 세대별로 «무엇을 만들다가 / 무엇이 발견됐고 / 무엇이 추가됐는가»로 적습니다.

0세대 — 원래 설계의 한 장 (2026-08-26)

봇은 hello { token }으로 평문 토큰을 실어 인증하고, 서버는 증명 없는 welcome으로 답합니다. 서버와 채널이 같은 머신의 로컬 소켓 위에서 만난다는 전제 위에서는 합리적인 설계였고, 공격자 모델(누가, 무엇을 볼 수 있는 상대인가)은 정의되어 있지 않았습니다.

1세대 — 카드 t9 · SPEC-CHANAUTH-001 (완료, 2026-08-28)

  • 만들다가 — 채널 플러그인이 서버와 주고받는 전송 계층 전반.
  • 발견됨 — t4 감사 F-01(Critical): 전송 계층 상대가 자신을 인증하지 않은 채 세션에 무언가를 밀어 넣는 경로가 열려 있었습니다.
  • 추가됨 — 세 겹의 방어: welcome 게이트(확립 전 프레임 폐기), 발신 request_id 집합 대조, 비루프백 호스트에 wss:// 강제.

해설 이 세대의 진짜 의미는 추가한 방어 세 겹이 아니라 남긴 기록에 있다고 봅니다. 이 SPEC은 «welcome은 인증의 증거가 아니다»라고 자기 한계를 문서에 새겨 두었고, 그 잔여를 후속 카드로 정확히 이월했습니다. 그 기록이 없었다면 다음 세대는 존재하지 않았을 것이라는 판단은 근거 문서가 아니라 이 문서의 해석입니다.

2세대 — 카드 t15 · SPEC-GWAUTH-001 (완료, 2026-08-30)

  • 만들다가 — 서버가 봇에게 «나는 진짜 게이트웨이다»를 증명하는 절반의 상호 인증. 채널이 매 접속마다 새 논스(한 번만 쓰려고 만드는 무작위 값)를 hello에 싣고, 서버는 HMAC(비밀 열쇠로 메시지의 진본을 증명하는 계산) 증명을 welcome에 실으며, 채널은 상수 시간 대조를 통과해야만 세션을 확립합니다.
  • 발견됨 ① — 이 카드 자체가 t9의 감사에서 태어났습니다. t9 계획 감사 C-01이 «welcome을 위조할 수 없다»는 문장을 반증했고, 계획 단계의 프로브(공격 경로를 실제로 재현해 보는 작은 실험 프로그램)가 세 갈래 공격 — 사칭 채팅 주입, 이력 오염, 판정 위조 — 이 전부 성립함을 실행으로 보였습니다. 사람이 «거부»를 누른 도구 실행이 승인으로 뒤집히는 결과까지 관측됐습니다.
  • 발견됨 ② — 동기화 감사가 이번에는 이 카드 자신을 잡았습니다(F-01, Critical). 채널이 hello에 평문 토큰을 계속 실어 보내기 때문에(channel/src/gateway-client.ts:83 — 본 문서 작성 시 직접 확인), «hello를 받는 자리»에 선 공격자는 방금 받은 그 토큰으로 유효한 증명을 만들 수 있습니다. 두 번째 프로브(probe-token-echo)가 토큰을 모르는 위조 게이트웨이가 세션을 확립하는 장면을 실행으로 남겼습니다.
  • 추가됨 — 논스·HMAC 증명과 상수 시간 대조. 그리고 정직한 결산: 이 설계가 배제하는 것은 «소켓에 쓸 수 있으나 hello를 읽을 수 없는 상대» 하나뿐이며, 적대적 상대에게는 그런 자리가 실질적으로 남지 않는다는 사실이 배제표에 명시됐습니다.

절차적으로도 이 세대는 길었습니다. 계획 감사가 1회차 FAIL 0.67 → 2회차 PASS 0.89 → 3회차 PASS 0.84로 세 번 반복됐고(SPEC-GWAUTH-001 작성 기록 기준), 동기화 감사는 FAIL 0.70에서 재검을 요구했습니다. 코드 구현 자체는 옳게 착지했고, 거짓이었던 것은 «닫았다»는 서술이었습니다.

3세대 — 카드 t22 · SPEC-GWAUTH-002 (진행 중, 초안)

  • 만들다가 — t15가 이월한 «실질 종결 세 요소»: hello에서 평문 토큰 제거, 토큰 해시 대신 검증자(서명을 검증할 수만 있고 만들 수는 없는 공개값) 저장, 확립 이후 프레임 인증.
  • 발견됨 ① — 세 요소만으로는 부족했습니다. 1회차 계획 감사가 보인 것은 위조가 아니라 전달입니다. 진짜 서버와 진짜 채널 사이에 선 중계자는 핸드셰이크를 글자 그대로 흘려보내기만 해도 양쪽 검증을 모두 통과하고, 그 뒤에 봇 세션을 가져갑니다. 이로써 요소는 셋에서 넷으로 늘었습니다 — «채널 바인딩»(양쪽이 같은 전송 연결 위에서만 같아지는 값, 프레임에 실리지 않습니다).
  • 발견됨 ② — 이 저장소의 서버는 TLS를 스스로 종단하지 않습니다(server/src/index.ts:34가 평문 HTTP 서버를 만듭니다 — 직접 확인). 따라서 채널 바인딩은 오늘의 배치에서 서지 않습니다(양쪽 모두 «unbound»). 종결은 «TLS 배치 조건부»로 격하됐고, 무조건 종결은 t23의 소유가 됐습니다.
  • 추가됨 — 서버가 논스를 먼저 내는 새 핸드셰이크(hello는 공개키와 논스만 싣습니다), 토큰에서 결정적으로 유도하는 Ed25519(빠른 전자서명 알고리즘) 서명 키쌍과 검증자 저장, 확립 후 모든 서버→채널 프레임을 감싸는 봉투(envelope — 프레임을 감싸 인증 정보를 덧붙이는 포장) env { seq, mac, payload }, 그리고 하위 호환 폐기 — 이미 발급된 모든 봇 토큰이 무효가 됩니다.

절차적으로는 이 문서가 «복잡해진 느낌»의 표본입니다. 계획 감사 1회차 FAIL → 개정(v0.2.0) → 2회차 FAIL → 개정(v0.3.0) → 3회차 — 세 번의 감사 보고서가 모두 이 나무에 남아 있고, 세 번 다 FAIL 판정이었습니다(본 문서 작성 시 세 보고서의 판정줄을 직접 읽어 확인했습니다). 자세한 분석은 §4에서 «해설»로 다룹니다.

4세대(예정) — 카드 t23 · 서버 TLS 종단

서버가 TLS를 스스로 종단하게 만들어 §1.1(사칭 채팅·이력 오염·판정 위조)의 무조건 종결을 완성합니다. 원래 설계가 «이후 업그레이드 경로»로 미뤄 둔 HTTPS가 정확히 이 자리로 돌아온 것입니다. 설계 문서는 역방향 프록시가 TLS를 종단하는 배치에서는 그 프록시 자체가 중계자가 된다는 점까지 지적하며, «무엇을 택할지가 그 카드의 첫 질문»이라고 적어 둡니다.

4. «복잡해진 느낌»의 정체 — 감사와 개정이 왜 여러 번 도는가

해설 이 절 전체는 근거 문서에서 읽은 사실 위에 세운 해설입니다. 사실 관계(감사 횟수, 점수 궤적, 결함 번호)는 문서에서 왔고, «이것이 무엇을 뜻하는가»의 해석은 이 문서의 것입니다.

4.1 루프가 도는 실제 모습

t15는 계획 감사 세 번(FAIL → PASS → PASS)과 동기화 감사 재검을 겪었고, t22는 세 번의 계획 감사가 모두 FAIL이었습니다. 각 감사는 이전 개정이 만든 새 결함을 잡는 형태였습니다. t22의 2회차 감사가 대표적입니다 — 1회차 결함 열둘을 닫았지만 새 결함 여섯을 낳았고, 여섯 전부가 같은 형태였습니다: «정정이 자기가 명명된 자리만 덮고, 명명되지 않은 형제를 남긴다». 한 절을 고치면 같은 사실을 서술하는 다른 절이 낡고, 한 줄 번호를 고치면 그 뒤의 줄 번호 인용이 전부 밀립니다.

4.2 반복해서 발견되는 결함 부류 셋

여러 카드의 감사 기록을 겹쳐 보면 같은 부류가 반복됩니다.

부류 ① — «A가 B를 지킨다» 주장이 위협 모형보다 넓습니다. t9의 «welcome을 위조할 수 없다»는 문장이 감사에 반증되어 t15가 태어났고, t15의 «배제한다»가 다시 반증되어 t22가 태어났으며, t22 자신의 첫 배제표도 같은 형태의 거짓을 안고 있었다가 감사가 잡았습니다. 방어 코드가 틀려서가 아니라, «지킨다»의 주어(누구로부터)와 조건(어떤 배치에서)이 문장에 빠져 있어서입니다.

부류 ② — 수용 기준(구현이 끝났는지 판정하는 검증 항목)의 공허성. t15는 기준 열다섯 중 0개가 명명한 공격자를 쟀습니다 — 기준은 전부 통과해도 그 사실은 «결함 있는 구현도 통과한다»는 뜻이었습니다. 이 공백은 지금 공시 의무가 되었습니다. t22 1차 감사는 같은 축에서 «스물한 기준 중 여섯이 명명된 공격자를 온전한 능력으로 잰다»고 셌습니다 — 부류가 잡히고 수치로 관리되기 시작한 것입니다.

부류 ③ — 문서 일관성. «정정이 스스로 낡은 기록을 남긴다»가 t15에서 네 라운드 연속 재현됐고, t22에서도 개정 절차 자체(«정정 후 전역 재도출» 상시 절차, 줄 번호 대신 앵커로 재도출, 표 행을 서수가 아니라 이름으로 참조)로 진화했습니다.

4.3 왜 이것이 설계의 악화가 아닌가

해설 루프가 도는 것은 설계가 나빠서가 아니라 «닫혔다»의 정의가 정밀해지는 과정이기 때문이라고 봅니다. 근거는 세 가지입니다.

첫째, 같은 코드를 두고 기준선이 세대마다 올라갔습니다. 1세대 감사는 «문장이 형태를 갖추었는가»를 봤다면, 2세대는 «공격을 프로브로 재현할 수 있는가»를 요구했고, 3세대는 «배제 주장에는 배치 조건이 붙는가», «기준이 명명한 공격자를 능력 그대로 잰가»를 요구합니다. t15의 경우 구현은 옳게 착지했고 거짓이었던 것은 서술이었습니다 — 루프의 비용이 문서 개정에 집중된 이유입니다.

둘째, 감사 스스로 개선을 수치로 인정합니다. t22 1차 감사는 «v1의 실패 형태 넷 중 둘은 재현되고 둘은 고쳐졌다»를 표로 남겼습니다. 루프가 같은 자리를 무한히 도는 것이 아니라 결함 부류가 하나씩 «재현되지 않음»으로 넘어가고 있습니다.

셋째, 부류 ③은 설계가 아니라 기록 관리의 문제이며, 그에 대한 처방도 절차로 착지했습니다(재도출 상시 절차, 앵커 인용). 이 부류의 재발이 «설계가 복잡해졌다»는 증거가 아닙니다.

해설 다만 대가도 분명합니다. 세대가 지날수록 문서가 두꺼워지고(요구사항 13건 → 21건, 수용 기준 15건 → 24건), 하나의 개정이 형제 문서 열 자리 이상을 흔들며, 감사 한 번에 드는 검토 비용이 커집니다. 이 비용이 합리적인지는 «닫힘»의 정의를 어디에 두느냐는 운영자의 판단 문제입니다. 현재 설계 문서들이 택한 답은 «공격자가 무엇을 가졌는지로 갈라 적고, 닫지 않은 것을 성과보다 먼저 적는다»입니다.
