**관측 수단의 안전성은 도구가 아니라 호출 형태가 결정한다.** 실패한 설계를 대체하며 「새 도구는 그 실패 모드를 피한다」고 적을 때, 도구의 성질이 아니라 **문서가 처방한 명령줄**을 그대로 돌려 확인한다.

**Why:** t25 6회차. 손수 만드는 기준선 파일이 「파일이 없으면 무조건 통과」로 무너지자 저자가 `git diff <base>` 로 갈아탔고, 근거를 「부재가 통과로 읽히지 않는다 — base 가 없으면 명령이 실패한다」로 적었다. 도구 단독으로는 참이다(`git diff deadbeef` → exit 128). 그런데 처방된 형태는 `git diff <base> -- path/ | grep '^-.*expect('` 였고, 실행해 보니 잘못된 base 는 **출력 없음 + exit 1**, 정상 base·위반 0건도 **출력 없음 + exit 1** — 셸이 보는 값은 git 의 128 이 아니라 grep 의 것이라 두 경우가 구별되지 않는다. 유일한 신호인 stderr 는 산출물 명세가 담게 하지 않았다. **죽인 실패 모드가 대체 설계 안에서 그대로 재현됐다.**

**How to apply:** 「이 관측은 부재를 통과로 읽지 않는다」류의 주장을 볼 때마다 (1) 문서에 적힌 명령을 **글자 그대로** 복사해 (2) 기준을 일부러 깨뜨려 돌리고 (3) 정상·위반 0건 경우와 **출력과 종료 코드를 나란히** 놓는다. 파이프·리다이렉트·`&&` 가 끼어 있으면 앞 명령의 종료 코드는 사라진다고 보는 편이 안전하다. 고침은 대개 두 줄이다 — 기준을 먼저 `rev-parse --verify` 로 확인하거나, 산출물에 종료 코드를 적게 하는 것. 관련: [[disclosed-gap-without-a-criterion]], [[negative-assertion-is-green-on-absence]], [[feedback-gh-run-list-needs-full-sha]].
