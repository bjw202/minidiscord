부정(negative) 수용 기준을 감사할 때는 **하네스가 공격자에게 무엇을 허용하는지 능력 단위로 세라.** 필드 단위로 세면 공허한 기준을 놓친다.

**Why**: t15(SPEC-GWAUTH-001) 에서 `rogueGateway` 위조자가 `nonce` 와 나가는 `permission_request` 의 `request_id` 는 프레임에서 읽으면서, 같은 `hello` 프레임의 `token` 만은 읽지 않고 하네스 상수 `'tok'` 을 썼다. 프레임을 읽는 능력은 **하나**인데 기준이 그것을 「논스는 읽는다 / request_id 는 읽는다 / token 은 안 읽는다」로 임의 분할한 것이다. 그 결과 AC 다섯(006·008·009·011·012)이 전부 초록인 채로 SPEC 이 지목한 실제 상대를 아무도 재지 않았고, `spec.md` §5 가 그 상대를 «배제한다» 로 적었다. 위조자에게 토큰을 읽게 하는 15줄짜리 프로브 하나로 세션이 확립됐다.

**How to apply**: 부정 기준의 스텁·모의 공격자를 볼 때
1. 그 공격자가 **실제로 접근 가능한 데이터 전부**를 열거한다 (받은 프레임 전체 · 보낸 프레임 전체 · 소켓 상태).
2. 기준이 그중 **일부만** 쓰게 강제하고 있다면 그 제약의 위협 모형상 근거를 찾는다. 근거가 없으면 그 기준은 공허하다.
3. 확인은 프로브로 — 「능력을 전부 준 공격자」를 한 번 돌려 보는 것이 판독 열 번보다 싸다.
4. 처방은 「그 갈래도 막아라」가 아니라 **「그 갈래는 통과한다는 것을 기준으로 못 박아라」** 일 수 있다. 통과 사실을 기준 이름에 적으면 경계가 매 실행마다 문서화되어 다시 과장되지 않는다.

관련: [[defence-claim-needs-threat-model]] — 방어 주장에 위협 모형을 붙이라는 규칙의 **측정 층 버전**이다. 저쪽은 문서가 무엇을 주장하는가, 이쪽은 하네스가 무엇을 재는가.
