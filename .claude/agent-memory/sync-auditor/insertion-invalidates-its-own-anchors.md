수리가 **줄을 삽입**하면 아래 줄이 밀리고, 그 수리가 적은 줄 번호 앵커는 적히는 순간 낡는다.
여기까지는 참이다. **그러나 「낡았다」에서 「이 수리가 낡게 했다」로 넘어가는 순간 별개의 주장이
되고, 그 주장에는 별개의 증거가 필요하다.**

귀속을 판정하는 것은 **상대 변위가 아니라 기준선 시점의 내용 일치**다. 세 자리를 나란히 읽는다:

```
git show <표가 고정한 base>:<file> | sed -n '<N>p'   # 앵커가 옳았던 시점
git show <HEAD>:<file>             | sed -n '<N>p'   # 수리 직전
sed -n '<N>p' <file>                                 # 지금
```

가운데가 그 행의 주제를 싣지 않으면 **수리 이전에 이미 낡아 있었다.**

**Why:** t34 2회차에 내가 「앵커 35개가 낡았고 **전부 HEAD 에서 유효했다 — 이 수리가 만든
낡음이다**」라고 적었다. 3회차에 35 전건을 세 기준선에서 다시 재니 **19 만 참이고 16 은
거짓**이었다 — 18행의 열둘은 run 단계 M4-7 커밋이 밀어냈고, 6·7·8행의 넷도 마찬가지였다.
내가 본 것은 「+1 이동」이라는 **상대 변위**였고, HEAD 시점의 내용 일치는 확인하지 않았다.

더 나쁜 것은 방법이 아니라 **반증을 쥐고도 결론을 고치지 않은 것**이다. 같은 보고서의 표가
「HEAD `:106` = ```` ```ts ````」·「HEAD `:136` = `**REQ-PERM-006**`」이라고 이미 적고 있었다 —
그 세 칸이 바로 위 산문의 「전부 유효했다」를 부정하는데, 표와 머리글이 서로를 부정한 채
나갔다. **자기 표의 칸이 자기 결론과 어긋나는지 보는 것이 마지막 검사다.**

반대 방향으로도 틀렸다: 11행의 둘을 「HEAD 와 불일치」로 적었으나 실제로는 HEAD 에서 유효했다.
한 표 안에서 양방향으로 틀릴 수 있다.

**How to apply:**
- 수리가 파일에 줄을 넣었으면 그 파일을 가리키는 **모든** 줄 번호 앵커를 재검한다.
  「이 행은 안 건드렸다」는 면제가 아니다 — 건드린 것은 파일이지 행이 아니다.
- **낡음 판정과 귀속 판정을 갈라 적는다.** 「낡았으니 고쳐야 한다」는 귀속 없이도 선다.
  수리 필요성을 세우는 데 귀속은 필요 없으니, 확신이 없으면 귀속을 **적지 않는다**.
- 수리가 **신설한** 행의 앵커에 「선재 낡음」을 붙이지 않는다. 그 번호는 기준선 시점에 존재한
  적이 없으므로 기준선 대조 자체가 범주 오류다(3회차 H-02 가 같은 오류를 반대편에서 냈다).
- 자동 추출로 앵커를 세지 말 것: `REQ-GW-020` 의 `020` 이 앵커로 잡혀 계수가 오염된다.
  손으로 대조한 것만 세고 **하한임을 명시**한다([[sample-match-does-not-size-the-list]]).
  — 실제로 3회차 전수 열거는 35 가 아니라 **79자리 중 52 낡음**을 냈다. 하한 공시가 옳았다.
- 권고는 「새 숫자로 갈아 끼우기」가 아니라 **grep 앵커**다. 숫자 교체는 다음 삽입에서 재발한다.
  t34 에서 이 형식 전환은 실제로 통했다 — 55/55 가 정확히 1건.
- 델타 감사의 기준선은 **직전 회차 실측값**이지 문서에 적힌 고정값이 아니다.
